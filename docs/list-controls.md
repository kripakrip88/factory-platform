# Единая кнопка «Настройка таблицы» на списках (saas_theme)

Слой поверх штатных списков Frappe v16: одна кнопка в шапке списка управляет
**фильтрами** и **видимостью колонок**. Реализован в `saas_theme` (Client Script +
CSS), ядро Frappe не патчится — слой снимается, родное цело.

## Решение по колонкам: общая база + личный слой (важно)

Двухуровневая модель.

### Уровень 1 — ОБЩАЯ БАЗА (штатный механизм, один на доктайп)
Делает поля *доступными* как колонки. Настраивается один раз администратором.
- Набор и порядок по умолчанию — `List View Settings.fields` (штатное хранилище).
- Чтобы поле вообще могло стать колонкой, у него должен быть `in_list_view=1`
  (иначе `reorder_listview_fields()` его не отрисует). Поля карточки лида
  (телефон, почта, город, источник и т.д.) включены через **Property Setter**
  `in_list_view=1` — обратимо удалением Property Setter.
- По умолчанию показываем **разумный широкий набор** — все включены; прятать
  лишнее каждый пользователь будет личным слоем.

### Уровень 2 — ЛИЧНЫЙ СЛОЙ (CSS по имени поля, per-user)
Скрытие И порядок колонок — персонально, без правки схемы/бэкенда.
- Видимость — `display:none` по классу поля `.list-row-col.<fieldname>`
  (Frappe кладёт имя поля CSS-классом и в шапке, и в строках).
- Порядок — CSS `order:N` на тех же ячейках (`.list-row` это flex).
- Скоуп per-doctype: контейнер получает класс `st-lc-<scrub(doctype)>`.
- Состояние — **localStorage** ключом `st_cols_<doctype>` = `{hidden:[], order:[]}`.
  На бэкенд ничего не пишем.
- Работает для **любой** колонки, включая ID (которую штатно убрать нельзя —
  ядро форс-добавляет `name` в `setup_columns()`).
- Полностью обратимо и переживает обновления: снять слой `saas_theme` → все
  колонки видны в общем порядке. Если Frappe сменит вёрстку — мягкая деградация.

### Почему не только штатный механизм
1. **List View Settings — ОДИН на доктайп, общий для всех.** «Менеджер скрыл у
   себя» так не выходит. Личный слой решает это поверх.
2. **Колонку ID убрать штатно нельзя** — ядро всегда добавляет `name`.
3. Личное скрытие через штатный picker меняло бы схему для всех.

### Перенос текста вместо горизонтальной прокрутки
Широкий набор колонок не должен давать горизонтальный скролл. Класс
`st-wrap-cols` на контейнере списка отменяет `white-space:nowrap`/ellipsis в
ячейках → длинные значения переносятся; строки выравниваются по верху.

### Что осталось на штатном механизме
- **Добавление новых полей в общую базу** — родной picker
  `cur_list.show_list_settings()` (кнопка «Расширенные…» в панели).
- **Фильтры** — штатный `cur_list.filter_area` (чтение/убрать/очистить) + родной
  popover для добавления. Своей логики/хранилища фильтров нет.

## Ключевые штатные API (на чём держится слой)
- `cur_list.page.add_inner_button(...)` — кнопка в шапке.
- `cur_list.filter_area` (`get`, `clear`, `filter_list.get_filters()[i].remove()`),
  `cur_list.get_filters_for_args()`.
- `cur_list.show_list_settings()` — родной конструктор колонок (хранилище
  `List View Settings`, серверные `get/set_list_settings`).
- Ячейка колонки: `.list-row-col` с классом = `fieldname` (для CSS-таргетинга).

## Распространение
Прототип на Лидах: кнопка «Настройка таблицы» гейтится `lv.doctype === "Lead"`.
Личный слой (`apply_personal_columns`) и тултипы заголовков работают на любом
списке. Распространять на сделки/покупатели/инбокс — после подтверждения
стабильности на Лидах: снять гейт в `try_render` + для каждого доктайпа собрать
свою общую базу (List View Settings.fields + Property Setters `in_list_view=1`
для полей карточки).

### Property Setters на Lead (общая база, обратимо)
`in_list_view=1` создан для: `mw_full_name, mw_job_title, phone, email_id,
mw_city, mw_state, mw_source, mw_estimated_volume, mw_desired_delivery_date`.
Откат — удалить эти Property Setter'ы (Customize Form → сброс, или delete).
