отдельный HTTP-запрос, атомарности нет (`database-patterns.md:120-125`).

## 1. Общие правила таблицы (канон)

Шаблон из `.claude/rules/conventions-database.md:41-75` — ему следуют почти все
таблицы:

```sql
CREATE TABLE "entityName" (
    "id" TEXT NOT NULL DEFAULT id(),
    "companyId" TEXT NOT NULL,
    ...
    "createdBy" TEXT NOT NULL REFERENCES "user"("id"),
    "createdAt" TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    "updatedBy" TEXT REFERENCES "user"("id"),
    "updatedAt" TIMESTAMP WITH TIME ZONE,
    "customFields" JSONB,
    "tags" TEXT[],
    PRIMARY KEY ("id", "companyId"),
    FOREIGN KEY ("companyId") REFERENCES "company"("id") ON DELETE CASCADE
);
```

Ключевые следствия:

1. **Мультиарендность (multi-tenancy) прошита в первичный ключ.** Составной PK
   `("id", "companyId")` почти везде. Один инстанс Carbon держит много «компаний»
   (`company`), причём есть ещё `companyGroup` — уровень, на котором шарятся план
   счетов, валюты и аналитические измерения (`conventions-database.md:82`,
   `company-backup-restore.md:59-61`).
2. **Идентификаторы — не UUID в чистом виде.** Функция `id(_prefix)`
   (`packages/database/supabase/migrations/20250923225147_uuid-ship-fix.sql:1-18`)
   генерирует UUIDv4, кодирует base58 и при наличии префикса выдаёт
   `po_3xK9…`, `si_…`, `job_…`. По этому префиксу UI аудита определяет тип
   сущности (`audit-log-system.md:120-124`).
3. **`updatedAt` пишет приложение, не триггер** (`conventions-database.md:84`).
   Универсального триггера обновления времени нет — это важно, если писать в БД
   в обход приложения (n8n, интеграции): такие записи «не постареют» корректно и
   попадут в аудит как «System».
4. **Обязательная пара `createdBy`/`updatedBy`.** Даже у журналов только-на-запись
   колонка `updatedBy` должна существовать, иначе общий код аудита падает с
   `column "updatedBy" does not exist` (`conventions-database.md:83`).
5. **Числовые колонки — голый `NUMERIC` без указания точности**
   (`conventions-database.md:86`, `:96`). Проверка `no-numeric-precision`
   (`packages/checks/src/conformance/no-numeric-precision.ts:3-8`) запрещает
   `NUMERIC(x,y)` в новых миграциях. См. раздел 8 — там же список мест, где старое
   ограничение ещё живо.
6. **RLS — реальная граница доступа.** Ровно четыре политики с именами
   `SELECT`/`INSERT`/`UPDATE`/`DELETE`; чтение через
   `get_companies_with_employee_role()`, запись через
   `get_companies_with_employee_permission('<module>_<action>')`
   (`conventions-database.md:104-142`). Старые хелперы `has_role` /
   `has_company_permission` объявлены устаревшими.
7. **Все представления — `SECURITY_INVOKER=true`**, чтобы RLS нижележащих таблиц
   применялась к вызывающему (`conventions-database.md:146`).
8. **Расширяемость без миграций** — `customFields JSONB` + `tags TEXT[]` на
   большинстве таблиц, плюс таблицы-метаданные `customField` (колонки:
   `table`, `name`, `dataTypeId`, `listOptions`, `required`, `sortOrder`) и
   `customFieldTable` (`table`, `name`, `module`). Это готовый механизм для
   российских реквизитов (ИНН/КПП/ОКПО, номер сертификата, номер плавки) без
   форка схемы.

**Правило чтения схемы:** миграции с префиксом-таймстампом, применяются по
порядку, **побеждает самая новая**. Первый найденный `CREATE TABLE` почти всегда
устарел (`database-patterns.md:229-232`, `material-tables.md:93`). Единственный
надёжный источник текущей формы — `packages/database/src/types.ts`.

## 2. Карта связности: где «центр тяжести»

Посчитано по FK-описаниям в `types.ts` (сколько внешних ключей указывают на
таблицу):

| Цель FK | Число ссылок | Роль |
|---|---|---|
| `user` | 663 | аудит `createdBy`/`updatedBy` + `assignee` почти везде |
| `company` | 313 | арендатор |
| **`item`** | **74** | **центральная сущность предметной области** |
| `account` | 72 | план счетов (GL) |
| `location` | 50 | площадка/склад |
| `supplier` | 33 | поставщик |
| `job` | 31 | производственный заказ |
| `customer` | 28 | заказчик |

Схема связности «ядра» (стрелка = FK или позиционная связь):

```
company ──< location ──< storageUnit (склад/ячейка/линия)
   │
   └──< item ─────────────┬──< itemCost / itemReplenishment / itemPlanning /
         (Part|Material|  │     itemUnitSalePrice / itemShelfLife / itemSupersession
          Tool|Service|   │
          Consumable|     ├──< makeMethod ──< methodOperation ──< methodMaterial   (мастер-BOM/маршрут)
          Fixture)        │
                          ├──< supplierPart ──> supplier                            (закупка)
                          ├──< itemLedger  (складские движения)
                          └──< trackedEntity (серии/партии)

opportunity ──< quote ──< quoteLine ──< quoteLinePrice   (КП, лестница количеств)
                    └──> quoteMakeMethod / quoteOperation / quoteMaterial
       ↓ convert
salesOrder ──< salesOrderLine ──> job ──< jobMakeMethod ──< jobOperation ──< jobMaterial
                    │                              └──< productionEvent / productionQuantity
                    └──> shipment ──< shipmentLine
purchaseOrder ──< purchaseOrderLine ──> receipt ──< receiptLine ──> trackedEntity
```

Связка «продажа → производство» жёсткая: `job.salesOrderId`,
`job.salesOrderLineId`, `job.quoteId`, `job.quoteLineId`, `job.customerId`,
`job.itemId` — всё прямо в строке `job` (см. дамп колонок ниже, раздел 5).
То есть от заказа клиента до операции на станке путь по FK непрерывный —
это сильная сторона модели по сравнению с ERPNext, где часть связей идёт через
`Dynamic Link`.

**Отдельная ось — аналитические измерения GL.** Таблицы `dimension`
(`entityType`, `required`, `companyGroupId`) и `dimensionValue`, а проводки несут
`journalLineDimension`. Это НЕ физические габариты, а аналитика учёта
(ЦФО/проект/статья). Физических размеров в модели нет (см. раздел 4).

## 3. Идентичность: user / employee / права

`.claude/rules/user-employee-job-relationships.md`.

- `user` (PK `id`, совпадает с `auth.users.id` Supabase) — глобальная личность.
  `fullName` — **генерируемая колонка** `firstName || ' ' || lastName` STORED.
- `userToCompany` (PK `(userId, companyId)`) — членство; `role` — enum
  `('customer','employee','supplier')`. Один пользователь может быть в нескольких
  компаниях с разными ролями (`:25-27`).
- `employee` (PK `(id, companyId)`, `id → user.id`) — сотрудник компании,
  `employeeTypeId`, `active`, `pin` (для «консольного» режима цеха).
- `employeeJob` (PK `(id, companyId)`) — должность/оргместо: `title`, `startDate`,
  `locationId`, `departmentId`, `shiftId`, `managerId`. Внимание: «job» здесь =
  должность, а **производственный заказ — это другая таблица `job`** (`:13-15`).
- Права: `employeeType → employeeTypePermission (module, view/create/update/delete
  TEXT[])` → материализуются в `userPermission.permissions` JSONB вида
  `<module>_<action> → [companyId…]`. Значение `"0"` в массиве = «все компании»
  (`:36-42`, `:81`).
- Claims собирает SQL `get_claims(uid, company)`; приложение кэширует их в Redis
  по ключу `permissions:${userId}`, гейт маршрута — `requirePermissions(request,
  {view|create|update|delete|role})` (`:44-60`).

**Грабля для внедрения:** `deactivateEmployee` удаляет `userToCompany` и
`employeeJob`, но НЕ чистит ссылки на пользователя в `assignee`,
`workCenterEmployee` и настройках групп уведомлений (`:83-86`). Ссылки повисают.

## 4. Номенклатура (items) и материалы

### 4.1 `item` — единая карточка

Колонки `item` (из `types.ts:20105+`):

```
id, companyId, readableId, revision, readableIdWithRevision (GENERATED STORED),
name, description, notes (JSONB), type (itemType), replenishmentSystem,
defaultMethodType, sourcingType, itemTrackingType, revisionStatus,
unitOfMeasureCode, mpn, thumbnailPath, modelUploadId, changeOrderId, assignee,
active, embedding, trackingMethod, createdAt/By, updatedAt/By
```

Перечисления:

- `itemType` = `Part | Material | Tool | Service | Consumable | Fixture`
- `itemReplenishmentSystem` = `Buy | Make | Buy and Make`
- `methodType` = `Purchase to Order | Pull from Inventory | Make to Order`
- `sourcingType` = `Specified | Drop Ship | Ship from Inventory`
- `itemTrackingType` = `Inventory | Non-Inventory | Serial | Batch`
- `itemRevisionStatus` = `Design | Prototype | Production | Obsolete`

Сателлиты 1:1 к `item` (PK = `itemId`): `itemCost` (`costingMethod` =
`Standard|Average|LIFO|FIFO`, `standardCost`, `unitCost`, `itemPostingGroupId`),
`itemUnitSalePrice` (`unitSalePrice`, `currencyCode`, `priceIncludesTax`,
`salesUnitOfMeasureCode`), `itemReplenishment` (`leadTime`, `lotSize`,
`scrapPercentage`, `conversionFactor`, `purchasingUnitOfMeasureCode`,
`preferredSupplierId`), `itemPlanning` (по локации: `reorderingPolicy`,
`reorderPoint`, `reorderQuantity`, `minimum/maximumOrderQuantity`,
`orderMultiple`, `demandAccumulationPeriod`), `itemShelfLife`, `itemSupersession`,
`pickMethod` (`defaultStorageUnitId`, `sortMethod`).

### 4.2 Типовые таблицы и **позиционная** связь (важнейшая грабля)

`part`, `material`, `tool`, `consumable`, `service` — таблицы свойств, общих для
всех ревизий. **`itemId` у них нет**: колонки удалены в
`20250519122022_revisions.sql`. Связь позиционная:

```
item.readableId = <typeTable>.id  AND  item.companyId = <typeTable>.companyId
```

(`material-tables.md:30-31`, `revision-system.md:22-24`). Добавлять колонку
`itemReadableId` явно запрещено (`conventions-database.md:86`). Это значит: любой
JOIN к свойствам номенклатуры делается по человекочитаемому коду, а не по
суррогатному ключу. Один `material` ↔ много строк `item` (ревизии).

### 4.3 Таксономия материалов

`.claude/rules/material-tables.md`. Строка `material` (PK `("id","companyId")`)
несёт только FK на справочники:

`materialFormId`, `materialSubstanceId`, `dimensionId`, `finishId`, `gradeId`,
`materialTypeId` (все nullable), плюс `approved`, `approvedBy`, `customFields`, `tags`.

| Справочник | Ключевые колонки | Чем ограничен | Уникальность |
|---|---|---|---|
| `materialForm` | `id, name, code, companyId` | форма проката: sheet, plate, roundbar, ingot… | `(code, companyId)` |
| `materialSubstance` | `id, name, code, companyId` | steel, aluminum, stainless… | `(code, companyId)` |
| `materialDimension` | `id, name, materialFormId, isMetric, companyId` | привязан к **форме** | `(materialFormId, name, companyId)` |
| `materialFinish` | `id, name, materialSubstanceId` | привязан к **веществу** | `(substance, name, company)` |
| `materialGrade` | `id, name, materialSubstanceId` | марка, привязана к веществу | `(substance, name, company)` |
| `materialType` | `id, name, code, materialSubstanceId, materialFormId` | вещество **и** форма (напр. горячекатаный стальной лист) | `(substance, form, code, company)` |

Справочники **глобальные или компанийские**: `companyId` NULLABLE, строки с
`NULL` — системные, видны всем; строки компании перекрывают их
(`material-tables.md:39-41`). Системные seed-идентификаторы человекочитаемые:
`steel-1018`, `sheet-1-16`, `mill-ti`.

Представление `materials` (`20251122152701_materials-view-fix.sql`) джойнит
`material` к `item` по `readableId`, резолвит FK в имена, агрегирует
`supplierPart` и список ревизий; RPC `get_material_details(item_id)` и
`get_material_naming_details(readable_id)` собирают карточку и «читаемое» имя из
таксономии.

### 4.4 ⚠️ Чего в модели материалов НЕТ (проверено grep'ом по всей схеме)

- **Нет колонок физических свойств.** Ни `weight`, ни `netWeight`, ни
  `grossWeight`, ни `density`, ни `thickness`, ни `width`, ни `length`, ни
  `diameter` — ни в `item`, ни в `material`, ни в `part`, ни в одной из 385
  таблиц (проверено `grep -niE '"(weight|density|thickness|...)"\s+(NUMERIC|…)'`
  по всем 1005 миграциям — 0 попаданий).
- **`materialDimension.name` — это TEXT-ярлык**, а не числа. «1/16», «2x4».
  Толщина 8 мм в системе — это строка, а не величина. Посчитать по ней массу
  нельзя, отсортировать по возрастанию толщины — тоже нельзя.
- **Нет таблицы конверсий единиц измерения.** `unitOfMeasure` содержит только
  `code`, `name`, `active`, `companyId` — ни `baseUnit`, ни `factor`. Пересчёт
  возможен только через `conversionFactor` на конкретной связке
  «поставщик-номенклатура» (`supplierPart.conversionFactor`) или на строке
  документа: `inventoryQuantity = purchaseQuantity × conversionFactor`,
  `inventoryUnitCost = purchaseUnitPrice / conversionFactor`
  (`.claude/rules/purchasing-conversion-factors.md:14-19`). Универсального
  «1 т = 1000 кг» или «1 м листа 8 мм = 62.8 кг/м²» в модели нет.
  У `quoteLine`/`salesOrderLine` `conversionFactor` **вообще отсутствует** —
  только один `unitOfMeasureCode` (`purchasing-conversion-factors.md:42-43`).
- **Нормы времени привязаны к штукам.** Enum `factor`:
  `Hours/Piece | Hours/100 Pieces | Hours/1000 Pieces | Minutes/Piece |
  Minutes/100 Pieces | Minutes/1000 Pieces | Pieces/Hour | Pieces/Minute |
  Seconds/Piece | Total Hours | Total Minutes`. Нет «минут на метр шва», «часов
  на тонну», «м²/час покраски». Для металлоконструкций нормирование сварки/резки
  по длине или массе придётся выражать через штуки либо доработать enum и весь
  расчётный тракт.
- `companySettings.useMetric` BOOLEAN есть — но это переключатель отображения,
  а не система конверсий.

**Вывод по номенклатуре:** таксономия материалов у Carbon сделана «по-американски»
— комбинаторная (форма × вещество × марка × размер-ярлык × покрытие), и она
неплохо ложится на сортамент. Но параметрики (масса погонного метра, площадь,
плотность) в схеме нет вообще, и это ключевая доработка под завод
металлоконструкций. Частично закрывается `customFields` (JSONB, см. §1.8) и
конфигуратором: `configurationParameter` c `configurationParameterDataType =
text | numeric | boolean | list | date | material` — то есть параметрическая
номенклатура в Carbon **есть**, но как отдельная подсистема-конфигуратор, а не
как поля материала.

## 5. Производство: job / методы / операции

`job` (41 колонка, `types.ts:22436`):

```
id, jobId (читаемый №), companyId, itemId, quantity, quantityComplete,
quantityReceivedToInventory, quantityShipped, scrapQuantity, productionQuantity,
unitOfMeasureCode, locationId, storageUnitId, status (jobStatus),
deadlineType, dueDate, startDate, releasedDate, completedDate,
projectedCompletionAt, scheduleOutdatedAt, scheduleOutdatedReason,
estimatedTime, actualTime, secondsToComplete, priority,
customerId, salesOrderId, salesOrderLineId, quoteId, quoteLineId,
modelUploadId, configuration (JSONB), assignee, notes, tags, customFields, аудит
```

`jobStatus` = `Draft | Ready | In Progress | Paused | Completed | Cancelled` (+ др.).

Иерархия метода производства:

- **Мастер-данные:** `makeMethod` (по одному на каждую ревизию item, создаётся
  AFTER INSERT триггером `create_make_method_related_records`) → `methodOperation`
  (маршрут) → `methodMaterial` (спецификация/BOM).
- **Снимок в заказ:** `jobMakeMethod` → `jobOperation` → `jobMaterial`.
- **Снимок в КП:** `quoteMakeMethod` → `quoteOperation` → `quoteMaterial`.

`methodMaterial`: `makeMethodId`, `itemId`, `quantity`, `scrapQuantity`,
`productionQuantity`, `methodType`, `sourcingType`, `materialMakeMethodId`
(подузел для Make-to-Order), `methodOperationId`, `order`, `kit`,
`storageUnitIds` (JSONB).

⚠️ `methodMaterial.methodType` и `.sourcingType` — **только зеркало** полей
компонента-item, форма их не редактирует: `upsertMethodMaterial` перезаписывает
присланные значения из `item.defaultMethodType` / `item.sourcingType`
(`.claude/rules/method-material-sourcing.md:81-83`). Каскад при изменении item
трогает **только методы в статусе `Draft`** — `Active`/`Archived` заморожены
(`:76-80`).

`makeMethod` версионируется отдельно от ревизии item: `makeMethod.version`
NUMERIC, `makeMethod.status` = `Draft | Active | Archived`, уникальность
`(itemId, version)`; представление `activeMakeMethods` выбирает текущую
(`revision-system.md:73-79`). **Не путать** версию метода (рецепт) с ревизией item
(отдельная строка `item`).

`jobOperation` несёт и нормы, и факт: `setupTime`/`setupUnit`,
`laborTime`/`laborUnit`, `machineTime`/`machineUnit`, `laborRate`, `machineRate`,
`overheadRate`, `operationUnitCost`, `operationMinimumCost`, `operationLeadTime`,
`operationQuantity`, `quantityComplete`, `quantityScrapped`, `quantityReworked`,
`workCenterId`, `processId`, `status`, `readyAt`, `hasConflict`, `conflictReason`,
`manuallyScheduled`, `procedureId`, `workInstruction` (JSONB).

Факт из цеха (MES): `productionEvent` (`startTime`, `endTime`, `duration`,
`employeeId`, `workCenterId`, `type`, `postedToGL`) и `productionQuantity`
(`quantity`, `type`, `scrapReasonId`, ссылки на три событийных id и на инспекцию).
`productionQuantity.quantity` был INTEGER и специально расширен до NUMERIC ради
весовых/погонных единиц — `20260416130000_production-quantity-to-numeric.sql:1-6`
(комментарий там буквально: «so it can hold fractional production for
weight/length UoMs»). Это хороший признак: вектор развития проекта учитывает
непоштучное производство.

## 6. Ревизии (revisions)

`.claude/rules/revision-system.md`.

- Ревизия — это **полноценная строка `item`** с тем же `readableId`,
  `companyId`, `type` и другим `revision`. Отдельной таблицы ревизий нет (`:17-19`).
- `item.revision` TEXT DEFAULT `'0'`. `'0'`, `''` и NULL — все считаются
  «исходной» ревизией, обрабатывать нужно все три (`:91-92`).
- `item.readableIdWithRevision` — **GENERATED STORED**: `readableId`, если ревизия
  `'0'`/пусто, иначе `readableId || '.' || revision` → `P000123.A`. TS-зеркало:
  `getReadableIdWithRevision` в `apps/erp/app/utils/string.ts` (`:27-30`).
- Уникальность: `item_unique UNIQUE ("readableId", "revision", "companyId", "type")`.
  Тип входит в ключ → Part и Consumable **законно могут иметь одинаковый
  `readableId`** (`:31-34`).
- **Флага «активная ревизия» нет.** Списочные представления схлопывают до одной
  строки на `(readableId, companyId)` через CTE `latest_items` (`DISTINCT ON`),
  причём порядок предпочитает **именованную** ревизию перед `'0'`, затем
  `createdAt DESC` (`20260325073453_fix-latest-revision-ordering.sql`) (`:38-45`).
- Создание ревизии: валидатор `revisionValidator` (`items.models.ts`), маршрут
  `apps/erp/app/routes/x+/items+/revisions.new.tsx`, сервис `createRevision`
  копирует поля и — если `replenishmentSystem !== "Buy"` — вызывает edge-функцию
  `get-method` (`type: "itemToItem"`), чтобы скопировать BOM/маршрут (`:59-62`).
- Грабля: RPC `get_<type>_details` фильтруют список ревизий **по типу**
  (`20260515120000_…`), иначе Consumable «просачивался» в список ревизий Part (`:86-90`).

## 7. Замены номенклатуры (supersession) и извещения об изменении

`.claude/rules/supersession-system.md`.

`itemSupersession` — **одна строка на item, PK = `("itemId")` один, без companyId**
(нетипично для схемы). Колонки: `supersessionMode`, `successorItemId`,
`successorEffectivityDate`, `discontinuationDate`, `conversionFactor`
(1 старая = N новых).

Три потребителя отвечают на **разные вопросы** и это сделано намеренно (`:20-30`):

| Потребитель | Источник | Вопрос |
|---|---|---|
| MRP (`mrp/index.ts`) | живой, каждый прогон | что закупать? |
| Создание заказа (`get-method`) | живой на момент создания, дальше **заморожен** | что потребляет этот заказ? |
| Подбор со склада (`inventory/supersession-pick.ts`) | живой, в момент подбора | что снимать с полки? |

`jobMaterial` — это **снимок**: правка замены задним числом не переписывает
существующие строки, но подбор пересчитывается каждый раз.

Режимы: `REDIRECTING_MODES = { "Consume First", "Prefer New" }` — только эти два
перенаправляют в MRP/создании заказа. `Stock Only` держит преемника как резерв,
`No Stock` преемника не имеет. При подборе правила **другие**: `Stock Only` →
брать преемника; `Prefer New` → преемника с откатом до даты вступления;
`Consume First` → предшественника, пока есть остаток на складе (`:33-48`).

`buildSupersessionRedirectMap` (`lib/supersession-pick.ts`) схлопывает `A→B→C` в
`A→C` с произведением коэффициентов. **Циклы отбрасываются, не схлопываются** —
двухшаговый цикл `A→B` + `B→A` из UI записать можно (запрещена только
самоссылка), и его схлопывание давало `A→A` с мусорным множителем (`:60-67`).

`asOfDate` у потребителей разный: MRP — сегодня в **часовом поясе компании**,
`get-method` — дата сборки заказа; при отсутствии дат `jobBuildDate` падает на
**UTC-сегодня** — здесь общая гарантия «оба считают одинаково» ломается (`:109-113`).

Провенанс замены есть только на заказе: `jobMaterial.substitutedFromItemId` и
`.substitutionFactor`. У `methodMaterial` аналога **нет** — то есть операция
«Save Method» (`jobToItem`) записывает подменённые позиции в мастер-BOM
**без следа** (`:95-98`).

**Извещения об изменении (change orders)** — отдельный контур:
`changeOrder` (`changeOrderId`, `type`, `status`, `reasonForChange` JSONB,
`approvalRequirements`, `requiredActionIds`, `nonConformanceId`, `dueDate`,
`openDate`, `sourceType`/`sourceId`), `changeOrderAffectedItem`,
`changeOrderRequiredAction`, `changeOrderActionTask`, `changeOrderSupersession`
(`predecessorItemId`, `successorItemId`, `supersessionMode`,
`successorEffectivityDate`, `discontinuationDate`). То есть у Carbon PLM-контур
ECO/ECN есть из коробки, и он связан с несоответствиями (`nonConformance`).

## 8. Прослеживаемость партий и серийных номеров

`.claude/rules/traceability-model.md`. Модель — **направленный граф**:

- **Узлы** = `trackedEntity` — физическая серия/партия.
- **Рёбра** = `trackedActivity` (событие) + `trackedActivityInput` (что съели) +
  `trackedActivityOutput` (что произвели). PK связок — `(trackedActivityId,
  trackedEntityId)`, обе `ON DELETE CASCADE`.

`trackedEntity` (14 колонок): `id` (`nanoid()`), `quantity` NUMERIC (у серийного
всегда 1), `status` (`Available | Reserved | On Hold | Consumed | Rejected |
Scrapped`), `itemId` (FK → `item(id)` **`ON DELETE RESTRICT`** — item с любой
сущностью, даже потреблённой, нельзя удалить физически, только деактивировать),
`readableId` (сам номер серии/партии), `expirationDate` DATE (первоклассная
колонка, питает FEFO), `sourceDocument`/`sourceDocumentId`/
`sourceDocumentReadableId` (полиморфная ссылка + денормализованный
`item.readableIdWithRevision`, синхронизируемый перехватчиком
`sync_propagate_item_readable_id_to_tracked_entity`), `attributes` JSONB
(GIN-индекс) — Receipt Line, Receipt, Supplier, Job, Job Material и т.д.

Где рождаются сущности (`:52-61`): приёмка (`update_receipt_line_batch_tracking` /
`…serial_tracking`, статус `On Hold`, дата годности через
`resolve_shelf_life_start_for_receipt`), и «посевные» сущности заказа
(триггеры `sync_insert_job_make_method` и др., статус `Reserved`).

Где пишутся рёбра (`:63-90`): edge-функции `post-picking`, `post-receipt`,
`post-shipment`, `post-stock-transfer`, `issue`, `trigger-rework`, плюс MES
`startProductionEvent`. Единой «post-production» нет.

Запросы родословной — строгие RPC:
`get_direct_ancestors_of_tracked_entity_strict(p_tracked_entity_id)` (откуда) и
`get_direct_descendants_of_tracked_entity_strict(…)` (куда), а также пакетные
варианты на `TEXT[]` (`20260430090114`) — BFS по фронту, а не по узлу (`:92-101`).
Граф в UI: `apps/erp/app/routes/x+/traceability+/graph.tsx` →
`fetchLineageSubgraph` в `apps/erp/app/modules/inventory/lineage.server.ts`,
лимит `MAX_ENTITIES = 500`.

**Соглашение о разделении партии (важное для металла):** при частичном отборе `q`
из партии **исходная сущность сохраняет свой id** и уменьшается на `q`, а
создаётся **новая дочерняя** сущность с тем же `readableId` и атрибутом
`"Split From Entity ID": parent.id`, и уходит именно она. Активность Split
пишет input `parent`@`q` → output `child`@`q`; в журнал идут ровно две
взаимокомпенсирующие строки `Batch Split` (`:147-161`). Серийные позиции не
делятся никогда. Есть и слияние остатка назад (`type: 'Merge'`) при возврате
неиспользованного.

**Оценка под металл:** механика «партия = плавка/сертификат, дробится при
раскрое, склеивается при возврате остатка, вся генеалогия — граф» ровно то, что
нужно для прослеживаемости стали по сертификатам качества. Номер плавки, ГОСТ,
сертификат кладутся либо в `readableId`, либо в `attributes` JSONB, либо через
`batchProperty` — таблицу пользовательских свойств партии
(`itemId`, `label`, `dataType` из `configurationParameterDataType`,
`listOptions`, `sortOrder`). Отдельного поля «сертификат/плавка» в схеме нет.

## 9. Точность чисел (критично для металла)

`.claude/rules/numeric-precision.md` — самый проработанный документ во всём
наборе правил. Источник истины —
`packages/database/supabase/functions/shared/precision.ts` (Deno-сторона),
`packages/utils/src/precision.ts` — реэкспорт для Node/браузера.

### 9.1 Две шкалы хранения

| Класс | Шкала | Примеры |
|---|---|---|
| Внутренние значения | `SCALE = 5` (`precision.ts:2`) | цены за единицу, ставки (доли 0–1), **количества**, строки проводок GL, курсы валют |
| Расчётные (settlement) | `currency.decimalPlaces` (колонка в БД, авторитетнее CLDR) | итоги документов, налог документа, кассовые суммы |

Колонки хранения — **голый NUMERIC**, границы обеспечивает вызывающий код
(`numeric-precision.md:52-55`).

### 9.2 Правило трёх границ

Округлять **только** при записи (persist), отображении (display) и сравнении
(compare). Промежуточные вычисления — полная точность float; производные значения
считает Postgres (генерируемые колонки); `sum()` сначала накапливает, потом
округляет один раз (`:57-61`).

### 9.3 API

- `round(value, scale = 5, mode = HalfUp)` — через сдвиг экспоненты, чтобы
  `round(1.005, 2) === 1.01` и чтобы совпадать с Postgres (ties away from zero),
  `precision.ts:21-32`.
- `scrapAllowance(target, rate)` — **добавка на брак в целых единицах**; дробная
  цель не округляется: `scrapAllowance(4.5, 0) === 0`, `31 + scrapAllowance(31,
  0.01) === 32` (`precision.ts:101-108`). Логика «нельзя выбросить треть детали».
- `applyRate(base, rate, decimals)` — налог/скидка → сумма, `decimals` берётся из
  данных, не из литерала.
- `deriveRate(amount, subtotal)` — единственное разрешённое место обратного
  вывода ставки из суммы (`precision.ts:119-120`).
- `distributeRoundingResidual(exactValues, target, scale)` — распределение остатка
  округления по методу наибольших остатков (Гамильтона), сдвиг максимум на одну
  младшую единицу на часть; отказывается работать, если остаток больше
  (`precision.ts:48-99`). Есть защита: часть не может сменить знак — иначе
  «отрицательный налог на положительной выручке» (`precision.ts:78-89`).
- `equals(a,b)` / `EPSILON = 1e-6`; `assertBalanced(debits, credits, tolerance,
  label)` — инвариант равенства дебета и кредита.

**Запрещено:** `Math.round/ceil/floor` и `.toFixed` на значимых числах
(проверка `no-raw-rounding`), числовые литералы в качестве `scale`, инлайновые
`minimumFractionDigits`/`maximumFractionDigits` (проверка
`no-inline-fraction-digits`) (`:95-99`, `:177-182`).

### 9.4 Отображение = ввод

`packages/utils/src/format.ts` — единственное место, где выбирается число знаков:

| Вид | Знаков | Комментарий |
|---|---|---|
| Процент / ставка | 0–3 | |
| Курс валюты | 0–5 | `SCALE_FORMAT`, `format.ts:166-169` |
| **Количество** | **0–5** | `formatQuantity`, `format.ts:229` — «3», «4.33333», «0.00125» |
| Деньги (settlement) | ровно `currency.decimalPlaces` | и пол, и **потолок** |
| Цена за единицу (rate) | min = `decimalPlaces`, max = `SCALE=5` | потолок — шкала хранения, а не валюты |

Критично: **формат поля ввода — часть арифметики хранения.** react-aria при
потере фокуса коммитит буквально `parse(format(x))`, поэтому форматтер решает,
с какой точностью запишется введённое значение (`format.ts:171-175`,
`numeric-precision.md:152`). Отсюда же разделение money/rate: двухзнаковый
потолок однажды превратил реальную цену метиза $0.00123 в $0.00
([issue #1203], `numeric-precision.md:150`).

**`step` — тоже арифметика:** react-aria прилипает к ближайшему кратному шага,
шаг грубее шкалы поля молча обрезает значение (`step={0.0001}` превращал 6.255%
в 6.25%). Брать из `INPUT_STEP.*` (`format.ts:198-210`), литералы запрещены.

### 9.7 Runtime-декодирование NUMERIC

Оба драйвера Postgres декодируют NUMERIC (OID 1700) **в JS number** (float64), а
не в строку/Decimal: node-postgres через `setTypeParser`, deno-postgres через
`controls.decoders`, оба регистрируются в
`packages/database/supabase/functions/lib/postgres/index.ts`
(`numeric-precision.md:184-190`).

**Это главное системное ограничение точности.** Вся арифметика Carbon — в
double: ~15–16 значащих десятичных цифр. Для металла это означает:
- 5 знаков после запятой на количествах и ценах — жёсткий контракт, не «пока
  так»; ниже 0.00001 кг/м величина существовать не может;
- накопление большого числа мелких строк (раскрой на сотни деталей) даёт
  флоат-шум, который система гасит не типом данных, а дисциплиной: `EPSILON`,
  `distributeRoundingResidual`, `assertBalanced`;
- никакого `Decimal.js` / `BigInt` в тракте нет.

**Практический вердикт для металлоконструкций:** масса, длина, толщина в
миллиметрах и килограммах помещаются в шкалу 5 с большим запасом (0.00001 кг =
0.01 г). Опасности не в разрядности, а в (а) отсутствии полей физических свойств
вообще, (б) отсутствии конверсий единиц, (в) «зажатых» нормах времени 10,2,
(г) том, что цена за единицу и сумма документа округляются по-разному и надо
понимать, где какая граница.

## 10. Даты и часовые пояса

`.claude/rules/date-handling.md`. Для Хабаровска (UTC+10) это первоочередной раздел.

**JS `Date` для разбора, форматирования и арифметики — запрещён** (`:13-15`).
Используется `@internationalized/date` + хелперы `@carbon/utils`. Причина названа
прямо: дата-без-времени, сохранённая как полночь UTC, у зрителя западнее UTC
рендерилась **на день раньше** — реальный баг, когда таблица показывала 8/11, а
форма 8/12 (`:19-25`). Плюс `setMonth` на 31 января даёт 3 марта.

Таблица замен (`:29-39`): `parseAbsolute(str, tz)` вместо `new Date(str)`,
`parseDate(str)` для `YYYY-MM-DD`, `zdt.add({days})` вместо `setDate`,
`a.compare(b)` вместо `d1 <= d2`, `getDayOfWeek(date, "en-US")` вместо `getDay()`.

**На сервере `getLocalTimeZone()` запрещён** — это зона сервера, а не
пользователя; `new Date().toISOString().split("T")[0]` — это UTC-день. Запрет
проверяется `no-local-timezone` из `@carbon/checks` и покрывает `*.service.ts`,
`*.server.ts`, `packages/jobs`, `supabase/functions` и **тела loader/action**
маршрутов (`:41-50`).

Серверный API (`packages/utils/src/datetime.ts:34-61`):

- `datetime.timestamp()` — UTC-инстант для `createdAt`/`updatedAt` (единственный
  метод без зоны);
- `datetime.today(tz)` / `datetime.now(tz)` — календарный день / момент в явной
  IANA-зоне;
- `datetime.businessDay(instantStr, tz)` — в какой день попадает инстант;
- `datetime.weekBounds(tz, offset?)` — границы недели пн→вс для табелей.

**Две разные зоны, и это не дубль** (`packages/database/src/timezone.ts:7-12`,
`:54-60`):

| Функция | Источник | Для чего |
|---|---|---|
| `getCompanyTimeZone(client, companyId)` | `company.timezone` | «бухгалтерский календарь»: даты проводок, учётные периоды, последовательности, старение задолженности |
| `getLocationTimeZone(client, locationId, companyId)` | `location.timezone`, откат на компанию | операционное: планирование, смены, MES, сроки годности |

В SQL — `company_today(p_company_id)` (`20260805023439`) и
`location_today(p_location_id, p_company_id)` (`20260805201623`) вместо
`CURRENT_DATE` для бизнес-дат. Представления «просрочено ли?» сравнивают с
`CURRENT_DATE` сознательно — они рисуют статус, а не хранят его (`:56`).

На клиенте `today(getLocalTimeZone())` разрешён **для отображения**, но значение
по умолчанию в форме, которое сохранится как бизнес-дата (`postingDate`,
`orderDate`, `dateIssued`, `openDate`), обязано браться из `useCompanyToday()`
(`:58-63`).

**DST-раздел** (`:85-110`): вывод *дня* в зоне безопасен всегда; опасно строить
*инстант из локального настенного времени*. Переход вперёд (02:30 не существует)
→ `disambiguation: "compatible"` сдвигает на 03:30, не падает; переход назад
(01:30 дважды) → берётся первое вхождение. Неделя перехода — 167 или 169 часов.
Cron не умеет выражать локальное настенное время, поэтому Inngest-кроны стоят на
UTC и вычисляют день компании/локации **внутри** прогона.

Для России DST не действует с 2014 года — этот пласт сложности к нам не относится,
но `Asia/Vladivostok` (UTC+10) как `company.timezone` и `location.timezone`
поддерживается штатно, никакого хардкода Америки в коде дат нет.

### ⚠️ Найденное расхождение: нумерация документов идёт по дате сервера

`get_next_sequence(sequence_name, company_id)` — новейшее определение в
`20260730185058_fix-get-next-sequence-race.sql` — подставляет токены даты в
префикс/суффикс через **`current_date`**, а не через `company_today(company_id)`:

```
v_derived_prefix := replace(v_derived_prefix, '%{yyyy}', to_char(current_date, 'YYYY'));
v_derived_prefix := replace(v_derived_prefix, '%{yy}',   to_char(current_date, 'YY'));
v_derived_prefix := replace(v_derived_prefix, '%{mm}',   to_char(current_date, 'MM'));
v_derived_prefix := replace(v_derived_prefix, '%{dd}',   to_char(current_date, 'DD'));
```
(строки 44-49 этого файла)

При этом doc-комментарий `getCompanyTimeZone` прямо заявляет, что «токены дат в
последовательностях» выводят бизнес-день именно оттуда
(`packages/database/src/timezone.ts:8-10`). Функция `company_today` существует и
используется в других местах (7 миграций), но эту не переписали.

**Последствие для Хабаровска (UTC+10):** документ, созданный 1 января в 08:00 по
местному, на сервере в UTC — это ещё 31 декабря 22:00, и номер получит **префикс
прошлого года**. То же с месячными префиксами: документы, созданные до 10:00
местного времени первого числа, уйдут в нумерацию предыдущего месяца.
Это правится либо `TimeZone` у роли Postgres, либо патчем функции на
`company_today(company_id)`.

Сама таблица `sequence`: `table`, `prefix`, `suffix`, `next`, `step`, `size`,
`companyId`. Номер = `lpad(next, size, '0')` с интерполяцией токенов. Гонка
чтения-записи была починена в том же файле атомарным `UPDATE … RETURNING`
(строки 1-4). Читаемые id клиентов/поставщиков (`CUS`/`SUP`, размер 6)
проставляет BEFORE INSERT триггер и **только если поле пустое**, так что импорт
из CSV со своими номерами выигрывает (`customer-supplier-database-schema.md:17`).

## 12. Аудит изменений

`.claude/rules/audit-log-system.md`.

- Таблицы создаются **динамически на компанию**: `auditLog_{companyId}`.
  Ключ партиционирования — **само имя таблицы**, колонки `companyId` в ней НЕТ
  (`:17-18`).
- Колонки: `id` (`id('aud')`), `tableName` (реальная таблица), `entityType`
  (семантическая сущность), `entityId`, `recordId`, `operation`
  (`INSERT|UPDATE|DELETE`), `actorId`, `diff` JSONB
  (`{ field: { old, new, snapshot? } }`), `metadata` JSONB (`ipAddress`,
  `userAgent`, `origin`, `requestId`), `createdAt`.
- **Только на добавление (append-only), NIST 800-171 3.3.8 / AU-9.** Триггер
  `append_only` (`prevent_audit_log_mutation()`,
  `20260818014100_audit-log-append-only.sql`) **всегда** запрещает UPDATE, а
  DELETE — если в транзакции не выставлен локальный флаг
  `app.audit_archiving = 'on'`. Даже service-role не может переписать историю
  (`:36-46`).
- Автор изменения ловится через `auth.uid()` в `dispatch_event_batch`, но на
  прямом соединении Kysely `auth.uid()` = NULL, поэтому handler откатывается на
  `new.updatedBy ?? new.createdBy ?? old.updatedBy ?? old.createdBy`. Запись,
  которая не проставила ни одного из них, логируется как «System» (`:26`).
- Включается **по компании** (`company.auditLogEnabled`) — кроме
  `CONTROLLED_ENVIRONMENT` (ITAR/CUI), где обязателен и не отключается (`:48-57`).
- Конфигурация — `packages/database/src/audit.config.ts`: ~27 сущностей,
  у каждой роль таблицы `root` / `extension` / `{entityIdColumn}` /
  `{resolve:{junction,fk,entityIdColumn}}`. Ключи не совпадают с именами таблиц:
  `salesQuote` (метка «Quote», таблицы `quote`/`quoteLine`), `productionJob`
  (метка «Job»). `skipFields: ["updatedAt","updatedBy","embedding"]`,
  `retentionDays: 30` (`:59-77`).
- FK в diff разворачиваются в имена: топология FK читается в рантайме RPC
  `get_foreign_key_map` (по `pg_constraint`), отображаемые колонки — из
  `fkDisplayRegistry` (~64 целевых таблицы).
- Путь записи: триггеры → очередь PGMQ → Inngest `carbon/event-audit` →
  `auditFunction` → RPC `insert_audit_log_batch`. Старый Trigger.dev-таск удалён.
- Архивация: `auditArchiveFunction`, cron `0 2 * * *`, gzip в JSONL, приватный
  бакет, затем удаление. **Грабля:** реальный путь
  `audit-logs/{companyId}/{year}/{month}/{YYYY-MM-DD}.jsonl.gz` не совпадает с
  `auditConfig.archivePath` — джоб строит его инлайном (`:113-115`).

**Оценка:** 30 дней удержания по умолчанию — для российской практики (где к
первичке предъявляют сроки хранения в годах) мало; параметр конфигурируемый, но
архив уезжает в объектное хранилище и из UI ERP не ищется.

## 13. Бэкап / восстановление / перенос компании

`.claude/rules/company-backup-restore.md`. Механика заслуживает внимания, потому
что решает вопрос «как переносить данные между средами».

- Каталог таблиц **интроспектируется из схемы**, а не ведётся руками:
  `getCompanyTableCatalog(db)` читает `information_schema`, находит каждую BASE
  TABLE с колонкой `companyId` или `companyGroupId`, строит FK-рёбра и
  **топологически сортирует** (`:52-61`). `companyId` выигрывает, если есть обе.
- Исключения: `SECRET_TABLES` (`apiKey`, `companyIntegration`, `webhook`,
  `oauthClient`, `oauthToken` — никогда не путешествуют), `STRUCTURAL_TABLES`
  (`company`), `TRANSIENT_TABLES` (выход планирования MRP — пересчитается),
  `IN_PLACE_SKIPPED_TABLES` (таблицы доступа, чтобы не запереть себя снаружи).
- Формат — **папка**, не файл: `exports/<name>/manifest.json` +
  `tables/<table>.ndjson.gz` на каждую непустую таблицу + `assets/`. Построчная
  сериализация, чтобы большая таблица не материализовалась в одну строку >512 МБ
  (у V8 это предел). Параллельность — 6 таблиц. `manifest.json` пишется
  **последним** и именно его наличие означает «бэкап завершён» (`:76-92`).
- При переносе id перевыпускаются (`newIdForTable`), FK ремапятся; строки,
  конфликтующие по реальному уникальному ключу (в обеих базах есть
  «Headquarters»), не вставляются — исходный id **отображается** на существующий
  в цели, чтобы все FK приземлились правильно (`:100-115`).
- **Ограничение доступа:** фича закрыта гейтом `canAccessBackups(email)` =
  `IS_LOCAL_DEV || isInternalEmail(email)`, где internal = `@carbon.ms` /
  `@carbon.us.org`. В продакшене, превью и **self-hosted** (все они
  `NODE_ENV=production`) она недоступна. Чтобы открыть — «выбросить
  `canAccessBackups` целиком» (`:38-46`).

Это важный практический вывод: **штатный per-company бэкап/восстановление у
self-hosted Carbon выключен**, и включение требует правки кода. Резервирование
придётся строить на уровне PostgreSQL (`pg_dump`), как и в текущей связке
ERPNext + MariaDB.

## 14. Что это значит для завода металлоконструкций — сводка

### Сильные стороны модели

1. **Сквозная связность без «динамических ссылок»**: `quote → salesOrder →
   job → jobOperation → productionEvent` и `item → makeMethod → methodOperation /
   methodMaterial` соединены нормальными FK. Любой бизнес-процесс выражается
   явным обходом графа, а не догадками.
2. **Прослеживаемость промышленного уровня**: граф `trackedEntity` /
   `trackedActivity` + дробление партии с сохранением id родителя и слиянием
   остатков — ровно модель «плавка → раскрой → деталь → узел → отгрузка».
3. **Ревизии и замены разведены** и обслуживают разные вопросы (закупка /
   потребление в заказе / подбор со склада) — редкая зрелость.
4. **Числовая дисциплина документирована и проверяется автоматически** (три
   conformance-проверки, отдельный модуль `precision.ts`, тесты). Таких инвестиций
   в округление нет в большинстве open-source ERP.
5. **Часовые пояса вынесены в две явные оси** (бухгалтерская / операционная) с
   запретом локальной зоны сервера — то, что обычно чинят постфактум.
6. **Расширяемость без форка**: `customFields` JSONB + `customField`/
   `customFieldTable`, `batchProperty`, конфигуратор с типом параметра `material`.
7. **PLM-контур из коробки**: `changeOrder` + `changeOrderSupersession` +
   `nonConformance`.

### Пробелы, которые придётся закрывать под металл

| Пробел | Что именно | Оценка объёма |
|---|---|---|
| **Нет физических свойств номенклатуры** | ни массы, ни плотности, ни толщины/ширины/длины как чисел — только текстовый ярлык `materialDimension.name` | либо `customFields` (быстро, но без расчётов), либо новые колонки + миграция + формы + расчётный тракт (**крупная доработка**) |
| **Нет конверсий единиц измерения** | `unitOfMeasure` — плоский справочник без базовой единицы и коэффициента; пересчёт только через `conversionFactor` на связке «поставщик-позиция» и строке закупки; у `quoteLine`/`salesOrderLine` его нет вовсе | новая таблица конверсий + подмешивание во все расчёты цены/количества (**крупная**) |
| **Нормирование только «на штуку»** | enum `factor` не знает «минут на метр шва», «часов на тонну», «м²/час» | расширение enum + вся арифметика планирования и себестоимости (**средняя–крупная**) |
| **Нормы времени зажаты `NUMERIC(10,2)`** | `jobOperation` / `methodOperation` `.setupTime/.laborTime/.machineTime` пропущены волной расширения 2026-08-11 | одна миграция ALTER TYPE (**малая**) |
| **Нумерация документов по дате сервера** | `get_next_sequence` использует `current_date`, а не `company_today` — для UTC+10 префикс года/месяца «съезжает» на 10 часов | патч SQL-функции (**малая**) |
| **Бэкап компании закрыт гейтом для self-hosted** | `canAccessBackups` пускает только локальную разработку и внутренние домены | либо выбросить гейт, либо строить бэкап на `pg_dump` (**малая–средняя**) |
| **Удержание аудита 30 дней** | `auditConfig.retentionDays: 30`, дальше архив в объектное хранилище без поиска из UI | конфигурация + при необходимости UI поиска по архиву (**средняя**) |
| **Нет полей «плавка / сертификат / ГОСТ»** | кладутся в `trackedEntity.attributes` JSONB, `batchProperty` или `customFields` | конфигурация, не код (**малая**) |
| **Нет ИНН/КПП/ОГРН как полей** | есть `taxId`, `vatNumber`, `registrationNumber`, `eori` на `company`; у контрагентов `taxId` + `taxPercent` | маппинг + `customFields` (**малая**) |

### Отдельно про «помешает ли точность работать с металлом»

Прямого ограничения по разрядности **нет**: количества и цены живут на шкале 5
знаков в голом `NUMERIC`, что даёт 0.00001 кг (0.01 г) и 0.00001 м (10 мкм) —
для металлоконструкций избыточно. Реальные риски другие:

1. **NUMERIC декодируется в JS `number` (float64)** на обоих драйверах
   (`numeric-precision.md:184-190`) — точных десятичных типов в тракте нет.
   Шум гасится дисциплиной (`EPSILON = 1e-6`, `distributeRoundingResidual`,
   `assertBalanced`), а не типом данных. При больших спецификациях (сотни строк
   раскроя) это работает, но любая своя доработка обязана пользоваться тем же API,
   иначе появится расхождение в копейку/грамм.
2. **Формат поля ввода = точность хранения.** react-aria коммитит
   `parse(format(x))`, поэтому неверно выбранный вид форматирования молча
   обрезает введённое значение (прецедент: цена $0.00123 → $0.00). Любая новая
   форма с массой/толщиной обязана использовать `INPUT_FORMAT.quantity` /
   `.rate` и `INPUT_STEP.*`, иначе потери данных будут тихими.
3. **Деньги и цена округляются по-разному**: сумма — по `currency.decimalPlaces`
   (для рубля 2), цена за единицу — до шкалы 5. Путать нельзя, и это обеспечено
   только соглашением в коде, потому что колонки в БД голые.
4. **46 колонок всё ещё зажаты `NUMERIC(x,y)`**, включая нормы времени операций,
   и автоматическая проверка их не увидит, потому что читает текст миграций, а не
   живую схему (`numeric-precision.md:203-205`). Перед промышленной эксплуатацией
   их стоит пройти отдельным аудитом.

## 15. Чего в коде нет (проверено, не додумано)

- Нет полей веса/плотности/толщины/ширины/длины ни в одной таблице.
- Нет таблицы конверсии единиц измерения (`unitOfMeasure` — плоский справочник).
- Нет `itemTracking` как таблицы в текущей схеме (в миграции
  `20250209000952_item_tracking.sql` была, в `types.ts` отсутствует).
- Нет `itemInventory` в текущей схеме; остатки — `itemStockQuantities`
  (`companyId, itemId, locationId, quantityOnHand`), поддерживаемая триггером
  (была materialized view, конвертирована в таблицу миграцией `20260812002454`).
- Нет отдельной таблицы ревизий — ревизия это строка `item`.
- Нет флага «активная ревизия» — выбирается порядком в CTE `latest_items`.
- Нет `itemId` на `part`/`material`/`tool`/`consumable` — связь позиционная по
  `readableId`.
- Нет `supplierStatus` как таблицы (enum), нет `invoicingContactId`, нет
  `externalId` как колонки на контрагентах.
- Нет `entityType` на `trackedActivityInput` (удалена в `20250301125444`).
- Нет провенанса замены на `methodMaterial` (есть только на `jobMaterial`).
- Нет Decimal-типа в рантайме — только float64.
- Нет ИНН/КПП/ОГРН, УПД, счёта-фактуры, книги покупок/продаж как сущностей.
- Нет русской локали в перечислениях домена (`methodType`, `jobStatus`,
  `itemType` и т.д. — значения на английском прямо в БД; правило
  `method-material-sourcing.md:20` фиксирует «DB + UI в синхроне, без перевода»),
  то есть русификация статусов потребует слоя отображения, а не переименования
  значений enum.
