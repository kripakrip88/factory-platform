# Carbon ERP/MES — бизнес-процессы: разбор 14 руководств + проверка по коду

Источник: `docs/content/guides/*.mdx` (14 файлов) + сверка каждого утверждения с кодом
репозитория `crbnos/carbon`. Везде, где руководство и код расходятся или где код
добавляет существенную деталь, — отдельная пометка **«В коде»**.

Все пути — от корня репозитория.

---

## 0. Как устроена система (нужно для чтения остального)

Carbon — это **две отдельные веб-приложения** над одной базой:

| Слой | Где | Что делает |
|---|---|---|
| ERP (офис) | `apps/erp/` | продажи, закупки, планирование, учёт, справочники |
| MES (цех) | `apps/mes/` | терминал оператора: старт/пауза операции, выдача материала, брак, сканирование |
| БД | `packages/database/supabase/migrations/` (1005 миграций) | PostgreSQL/Supabase, ~330 таблиц |
| Транзакционная логика | `packages/database/supabase/functions/` (Deno edge functions) | проводка документов, копирование методов, конвертации |
| Планирование | `packages/ee/src/planning/` | MRP (`mrp/mrp.ts`, 1149 строк) и конечное расписание (`scheduling/`, ~14 тыс. строк) |
| Интеграции | `packages/ee/src/` | QuickBooks, Xero, Sage, Rillet, Slack, Jira, Linear, Onshape, Paperless Parts, **Radan** (нестинг листового металла) |

Принципиальное архитектурное решение: **тяжёлая логика вынесена из приложения в
edge-функции и SQL**. Например, «провести отгрузку (post shipment)» — это не код
React-роута, а `packages/database/supabase/functions/post-shipment/index.ts` (4467 строк).
Роуты приложения — тонкие: валидация формы → вызов edge-функции → redirect.
Это важно для оценки адаптации: бизнес-правила править надо в Deno/SQL, а не в TS-фронте.

Перечень статусов (enum-ов) базы — `packages/database/src/types.ts:83321–84039`.
Это самый полезный единственный фрагмент для понимания, какие состояния вообще
существуют в системе.

# ЧАСТЬ I. Разбор 14 процессов

Руководства сгруппированы в 5 «потоков» (flow) через frontmatter-поле `flow:`.
Пять руководств без `flow` — это сквозной «тур make-to-order»: order → build → plan → floor → ship.

## Поток A. Тур «под заказ» (make-to-order), 5 руководств

### A1. `order.mdx` — «Начинается с заказа»

**С чего начинается.** Подтверждённый заказ клиента (sales order). Пример в
руководстве: SO000009, 90 шт. SAW-001 по $35 000, разбитый на **три строки по 30 шт.**
под три недели поставки.

**Что создаётся по шагам.**
1. `salesOrder` + три `salesOrderLine` (по одной на партию поставки).
2. Баннер «Jobs Required» на заказе → кнопка **«Create Jobs»** создаёт производственные
   задания (job) по всем строкам сразу; либо построчно через карточку Jobs →
   **«Make to Order»** → диалог **«Convert Line to Job»** с преднаполненным количеством.
3. На каждое задание копируется **метод (method)** — рецепт: BOM + маршрут.

**Статусы.**
- Заказ (`salesOrderStatus`, `packages/database/src/types.ts:83914`):
  `Draft | Needs Approval | Confirmed | In Progress | Completed | Invoiced | Cancelled | Closed | To Ship and Invoice | To Ship | To Invoice`.
  Рабочая последовательность: `To Ship and Invoice` → (`To Ship` | `To Invoice`) → `Completed`.
- Бейдж **«In Progress»** — это **вычисляемый** статус витрины, а не хранимый: пока
  у make-to-order строк есть незакрытые задания, список показывает «In Progress»,
  а в базе лежит `To Ship and Invoice`.
- Задание (`jobStatus`, `types.ts:83617`):
  `Draft | Planned | Ready | In Progress | Paused | Completed | Closed | Cancelled` (+ витринные `Overdue`, `Due Today`).

**Маршруты.**
- `/x/sales-order/:orderId` — `apps/erp/app/routes/x+/sales-order+/$orderId.tsx`
- Создание заданий по всему заказу — `x+/sales-order+/$orderId.lines.jobs.tsx`
- По одной строке — `x+/sales-order+/$orderId.$lineId.job.tsx`
- Список заказов — `/x/sales/orders`; задания — `/x/production/jobs` (`utils/path.ts:1354`)

**Таблицы.** `salesOrder`, `salesOrderLine`, `job`, `jobMakeMethod`, `jobMaterial`,
`jobOperation`, `opportunity`.

**Ключевые поля строки заказа** (`types.ts`, блок `salesOrderLine`):
`saleQuantity`, `quantitySent`, `quantityInvoiced`, `quantityToSend`, `quantityToInvoice`,
`sentComplete`, `invoicedComplete`, `methodType`, `promisedDate`, `salesOrderLineType`.

**В коде — три существенных уточнения к руководству:**

1. **Разбивка на задания автоматическая, по `lotSize`.** Функция
   `convertSalesOrderLinesToJobs` (`apps/erp/app/modules/production/production.service.ts:107`)
   читает `itemReplenishment.lotSize` и делит строку:
   `totalJobs = Math.ceil(totalQuantity / lotSize)` (строка ~188), последнее задание
   добирает остаток. То есть «три строки по 30» в руководстве — ручная разбивка
   менеджером, но система умеет и автоматическую по размеру партии.
2. **Припуск на брак считается при создании задания:**
   `scrapQuantity = scrapAllowance(jobQuantity, itemReplenishment.scrapPercentage)`
   (`production.service.ts:~237`). Поле `job.scrapQuantity`.
3. **Рецепт для задания берётся из КП, а не из номенклатуры, если КП было.**
   Руководство говорит «Get Method копирует метод детали». В коде
   (`production.service.ts:314–340`): если у сделки (opportunity) есть КП, вызывается
   `get-method` с `type: "quoteLineToJob"` и `sourceId = "<quoteId>:<lineId>"`;
   и только если КП нет — `type: "itemToJob"`. **Это важно:** цех строит по той
   спецификации, которую посчитали в КП, включая сделанные там правки, а не по
   мастер-рецепту номенклатуры.

**Release vs Plan** (ключевая развилка руководства):
- `Plan` — считает потребность в материалах (MRP), но НЕ ставит в расписание цеха.
- `Ready` (Release) — то же + расписание + цех видит работу.
  В коде (`x+/job+/$jobId.status.tsx:59–71`) оба статуса вызывают
  `recalculateJobRequirements` + `runMRP`; и только для `Ready`/`Planned` с
  `?schedule=1` дополнительно запускается `runLocationSchedule` и
  `create` → `purchaseOrderFromJob` (строки 109–133) — то есть **релиз задания сразу
  поднимает заказы поставщикам на кооперацию (outside processing)**.
  `job.releasedDate` штампуется на строке 136–142.

### A2. `build.mdx` — «Внутри задания»: BOM, типы обеспечения, версии методов

**Что описывает.** Структуру изделия и то, как каждая позиция добывается.

**`methodType` — самое нагруженное поле каталога** (`types.ts:83710`), три значения:

| Значение | Русский смысл | Что происходит |
|---|---|---|
| `Make to Order` | изготавливаем под заказ | создаётся отдельное задание (job) со своим маршрутом |
| `Purchase to Order` | покупаем под заказ | уходит в закупку, становится строкой заказа поставщику |
| `Pull from Inventory` | берём со склада | просто списание со склада при сборке родителя |

Ставится **на самой номенклатуре**, все BOM его зеркалят. В `methodMaterial`
(`types.ts`, блок `methodMaterial`) поля `methodType` и `sourcingType` помечены в
`apps/erp/app/modules/items/AGENTS.md:33` как **производные — править построчно нельзя**,
менять надо на номенклатуре (`updateItemMethodAndSourcing`).

**Отдельная ось — `replenishmentSystem`** (`types.ts:83593`): `Buy | Make | Buy and Make`.
Отвечает на вопрос «как эта позиция пополняется вообще и в какую очередь планирования
попадает», в отличие от `methodType` («как она попадает в конкретного родителя»).
Одна и та же деталь может быть Make для одного родителя и Pull from Inventory для другого.

**Узел (subassembly) vs комплект (kit).**
- `Subassembly` — строится как отдельное задание, со своим маршрутом и завершением.
- `Kit` — отдельно не строится; компоненты выдаются в родительское задание пачкой.
  В коде это булево поле `methodMaterial.kit` (и `jobMaterial.kit`, `quoteMaterial.kit`) —
  см. `types.ts:23184, 29506, 45396, 81441, 82195`.

**Версионирование методов.** `makeMethodStatus` (`types.ts:83706`): `Draft | Active | Archived`.
Редактировать можно **только Draft**. Active заморожен — задания, которые по нему идут,
не поплывут. Ревизия = публикация новой версии, а не правка живой.

**Таблицы.** `makeMethod`, `methodMaterial`, `methodOperation`, `methodOperationStep`,
`methodOperationParameter`, `methodOperationTool`, `methodMaterialStep`.

**Маршруты.** Карточка детали `/x/part/:id`; дерево метода на задании —
`x+/job+/$jobId.method.$methodId.tsx` и `x+/job+/$jobId.make.$methodId.tsx`.

**Get Method.** `packages/database/supabase/functions/get-method/index.ts` (8176 строк) —
единая машина копирования рецептов. 15 направлений копирования
(`itemToJob:451`, `itemToQuoteLine:2426`, `quoteLineToJob:5938`, `jobToItem:3874`,
`jobToJob:4205`, `makeMethodToMakeMethod:4966`, `quoteToQuote:6830` и т. д.).
Смысл: **у задания своя копия рецепта**. Правка задания не переписывает библиотеку
деталей; правка детали не трогает задание в работе. Обратный подъём улучшения в
мастер — `jobToItem` / `jobMakeMethodToItem`.

### A3. `plan.mdx` — «Планировать наперёд»: прогноз, политики пополнения, MRP

**С чего начинается.** Задание создало потребность. Но подтверждённые заказы — не вся
картина: воронка говорит, что будут ещё заказы, которых пока нет.

**Что создаётся по шагам.**
1. **Прогноз спроса (demand forecast)** — Production → Projections:
   вручную вводятся ожидаемые недельные количества.
   Маршрут `/x/production/demand-forecasts` (`utils/path.ts:914`),
   файл `x+/production+/demand-forecasts.tsx`, ввод —
   `demand-forecasts.$itemId.$locationId.tsx`.
   Таблицы: `demandProjection` (что ввёл человек), `demandForecast`, `demandForecastSource`,
   `demandActual`, `supplyForecast`, `supplyActual`.
2. **Политика пополнения (reordering policy)** на каждой номенклатуре —
   `itemReorderingPolicy` (`types.ts:83588`):
   - `Manual Reorder` — планирование не вмешивается;
   - `Demand-Based Reorder` — заказывать ровно под спрос, группируя за период накопления;
   - `Fixed Reorder Quantity` — при падении до точки заказа (`reorder point`) заказать фиксированную партию;
   - `Maximum Quantity` — классический min/max, добить до максимума.
   Таблицы `itemPlanning`, `itemReplenishment`. Экран — вкладка Planning на детали.
3. **Запуск MRP** нетит спрос против наличия (остатки + открытые задания + открытые заказы
   поставщикам) и предлагает разницу:
   - **Production Planning** → `/x/production/planning` (`x+/production+/planning.tsx`),
     сервис `getProductionPlanning` → RPC `get_production_planning`;
   - **Purchasing Planning** → `/x/purchasing/planning` (`x+/purchasing+/planning.tsx`),
     `getPurchasingPlanning` → RPC `get_purchasing_planning`.
   **Ничего не создаётся, пока предложение не подтверждено** (`planning.update.tsx`).

**Движок MRP.** `packages/ee/src/planning/mrp/mrp.ts`. Точка входа
`runMrp(client, db, payload)` (строка 94). Триггеры (`payload.type`, строки 60–80):
`location` / `job` / `purchaseOrder` / `salesOrder`. Периоды — недельные
(`getStartAndEndDates(today, "Week")`, строка 105). Раньше был Deno edge function,
сейчас выполняется **в процессе Node** — см. комментарий на строках 85–93.
Из ERP вызывается обёрткой `runMRP` (`production.service.ts:2622`).

**Приёмка (в этом же руководстве).** Приход по заказу поставщику:
`receipt` в статусе `Draft` → **проводка (posting)** превращает в остаток на полке.
Для партионного товара номер партии вводится прямо в строке прихода;
**коэффициент пересчёта (conversion factor)** превращает купленное в складское
(коробка из 10 → 10 шт. на полке).

**Статусы.** `receiptStatus` (`types.ts:83872`): `Draft | Pending | Posted | Voided`.

### A4. `floor.mdx` — «Цех»: расписание, операции, выдача материала, прослеживаемость

**С чего начинается.** Задание переведено в `Ready` — работа попала на доску MES.

**Доска расписания MES.** Канбан, **колонка = рабочий центр (work center)**,
внутри — операции, отсортированные по приоритету диспетчеризации.
Настройка отображения через Display popover (показывать/скрывать клиента, описание,
срок, длительность, прогресс, статус, заказ, миниатюру), фильтры по рабочему центру,
процессу, тегу, исполнителю.
**Важно:** доска цеха — только чтение плана. Перетаскиванием пересобрать расписание
нельзя; перебалансировка — в ERP-досках планировщика.
В коде: `jobOperation.priority` — «порядок размещения внутри рабочего центра, единственный
источник истины для порядка диспетчеризации; настраиваемой политики диспетчеризации нет»
(`apps/erp/app/modules/production/AGENTS.md:118`).

**Операции и рабочие центры.** Маршрут задания — упорядоченный список операций.
У каждой операции отдельно **время наладки, труда и машины**
(`methodOperation.setupTime / laborTime / machineTime` + единицы
`setupUnit / laborUnit / machineUnit` типа `factor`, `types.ts:83482`:
`Hours/Piece`, `Minutes/Piece`, `Pieces/Hour`, `Seconds/Piece`, `Total Hours`…).

`operationType` (`types.ts:83795-ish`, значения): `Process | Assembly | Inspection | Outside Processing`.

**Кооперация (outside operation).** Процесс привязывается к поставщику
(`supplierProcess`), операция помечается Outside. **Релиз задания поднимает заказ
поставщику типа Outside Processing** на этот шаг, по ставке поставщика; срок поставки
занимает место операции в маршруте. В коде — вызов
`create` → `purchaseOrderFromJob` в `x+/job+/$jobId.status.tsx:125–132`,
реализация — `packages/database/supabase/functions/create/index.ts:441`.

**Рабочие инструкции.** Оператор видит не таблицу, а чек-лист шагов с допусками измерений
для конкретной операции, всегда текущей ревизии. Таблицы `jobOperationStep`,
`jobOperationStepRecord`, `jobOperationStepSlide`, `procedure`/`procedureStep`.

**Пульт оператора (MES).** Кнопки: Start/Pause, Labor (и Setup/Machine, если операция их
несёт), «Issue Material», «Log Completed», «Log Scrap» (с причиной), «Log Rework»,
«Complete All», «Finish».
- Нажатие таймера открывает/закрывает **производственное событие (production event)** —
  `productionEvent`, тип `productionEventType` (`types.ts:83805`): `Setup | Labor | Machine`.
- Количества — `productionQuantity`, тип `productionQuantityType` (`types.ts:83806`):
  `Production | Scrap | Rework`, с `scrapReason`.
- «Finish» закрывает операцию насовсем; «End Operations» (конец смены) только гасит
  таймеры, оставляя работу открытой.

Маршруты MES: `apps/mes/app/routes/x+/operation.$operationId.tsx`,
`start.$operationId.tsx`, `end.$operationId.tsx`, `finish.tsx`, `issue.tsx`,
`scrap.tsx`, `rework.tsx`, `record.tsx`, `timecard.tsx`, `picking.$pickingListId.tsx`.

**Два способа списать материал.**
- **Issued (выдача)** — прослеживаемый материал выдаётся на операцию поштучно/по партиям.
- **Backflush (обратное списание)** — непрослеживаемый материал списывается автоматически
  в момент завершения операции/задания.
  Выбор — на строке BOM.
  В коде: edge-функция `packages/database/supabase/functions/issue/index.ts` (~4800 строк)
  обслуживает `partToOperation:1887`, `trackedEntitiesToOperation:2687`,
  `jobOperation:1004`, `jobOperationScrap:1413`, `scrapTrackedEntity:2182`,
  `unconsumeTrackedEntities:3259`.

**Сканирование и генеалогия.** Каждая физическая единица — `trackedEntity`
(`trackedEntityStatus`, `types.ts:20778`: `Available | Reserved | On Hold | Consumed | Rejected | Scrapped`).
Сканирование ребёнка в собираемую единицу пишет `trackedActivity` +
`trackedActivityInput` / `trackedActivityOutput`: ребёнок помечен потреблённым,
родитель произведённым, связь постоянна.
`itemTrackingType` (`types.ts:83600`): `Inventory | Non-Inventory | Serial | Batch`.

**Планировщик (в коде, руководством почти не раскрыт).**
`packages/ee/src/planning/scheduling/` — конечное расписание вперёд (forward-ASAP),
регенерирует **целую площадку (location)** за один детерминированный проход.
Из `production/AGENTS.md:118`:
- доступность станка — лестница: `workCenter.alwaysOn` (24×7) → `workCenterShift` →
  смены площадки (`shift`) → дефолт Пн–Пт 8 ч; открытые заявки на ремонт с
  `takesWorkCenterOffline` вычитают простой;
- рабочие центры конечны (ёмкость 1 — одна операция за раз);
- **люди тоже конечны**: для операций с требованием квалификации работа копится, только
  пока квалифицированный сотрудник на смене (`employeeShift` ⋈ `shift`);
- результат — строки `capacityReservation` + `job.projectedCompletionAt`;
- **двойные даты**: `jobOperation.dueDate` — обратный расчёт «когда надо» от `job.dueDate`
  (`need-by-calculator.ts`), `startDate` + `projectedCompletionAt` — прямой прогноз.
  Опоздание против цели — информационное жёлтое состояние, не блокировка.
- Квалификация резолвится **через процесс**: `process.requiresAbility` → `ability.processId`
  → наличие строки `employeeAbility`. **Требований квалификации на уровне операции нет.**

**Батчи операций (`jobOperationBatch`)** — в руководствах не описаны совсем, но в коде
это крупная фича: N операций разных заданий, идущих одним прогоном на «батчуемом»
процессе (`process.batchable` — лазерный стол, печь, гальваника), с `process.batchType`
`Sequential`/`Simultaneous`. Время и стоимость делятся **пропорционально
`operationQuantity`** и материализуются как персональные `productionEvent` на каждое
задание, так что учёт не меняется. Статусы `Planned → Active → Completing → Completed`.
Экран `/x/production/batches`, конструктор — `production/ui/Batches/BatchBuilder.tsx`.
**Для завода МК это прямой аналог «одна карта раскроя / одна загрузка печи на несколько заказов».**

### A5. `ship.mdx` — «Качество, прослеживаемость, отгрузка»

**С чего начинается.** Изделие собрано, надо доказать, что собрано правильно.

**Несоответствие (issue / non-conformance).**
Оператор поднимает Issue — это `nonConformance`.
Статусы `nonConformanceStatus` (`types.ts:83751`): `Registered | In Progress | Closed`.
Связывается с деталью и с операцией задания (`nonConformanceJobOperation`),
а также с поставщиком, клиентом, строками заказов/приходов/отгрузок —
см. семейство таблиц `nonConformance*` (17 таблиц).

**Рабочий процесс несоответствия.** Не просто запись, а workflow
(`nonConformanceWorkflow`, `nonConformanceRequiredAction`, `nonConformanceActionTask`),
который порождает задачи по типам: **Containment** (сдерживание — всплывает в цехе,
чтобы следующий оператор не продолжал гнать брак), **Corrective** (устранение причины),
**Preventive** (чтобы не повторилось), **Verification**, **Communication**.
Классический 8D — один из таких настраиваемых workflow.

**Решение по задержанному материалу (disposition).** Гейт: `use as is` / `rework` /
`scrap` / `return to supplier`. Код — `apps/erp/app/modules/quality/quality-disposition.server.ts`.
Маршруты: `/x/issue/:id` (`x+/issue+/$id.tsx`), `$id.review.tsx`, `$id.close.tsx`,
`$id.supplier-return.tsx`; список `/x/quality/issues`.

**Версионированные процедуры.** Рабочие инструкции генерируются из процедур с той же
дисциплиной Draft/Active/Archived. Новые задания берут последнюю версию; уже идущие
остаются на своей. Карточка изделия фиксирует ревизию, по которой его реально собрали.
Таблицы `procedure`, `procedureStep`, `procedureParameter`; маршрут `/x/procedure/:id`.

**Прослеживаемость.** Граф `trackedEntity` + `trackedActivity`. От серийника можно идти
назад ко всем предкам (какая рама, какая партия батарей, какой лист) и вперёд — где ещё
использовалась партия. Маршрут `/x/traceability` и `/x/traceability/graph`
(`utils/path.ts:2254–2255`), сервис `apps/erp/app/modules/inventory/lineage.server.ts`.
QR-этикетка на изделии открывает ту же карточку.

**Отгрузка.** Создаётся `shipment` против заказа; строки наполняются из невыполненного
остатка; можно отгрузить **часть** (в примере — 2 из 3), остаток остаётся открытым.
Дальше — счёт на ту же фактически отгруженную часть.

## Поток B. «Quote to cash» (от КП до денег), 2 руководства

### B1. `quote-to-cash.mdx` — «От КП к заказу»

**Ключевая идея: жёсткой цепочки нет.** RFQ клиента, КП и заказ — три документа,
висящие на одной **сделке (opportunity)**. У сделки есть слоты `salesRfqId`,
`quoteId`, `salesOrderId`, и любой может быть пустым. Можно завести заказ «с холода»,
можно котировать без формального RFQ.
Таблица `opportunity`; сервис `getOpportunity` (`sales.service.ts:1044`).

**Построение КП.** Строка на каждую позицию; цена живёт на строке и поддерживает
**количественные ступени (quantity breaks)** — `quoteLinePrice`, первичный ключ
`(quoteLineId, quantity)`, без `id`-колонки (`sales/AGENTS.md:10`).
⚠️ `discountPercent` хранится **дробью 0–1**, не 0–100.

**Статусы.**
- КП `quoteStatus` (`types.ts:83853`): `Draft | Sent | Ordered | Partial | Lost | Cancelled | Expired`.
- Строка КП `quoteLineStatus`: `Not Started | In Progress | Complete | No Quote`.
  Строки доводятся до готовности независимо — многопозиционное КП считается кусками.

**Финализация** переводит КП в `Sent` и помечает строки `Complete`. Это гейт следующего шага.

**Цифровое КП (digital quote).** У `Sent`-КП появляется приватная ссылка с неугадываемым id,
без логина; внутренние заметки вырезаются. Клиент жмёт **Accept Quote** → КП
конвертируется в заказ (с возможностью приложить свой PO в PDF), либо **Reject Quote** → `Lost`.
Маршрут `apps/erp/app/routes/share+/quote.$id.tsx`; ссылка хранится в `externalLink`.

**Ревизии КП.** `quote.revisionId`. Ревизия — **новая строка `quote`** с тем же `quoteId`
и `revisionId = max+1`, той же `opportunityId`, созданная через `copyQuote` →
`get-method` (`quoteToQuote`, `asRevision: true`). Отображается как `Q000001-1`
(`sales/AGENTS.md:9`). Проигранное/просроченное КП не теряется — поднимается новая ревизия.

**Конвертация в заказ.** `convertQuoteToOrder` (`sales.service.ts:217`) вызывает
edge-функцию `convert` с `type: "quoteToSalesOrder"`
(`packages/database/supabase/functions/convert/index.ts:472`).
КП переходит в `Ordered` (или `Partial`, если сконвертированы не все строки),
заказ открывается в `To Ship and Invoice`, наследует согласованные цены и ту же сделку.

**⚠️ Правило: заданий из КП напрямую нет.** Задание рождает только строка
**заказа**: quote → order → job. Подтверждается кодом: `convertSalesOrderLinesToJobs`
принимает `orderId`, не `quoteId`. **НО** (см. A1) метод/спецификация в задание копируется
именно из строки КП, если КП существовало (`quoteLineToJob`).

**Ценообразование (в коде, в руководстве не раскрыто).** Приоритет разрешения цены
(`sales/AGENTS.md:12`): цена клиента > цена типа клиента > цена для всех клиентов > базовая.
Таблицы `customerItemPriceOverride`, `customerItemPriceOverrideBreak`, `pricingRule`.
Скидки **не складываются** (побеждает высший приоритет), наценки **складываются и
компаундируются** по приоритету (`applyPriceRules`, `sales.service.ts:103`).
Трассировка цены пишется в `salesOrderLine.priceTrace` (JSON).

### B2. `order-to-cash.mdx` — «Отгрузить, выставить счёт, получить деньги»

**С чего начинается.** Заказ в статусе `To Ship and Invoice`.
Четыре хода до денег, **ни один не цепляется автоматически за предыдущий**.

**Правило открытой строки.** Строка считает `saleQuantity` против `quantitySent` и
`quantityInvoiced`; `quantityToSend` / `quantityToInvoice` вычисляются.
**Строка закрывается только когда И отгружена, И выставлена.** Это и позволяет
отгружать и выставлять частями, не теряя остаток.

**Три способа закрыть строку** — по `methodType`:
- `Make to Order` → производственное задание;
- `Pull from Inventory` → отбор со склада, без задания;
- `Purchase to Order` → закупка под заказ; вариант **drop-ship** (`sourcingType`
  = `Drop Ship`, `types.ts:83951`) — поставщик везёт сразу клиенту, товар не заходит на склад.
Любое исполнение сводится к одному из двух типов `fulfillmentType` (`types.ts`):
`Inventory` или `Job`.

**Шаг 1 — отгрузка.** Создаётся `shipment` (одна таблица обслуживает продажи, закупки и
перемещения — различает `shipmentSourceDocument`: `Sales Order | Sales Invoice |
Sales Return Order | Purchase Order | Purchase Invoice | Purchase Return Order |
Inbound Transfer | Outbound Transfer`). Открывается в `Draft`.

**Создание ничего не двигает. Двигает проводка (posting).** При проводке одновременно:
статус → `Posted`, склад уменьшается через `itemLedger`, растёт `quantitySent`,
заказ переходит в `To Invoice` (или `Completed`). `sentComplete` взводится только когда
накопленная отгрузка достигла заказанного.
Код: `packages/database/supabase/functions/post-shipment/index.ts`;
проводка COGS — строки 435–470 (`costOfGoodsSoldAccount` против счёта запасов,
разрешаемого `resolveInventoryAccount` по `replenishmentSystem`);
строки `itemLedger` с `documentType: "Sales Shipment"` — 353, 369, 401;
слой себестоимости `costLedger` (`itemLedgerType: "Sale"`, `costLedgerType: "Direct Cost"`) — 1113–1118.
**Проводка отгрузки НЕ создаёт счёт** — это отдельный шаг.

**Шаг 2 — счёт.** Два источника: прямо из **заказа** или из **проведённой отгрузки**
(второй путь привязывает счёт к отгрузке и ограничивает количество фактически отгруженным).
Открывается в `Draft`, полностью редактируемый; как только выходит из Draft — блокируется.
Конвертации: `convert` edge fn, `salesOrderToSalesInvoice:807` и `shipmentToSalesInvoice:1346`.

**Шаг 3 — проводка счёта.** `salesInvoiceStatus` (`types.ts:83894`):
`Draft | Pending | Submitted | Return | Credit Note Issued | Paid | Partially Paid | Overdue | Voided`.
Проводка пишет ГК (Дт Дебиторка / Кт Продажи, и Дт COGS / Кт Запасы) —
**только если учёт включён**; поднимает `quantityInvoiced`, ставит дату проводки,
переводит в `Submitted`. **Проводка НИКОГДА не делает счёт «Paid».**

**Шаг 4 — платёж.** Платёж — **самостоятельная проведённая сущность**, не галочка:
таблица `payment`, статусы `Draft | Posted | Voided`; применяется к одному или нескольким
счетам через **зачёт (settlement)** — `invoiceSettlement`, где каждая строка несёт
основную сумму + скидку за раннюю оплату + списание. Кредит-нота (`memo`) применяется
так же, просто без денег.
Статус оплаты счёта **выводится** из зачётов: покрыт → `Paid`, частично → `Partially Paid`,
просрочен и не закрыт → `Overdue`.
Отмена проведённого счёта — **сторно** (`Voided` с обратными проводками), не удаление.
Код: `packages/database/supabase/functions/post-payment/` (index + `build-payment-journal.ts`
+ `post-payment-transaction.ts`, суммарно ~3200 строк).
Маршруты: `/x/payments/:id`, `/x/payments/:id/post`, `/x/payments/:id/void`,
`/x/payments/:id/applications` (`utils/path.ts:1736–1748`).

## Поток C. «RFQ to bill» (закупки), 2 руководства

### C1. `rfq-to-po.mdx` — «От запроса к заказу поставщику»

**Асимметрия с продажами.** Продажное КП — один документ одному клиенту.
**Закупочный RFQ создан, чтобы веером разойтись**: один запрос, те же строки,
нескольким поставщикам сразу, чтобы сравнить ответы.

**Шаги.**
1. `purchasingRfq` в `Draft`. Статусы `purchasingRfqStatus`: `Draft | Requested | Closed`.
2. Финализация → система создаёт **по одному `supplierQuote` на поставщика** из строк RFQ,
   связывает обратно и (опционально) шлёт письмо с приватной ссылкой.
   RFQ → `Requested`, каждое КП поставщика → `Draft`.
   Связующие таблицы: `purchasingRfqSupplier`, `purchasingRfqToSupplierQuote`,
   `purchasingRfqToPurchaseOrder`. **Связи — junction-записи, не жёсткая цепь**;
   один запрос может разойтись по многим поставщикам и многим заказам.
3. Поставщик открывает ссылку (без логина), вбивает цену, ступени количества и срок.
   Submit → `Active` и цены пишутся обратно в Carbon; отказ → `Declined`.
   `supplierQuoteStatus` (`types.ts:83968`): `Active | Expired | Draft | Declined | Cancelled`.
   Маршрут портала: `apps/erp/app/routes/share+/supplier-quote.$id.tsx`;
   портал висит **на КП поставщика, а не на запросе**.
4. Победившее КП конвертируется в заказ поставщику:
   `convertSupplierQuoteToOrder` → `convert` edge fn,
   `supplierQuoteToPurchaseOrder` (`convert/index.ts:1565`) — переносит поставщика,
   строки, согласованные цены (через `conversionFactor` и курс), тот же тред взаимодействия.

**Типы заказа поставщику** `purchaseOrderType` (`types.ts:83845`):
`Purchase | Return | Outside Processing`.

**Статус заказа поставщику НИКОГДА не вводится руками — он вычисляется из строк.**
`purchaseOrderStatus` (`types.ts:83827`): `Draft | To Review | Rejected | To Receive |
To Receive and Invoice | To Invoice | Completed | Closed | Planned | Needs Approval`.
Финализация свежего заказа → `To Receive and Invoice`. Если сумма превышает порог
согласования — застревает в `Needs Approval` (таблицы `approvalRule`, `approvalRequest`).

**Заказ может покупать не деталь, а ОПЕРАЦИЮ.** Тип `Outside Processing` привязывается
к операции задания (`purchaseOrderLine.jobOperationId`), а не к складской позиции.
Проводка прихода по такому заказу **ничего не кладёт на полку** — она двигает операцию
задания вперёд и **относит счёт поставщика прямо в НЗП (WIP) задания**.
Субподрядный шаг оказывается в том же балансе, что и собственные операции.
Поля: `purchaseOrderLine.jobId`, `purchaseOrderLine.jobOperationId`.

**Ревизия заказа поставщику — в отличие от КП, «на месте»**: `purchaseOrder.revisionId`
инкрементируется, **новой строки не создаётся**, приходы и счета остаются привязаны
(`purchasing/AGENTS.md:8`). Отображается `PO000123-1`.

### C2. `receive-and-bill.mdx` — «Принять, сопоставить, оплатить»

**Ключевая идея: приёмка и счёт — две независимые оси.**
Строка заказа поставщику считает `purchaseQuantity` против **двух независимых счётчиков**
`quantityReceived` и `quantityInvoiced`; `quantityToReceive` / `quantityToInvoice`
вычисляются; два флага `receivedComplete` и `invoicedComplete` — строка закрыта, только
когда оба true. Статус шапки — свёртка этих флагов.

**Приход.** Создаётся из заказа, преднаполняется из невыполненных строк,
каждая строка прихода ссылается на строку заказа. Открывается в `Draft`.
**Проводка** двигает: склад через `itemLedger` с `documentType: "Purchase Receipt"`,
`quantityReceived` растёт, `receivedComplete` взводится, статус прихода → `Posted`.
Код — `packages/database/supabase/functions/post-receipt/index.ts` (3195 строк).

> **Склад и ГК ходят по разным выключателям.** Проводка прихода **всегда** обновляет
> склад. Проводки ГК (Дт Запасы или НЗП / Кт GR-IR — товары получены, не оприходованы)
> пишутся **только если у компании включён учёт** (`companySettings.accountingEnabled`).

**Гейт качества.** Если у позиции есть назначение инспекционного документа с
usage = Receipt, её `trackedEntity` приходят в статусе **`On Hold`**, и открывается
входная инспекция в `Pending`. Принято, но на карантине.
Таблицы `inspection`, `inspectionSample`, `inspectionMeasurement`, `inspectionSamplingPlan`,
`itemInspectionDocumentAssignment`; маршрут `/x/quality/inbound-inspections`.

**Покупаем коробками, храним штуками.** `purchaseOrderLine.conversionFactor` +
`purchaseUnitOfMeasureCode` / `inventoryUnitOfMeasureCode`. При проводке прихода
`inventoryQty = purchaseQty × conversionFactor`. С поставщиком договариваетесь в его
единицах, цех тянет в своих.

**Счёт поставщика.** Берётся из заказа; остаются строки, по которым есть что выставить;
открывается в `Draft`. Каждая строка счёта ссылается на **строку заказа** —
**и это единственная структурная связь в цепочке**.

> **⚠️ Прямой связи «счёт → приход» НЕТ, и приход не обязателен перед счётом.**
> Прямой счёт может создать приход сам при проводке. Трёхстороннее сопоставление
> (three-way match) делается **по количествам на общей строке заказа**, а не сверкой
> документа-прихода с документом-счётом.

**Проводка счёта поставщика** (только при включённом учёте):
Кт Кредиторка, Дт Запасы или НЗП, **реверс GR-IR**, который поставил приход,
разница между ценой заказа и ценой счёта → на счёт отклонений закупочной цены
(`purchaseVarianceAccount`). Поднимает `quantityInvoiced`, взводит `invoicedComplete`,
пересчитывает статус заказа. Счёт встаёт в **`Open`**.
Код — `post-purchase-invoice/index.ts` + `purchase-posting-amounts.ts`.
`purchaseInvoiceStatus` (`types.ts:83807`): `Draft | Pending | Open | Return |
Debit Note Issued | Paid | Partially Paid | Overdue | Voided`.

**Проведён ≠ оплачен.** Как и на продажной стороне: платёж (`Disbursement` — деньги
наружу) — отдельная проведённая сущность, применяется зачётом; дебет-нота — так же без денег.
Статус оплаты выводится из применённого. Сторно вместо удаления.

## Поток D. «Производственный учёт», 4 руководства

### D1. `job-costing.mdx` — «Как считается себестоимость задания»

**Учёт — это выключатель.** Настройка компании `accountingEnabled` **по умолчанию выключена**.
С выключенным: `itemLedger` пишется, статусы двигаются, материал выдаётся — но **ни одной
проводки ГК и ни одного слоя себестоимости**. Цех может работать раньше, чем бухгалтерия.
Проверяется в каждой edge-функции; пример — `close-job/index.ts:49–52`:
```
if (!accountingEnabled) { return jsonResponse({ success: true }); }
```

**Два потока наполняют НЗП (WIP).**

1. **Материал.** Потребление детали (выдача на операцию или backflush при завершении)
   переносит её себестоимость из запасов в НЗП:
   **Дт Незавершённое производство / Кт Запасы**, тег `Job Consumption`
   (`journalEntrySourceType`, `types.ts:83628`).
2. **Труд, машина, накладные.** Каждое производственное событие несёт длительность.
   Carbon оценивает её **по ставкам рабочего центра** и проводит **в реальном времени**:
   Дт НЗП / Кт счёт поглощения, тег `Production Event`.
   Код — `post-production-event/index.ts:114–131`:
   читаются `workCenter.laborRate / machineRate / overheadRate`;
   машина считается по `machineRate`, труд и наладка по `laborRate`;
   накладные `durationHours × overheadRate` уходят на `overheadAbsorptionAccount`
   (строки 283 и далее), труд — на `laborAbsorptionAccount` (строка 257).
   **Все три ставки берутся с рабочего центра, а не из оценки операции.**

**Брак уходит из НЗП.** Скрапирование прослеживаемой детали снимает её стоимость с задания:
Дт специальный счёт брака / Кт НЗП (или сразу Кт Запасы, если деталь ещё была на складе),
с тегом причины, рабочего центра и оператора. **Испорченная стоимость покидает задание,
а не доезжает до закрытия**, и брак **переоткрывает маршрут**, чтобы построили замену.

**«НЗП — не таблица».** Ключевой архитектурный факт, который стоит понять сразу:
> В Carbon НЗП — это **не колонка и не таблица на задании**, а **сальдо в главной книге**:
> сумма всех проводок по счёту НЗП с идентификатором этого задания. НЗП задания — это запрос.

Подтверждается кодом `close-job/index.ts:63–76`: остаток НЗП считается прямым запросом
`journalLine ⋈ journal` по `accountId = workInProgressAccount AND documentId = jobId`.

**Себестоимость и слои.** Живёт в `costLedger`; каждая входящая запись открывает слой с
остатком количества. Способ списания — `costingMethod` на номенклатуре:
**FIFO / LIFO** (идут по открытым слоям), **Average** (текущая средняя),
**Standard** (плановая). Метод влияет на **сумму** записи в НЗП, но не на схему движения.
> **Отдельной таблицы слоёв нет.** Открытые слои — это строки `costLedger` с остатком.

### D2. `job-finish-close.mdx` — «Завершить, продать, закрыть»

Три разных события, порядок важен.

**1. Завершение в запас.** Диалог «Complete Job»: количество **не вводится руками** —
выводится из серийников и партий, завершённых в MES. Затем система:
backflush-ит оставшийся непрослеживаемый материал (**прослеживаемый никогда не
backflush-ится — его надо было отсканировать в цехе**), догоняет непроведённый труд,
и **приходует готовую продукцию на склад**: **Дт Запасы / Кт НЗП**, тег `Job Receipt`.
Задание → `Completed`.

> **Приход по фактической накопленной себестоимости НЗП.** Carbon **не** приходует по
> плановой себестоимости с отклонением. Себестоимость единицы = сумма того, что задание
> потратило. Отклонения в момент завершения нет: дебет = кредит.

Код: RPC `complete_job_to_inventory`
(`packages/database/supabase/migrations/20260508120000_complete-job-to-inventory.sql`,
уточнена в `20260914095239_complete-job-received-quantity.sql`),
вызов — `apps/erp/app/routes/x+/job+/$jobId.complete.tsx:47–54`.
Из `production/AGENTS.md:123–128`:
- `p_quantity_complete` — **кумулятивное**, не дельта; функция идемпотентна,
  повторное завершение на уже принятом количестве ничего не приходует и ничего не потребляет;
- отказывает при количестве ≤ 0, ниже уже принятого, и при дробном на серийном задании;
- серийная ветка приходует по одной пронумерованной единице, пропуская
  `Consumed`/`Rejected`/`Scrapped`;
- после завершения — «подметание» непотреблённого отобранного материала обратно на склад
  (`returnPickedRemaindersForJob`, `$jobId.complete.tsx:81–86`).

**2. «Под заказ» всё равно идёт через склад.**
> Прямой отгрузки готового изделия с задания **не существует**. Задание «под заказ»
> отличается только ссылкой `job.salesOrderLineId`; его учёт **идентичен** складскому
> заданию: сначала приход на склад, потом заказ отгружает **со склада**.
> Задание и отгрузка — две разные проводки.

**3. Продажа.** При отгрузке себестоимость уходит **из запасов**, а не из НЗП:
Дт COGS / Кт Запасы, тег `Sales Shipment` — из слоёв себестоимости запасов.
К моменту продажи НЗП давно списано (при завершении).

**4. Закрытие задания.** Завершение обнуляет НЗП «один в один», но округления, поздний
материал или позднее событие могут оставить копейки. **Закрытие подметает остаток**:
Дт **Production Variance** / Кт НЗП, тег `Job Close`. Задание → `Closed`, НЗП доказуемо ноль.
> **Это единственное место, где у задания появляется отклонение.** Отклонений по плановой
> себестоимости по ходу дела Carbon не пишет вообще.

Код: `packages/database/supabase/functions/close-job/index.ts`.
Порог — `Math.abs(remainingWip) < 0.01` (строка 76). Счёт —
`accountDefaults.materialVarianceAccount` с описанием `"Production Variance"` (строка 115).
Знак проводки подписан, так что и перекредитованный остаток тоже обнуляется (строки 112–114).

### D3. `fixed-assets-acquire.mdx` — «Принять на баланс и амортизировать»

> **Основное средство ≠ рабочий центр.** Станок, на котором планируете производство, —
> это `workCenter`; станок, который амортизируете, — `fixedAsset`.
> **Связи между ними в системе нет вообще.** Один и тот же пресс живёт двумя записями.

**Класс ОС (`fixedAssetClass`)** несёт счета ГК, на которые проводят все ОС этого вида:
счёт актива, накопленная амортизация, расход на амортизацию, счета списания.
Соответствующие поля в `accountDefault`: `assetAquisitionCostAccount`,
`accumulatedDepreciationAccount`, `assetDepreciationExpenseAccount`,
`assetGainOnDisposalAccount`, `assetLossOnDisposalAccount`,
`accumulatedDepreciationOnDisposalAccount`, `assetAquisitionCostOnDisposalAccount`
(`types.ts:352–406`).

**Два пути на баланс**, оба начинаются в `Draft`
(`fixedAssetStatus`, `types.ts:83494`: `Draft | Active | Fully Depreciated | Disposed`):
1. **Зарегистрировать то, что уже есть.** Указываются стоимость приобретения, дата
   приобретения и дата начала амортизации → статус `Active`. **Денег не проводится.**
   Маршрут `x+/fixed-asset+/$fixedAssetId.register.tsx`.
2. **Купить через закупку.** Строка заказа поставщику типа **`Fixed Asset`**
   (`purchaseOrderLineType`, `types.ts:83815`, значение `Fixed Asset`), указывающая на
   актив, затем приход. При проводке прихода — **и только если учёт включён** — Дт счёт
   актива / Кт GR-IR, **стоимость ПРИБАВЛЯЕТСЯ** к активу, штампуются даты, `Draft → Active`.
   Поскольку прибавляется — актив может набирать стоимость несколькими приходами.
   Таблица `receiptFixedAssetLine`; маршрут `$fixedAssetId.purchase.tsx`.
   > С выключенным учётом строка заказа будет принята, но **сам актив не тронут** —
   > регистрировать придётся вручную.

**Амортизация — ежемесячный пакет, который вы запускаете сами.**
Фоновой ночной задачи нет. Создаётся прогон за период, система подтягивает все активные
активы и считает начисление каждого, вы смотрите **черновик**, потом проводите:
Дт Расход на амортизацию / Кт Накопленная амортизация.
Таблицы `depreciationRun`, `depreciationRunLine`; маршруты
`/x/accounting/depreciation-runs`, `x+/depreciation-run+/$depreciationRunId.post.tsx`,
`.repeat.tsx`. Методы `depreciationMethod` (`types.ts:83385`):
`Straight Line | Declining Balance | Units of Production`.
Когда остаточная стоимость доходит до ликвидационной — проводка переводит в `Fully Depreciated`.

**Две книги сразу.** Каждый актив ведёт **бухгалтерский** и **налоговый** графики
независимо, каждый со своим методом. Налоговый включает полный **MACRS** с таблицами
классов имущества IRS: `taxDepreciationMethod` (`types.ts:83979`):
`Straight Line | Declining Balance | MACRS`, плюс поля `macrsPropertyClass`,
`macrsConvention`, `bonusDepreciationPercent`, `taxUsefulLifeMonths`,
`taxResidualValuePercent`, `accumulatedTaxDepreciation`.
При включённой налоговой амортизации проводка прогона может также начислять
**отложенный налог** (`deferredTaxExpenseAccountId`, `deferredTaxLiabilityAccountId`).

> ⚠️ **MACRS — это налоговое законодательство США.** Для России этот блок не применим
> и требует замены на классификацию ОС по амортизационным группам. См. часть III.

### D4. `fixed-assets-sell.mdx` — «Продать или списать»

Два **разных** выхода, разными командами, с разными эффектами. Оба стартуют из
`Active` или `Fully Depreciated`. Якорь обоих — **остаточная стоимость (net book value)**
= стоимость приобретения − накопленная амортизация.

**Продажа.** Действие **Sell** создаёт **настоящий заказ клиенту** с одной строкой типа
`Fixed Asset`, по цене = остаточной стоимости. Дальше — обычный quote-to-cash:
отгрузить, выставить, получить. Строка заказа помнит, какой актив продан
(`salesOrderLine.assetId`, `shipmentFixedAssetLine`).
Маршрут `x+/fixed-asset+/$fixedAssetId.sell.tsx`.
> Отдельного механизма продажи не изобретено — это обычный заказ.

**Списание (dispose).** Бухгалтерское действие. Проводится как списание:
Дт Накопленная амортизация, Дт счёт списания на остаточную стоимость,
Кт счёт актива на полную стоимость приобретения; остаток признаётся **убытком**.
Актив → `Disposed`. **Выручки на этом пути не бывает.**
Таблица `fixedAssetDisposal`; `disposalMethod` (`types.ts:83405`): `Sale | Scrapping`.
Маршрут `$fixedAssetId.dispose.tsx`.

## Поток E. «Инженерное изменение», 1 руководство

### E. `change-order.mdx` — «Ревизия детали» (change notice / ECO)

Самое длинное и, пожалуй, самое ценное руководство. Кратко: **нельзя просто отредактировать
живую деталь**. Открывается извещение об изменении, правится **скрытый черновик** метода
детали, изменение просматривается как **diff**, и только релиз делает его правдой.
До этого момента все задания, планы и расчёты себестоимости видят старую деталь.

**Откуда стартует.** Items → Change Notices → New; либо действие **«Create Change Notice»**
в шапке детали; либо из строки детали в таблице; либо из меню версий метода
(**New Change Notice** рядом с **New Version**). Каждый вариант заранее прицепляет деталь
как первый затронутый объект. Может стартовать **из проблемы качества** — тогда
несоответствие привязывается к извещению.

**Шапка.** Name, Category (`changeOrderType`, стартовый набор: Design Improvement,
Cost Reduction, Obsolescence / End-of-Life; `changeOrderTypeEnum`, `types.ts:83364`:
`Engineering | Manufacturing | Documentation`), Reason for Change, Description of Change,
Owner, Priority, даты.

> **Добавлять можно ТОЛЬКО Parts.** Материал, расходник или услуга не несут инженерной
> ревизии и в подборе не появляются.

Деталь, попавшая в открытое извещение, показывает у себя на карточке предупреждение
«This part is on 1 open change notice». **Оно информирует, а не блокирует**: второе
извещение на ту же деталь разрешено, черновики не сталкиваются.
**В коде подтверждено** (`items/AGENTS.md:89`): «Одновременные извещения на одну деталь
теперь разрешены — страж "одно открытое извещение на деталь" снят;
`findOtherOpenChangeNoticesForItem` остался, но только как подсказка».

**Черновик на месте.** Добавление детали тихо снимает снимок её живого метода в новую
версию **Draft**, помеченную этим извещением. Черновик **невидим везде** — его нет ни
в переключателе версий, ни в целях копирования, ни для MRP, ни для заданий, ни для
расчёта себестоимости. Редактируется теми же редакторами BOM и маршрута.

**Тип изменения (`changeOrderChangeType`, `types.ts:83351`)** — самый важный выбор,
он решает и что можно трогать, и что создаст релиз:

| Тип | Что делает | Создаёт замещение (supersession)? |
|---|---|---|
| `Version` | правит **как** делается та же деталь: новая версия метода, старая в архив | **Нет** |
| `Revision` | новая ревизия детали (тот же Part ID, следующая ревизия): атрибуты, документы, метод | **Да**, автоматически |
| `Replacement Part` | выводит **новый номер детали** из этой | **Да**, автоматически |
| `New Part` | абсолютно новая деталь, предшественника нет | **Нет** (нечего выводить) |

> ⚠️ Смена типа после начала правок **выбрасывает черновик и создаёт новый** из живого
> метода — правки теряются. Тип выбирают ДО редактирования.
> ⚠️ У покупной детали нет метода, который можно версионировать, поэтому добавление
> Buy-позиции автоматически садится на `Revision`.
> ⚠️ У покупной ревизии **не копируются поставщики со старой**: сетка Supplier Parts
> начинается пустой, и без заполнения деталь выйдет в релиз «некупибельной» — ни один
> заказ поставщику на неё не сошлётся.

**Стадии (`changeOrderStatus`, `types.ts:83356`):**
`Draft → Start → Engineering Complete → Implementation → Done`, плюс `Cancelled`.
Движение **только вперёд, по одному шагу**. Стадии `Start`, `Implementation` и `Done`
уведомляют исполнителя и назначенных на задачи.
> **Отдельного шага согласования нет и настроить его нельзя — стадии и есть workflow.**
> Подтверждено кодом: `items/AGENTS.md:89` — «Согласований в V1 нет. Ни гейта согласования,
> ни механики рецензентов/задач согласования, ни переключателя».

`Cancel` доступен в шапке на любой открытой стадии: блокирует извещение, но **сохраняет
все черновики**; `Reopen` возвращает в `Draft` с целыми правками. Отложить изменение ничего не стоит.

**Diff.** Карточка **Changes** на обзорной странице сводит diff всех затронутых объектов
**по ходу редактирования**, а не только на гейте. На стадии `Implementation` открывается
действие **Release**, которое сперва показывает изменение каждого объекта как
read-only diff: добавленные/удалённые материалы, изменённые операции и шаги, съехавшие атрибуты.
> **Diff точен по построению**: теневой копии правок нет, вы редактировали настоящий
> черновик, и diff — это просто он против живого метода, из которого снят.
Код: `diffMethod` (чистый движок) + `getChangeNoticeDiff` в `items.service.ts`,
визуализация `ChangeNoticeDiffViewer`.

**Релиз.** Подтверждение → система обходит затронутые объекты. Для ревизии детали:
активирует черновик метода, архивирует прошлую версию, **показывает новую ревизию как
живую позицию** (`item.active = true`, штамп `item.changeOrderId`) и **пишет замещение
(supersession)** от старой ревизии к новой. Когда все объекты обработаны — извещение
переходит в `Done` и блокируется как read-only запись.

Код: `applyChangeNotice` → `releaseAffectedItem` в `apps/erp/app/modules/items/items.server.ts`,
вызывается из `apps/erp/app/routes/x+/items+/change-notice+/$id.status.tsx:41–47`
(переход в `Done` **и есть** применение). Особенности (`items/AGENTS.md:104`):
- `New Part` релизится **первым** (стабильная сортировка), чтобы строка BOM
  родительской сборки нашла уже активную новую деталь;
- финальный перевод в `Done` — Kysely CAS (compare-and-swap);
- **идемпотентно**: у выпущенного черновика `makeMethod.changeOrderId` обнуляется, повтор пропускает;
- **это НЕ одна транзакция** — оркестрация через вызовы edge-функций.

**Замещение вы не пишете руками.** Выбирается только **как** оно перетекает, через поля
перехода на затронутом объекте: `supersessionMode` (`types.ts:83955`) —
`Consume First` (по умолчанию) | `Prefer New` | `Stock Only` | `No Stock`,
дата снятия с производства и дата вступления преемника в силу.
- `Consume First` — сначала израсходовать остаток старой, потом переключиться;
- `Prefer New` — новый спрос сразу на новую.
После вступления в силу MRP перенаправляет плановый спрос на новую ревизию, а **Get Method**
подставляет её в новые задания, записывая, откуда пришла замена.
Таблицы `itemSupersession`, `changeOrderSupersession`;
логика выбора — `packages/database/src/supersession-pick.ts` и
`apps/erp/app/modules/inventory/supersession-pick.ts`.

> **Релиз рулит будущим, а не прошлым.** Существующий остаток остаётся на старой детали;
> любое уже созданное задание сохраняет ровно тот материал и ту версию метода, против
> которых создавалось. То же и с бумагами: **открытый заказ поставщику или строка КП,
> в которых стоит старая ревизия, её и сохраняют, и релиз их не предупреждает и не переписывает.**
> Замещение трогает только прямое планирование: задание, запущенное после даты вступления
> в силу, возьмёт новую ревизию, запущенное до — нет.

После релиза новая ревизия несёт обратную ссылку «Created by CN-…», а карточка детали
показывает полную историю изменений.

Маршруты: `/x/items/change-notices`, `/x/items/change-notice/:id`,
`…/:id/affected`, `…/:id/affected/:affectedId/change-type`,
`…/:id/affected/:affectedId/cutover`, `…/:id/status` (`utils/path.ts:438–492`).

- задание не отгружается напрямую клиенту;

```
        ▼
 supplierQuote (Draft) ── поставщик по share-ссылке ──► Active | Declined
   вводит цену, ступени количества, срок; цены пишутся обратно
        │
        │  convert(supplierQuoteToPurchaseOrder)
        ▼
 purchaseOrder  (статус ВЫЧИСЛЯЕТСЯ из строк, руками не ставится)
   тип: Purchase | Return | Outside Processing
   финализация → To Receive and Invoice
   выше порога согласования → Needs Approval (approvalRule / approvalRequest)
        │
        ├──── ось 1: приёмка ─────────────┐        ├──── ось 2: счёт ────────────┐
        ▼                                  │        ▼                              │
 receipt (Draft) ── post-receipt ──► Posted│  purchaseInvoice (Draft) ── post ──► Open
   склад ВСЕГДА;  ГК — только если учёт вкл.│    Кт Кредиторка, Дт Запасы/НЗП,
   Дт Запасы|НЗП / Кт GR-IR                 │    РЕВЕРС GR-IR, разница цены →
   quantityReceived +, receivedComplete     │    purchaseVarianceAccount
   inventoryQty = purchaseQty × conversionFactor   quantityInvoiced +, invoicedComplete
   инспекция ⇒ trackedEntity = On Hold      │
        └──────────────┬───────────────────┴──────────────┬───────────────────────┘
                       ▼                                   ▼
        строка закрыта, только когда receivedComplete И invoicedComplete
        статус заказа = свёртка строк → Completed
                       │
                       ▼
        payment (Disbursement) → Posted ── invoiceSettlement ──► Paid
```

**Особый случай — кооперация (Outside Processing):**
```
операция задания помечена Outside + процесс привязан к поставщику (supplierProcess)
        │  релиз задания
        ▼
 purchaseOrder (type = Outside Processing), строка ссылается на
 purchaseOrderLine.jobId + .jobOperationId  (не на складскую позицию)
        │  проводка прихода
        ▼
 НИЧЕГО не кладётся на полку;
 операция задания двигается вперёд; стоимость поставщика → прямо в НЗП задания
```

**Где две цепочки встречаются:**
1. **Строка заказа клиента с `Purchase to Order`** — продажа поднимает закупку;
   `Drop Ship` вообще минует склад.
2. **Outside Processing** — одна бумага соединяет закупку, производство и учёт.
3. **Основное средство** — покупается строкой заказа поставщику типа `Fixed Asset`,
   продаётся заказом клиента со строкой `Fixed Asset` по остаточной стоимости.
4. **Общая таблица `shipment`** обслуживает и продажи, и возвраты поставщику,
   и межскладские перемещения (различитель — `shipmentSourceDocument`).

# ЧАСТЬ III. Как это ложится на завод металлоконструкций

## 3.1. Позаказное производство — ложится почти идеально

Carbon **изначально спроектирован под make-to-order**, а не под серийную сборку.
Конкретно под завод МК работают:

| Потребность завода МК | Механизм Carbon | Где |
|---|---|---|
| «Заказ на 12 ферм, отгружаем тремя партиями» | несколько строк заказа с разными `promisedDate`, каждая → своё задание | `salesOrderLine.promisedDate`, `convertSalesOrderLinesToJobs` |
| «Разбить 90 штук на партии по 30» | автоматически по `itemReplenishment.lotSize` | `production.service.ts:~188` |
| «На эту ферму нужен другой крепёж, чем в типовом чертеже» | у задания **своя копия** метода; правка не трогает библиотеку | `get-method`, `jobMakeMethod` |
| «Посчитали в КП с изменённой спецификацией — цех должен строить именно так» | метод в задание копируется **из строки КП** | `production.service.ts:314–330` |
| «Ферма состоит из балок, балка — из листа и профиля» | дерево `jobMakeMethod` через `parentMaterialId`, любой глубины | `jobMakeMethod`, `methodMaterial` |
| «Резка, сварка, зачистка, окраска, ОТК» | маршрут `jobOperation` с типами `Process`/`Assembly`/`Inspection` | `operationType` |
| «Оцинковку отдаём на сторону» | `Outside Processing`: релиз задания сам поднимает заказ поставщику, срок встаёт в маршрут, стоимость падает в НЗП | `create/index.ts:441`, `purchaseOrderLine.jobOperationId` |
| «Сколько реально стоила эта ферма» | НЗП = сальдо ГК по заданию; материал по факту + время по ставкам рабочего центра | `job-costing`, `post-production-event` |
| «Куда делся сертификат на этот лист» | `trackedEntity` (партия) → `trackedActivity` → граф генеалогии | `/x/traceability/graph` |
| «Сертификат на металл нужен по каждой партии» | `batchProperty` — произвольные свойства партии | таблица `batchProperty` |
| «Припуск на брак при раскрое» | `itemReplenishment.scrapPercentage` → `job.scrapQuantity` при создании | `scrapAllowance` |
| «Сварщик Иванов имеет допуск НАКС на эту работу» | `process.requiresAbility` → `ability` → `employeeAbility`; планировщик **не поставит** операцию, если нет квалифицированного на смене | `packages/ee/src/planning/scheduling/operator-eligibility.ts` |

**Отдельно стоит отметить `jobOperationBatch`** (в руководствах его нет, в коде — большая
фича): N операций **разных заданий** идут одним прогоном на «батчуемом» процессе.
Для завода МК это ровно «одна карта раскроя на пять заказов» или «одна загрузка печи».
Время и деньги делятся **пропорционально `operationQuantity`** и материализуются
персональными `productionEvent` на каждое задание — то есть **себестоимость каждого заказа
остаётся честной**, никакого спецкейса в учёте. Конструктор батча
(`production/ui/Batches/BatchBuilder.tsx`) умеет группировать кандидатов по **сигнатуре
материала** (вещество/марка/типоразмер/форма) и предлагать группы, ранжированные по
экономии наладки и срочности. Совместимость правится через `process.batchRules`
(«игнорировать» / «подсказка» / «обязательно»).

## 3.2. Каталог металла — неожиданно сильная сторона

Carbon везёт **готовую таксономию металлопроката**, а не абстрактную номенклатуру.
`packages/database/supabase/migrations/20250719100358_material-seed.sql`:

- **`materialForm`** (20 форм, строки 13–33): `Angle` (уголок), `Channel` (швеллер),
  `W-Beam` / `S-Beam` (двутавры), `Flat Bar` (полоса), `Round Bar`, `Square Bar`,
  `Hex Bar`, `Plate` (лист толстый), `Sheet` (лист тонкий), `Round Tube`,
  `Square Tube`, `Rectangular Tube` (профтруба), `Tread Plate` (рифлёный лист),
  `Billet`, `T-Bar`, `Wide Bar`, `Filament`, `Pellet`.
- **`materialSubstance`** (17, строки 35–53): `Steel`, `Stainless Steel`, `Aluminum`,
  `Brass`, `Bronze`, `Copper`, `Titanium`, `Inconel`, `Monel`, `Zinc`, и т. д.
- **`materialFinish`** (строки 79+): привязан к веществу — для нержавейки `#1/#2B/#2D/#3/#4/#6/#7/#8/BA`,
  для латуни/бронзы/меди — щётка #120/#180/#240, зеркало, сатин; для титана — анодирование.
- **`materialDimension`** — типоразмеры, привязанные к форме, с флагом `isMetric`.
  **Метрические ряды в сиде есть** (строки 361+: `0.5mm`, `0.8mm`, `1.0mm`, `1.2mm`,
  `1.5mm`, `2.0mm`, `2.5mm`, `3.0mm`…), наряду с имперскими (дюймы и gauge).
- `materialGrade` (марка) и `materialType` — company-scoped, заполняются под себя.

**Метрика переключается настройкой компании** `companySettings.useMetric`, и она
**ставится автоматически при создании компании**: `useMetric = false`, только если
страна = US или валюта = USD, иначе `true`
(`migrations/20250725212215_metric-default.sql:10–20`). Для российской компании
с RUB метрика включится сама. Выборка типоразмеров фильтруется по этому флагу —
`apps/erp/app/routes/api+/items.dimensions.$formId.ts:22`.

> **Вывод:** ГОСТ-номенклатуру (уголок 63×5, швеллер 16П, лист 08пс 3 мм, труба 80×80×4)
> можно завести штатными средствами: форма + вещество + марка + типоразмер, без доработки
> схемы. Понадобится только залить свои `materialGrade` (Ст3сп, 09Г2С, 20, 12Х18Н10Т)
> и добавить недостающие типоразмеры в `materialDimension`.

## 3.3. Раскрой металла — это надо обходить

**Функции раскроя/нестинга в Carbon НЕТ.** Проверено: в `apps/erp/app` и в 1005 миграциях
нет ни одной сущности нестинга, карты раскроя, остатка листа (remnant/offcut) или деловых
обрезков. Единственное упоминание — **интеграция с Radan**
(`packages/ee/src/radan/config.tsx`), которая описана как «category: Nesting» и умеет
ровно одно: синхронизировать данные выбранных **процессов** из Carbon в Radan и обратно
(единственная настройка — `processes`, строки 18–31). Самого раскроя Carbon не делает.

**Что это значит практически:**

| Задача раскроя | Как в Carbon | Обход |
|---|---|---|
| Разложить детали по листу, посчитать коэффициент использования | **нет** | внешний CAM (Radan, SigmaNest, Lantek, «Техтран») |
| Карта раскроя как документ | **нет** | внешняя система + файл на задании (`document`) |
| Учёт делового остатка листа | **нет** отдельной сущности | ⚠️ обходится через `trackedEntity` с `batchNumber` = номер остатка и `quantity` = остаток площади/массы, но это самодельная схема |
| Списание одного листа на несколько заданий | **частично**: `jobOperationBatch` объединяет операции нескольких заданий на одном прогоне и делит время/стоимость пропорционально | это **не** раскрой, но покрывает 80 % экономики: одна наладка, одна загрузка, честное распределение затрат |
| Отход раскроя | `job.scrapQuantity` от `scrapPercentage`, плюс `productionQuantity` типа `Scrap` со `scrapReason` | достаточно для статистики, но это «процент», а не «фактическая обрезь по карте» |

**Рекомендуемый обход:** Carbon — система записи (заказ, задание, себестоимость,
прослеживаемость), CAM — система раскроя. Точка стыковки — операция типа `Process` на
батчуемом процессе (`process.batchable = true`) плюс `jobOperationBatch` как «одна карта
раскроя». Количество и масса возвращаются в Carbon как `productionQuantity`. Остатки
листа — отдельная позиция номенклатуры с партионным учётом.

## 3.4. Спецификации и КМД

**Что ложится:**
- Многоуровневая спецификация (`jobMakeMethod` через `parentMaterialId`) — ровно структура
  «конструкция → отправочная марка → деталь».
- `Subassembly` vs `Kit` — «отправочная марка со своим заданием» против «комплект метизов,
  который просто выдаётся».
- Версионирование метода Draft/Active/Archived + извещение об изменении с настоящим diff —
  это полноценный ECO-процесс, ближе к «извещению об изменении КМД», чем что-либо в ERPNext.
- Ревизии детали с автоматическим замещением и режимом перехода
  (`Consume First` — «доработать остаток по старой марке») — прямо про доработку чертежей
  по замечаниям заказчика.
- Чертежи и PDF цепляются к детали и к заданию (`document`, `jobOperationStepSlide`,
  `inspectionDocument` с балунами `balloon` и допусками `inspectionFeature`).
- `JobTravelerPDF` (`packages/documents/src/pdf/JobTravelerPDF.tsx`) — маршрутный лист в цех.

**Что придётся обходить:**
- **Импорта DWG/DXF/IFC и разбора спецификации из чертежа нет.** Есть `modelUpload` +
  3D-просмотрщик (`packages/viewer`) + конвертер STEP на Rust (`crates/occt-bridge`) —
  это про машиностроительную 3D, не про КМД в AutoCAD/Tekla.
  Спецификацию придётся загружать CSV-импортом (`shared/imports.models.ts`,
  маршрут `x+/shared+/import.$tableId.tsx`) или через API.
- **Единицы измерения металла.** Carbon считает в `unitOfMeasure` с `conversionFactor`
  на строке. Связки «метр погонный ↔ килограмм по ГОСТ-массе» из коробки нет —
  коэффициент придётся вести вручную на каждой позиции или через `supplierPart.conversionFactor`.
- **Сертификаты на металл** — привязываются как документы к `trackedEntity`/партии;
  специального реестра сертификатов нет.

## 3.5. Что ляжет хорошо — сводка

1. **Позаказное производство с частичными отгрузками** — это ядро системы, а не надстройка.
2. **Честная фактическая себестоимость заказа**: материал по факту + время по ставкам
   рабочего центра + кооперация, всё в одном балансе НЗП, отклонение только одно и в конце.
3. **Кооперация как первоклассный объект** — релиз задания сам поднимает заказ поставщику
   на оцинковку/термичку, срок встаёт в расписание, стоимость падает в НЗП.
4. **Прослеживаемость до партии металла** — от серийника конструкции вниз до листа.
5. **Каталог металлопроката из коробки**, включая метрические ряды.
6. **Конечное расписание с учётом людей и квалификаций** — не «бесконечная мощность».
7. **ECO-процесс с настоящим diff** — редкость даже в дорогих ERP.
8. **Порталы без логина** — клиент жмёт «Принять КП», поставщик вбивает цену по ссылке.
9. **Русская локализация уже есть**: `packages/locale/locales/ru/erp.po` — 6487 строк
   `msgid`, из них **пустых всего 32**, т. е. переведено ~99,5 %. Плюс `ru/mes.po`.
   `lingui.config.js` перечисляет `ru` среди 13 поддерживаемых локалей.

## 3.6. Что придётся обходить или дорабатывать — сводка

| Пробел | Серьёзность | Комментарий |
|---|---|---|
| **Нет раскроя/нестинга** | высокая для МК | обход через внешний CAM + `jobOperationBatch`; см. 3.3 |
| **Нет учёта деловых остатков листа** | высокая | самодельно через `trackedEntity` |
| **Нет импорта DWG/DXF/спецификации из чертежа** | высокая | CSV-импорт / API |
| **MACRS-амортизация вместо российских амортизационных групп** | высокая для бухучёта | `taxDepreciationMethod`, `macrsPropertyClass`, `macrsConvention`, `bonusDepreciationPercent` — чисто налоговое право США. Придётся либо не использовать налоговую книгу, либо переписывать |
| **Нет НДС в российском смысле** | высокая | есть `salesTaxPayableAccount`, `purchaseTaxPayableAccount`, `taxPercent` на строке, `reverseChargeSalesTaxPayableAccount`, `taxExemptionReason` (американский набор: Resale/Government/Nonprofit…). Счёта-фактуры, книги покупок/продаж, УПД — **нет** |
| **Нет российских печатных форм** | высокая | PDF-шаблоны в `packages/documents/src/pdf/` — Quote, SalesOrder, PurchaseOrder, SalesInvoice, PackingSlip, JobTraveler, BatchList. ТОРГ-12, М-11, М-15, счёт-фактуры, УПД — писать заново |
| **Интеграции бухучёта — QuickBooks / Xero / Sage / Rillet** | средняя | 1С нет; придётся писать свою (`packages/ee/src/` — понятная точка расширения, `POSTING_POLICY`) |
| **Нет связи основное средство ↔ рабочий центр** | низкая | по дизайну; если нужна — своё поле |
| **Нет шага согласования в извещении об изменении** | средняя | «Согласований в V1 нет» (`items/AGENTS.md:89`); стадии = workflow. Для директорского визирования — свой `approvalRule` или обходной workflow |
| **Отгрузка не создаёт счёт, счёт не создаёт платёж** | низкая | сознательное решение; можно закрыть движком `packages/workflows` |
| **Задание нельзя отгрузить напрямую** | низкая | «MTO = MTS для учёта»; всегда через склад |
| **Себестоимость считается только при `accountingEnabled = true`** | **важно знать** | по умолчанию **выключено**. Количества двигаются всегда, деньги — нет |
| **Метрика по умолчанию — от страны/валюты компании** | информационно | RUB ⇒ `useMetric = true` автоматически |

## 3.7. Практический вывод по пригодности

**Carbon покрывает «завод металлоконструкций» на уровне производственного контура
существенно глубже, чем ERPNext:** позаказное задание со своей копией спецификации,
кооперация как объект первого класса, фактическая себестоимость в главной книге,
конечное расписание с людьми и квалификациями, прослеживаемость до партии металла,
готовый каталог металлопроката и настоящий ECO-процесс.

**Главные риски — не в производстве, а по краям:**
1. **Раскрой** — центральная операция завода МК — вне системы. Это не доработка, это
   выбор внешнего CAM и протокола стыковки.
2. **Российский бухгалтерский и налоговый контур** отсутствует целиком: НДС, счета-фактуры,
   первичка, амортизационные группы, обмен с 1С. Объём этой работы сопоставим с объёмом
   внедрения самого Carbon.
3. **Учёт КМД/DWG** — придётся строить мост из чертежа в спецификацию.

Наиболее вероятная рабочая конфигурация: **Carbon как производственно-складской контур
(заказ → задание → цех → отгрузка → фактическая себестоимость → прослеживаемость),
российский бухучёт остаётся в 1С**, стык — через `packages/ee/src/` по образцу
существующих коннекторов (QuickBooks/Xero/Sage/Rillet — уже реализованный паттерн
синхронизации с `POSTING_POLICY` и `accountingSyncOperation` / `accountingSyncTieOut`).
