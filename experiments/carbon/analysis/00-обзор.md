# Carbon ERP/MES — обзор для завода металлоконструкций

Головной документ по материалам десяти детальных разборов репозитория `crbnos/carbon`
(shallow-клон, HEAD `7daffaa`, сентябрь 2026). Все пути — от корня репозитория Carbon.
Здесь только сводка и навигация; доказательства и построчные ссылки — в частных документах,
на которые ведут ссылки в каждом разделе.

## 1. Что такое Carbon — честно, без рекламы

Carbon — это **дискретная производственная ERP с отдельным цеховым приложением (MES)**,
написанная на TypeScript поверх Supabase/PostgreSQL. Физически это два веб-приложения над
одной базой: `apps/erp` (офис: продажи, закупки, планирование, склад, учёт) и `apps/mes`
(цех: планшет оператора — старт/пауза операции, выдача материала, брак, сканирование).
Плюс необязательный Rust-сервис `apps/assembler` (STEP→GLB для 3D-просмотра). Масштаб
реальный, не прототип: **1005 файлов миграций**, по сгенерированным типам
`packages/database/src/types.ts` (85 494 строки) — **385 таблиц, 104 представления,
217 RPC-функций, 164 перечисления (enum)**. Опубликованный API даёт **1554 операции
в 15 модулях** (`apps/erp/app/routes/api+/mcp+/lib/tool-manifest.digest.json`), из них
READ 796 / WRITE 525 / DESTRUCTIVE 233. Продукт спроектирован под **позаказное
производство (make-to-order)**: заказ клиента → производственное задание со своей копией
спецификации → конечно-ёмкостное расписание → цех → фактическая себестоимость в главной
книге → отгрузка. Это ровно та модель, по которой живёт завод металлоконструкций.

Теперь честная вторая половина. Carbon — **интернационализированный, но не
локализованный** продукт: русский интерфейс переведён на 99,5 %, метрика и рубль есть,
но российской налоговой и учётной специфики нет **нигде и никакой** — ни НДС в российском
смысле, ни счёта-фактуры/УПД, ни банковских реквизитов контрагента, ни плана счетов РСБУ,
ни обмена с 1С, ни ЭДО. Печатные формы (PDF) **физически не печатают кириллицу** —
в шрифты вшито только латинское подмножество (`packages/documents/scripts/generate-fonts.mjs:19`
→ `const SUBSET = "latin"`). Для металла отсутствуют две отраслевые вещи: **раскрой/нестинг
и учёт деловых остатков** (проверено грепом по всем миграциям — нет ни одной сущности) и
**масса/погонаж как первый класс** (в `item` нет ни веса, ни плотности, ни габаритов).
И главное — **лицензия**: корневой `LICENSE:5,8` требует коммерческую лицензию на всё,
что лежит в `packages/ee` и на любой файл с `.ee` в имени, а внутреннее промышленное
использование без открытия своих доработок под AGPLv3 запрещено прямым текстом. При этом
**в `packages/ee/src/planning/` лежат и MRP, и планировщик расписания** — то есть ровно
те два движка, ради которых систему и берут. Это не техническая, а юридическая развилка,
и решать её надо до всякой оценки трудозатрат.

## 2. Карта системы: модули и как они связаны

### 2.1 Физическая карта

| Слой | Где | Роль | Зависит от |
|---|---|---|---|
| ERP (офис) | `apps/erp/` — 18 модулей кода | продажи, закупки, планирование, учёт, справочники; **хост всех фоновых задач** | БД, Redis, Inngest |
| MES (цех) | `apps/mes/` | терминал оператора под планшет, вход по 4-значному PIN | та же БД |
| БД + логика | `packages/database/supabase/` | 1005 миграций, RLS-политики, ~90 таблиц с событийными триггерами, PGMQ-очередь | — |
| Транзакционное ядро | `packages/database/supabase/functions/` (~40 Deno edge-функций) | проведение документов, MRP, копирование методов, импорт CSV | БД |
| Планирование | `packages/ee/src/planning/` | MRP (`mrp/mrp.ts`, 1149 строк) + конечное расписание (~14 тыс. строк) | **коммерческая лицензия** |
| Печать | `packages/documents/` | React-PDF шаблоны + ZPL для Zebra | — |
| Фоновые задачи | `packages/jobs/` — 55 функций Inngest | события, вебхуки, синхронизация, печать | Inngest обязателен в проде |
| Процессы | `packages/workflows/` | визуальный конструктор автоматизаций | EE/план Business |
| Интеграции | `packages/ee/src/` | Xero, QuickBooks, Rillet, Sage(заглушка), Jira, Linear, Slack, Onshape, Paperless Parts, Radan(выключен), Stripe, Email | **коммерческая лицензия** |
| Локализация | `packages/locale/` | Lingui v5.9.4, 13 языков, `.po` | — |

18 модулей ERP (`apps/erp/app/modules/`): account, accounting, agent, documents, inventory,
invoicing, items, people, production, purchasing, quality, resources, sales, settings,
shared, storage-rules, users, workflows.

### 2.2 Архитектурный принцип, определяющий стоимость любой доработки

**Тяжёлая логика вынесена из приложения в Postgres и Deno-функции.** Пример:
«провести отгрузку» — это не React-роут, а `packages/database/supabase/functions/post-shipment/index.ts`
(4467 строк). Роуты тонкие: валидация zod → вызов сервис-функции/edge-функции → redirect.
Права — тоже в БД (RLS), итоги — в представлениях (views), события — триггеры + очередь.

Практические следствия:
- **Писать напрямую в таблицы нельзя** — итоги, статусы и проводки не пересчитаются.
  Для `salesInvoice`/`purchaseInvoice` хранимые колонки totals/status выставляются при
  создании и **не обновляются**; правду знает только представление.
- Бизнес-правила правятся в Deno/SQL, а не в TS-фронте — нужна соответствующая компетенция.
- Транзакций через `supabase-js` нет вообще: каждый `.from()` — отдельный HTTP-запрос.
  Настоящая транзакция — только Kysely, а **Kysely не применяет RLS**.

### 2.3 Граф зависимостей предметной области

Посчитано по FK в `types.ts` (сколько внешних ключей указывают на таблицу):
`user` 663 (аудит), `company` 313 (арендатор), **`item` 74 — центр тяжести предметной
области**, `account` 72, `location` 50, `supplier` 33, `job` 31, `customer` 28.

```
company ──< location ──< storageUnit
   └──< item ──┬──< itemCost / itemReplenishment / itemPlanning / itemUnitSalePrice
               ├──< makeMethod ──< methodOperation ──< methodMaterial   (мастер-BOM + маршрут)
               ├──< supplierPart ──> supplier
               ├──< itemLedger                       (складские движения)
               └──< trackedEntity                    (партии/серии)

opportunity ──< quote ──< quoteLine ──< quoteLinePrice
       │ convert(quoteToSalesOrder)
       ▼
salesOrder ──< salesOrderLine ──> job ──< jobMakeMethod ──< jobOperation ──< jobMaterial
                    │                              └──< productionEvent / productionQuantity
                    └──> shipment ──< shipmentLine ──> salesInvoice ──> payment
purchaseOrder ──< purchaseOrderLine ──> receipt ──< receiptLine ──> trackedEntity
```

**Важная сильная сторона против ERPNext:** связь «продажа → производство» жёсткая и
прямая — `job.salesOrderId`, `job.salesOrderLineId`, `job.quoteId`, `job.quoteLineId`,
`job.customerId`, `job.itemId` лежат прямо в строке `job`. Никаких `Dynamic Link`:
путь от заказа клиента до операции на станке — непрерывный обход по FK.

Мультиарендность прошита в первичный ключ: составной PK `("id","companyId")` почти везде,
текущая компания — из cookie-сессии, **никогда из URL**.

Подробно: **03-модель-данных.md**, разделы 1–2; **02-платформа.md**, разделы 1–2.

## 3. Ключевые сущности и сквозные цепочки

### 3.1 Сущности, которые надо понять первыми

| Сущность | Что это | Ловушка |
|---|---|---|
| `item` | единая карточка: деталь, материал, инструмент, расходник, оснастка | Связь с `part`/`material`/`tool` — **позиционная по `readableId`**, не по FK |
| `makeMethod` / `method` | в терминах Carbon **«метод» = спецификация (BOM) + маршрут**. `docs/.../glossary.mdx:6` | Версии Draft/Active/Archived |
| `methodType` | самое нагруженное поле каталога (`types.ts:83710`): `Make to Order` / `Purchase to Order` / `Pull from Inventory` | Решает, что породит строка заказа: задание, закупку или отбор со склада |
| `job` | производственное задание с **собственной копией** метода | Правка метода задания не трогает библиотеку — это ровно «эта ферма делается не как типовая» |
| `jobOperation` | операция маршрута; типы `Process` / `Assembly` / `Inspection` / **`Outside Processing`** | Outside Processing = кооперация первым классом |
| `trackedEntity` / `trackedActivity` | партии/серии + граф генеалогии «что во что вошло» | Ровно модель «плавка → раскрой → деталь → узел → отгрузка» |
| `materialForm/Substance/Grade/Dimension/Finish` | **готовая таксономия металлопроката** | 20 форм (`Angle`, `Channel`, `W-Beam`, `Plate`, `Sheet`, `Square Tube`…), 17 веществ, метрические ряды есть |
| `costLedger` / `journalLine` | себестоимость через счёт НЗП (WIP) | **Работает только при `accountingEnabled = true`, а по умолчанию оно выключено** |
| `customField` / `customFields JSONB` | расширение без миграции, ~55 таблиц | Тип поля **нельзя изменить** после создания; CSV-импорт/экспорт кастомные поля **игнорирует** |

### 3.2 Цепочка 1 — КП → заказ → производство → отгрузка → счёт → деньги

```
opportunity (salesRfq → quote → salesOrder — все три слота необязательны)
   → salesOrderLine (methodType решает источник)
   → convertSalesOrderLinesToJobs  (делит по itemReplenishment.lotSize, + scrapQuantity)
   → job: get-method = quoteLineToJob (если было КП!) ИЛИ itemToJob
        Plan  → MRP, цех НЕ видит
        Ready → MRP + расписание + АВТО-создание заказов поставщику на кооперацию
   → MES: productionEvent (время) / issue-backflush (материал) / productionQuantity (брак)
   → complete_job_to_inventory: приход на склад по ФАКТИЧЕСКОЙ себестоимости
   → shipment (post) → salesInvoice (post) → payment → close job (отклонение в ГК)
```

Четыре узла цепочки **сознательно не автоматизированы**: отгрузка не создаёт счёт, счёт
не помечает себя оплаченным, задание не отгружается напрямую клиенту (всегда через склад),
КП не порождает задание. Закрывается движком Workflows или доработкой.

Самая ценная деталь для завода: **рецепт в задание копируется из строки КП**, если КП было
(`apps/erp/app/modules/production/production.service.ts:314–340`). Цех строит по той
спецификации, которую посчитали и согласовали в КП, а не по мастер-рецепту.

### 3.3 Цепочка 2 — потребность → закупка → приёмка → счёт поставщика

```
purchasingRfq → (веером) supplierQuote по share-ссылке без логина
   → purchaseOrder (статус ВЫЧИСЛЯЕТСЯ из строк; порог согласования → Needs Approval)
   → две независимые оси: receipt (склад всегда, ГК — если учёт включён)
                          purchaseInvoice (реверс GR-IR, отклонение цены)
   → строка закрыта только когда receivedComplete И invoicedComplete → payment
```

Особый случай — **кооперация (Outside Processing)**: операция помечена Outside, релиз
задания сам поднимает заказ поставщику (`purchaseOrderLine.jobOperationId`), срок встаёт
в расписание, приход **ничего не кладёт на полку**, а стоимость поставщика падает прямо
в НЗП задания. Для «оцинковку отдаём на сторону» — точное попадание.

Полные схемы, статусы, проводки: **01-бизнес-процессы.md**, Часть II; карта
«процесс → маршруты → таблицы» — приложение того же документа.

## 5. Сильные стороны применительно к заводу металлоконструкций

1. **Позаказное производство — ядро, а не надстройка.** Заказ на 12 ферм с тремя
   отгрузками = три строки с разными `promisedDate`, каждая → своё задание. Разбивка
   на партии автоматическая по `itemReplenishment.lotSize`, припуск на брак —
   по `scrapPercentage`.
2. **У задания своя копия спецификации.** «На эту ферму нужен другой крепёж» правится
   в задании и не трогает библиотеку. Многоуровневое дерево `jobMakeMethod.parentMaterialId`
   любой глубины = «конструкция → отправочная марка → деталь».
3. **Кооперация как объект первого класса.** Релиз задания сам создаёт заказ поставщику
   на оцинковку/термичку, срок встаёт в маршрут, стоимость падает в НЗП.
4. **Готовый каталог металлопроката из коробки** (`20250719100358_material-seed.sql`):
   уголок, швеллер, двутавры, лист/тонколист, круглая/квадратная/прямоугольная труба,
   полоса, рифлёный лист + 17 веществ + покрытия. Метрические ряды (0,5/0,8/1,0/1,2/1,5/
   2,0/2,5/3,0 мм) есть. ГОСТ-номенклатура заводится штатно: форма + вещество + марка +
   типоразмер, без правки схемы.
5. **Конечно-ёмкостное расписание с людьми и квалификациями.** `process.requiresAbility`
   → `employeeAbility`: планировщик **не поставит** сварку, если на смене нет сварщика
   с допуском (`packages/ee/src/planning/scheduling/operator-eligibility.ts`).
6. **Пакетирование операций разных заказов** (`jobOperationBatch`): одна наладка/одна
   загрузка печи на пять заказов, время и деньги делятся пропорционально `operationQuantity`
   — себестоимость каждого заказа остаётся честной. Конструктор батча умеет группировать
   кандидатов **по сигнатуре материала** (вещество/марка/типоразмер/форма).
7. **Фактическая себестоимость в главной книге**: материал по факту + время по ставкам
   рабочего центра + кооперация, одно отклонение в конце при закрытии задания.
8. **Прослеживаемость до партии металла** — граф генеалогии от серийника конструкции
   вниз до листа; номер плавки и сертификат кладутся в `batchProperty` /

## 6. Слабые места и риски

### 6.1 Лицензия — риск номер один, решается не программистами

`LICENSE:5,8`, дословно: всё под `packages/ee` и любой файл с `.ee` в имени **требуют
покупки коммерческой лицензии**; и — «any use of this software for internal production use
is strictly prohibited unless the modifications are made open-source in accordance with
the AGPLv3 license or a commercial license is obtained».

Коммерческая лицензия обязательна, если выполнен **любой** пункт (`licensing.mdx:55-60`):
приватный форк или приватные изменения; использование чего-либо из `packages/ee`;
хостинг Carbon для кого-то ещё; перепродажа/white-label.

Что попадает под гейт и почему это больно именно нам:
- **MRP и планировщик расписания** — `packages/ee/src/planning/`. Два движка, ради которых
  система и берётся.
- **Редактор конфигуратора и песочница исполнения его правил** —
  `ConfigurationEditor.ee.tsx`, `sandbox.ee.ts`. Для завода, где параметрика (вентзонты,
  отводы, фасонка) — ядро ценности, это существенно.
- **Все интеграции**, SSO, storage rules, часть уведомлений, серверные хуки бухгалтерии.

Отдельная тонкость: **рантайм-гейта по плану при self-host нет** —
`packages/ee/src/plan.server.ts:76`: `if (CarbonEdition !== Edition.Cloud) return true;`.
Единственный жёсткий edition-гейт — SAML SSO. То есть разделение Community/Enterprise при
self-hosting **преимущественно юридическое, а не техническое** — «работает» ≠ «можно».

Три варианта, честно:
- (а) купить коммерческую лицензию (подписка на пользователя в год или перпетуальная;
  цен в репозитории нет, только `mailto:chase@carbon.ms`);
- (б) Community + все доработки открыть под AGPLv3 и не трогать `packages/ee` — тогда нет
  конфигуратора, интеграций, SSO, storage rules, **и надо проверить, собирается ли система
  вообще без этого пакета**;
- (в) **держать всю российскую специфику снаружи**, отдельным сервисом через Carbon API /
  MCP / вебхуки — форка нет, копилефт не срабатывает. Наиболее реалистичный путь, но он не
  снимает вопрос по `packages/ee/src/planning/`, который импортируется самим приложением.

### 6.2 Зависимость от Supabase-стека

Supabase — не «просто Postgres»: PostgREST, GoTrue (Auth), Storage, Realtime, Kong,
edge-runtime (Deno). Плюс **Redis обязателен** и **Inngest обязателен в проде** — без
`INNGEST_SIGNING_KEY`/`INNGEST_EVENT_KEY` приложение не стартует и **не работает ни одна
фоновая задача**: MRP, планирование, уведомления, синхронизация (`environment-variables.mdx:68-70`).
Self-host описан честно (Docker Swarm + Caddy, ≥4 ГБ RAM на запуск, ~8 ГБ на сборку),
но:
- **профиля нагрузки нет** — как ведёт себя стек на реальном объёме завода, неизвестно;
- **наблюдаемость сознательно тонкая**: LogTape + JSON-строки, **нет Sentry, нет
  трассировки, нет отгрузки логов**;
- **встроенные «бэкапы компании» — это не disaster recovery**, а снимок одной компании
  без расписания и point-in-time; страница Backups на проде вообще видна только сотрудникам
  Carbon. Реальный бэкап — `scripts/backup.sh` (pg_dump + архив storage) своими руками;
- **тегирования версий и кнопки отката нет** — откат = передеплой старого коммита;
  миграции и код деплоятся параллельно без порядка.

Внешние SaaS (Resend, Stripe, PostHog, Turnstile, Google Places, OpenAI/Anthropic)
опциональны и отключаемы — для РФ это хорошо. Почту закрывает **свой SMTP** (mail.ru,
Яндекс заведутся как обычный SMTP).

### 6.3 Отсутствие российской специфики

Проверено по коду, а не по документации. **Нет:** 1С (ни коннектора, ни CommerceML),
ЭДО (Диадок/СБИС/Такском — ни слова, и ГОСТ-криптографии в JS-стеке нет вообще),
счёта-фактуры/УПД/ТОРГ-12/М-11/М-15/КС-2/КС-3, книг покупок и продаж, плана счетов РСБУ
(seed западный, типы счетов — закрытый enum из 21 западного значения), «в том числе НДС»
(колонка есть, **валидатор закомментирован** `items.models.ts:771`, формулы не читают),
разбивки итога по ставкам НДС, банковских реквизитов контрагента (р/с, БИК, корсчёт),

(есть только табель), Telegram как канала уведомлений (ровно три: in-app, email, Slack).

право США, а не амортизационные группы РФ.

### 6.4 Отраслевые пробелы под металл

| Пробел | Серьёзность | Комментарий |
|---|---|---|
| **Нет раскроя/нестинга и деловых остатков** | критично | Ни одной сущности во всех 1005 миграциях. Интеграция Radan **закомментирована** (`packages/ee/src/index.ts:7,32`) и умеет только синхронизировать процессы. Обход: внешний CAM + `jobOperationBatch` как «одна карта раскроя», остаток листа — отдельная позиция с партионным учётом |
| **Нет массы/плотности/габаритов у номенклатуры** | высокая | Проверено грепом по всем миграциям — ни одного поля. `materialDimension.name` — текстовый ярлык, не числа |
| **Нет конверсий единиц** | высокая | `unitOfMeasure` — плоский справочник без базовой единицы и коэффициента. «Тонна ↔ погонный метр по ГОСТ-массе» из коробки нет; `conversionFactor` есть только в закупочной цепочке, у `quoteLine`/`salesOrderLine` его **нет вовсе** |
| **Нормирование только «на штуку»** | средне-высокая | enum `factor` не знает «минут на метр шва», «часов на тонну», «м²/час» |
| **Планирование только «вперёд, как можно раньше»** | средняя | Обратного планирования от срока в размещении нет (покрыто тестом). Для монтажных графиков «не раньше чем» — ограничение |
| **Нет проектного учёта** | средняя | Нет сущности «объект/стройка/шифр заказа» выше `job`. Связка «много заданий одного объекта» держится на `salesOrderId`/`customerId` |
| **Нет импорта DWG/DXF/IFC и разбора спецификации из чертежа** | высокая | Есть STEP→GLB и 3D-просмотрщик — это машиностроительная 3D, не КМД в AutoCAD/Tekla. Спецификацию грузить CSV или через API |
| **Себестоимость единицы «плоская»** | средняя | В `costLedger` одна сумма; разложение на материал/труд/накладные восстанавливается только запросом по `journalLine`. План-vs-факт по материалам считает факт **по текущей цене**, а не по стоимости списания (`JobEstimatesVsActuals.tsx:295-296`) — на растущих ценах на прокат это систематически искажает «факт» |
| **Себестоимость собирается только при `accountingEnabled = true`** | знать обязательно | По умолчанию **выключено**: количества двигаются всегда, деньги — нет |

### 6.5 Технические грабли, которые аукнутся при доработках

- **`bypassRls: true`** — служебный клиент без RLS на горячих путях; проверку `companyId`
  надо делать руками. Самый вероятный источник утечки данных между компаниями при форке.
  Kysely и CSV-импорт RLS тоже не применяют.
- **NUMERIC декодируется в JS `number` (float64)** — точных десятичных типов в тракте нет.
  Шум гасится дисциплиной (`EPSILON = 1e-6`, `distributeRoundingResidual`, `assertBalanced`),
  а не типом данных. Любая своя доработка обязана пользоваться тем же API.
- **Формат поля ввода = точность хранения**: react-aria коммитит `parse(format(x))` —
  неверно выбранный форматтер **молча обрезает** введённое значение (прецедент: $0,00123 → $0,00).
- **46 колонок всё ещё зажаты `NUMERIC(x,y)`**, включая нормы времени операций
  (`setupTime`/`laborTime`/`machineTime`), и автопроверка их не видит.
- **Нумерация документов идёт по дате сервера** (`get_next_sequence` использует
  `current_date`, а не `company_today`) — для Хабаровска (UTC+10) префикс года/месяца
  «съезжает» на 10 часов. Патч маленький, но найти это в бою неприятно.
- **Вебхуки не подписываются** — ни секрета, ни заголовка подписи; документация предлагает
  считать секретом сам URL. Для промышленной интеграции нужен свой reverse-proxy.
- **Workflows не умеют писать статусы и не умеют удалять**, наблюдают только 10 типов
  записей, цикл — максимум 100 элементов, кнопки «перезапустить прогон» нет.
- **Экосистема мала.** Клон shallow, поэтому оценить частоту изменений затронутых файлов
  в апстриме невозможно — но правки под русскую вёрстку ложатся в 10 общих компонентов,
  которые апстрим активно развивает. Конфликты при обновлении форка — самостоятельный риск.
- **Документация местами разошлась с кодом** (примеры: `requirePermissions` указан
  на `auth.server.ts:195`, фактически `:211`; утверждение «ERP не стартует без Resend-ключа»
  уже неверно). Проверять по коду, а не по docs.

### 7.4 Рекомендуемая конфигурация (вывод трёх аудитов сходится)

**Carbon = производственно-складской контур** (КП → заказ → задание → цех → фактическая
себестоимость → прослеживаемость → отгрузка). **1С = регламентированный учёт.**
Стык — периодическая синхронизация номенклатуры, контрагентов, реализаций и поступлений
через Carbon API / Data API / вебхуки. Российская специфика (ЭДО, первичка, отчётность) —
**снаружи**, отдельным сервисом: это одновременно самый дешёвый технический путь и
единственный, который не втягивает проект в копилефт AGPL.

   инсталляции — и отдельно позицию по `packages/ee/src/planning/` (MRP + расписание)
   и по Email-интеграции в Community (`packages/ee/src/email/config.tsx` против
   `integrations/index.mdx:9-12` — прямое противоречие документации и лицензии).
2. **Проверить, собирается ли Carbon при `CARBON_EDITION=community` без `packages/ee`.**
   Если нет — вариант (б) из §6.1 отпадает, и развилка сводится к «купить или не брать».
3. Поднять self-host на тестовом VPS, включить `ru` + метрику + RUB, залить демо-данные
   (`Precision Manufacturing` — ближайший шаблон), починить шрифты PDF и посмотреть
   **реальные** экраны и печать глазами заказчика.
4. Прогнать один настоящий заказ завода от КП до отгрузки — и только после этого считать бюджет.
