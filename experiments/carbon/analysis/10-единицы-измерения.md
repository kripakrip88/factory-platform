# Carbon ERP/MES — единицы измерения (units of measure) и адаптация под метрику/Россию

Анализ репозитория `crbnos/carbon` (локальный клон). Все пути — от корня репозитория.

---

## 0. Краткий вывод (TL;DR)

1. **Настройка `useMetric` — это НЕ глобальный переключатель системы единиц.** Она влияет
   ровно на **три вещи**: (а) фильтр каталога типоразмеров материалов (material dimensions),
   (б) подпись единицы температуры в поверке средств измерений (gauge calibration),
   (в) вкладка по умолчанию в окне скачивания этикеток. Всё. Больше нигде она не читается.
2. **Найден баг (регрессия):** автоопределение метрики по стране компании сломано.
   Новая компания **всегда** получает `useMetric = false` (имперские единицы), даже
   если страна = RU и валюта = RUB. Это и есть причина «увидел дюймы».
   Подробности — раздел 2.
3. **Хорошая новость:** числа (разделители), даты, валюта — **полностью локале-зависимые**
   через `Intl`, править код не надо. Русский перевод интерфейса в репо **уже есть и
   практически полный** (6487 строк, 32 пустых).
4. **Основной PDF деловых документов — уже A4**, не Letter. Letter зашит только в
   этикетках канбан (Kanban labels).
5. **Главная реальная работа** — не переключатель, а **наполнение справочников**:
   единицы измерения (нет мм, м, м², м³, кг, т, пог.м) и каталог типоразмеров проката
   под ГОСТ (двутавра/тавра вообще нет ни в каком виде, ни в дюймах, ни в мм).

## 2. БАГ: новая компания всегда получает имперские единицы

Это, скорее всего, прямая причина жалобы «увидел дюймы».

Триггер на таблице `company` был переписан на «интерсепторную» схему:

```
packages/database/supabase/migrations/20260410031811_remaining-interceptors.sql:542
  DROP TRIGGER IF EXISTS create_company_related_records_after_insert ON "company";

packages/database/supabase/migrations/20260410031811_remaining-interceptors.sql:452-464
  CREATE OR REPLACE FUNCTION sync_insert_company_related_records(...)
  BEGIN
    IF p_operation != 'INSERT' THEN RETURN; END IF;
    INSERT INTO "terms" ("id") VALUES (p_new->>'id');
    INSERT INTO "companySettings" ("id")          -- <<< useMetric НЕ передаётся
    VALUES (p_new->>'id');
  END;

packages/database/supabase/migrations/20260410031811_remaining-interceptors.sql:619-623
  CREATE TRIGGER "trg_event_after_sync_company"
  AFTER INSERT OR UPDATE OR DELETE ON "company" FOR EACH ROW
  EXECUTE FUNCTION public.dispatch_event_after_interceptors('sync_insert_company_related_records');
```

Новая функция вставляет `companySettings` **без колонки `useMetric`** → срабатывает
`DEFAULT FALSE` из миграции `20250719100358_material-seed.sql:2`. Логика
«страна ≠ US и валюта ≠ USD → метрика» потеряна при рефакторинге.

Побочно потеряно и другое: старая версия функции
(`20260304112615_purchasing-info.sql:393-397`) создавала ещё записи
`companyAccountsPayableBillingAddress` и `companyAccountsReceivableBillingAddress` —
новая их не создаёт. Это отдельный дефект, к единицам отношения не имеет,
но стоит проверить на своём стенде.

**Трудоёмкость фикса:** ~1 час. Одна миграция, добавляющая `useMetric` в `INSERT`
внутри `sync_insert_company_related_records` (и, если нужно, восстанавливающая
адресные записи). Плюс разовый `UPDATE` существующих компаний.

### 3.1. Ловушка при переключении тумблера

Флаг `isMetric` хранится **на строке типоразмера** (`materialDimension.isMetric`,
DDL: `packages/database/supabase/migrations/20250719100358_material-seed.sql:304-314`),
а не вычисляется. Поэтому:

- Типоразмеры, **созданные пользователем** пока `useMetric = false`, получают
  `isMetric = false` и после включения метрики **исчезают из всех списков**.
  Никакой миграции/конвертации нет. Лечится `UPDATE`-ом вручную.
- Само поле `material.dimensions` — **TEXT** (`packages/database/supabase/migrations/20240608114413_materials.sql:146`),
  то есть хранится строка-название (`'0.010"'`, `'6mm'`). Числового значения с единицей
  в базе нет → **пересчёта величин не требуется и не существует**. Это упрощает жизнь:
  переключение — чисто вопрос справочника, а не конвертации данных.

### 5.1. Что создаётся новой компании

### 5.3. Чего НЕТ и что придётся завести для металла

Отсутствуют полностью: **мм, см, м² (кв.м), м³ (куб.м), кг, т (метрическая),
пог. м** (погонный метр — можно закрыть кодом `MT`/`М`), **лист**, **прут**, **комплект**.

Это заводится руками/CSV за час — **но есть важное ограничение**:

> **Коэффициентов пересчёта между единицами в системе НЕТ.**
> Конверсия существует только в одном узком месте — закупка: колонка
> `conversionFactor NUMERIC(10,2)` на строках закупки
> (`packages/database/supabase/migrations/20240402052512_purchasing-conversion-factors.sql:1-2,25`:
> `purchaseOrderLine`, `purchaseInvoiceLine`, `receiptLine`). У самой таблицы
> `unitOfMeasure` полей пересчёта нет.
>
> Следствие для металлоконструкций: **связка «тонна ↔ погонный метр ↔ штука»
> через погонный вес профиля системой не поддерживается**. Если закупаете в тоннах,
> а списываете в метрах, пересчёт придётся либо вбивать в `conversionFactor` на
> каждой строке закупки, либо дорабатывать.

**Оценка:**
- Завести список единиц (мм/м/м²/м³/кг/т/пог.м/лист/компл.) — **1-2 часа** (CSV-импорт
  или руками), кода не требуется.
- Подмена seed-списка, чтобы новые компании получали русский набор — правка
  `packages/database/supabase/functions/lib/seed.data.ts:118-137`, **1 час**.
- Погонный вес профиля / пересчёт т↔м — **доработка, 3-5 дней** (новая таблица
  коэффициентов + применение в BOM, закупке, списании). Отдельная задача, не «настройка».

в системе **нет ни одного типоразмера вообще** — формы объявлены
(`...material-seed.sql:27,32`), но справочник пуст. Рифлёного листа (`treadplate`) тоже нет.

   (`dimensions.new.tsx:49`). Значит, **сначала включить метрику, потом заводить**.
2. **CSV-импорт — поддерживается, и колонка `isMetric` в нём есть:**
   - маппинг полей: `apps/erp/app/modules/shared/imports.models.ts:1965-1969`
     (`label: "Metric"`, `type: "boolean"`)
   - схема: `apps/erp/app/modules/shared/imports.models.ts:2900-2903`
   - парсер значения: `packages/database/supabase/functions/import-csv/material-property-import.ts:23-26`
     — принимает `true / 1 / yes / y / metric`
   - вставка: `.../material-property-import.ts:354`

**Оценка:** залить ГОСТ-сортамент (двутавр Б/Ш/К, швеллер П/У, уголок равно- и
неравнополочный, труба профильная, лист, круг) через CSV — **1-2 дня** работы
с данными, кода не требуется.

- Таблица: `apps/erp/app/modules/quality/ui/Calibrations/GaugeCalibrationRecordsTable.tsx:84-88`

**Что работает:** при `useMetric = true` подпись становится `°C` автоматически, перевод
через `Intl` — по-русски будет корректно.

**Чего НЕТ:** конвертации значения. Число хранится «как есть», без единицы. Если в базе
уже лежат фаренгейты, после переключения они станут «градусами Цельсия» без пересчёта.
На чистом внедрении это не проблема.

**Оценка:** 0 (работает из коробки при включённой метрике). Если нужен пересчёт
исторических данных — разовый SQL, ~1 час.

## 9. Форматы чисел: разделитель дробной части и разрядов

**Это самая приятная часть: править код не нужно.** Всё построено на `Intl.NumberFormat`
с передачей локали, нигде нет ручных `.toFixed()` со склейкой строк и нигде не зашит
`en-US` в продуктовом коде (только в тестах и preview-сэмплах).

### 9.1. Как локаль доезжает до форматтеров

```
packages/utils/src/headers.ts:6-39   getPreferenceHeaders(request)
   ├─ читает cookie "locale"  (packages/locale/src/config.ts:28)
   ├─ иначе Accept-Language   (:12-14)
   └─ fallback "en-US"        (:26)
              ↓
apps/erp/app/root.tsx:291-298

```

(Аналогично в MES: `apps/mes/app/root.tsx:263-269`.)

### 9.2. Форматтеры

| Валюта | `apps/erp/app/hooks/useCurrencyFormatter.tsx:56,72` — `new Intl.NumberFormat(locale, …)` |

Для `ru` / `ru-RU` `Intl` даст `1 234,56` (запятая — дробная часть, узкий неразрывный
пробел — разряды). Именно то, что нужно.

### 9.3. Ввод чисел

Поля построены на react-aria (`packages/form/src/components/Number.tsx`,
`NumberControlled.tsx`), который **парсит по той же локали** — в русской локали
пользователь вводит `1,5` и получает `1.5`. Комментарий в
`packages/utils/src/format.ts:102-105` прямо подтверждает: react-aria коммитит
`parse(format(x))`.

### 9.4. Валюта RUB

Рубль уже в сид-справочнике валют: `packages/database/supabase/functions/lib/seed.data.ts:612`
— `{ code: "RUB", decimalPlaces: 2, createdBy: "system" }`.
Базовая валюта компании выбирается при онбординге (`company.baseCurrencyCode`) и
**не меняется потом по дизайну** (`docs/content/docs/reference/company-settings.mdx:66,98-99`) —
это важно: RUB нужно выбрать сразу.

### 9.5. Единственные шероховатости

1. `packages/utils/src/date.ts:9` — `DEFAULT_LOCALE = "en-US"` как фолбэк там, где
   локаль не передали. Стоит поменять на `"ru-RU"` при форке (5 минут) либо
   убедиться, что локаль передаётся всегда.
2. Названия стран в PDF всегда английские — `packages/documents/src/utils/shared.ts:10`
   (`Intl.DisplayNames(["en"], …)`). Правка на одну строку, **30 минут**.
3. **PDF берут локаль из HTTP-заголовков запрашивающего**, а не из настроек компании:
   `apps/erp/app/routes/file+/quote+/$id[.]pdf.tsx:47`, `.../sales-order+/$id[.]pdf.tsx:142`,
   `.../purchase-order+/$orderId[.]pdf.tsx:148`, `.../sales-invoice+/$id[.]pdf.tsx:177`
   и остальные — все через `getPreferenceHeaders(request)`. Для PDF, генерируемых
   фоновыми задачами (рассылка клиенту), локаль не передаётся явно
   (`packages/jobs/src/inngest/functions/tasks/print-job/renderers.tsx` — грep `locale`
   пуст) → скорее всего будет `en-US`. **Проверить на стенде**, править ~0.5 дня.
4. Переменная окружения `DEFAULT_LANGUAGE` (`packages/locale/src/config.ts:20-26`)
   позволяет задать язык по умолчанию `ru` без правки кода — **самый дешёвый рычаг**.

### 9.6. Русский перевод интерфейса — уже есть

- `packages/locale/locales/ru/erp.po` — 6487 строк, **32 непереведённых**

## 11. Чего в коде НЕТ (чтобы не искали)

- Нет настройки размера бумаги (`paperSize`/`pageSize` — только пагинация списков).
- Нет конвертации величин между системами единиц — ни длин, ни весов, ни температур.
- Нет колонок веса/объёма/габаритов у номенклатуры (искал по всем миграциям).
- Нет коэффициентов пересчёта у `unitOfMeasure` (только `conversionFactor` на строках
  закупки/приёмки).
- Нет двутавра, тавра, рифлёного листа, широкой полосы — ни одного типоразмера.
- Нет отдельной настройки локали/формата чисел на уровне компании — только per-user
  cookie + `Accept-Language` + env `DEFAULT_LANGUAGE`.
- Нет ГОСТ-обозначений в справочниках форм проката (только ANSI/DIN).
