Разбор по документации репозитория `crbnos/carbon` — папка `docs/content/docs/`
(building, integrations, platform, reference, glossary.mdx, index.mdx) плюс проверка

«снимок, а не контракт» (`docs/content/docs/building/architecture.mdx:20-24` — «file paths,

## 1. Что это за платформа

Carbon — производственная система из двух приложений над **одной** базой данных
(`docs/content/docs/index.mdx:6-8`):

| Приложение | Что это | Порт в dev |
|---|---|---|
| `apps/erp` | ERP «для офиса» (продажи, закупки, планирование, учёт). Главный сервис + хост всех фоновых задач | 3000 |
| `apps/mes` | MES «для цеха» (операции, отчёт по количеству, время, списание материала), интерфейс под планшет и перчатки | 3001 |
| `apps/academy` | Обучающее приложение | 4111 |
| `apps/starter` | Минимальный пример (auth + БД + формы) | 4000 |
| `apps/assembler` | Rust-сервис: STEP→GLB (3D в браузере) + расчёт порядка разборки. **Опционален**, без него всё работает | — |
| `docs` | Сайт документации (единственный Next.js в репо) | 3002 |

Источник таблицы — `docs/content/docs/building/architecture.mdx:648-658`.

Стек (`README.md:113-127`, `architecture.mdx:278-282`): React Router v7 (не Remix, не Next),
TypeScript, Tailwind v4, Radix UI, Supabase (Postgres 15 + PostgREST + Auth + Storage +
Realtime + Edge Functions), Redis, Inngest (фоновые задачи), Resend (почта), Lingui (i18n),
Stripe (биллинг, только Cloud), Rust (геометрия).

Масштаб базы (`architecture.mdx:468-469`): **923 файла миграций, 362 таблицы, 101 представление
(view), 238 функций БД, 154 enum-типа**. Это не «конструктор», это готовая ERP с жёсткой схемой.

Ключевая архитектурная особенность, которая определит всю адаптацию:
**значительная часть логики живёт внутри Postgres**, а не в коде приложения
(`architecture.mdx:35-39`): права (RLS), вычисляемые итоги (views), события («что-то
изменилось» — триггеры + очередь PGMQ). Пишем в таблицы, читаем из представлений
(`architecture.mdx:495-512`). Это значит: обойти бизнес-логику через прямой доступ к
таблицам можно, но данные поедут (см. предупреждение про Data API, раздел 4.3).

## 2. Модули (карта функциональности)

В ERP 18 модулей кода (`apps/erp/app/modules/`): account, accounting, agent, documents,
inventory, invoicing, items, people, production, purchasing, quality, resources, sales,
settings, shared, storage-rules, users, workflows.

Справочник продукта (`docs/content/docs/reference/meta.json`) — 70 страниц, сгруппированных так:

**Изделия и техпроцесс**
- `items` — мастер-запись всего: детали (part), материалы, инструмент, расходники, оснастка.
- `methods` — «метод» = спецификация (BOM) + решение make/buy/pull from stock. Внимание на
  терминологию: в Carbon `method` — это BOM (`docs/content/docs/glossary.mdx:6`).
- `routings` — маршрут: операции и рабочие центры.
- `materials` — таблицы свойств материала: вещество, форма, размер, покрытие, марка, тип.
  Это ровно то, что нужно металлоконструкциям (лист/труба/уголок/марка стали).
- `configurator` — **параметрическое семейство из одного артикула**: параметры (numeric/list/
  material/boolean/date) + правила на TypeScript, которые на лету пересобирают BOM, маршрут и цену
  (`docs/content/docs/reference/configurator.mdx:5-45`). Редактор правил — Monaco, исполнение —
  песочница без `fetch`/таймеров/динамического `import`. **Редактор и песочница — EE-файлы**
  (`apps/erp/app/components/Configurator/ConfigurationEditor/ConfigurationEditor.ee.tsx`,
  `packages/database/supabase/functions/lib/sandbox.ee.ts`) — см. раздел 9.
- `change-orders` (5 страниц) — извещения об изменении (ИИ/ECN): черновик против реального
  метода, ревью в виде diff, релиз с суперсессией и «переходом» (cutover) в MRP.

**Производство**
- `jobs`, `work-centers`, `scheduling` (конечная мощность), `batching` (объединение одинаковых
  операций разных заказов в одну наладку), `kanban`, `mes`, `maintenance` (ППР и аварийный ремонт).

**Планирование**
- `planning` (MRP — выполняется как edge-функция, крон каждые 3 часа, `architecture.mdx:592-595`),
  `reordering` (политика пополнения), `forecast` (понедельный прогноз спроса).

**Продажи**
- `quotes`, `pricing`, `sales-orders`, `rmas` (возвраты от клиента), `customer-portal`,
  `approvals` (согласование с порогом по сумме).

**Закупки**
- `purchase-orders`, `supplier-quotes`, `supplier-returns`, `suppliers-and-customers`.

**Логистика/склад**
- `shipments`, `picking`, `receipts`, `inventory`, `inventory-count`, `scrap`, `storage-rules`,
  `shelf-life`, `traceability` (серии/партии + генеалогия «что во что вошло»).

**Финансы**
- `invoices`, `payments`, `accounting` (журнал/проводки), `financial-reports` (баланс, ОПУ,
  оборотно-сальдовая), `period-close`, `dimensions` (аналитики на строках проводок),
  `intercompany` (взаимозачёт и элиминация между компаниями группы), `fixed-assets`.

**Качество (QMS)**
- `quality`, `issues` (несоответствия/8D), `inspections` (AQL-выборка, FAI с «шариками» на
  чертеже), `calibration` (поверка средств измерения), `quality-documents` (СТП/рабочие
  инструкции с версионированием), `risks` (реестр рисков).

**Система**
- `company-settings`, `printing`, `custom-fields`, `audit-log`, `sequences`, `import-export`,
  `documents`, `people`, `training`, `permissions`, `two-factor`, `single-sign-on`, `account`,
  `onboarding`, `sharing`, `agent`, `workflows`, `notifications`.

Сквозные сценарии описаны в `docs/content/guides/` (14 нарративов): order → plan → build →
floor → ship, quote-to-cash, rfq-to-po, receive-and-bill, job-costing, change-order,
основные средства.

**Чего в модулях нет вообще** (не нашёл ни в docs, ни в коде): нет модуля зарплаты/кадрового
учёта (people = только мастер-данные сотрудников, отделы, смены, праздники, табель времени),
нет CRM-воронки как отдельной сущности (есть RFQ→quote→order), нет управления проектами
(есть только интеграции-выгрузки в Jira/Linear), нет складской адресной топологии сверх
storage unit, нет транспортной логистики/маршрутизации.

## 3. Как реализуется «любой бизнес-процесс» — четыре уровня

Это, вероятно, самый практически важный вывод для оценки. Уровни идут от «настройка» к
«форк репозитория».

### 3.1 Настройкой, без кода
- **Custom fields** — до 9 типов (Boolean, Date, List, Numeric, Text, File + ссылочные User/
  Customer/Supplier), кладутся в JSON-колонку `customFields`, которая есть на каждой ключевой
  таблице; схема БД не меняется (`docs/content/docs/reference/custom-fields.mdx:20-30`).
  Ограничения, важные на практике: **тип поля нельзя изменить после создания**; **CSV-импорт и
  CSV-экспорт кастомные поля игнорируют** (`custom-fields.mdx:28-32`); список сущностей, куда
  можно добавить поле, — закрытый каталог в коде (`customFieldTable`), из UI новую сущность не
  добавить.
- **Sequences** — свои префиксы/счётчики/паддинг для номеров документов, с датными токенами
  (`PAY-%{yyyy}-%{mm}-`), `docs/content/docs/reference/sequences.mdx:8-28`. Номер документа
  штампуется при создании и потом не пересчитывается.
- **Approvals** — правила согласования с суммовыми порогами; только для 3 типов документов:
  заказ поставщику (с порогом), документ качества, поставщик
  (`docs/content/docs/reference/approvals.mdx:17-28`). Глобального «включить согласование»
  нет — правило есть, значит согласование есть.
- **Company settings** — ~30 флагов: `accountingEnabled` (учёт целиком выключается),
  `useMetric`, `requireMfa`, `plmReleaseControl`, `enforceInspectionFourEyes`, политика
  обновления закупочных цен и т.д. (`docs/content/docs/reference/company-settings.mdx:35-56`).
- **Storage rules** (EE, план Business) — предикатные проверки на складских проводках:
  блокировать с ошибкой или предупредить. Поля берутся из фиксированного реестра
  (`item.type`, `storageUnit.storageTypeId`, `transaction.quantity`, …), операторы
  `eq/neq/in/notIn/isSet/isNotSet/gt/lt` (`docs/content/docs/reference/storage-rules.mdx:20-30`).
  Правило **ничего не меняет и не вычисляет** — только сообщение и уровень.

### 3.2 Визуальным конструктором автоматизаций (Workflows, EE/Business)
`docs/content/docs/reference/workflows.mdx`. Canvas: один триггер → условия → действия.
Что надо знать заранее, потому что это жёсткие рамки:
- Триггер: либо **событие** (created / deleted / изменение конкретного поля), либо **расписание**
  (daily/weekly/monthly + таймзона). **Обобщённого «updated» нет** — поле выбирается явно, и
  наблюдать можно только **10 типов записей**: purchase order, sales order, job, item, receipt,
  shipment, quote, supplier, customer, issue (`workflows.mdx:23-25`).
- Плюс 9 «бизнес-моментов»: job released/hold, операция завершена, quote sent/accepted,
  receipt/shipment posted, sales/purchase invoice posted (`workflows.mdx:27`).
- Шаги: Trigger, Condition, Action, Compute, Find, Filter (`workflows.mdx:41-49`).
- Действия: создать 4 типа записей (job, issue, purchase order, sales order), обновить
  10 типов, «уведомить» и «вызвать внешний URL». **Статусы из workflow не пишутся,
  действия удаления нет вообще** (`workflows.mdx:52-54`).
- Исходящий HTTP: только `https`, приватные/link-local адреса и метаданные облака запрещены,
  редиректы не следуются, таймаут 10 с, подписи запроса **нет** (`workflows.mdx:73-75`).
- Цикл по списку — не галочка, а «подать список в поле одиночного значения», максимум
  **100 элементов** (`workflows.mdx:60`).
- Workflow исполняется **от имени владельца** с его правами, история прогонов неизменяема,
  ретеншн: 24 ч → закрытие зависших, 7 дней → сворачивание значений, 30 дней → удаление шагов,
  90 дней → удаление прогона (`workflows.mdx:122`).
- Кнопки «перезапустить прогон» нет (`workflows.mdx:118-120`).

Вывод по workflows: это хороший инструмент для уведомлений и простых цепочек, но **не замена
кастомной логики**: нельзя поменять статус, нельзя удалить, нельзя обратиться к большинству
сущностей, нет подписи вебхука.

### 3.3 Через API снаружи (см. раздел 4) — интеграционный слой без правки Carbon.

### 3.4 Правкой кода (форк)
Структура модуля жёстко регламентирована (`architecture.mdx:689-699`, `AGENTS.md:195-207`):

```
apps/erp/app/modules/{module}/
├── {module}.models.ts    zod-схемы и производные типы
├── {module}.service.ts   все операции с БД для модуля
├── {module}.server.ts    серверные хелперы (опционально)
├── types.ts, index.ts
└── ui/                   React-компоненты
```

Форма любой записи одинакова (`architecture.mdx:189-191`):
**assert метода → проверка прав → валидация zod → вызов сервис-функции → redirect**.
Одна zod-схема используется трижды: браузером, сервером и как тип аргумента сервис-функции
(`architecture.mdx:147-149`).

Практические грабли, которые документация называет прямо (`architecture.mdx:245-249`, `825-834`,
`842-851`):
- цепочка `supabase-js .insert()` — это НЕ транзакция, три вызова = три HTTP-запроса; откат
  пишется руками. Настоящая транзакция — только через Kysely, и Kysely **не применяет RLS**;
- типы БД генерируются (`pnpm run generate:types`, ~80 000 строк в `packages/database/src/types.ts`),
  руками не правятся;
- `Date` из JavaScript запрещён (сборочная проверка ловит), только `@internationalized/date`;
- типизировать весь репозиторий разом нельзя — не хватает памяти, только `--filter`.

Для форка есть неочевидный плюс: в `.claude/rules/` лежат **65 внутренних технических
документов** по подсистемам (workflow-engine, mrp-system, printing-system, traceability-model,
event-system, csv-import-system, pdf-generation-patterns, xero-webhooks и т.д.). Это
существенно снижает стоимость входа для команды разработки.

**И тут же главное юридическое ограничение:** любая приватная правка кода требует коммерческой
лицензии (раздел 9). Держать форк закрытым на AGPLv3 нельзя.

## 4. API и способы расширения

### 4.1 Carbon API — основной слой
`docs/app/api/page.tsx:57-110`. Это тот же сервисный слой, который вызывает само приложение:
валидация входа, пересчёт зависимых значений, проверка прав.

Фактические цифры из сгенерированного манифеста
`apps/erp/app/routes/api+/mcp+/lib/tool-manifest.digest.json`:
- **1554 операции, 15 модулей**;
- классификация риска: **READ 796 / WRITE 525 / DESTRUCTIVE 233** — клиент может фильтровать
  по риску;
- по модулям: production 251, sales 208, items 200, inventory 133, purchasing 133,
  accounting 130, resources 98, settings 95, quality 80, invoicing 65, shared 50, people 49,
  users 34, documents 15, account 13.

Транспорт — два, с одинаковыми аргументами и правами:
- HTTP: `POST /api/v1/{module}/{operation}` (роут-ловушка `apps/erp/app/routes/api+/v1+/$.ts`);
- MCP (Model Context Protocol) — `apps/erp/app/routes/api+/mcp+/`.

**OpenAPI-спека публичная**, отдаётся без ключа: `https://app.carbon.ms/api/v1/openapi.json`
(`apps/erp/app/routes/api+/v1+/openapi[.]json.ts`). Из неё генерируется типизированный клиент
на любом языке — hey-api (TS), openapi-python-client, oapi-codegen (Go), openapi-generator
(`docs/app/api/sdks/page.tsx:36-80`). Готовых официальных SDK нет — есть генератор.

### 4.2 MCP — AI-интеграция «из коробки»
`docs/app/api/mcp/page.tsx:137-175`. Сервер **не регистрирует все 1554 операции как инструменты**
(залил бы контекст модели), вместо этого три мета-инструмента: `search_tools` →
`describe_tool` → `call_tool`. Подключение: Claude.ai/Desktop/ChatGPT — по OAuth (наследуют
роль и компанию авторизовавшего), Claude Code/Cursor/VS Code/Codex — по API-ключу.
Для нашего случая (AI-ассистент как центр платформы) это прямое попадание: не надо писать
интеграционный слой к ERP, он уже есть.

### 4.3 Data API — «аварийный люк»
`docs/app/api/data/page.tsx:47-101`. Прямой REST (PostgREST) ко всем таблицам и представлениям,
на хосте `rest.carbon.ms` (self-hosted — Kong на `api.<домен>`, заголовок `carbon-key` вместо
`Authorization: Bearer`).

Два предупреждения, которые нельзя игнорировать:
- **вы вне сервисного слоя**: запись в таблицу не пересчитывает итоги, статусы и проводки;
- **читать всегда из представления**, не из таблицы: у `salesInvoice`/`purchaseInvoice`
  хранимые колонки totals/status выставляются при создании и **не обновляются** при изменении
  строк; актуальные значения считает представление `salesInvoices`/`purchaseInvoices`
  (`docs/app/api/data/page.tsx:70-80`).

### 4.4 API-ключи
`docs/content/docs/building/api-keys.mdx`. Формат `crbn_…`, хранится SHA-256 + 5 символов
превью, **показывается ровно один раз**. Ключ **не наследует права создателя** — у него
собственный набор скоупов `module_action`. Лимит **60 запросов/минуту на ключ**, поднять из
UI нельзя (`api-keys.mdx:40-42`). На Carbon Cloud API — фича тарифа Business, Starter получает
403 на любой вызов.

### 4.5 Webhooks
`docs/content/docs/building/webhooks.mdx`. Подписка на **одну таблицу** из закрытого списка:
`customer, quote, salesOrder, salesRfq, purchaseOrder, supplier, supplierQuote, salesInvoice,
purchaseInvoice, job, receipt, item, employee` — 13 таблиц. Операции insert/update/delete.
Payload: `{type, table, companyId, eventId, record, old}`.

Ограничения: доставка **at-least-once** (дедуплицировать по `eventId`), при длительной
недоступности приёмника события **теряются** после исчерпания ретраев, и —
**Carbon не подписывает payload**: ни секрета, ни заголовка подписи; документация предлагает
считать секретом сам URL (`webhooks.mdx:67-69`). Для промышленной интеграции это слабое место,
обойти можно только своим reverse-proxy с проверкой токена в пути.

### 4.6 Событийная шина внутри
`architecture.mdx:542-602`. Таблица начинает эмитить события только после `attach_event_trigger('таблица')`
в миграции — таких **около 90**; и даже тогда триггер ничего не кладёт в очередь, пока у компании
нет активной подписки. Дальше PGMQ (очередь в обычных таблицах Postgres) → pg_net (исходящий
HTTP после коммита) → Inngest → обратно в контейнер ERP (`/api/inngest`). **Inngest не исполняет
код у себя — он таймер и очередь, работа идёт внутри ERP** (`architecture.mdx:52-56`, `577`).
Всего 55 фоновых функций (`packages/jobs/src/inngest/index.ts`).

### 4.7 Edge-функции и RPC
~40 Deno-функций в `packages/database/supabase/functions/`: MRP, планирование производства,
проводка отгрузки/счёта в главную книгу, CSV-импорт, экспорт компании
(`architecture.mdx:436-450`). Плюс ~85 мест вызова Postgres-RPC. Оба механизма — валидные точки
расширения при форке.

### 4.8 Интеграционный SDK
`packages/ee/src/fns.ts` — `defineIntegration({id, name, category, logo, description, settings,
schema, oauth?, onInstall?, onHealthcheck?})`. То есть добавить свою интеграцию (например,
«Диадок» или «1С») — это описать конфиг, поля настроек (`text/number/password/secret/switch/
options/cards/array`, `packages/ee/src/types.ts:52-72`) и серверные хуки. Механизм готов,
но живёт **в `packages/ee`** → приватная реализация требует коммерческой лицензии.

### 4.9 Импорт/экспорт CSV
`docs/content/docs/reference/import-export.mdx`. Экспорт — с любой таблицы, но **только текущая
страница/выборка и только видимые колонки**, файл всегда `data.csv`, собирается в браузере.
Импорт — мастер из 4 шагов, только для: клиенты, поставщики, детали/материалы/инструмент/
расходники/оснастка, рабочие центры, процессы + три формата «методов» (BOM, операции,
деталь-с-методом). Импорт идемпотентен (матчинг по Unique ID, затем по Name), но
**обходит RLS** и **не пишет кастомные поля**. Основные средства импортировать нельзя
(есть модель, но нет в enum edge-функции — `import-export.mdx:40-42`).

## 5. Модель прав доступа

`docs/content/docs/reference/permissions.mdx`. Модель простая и предсказуемая — это плюс.

**Атом права: `<module>_<action>`** — `sales_view`, `purchasing_create`, `inventory_update`.
- Модули (enum в БД, `packages/database/supabase/migrations/20240909194622_jobs.sql:10` +
  Quality из `20250325103806_quality-module.sql`): Accounting, Documents, Invoicing, Inventory,
  Parts, People, Production, Purchasing, Quality, Resources, Sales, Settings, Users. Внутренние
  (Items, Messaging, Timecards) скрыты из UI прав.
- Действия ровно четыре: view / create / update / delete.
- **Ничего не подразумевается**: человек без грантов входит и не видит ничего.

**Два уровня контроля одновременно** (`permissions.mdx:31`):
1) приложение прячет экраны и кнопки — это косметика;
2) **база данных** через RLS не отдаёт чужие строки. Политики выглядят так
   (`architecture.mdx:367-372`):
   ```sql
   CREATE POLICY "SELECT" ON "public"."reportPin"
   FOR SELECT USING ("companyId" = ANY ((SELECT get_companies_with_employee_role())::text[]));
   ```

**Точка входа на сервере одна** — `requirePermissions(request, {...})`, ~1600 вызовов;
фактически определена в `packages/auth/src/services/auth.server.ts:211` (документация указывает
`:195` — уже разъехалось). Делает четыре вещи: идентифицирует вызывающего (cookie-сессия
**или** заголовок `carbon-key` для API), грузит права (Postgres-функция `get_claims`, кэш в
Redis на час — **права не в JWT**), отказывает, возвращает клиента БД уже под этого пользователя.

**Аварийный люк `bypassRls: true`** (`architecture.mdx:378-387`): RLS стоит времени на горячих
путях, поэтому для доверенных запросов сотрудников выдаётся service-role клиент **без RLS** —
и тогда проверку компании надо делать руками:
```ts
if (purchaseOrder.data?.companyId !== companyId) throw redirect(path.to.purchaseOrders);
```
Это место, где чаще всего появляется утечка между компаниями при доработках. Сюда же:
Kysely и CSV-импорт RLS не применяют.

**Шаблоны прав — employee types**: «Закупщик» = вся Закупка + Склад только просмотр.
Два системных типа неудаляемы: **Admin** и **Console Operator**. Важная ловушка: правка типа
меняет только шаблон для будущих назначений, существующим сотрудникам права не переписываются —
для этого есть массовый редактор с режимами **Add** (наложить) и **Update** (перезаписать)
(`permissions.mdx:37-61`).

**Три рода пользователей** в одной системе логина, различаются полем `role` на членстве в
компании: `employee`, `customer`, `supplier`; роуты могут требовать `{role: "employee"}`
(`architecture.mdx:389-392`).

**Цеховые PIN-аккаунты**: рабочий входит в MES по **4-значному PIN** на общем планшете, без
почты; создаётся под **Settings → Users → Operators** (видно только при `consoleEnabled`),
получает тип Console Operator; потом может быть «повышен» до полноценного пользователя с
сохранением истории (`permissions.mdx:81-91`). Для завода это прямо то, что нужно — не надо
заводить почту каждому сварщику.

**Безлогинные ссылки** (`share+/` роуты, `docs/content/docs/reference/sharing.mdx`): цифровое
КП клиенту (принять/отклонить), запрос цены поставщику, портал клиента, SCAR поставщику.
Единственный секрет — длинный неугадываемый токен в URL. Отзыва ссылки как отдельного действия
нет: страница «протухает» вместе с документом.

**Приглашения**: пароли не создаются администратором — приглашение по email, статусы
Invited → Active → Inactive (`permissions.mdx:71-79`).

**Вход**: `AUTH_PROVIDERS` = email (magic link), google, azure, passkey, sso. Плюс 2FA
(TOTP), которое можно сделать обязательным по компании (`requireMfa`), и в ITAR-сборках
оно принудительно включено. SAML SSO — **только Enterprise** и жёстко:
`packages/ee/src/sso/gate.ts:12` — `CarbonEdition === Edition.Enterprise && isAuthProviderEnabled("sso")`.

## 6. Мультикомпанийность

Это сильная сторона Carbon и она реализована на двух уровнях.

**Уровень 1 — внутри инсталляции** (`architecture.mdx:358-361`): почти каждая таблица имеет
колонку `companyId` и **составной первичный ключ `("id","companyId")`**. Текущая компания
читается из cookie-сессии, **никогда из URL**. Один логин может держать несколько компаний и
переключаться селектором; права хранятся с перечнем компаний, где они действуют, спец-значение
`"0"` = «все компании» (сквозной администратор) — `permissions.mdx:27-29`.

**Уровень 2 — отдельная инсталляция на клиента** (`architecture.mdx:750-757`): в таблице
`workspaces` по строке на клиента, и `ci/src/deploy.ts` на каждом деплое прогоняет
`sst deploy --stage prod` по строкам — у каждого свой AWS-аккаунт, регион, домен, свой проект
Supabase и свой Redis.

**Группа компаний и консолидация**:
- `company.parentCompanyId` — дочерняя компания; `company.companyGroupId` — группа для
  переключателя; `company.isEliminationEntity` — техническая компания под элиминирующие проводки
  (`docs/content/docs/reference/company-settings.mdx:22-23`).
- У группы общие план счетов, валюты и аналитики (`intercompany.mdx:79`).
- При вступлении компании в группу Carbon **автоматически создаёт встречные записи
  клиент/поставщик** между ней и каждой сестринской компанией (`intercompany.mdx:82`).
- Внутригрупповые счета попадают на контрольные счета **Inter-Company Receivables/Payables**;
  сопоставление (matching) — ручной прогон, строгое правило «A→B и B→A на **ровно ту же сумму**»;
  элиминация — второй ручной прогон, пишет реальные сторнирующие проводки на элиминирующую
  компанию, **отката в один клик нет** (`intercompany.mdx:45-69`).
- Базовая валюта у каждой компании своя и **не меняется** — это деноминация всей истории
  (`company-settings.mdx:64-66`).

Практический вывод для завода: если у заказчика юрлицо + ИП + торговый дом — модель это
покрывает, но консолидация полуручная (два прогона кнопками) и рассчитана на западную схему
учёта, а не на РСБУ.

## 9. Enterprise: `packages/ee` и лицензия

Это раздел, который определяет бюджет проекта не меньше, чем разработка.

### Что лежит в `packages/ee`
Интеграции (Xero, QuickBooks, Rillet, Sage, Jira, Linear, Onshape, Paperless Parts, Slack,
Stripe Connect, Email, Radan), SAML SSO (`src/sso/`), storage rules (`src/storage-rules/`),
план-гейтинг (`src/plan.ts`, `src/plan.server.ts`), часть уведомлений (`src/notifications/`),
серверные хуки accounting (`src/accounting/`), planning (`src/planning/`).

Плюс шесть `.ee.`-файлов вне пакета (полный список, `find . -name "*.ee.*"`):
```
apps/erp/app/components/Configurator/ConfigurationEditor/ConfigurationEditor.ee.tsx
apps/erp/app/components/Configurator/ConfigurationEditor/ParameterPanel.ee.tsx
apps/erp/app/components/Configurator/ConfiguratorForm/ConfiguratorForm.ee.tsx
apps/erp/app/modules/accounting/accounting.ee.server.ts
apps/erp/app/modules/accounting/accounting.ee.service.ts
packages/database/supabase/functions/lib/sandbox.ee.ts
```
То есть **UI конфигуратора и песочница исполнения его правил — коммерческие**. Для завода
металлоконструкций, где параметрика (вентзонты, отводы, фасонка) — ядро ценности, это
существенно.

### Какие фичи гейтятся планом
`packages/ee/src/plan.ts:8-22` — `FEATURE_PLANS`, все требуют Business (или Partner):
`API_KEYS, WEBHOOKS, INTEGRATIONS, ITEM_RULES, AUDIT_LOG, EMAIL_NOTIFICATIONS, STORAGE_RULES,
CUSTOMER_PORTALS, AI_AGENT, WORKFLOWS, FORECAST, TWO_FACTOR`.
Исключение: `INTEGRATION_WHITELIST = {"email"}` (`plan.ts:29`).

**Тонкость, которую надо знать:** проверка плана **работает только в Cloud-издании** —
`packages/ee/src/plan.server.ts:76`: `if (CarbonEdition !== Edition.Cloud) return true;`.
То есть при self-hosted рантайм-гейта по плану нет; единственный жёсткий edition-гейт,
который я нашёл, — SAML SSO (`packages/ee/src/sso/gate.ts:12`). Практический смысл:
**разделение Community/Enterprise при self-host — преимущественно юридическое, а не техническое.**

### Издания
`docs/content/docs/platform/licensing.mdx:10-16`:

| Издание | Что | Лицензия |
|---|---|---|
| Community | Открытое ядро ERP+MES, self-hosted | AGPLv3 |
| Enterprise | Self-hosted + коммерческая лицензия: включает EE-функции и снимает копилефт | Коммерческая |
| Cloud | app.carbon.ms, планы Starter и Business | Коммерческая |

Переключатель — переменная `CARBON_EDITION`: `community | cloud | enterprise | test`
(`docs/content/docs/platform/self-hosting/environment-variables.mdx:16`); self-hosting по
умолчанию `community`.

### Когда коммерческая лицензия ОБЯЗАТЕЛЬНА
`licensing.mdx:55-60` — достаточно любого одного пункта:
- вы держите **приватный форк или делаете приватные изменения**;
- вы используете **что-либо из `packages/ee` или любой `.ee`-файл**;
- вы хостите Carbon для кого-то ещё (включая интегратора, который ведёт клиентов);
- вы перепродаёте / white-label / встраиваете в свой продукт.

И отдельно из самого `LICENSE:8`, дословная формулировка жёстче стандартного AGPL:
«any use of this software for internal production use is strictly prohibited unless the
modifications are made open-source in accordance with the AGPLv3 license or a commercial
license is obtained».
Трактовка в документации (`licensing.mdx:77-79`): эксплуатировать Carbon в проде можно, но
**без коммерческой лицензии ваши доработки придётся публиковать под AGPLv3**.

Формы коммерческой лицензии: подписка (на пользователя в год) или **перпетуальная**
(разовая, премиальная, есть путь rent-to-own), срок 1/3/5 лет. Пользователи клиентского
портала **не считаются** (`licensing.mdx:95-97`).

**Что это значит для нашего кейса.** Русификация справочников, свои печатные формы (УПД,
ТОРГ-12), коннектор к 1С внутри `packages/ee`-механизма, кастомные поля — часть из этого
приватная правка кода ⇒ коммерческая лицензия. Альтернативы две: (а) купить лицензию;
(б) публиковать все доработки под AGPLv3 и не трогать `packages/ee`/`.ee` — тогда не будет
конфигуратора-редактора, интеграций, SSO, storage rules, и надо будет проверить, как система
собирается без них. Третий вариант — держать всю российскую специфику **снаружи**, отдельным
сервисом, общающимся по Carbon API/MCP/webhooks: тогда форка нет, копилефт не срабатывает.
Этот третий путь, на мой взгляд, самый реалистичный.

## 10. Развёртывание и эксплуатация

**Self-host рецепт 1 — один VPS** (`docs/content/docs/platform/self-hosting/docker-caddy.mdx`):
одноузловой Docker Swarm + Caddy (авто-HTTPS), наружу только 80/443, секреты — настоящие
Swarm-секреты. Сервисы: caddy, erp, mes, postgres, gotrue, postgrest, realtime, storage, meta,
kong, studio, edge-runtime, redis, inngest. Требования: Ubuntu 22.04+, **≥4 ГБ RAM** на запуск,
**~8 ГБ** если собирать образы на том же хосте. Скрипты: `deploy.sh init/up/status/logs/migrate`,
`scripts/harden.sh` (firewall+fail2ban+swap), `scripts/backup.sh` (дамп + архив файлов).
Первый запуск накатывает сотни миграций, приложения при этом несколько раз перезапускаются.

**Self-host рецепт 2 — свой AWS** (`aws-sst.mdx`): ECS Fargate + ECR + WAF, описано в
`sst.config.ts`, health-check `/health`, автоскейл 1–10 копий.

**Переменные окружения** (`environment-variables.mdx`): реестр в `packages/env`. Обязательный
минимум — четыре Supabase-переменные + `SESSION_SECRET` + `REDIS_URL`. В проде обязательны
`INNGEST_SIGNING_KEY` и `INNGEST_EVENT_KEY` — без них приложение не стартует и **не работает
ни одна фоновая задача**: MRP, планирование, уведомления, синхронизация интеграций
(`environment-variables.mdx:68-70`).
Опциональны: Resend, Stripe, OpenAI/Anthropic (AI-функции), PostHog, все OAuth-клиенты
интеграций, `GOOGLE_PLACES_API_KEY` (автодополнение адреса), Cloudflare Turnstile.
Особый флаг `CONTROLLED_ENVIRONMENT` (режим ITAR): отключает Slack и аналитику, включает
принудительный 2FA.

**Бэкапы** (`docs/content/docs/platform/backups.mdx`): встроенные «бэкапы компании» —
**это не disaster recovery**, а снимок одной компании (данные ± файлы) для клонирования и
отката неудачного изменения: без расписания, без point-in-time. Секреты и вебхуки в снимок
**не попадают** намеренно — после восстановления интеграции придётся переподключать. Плюс на
проде страница Backups **видна только сотрудникам Carbon** (`backups.mdx:83-85`). Реальный
бэкап при self-host — `scripts/backup.sh` (pg_dump + архив storage) с вывозом за пределы VPS.

**Демо-данные** (`demo-data.mdx`): 4 отраслевых шаблона (Aerospace & Satellite, Robotics OEM,
Precision Manufacturing, Motor Assembly) со сквозной историей и относительными датами. Для
демонстрации заказчику — идеально; шаблона «металлоконструкции» нет, ближайший — Precision
Manufacturing. Страница тоже ограничена сотрудниками Carbon на проде.

**Наблюдаемость** — сознательно тонкая (`architecture.mdx:804-812`): LogTape, JSON-строки,
request-id сквозным. **Нет своей отгрузки логов, нет Sentry, нет распределённой трассировки.**
Логи = то, что соберёт платформа (CloudWatch / `docker service logs`).

**CI/деплой** (`architecture.mdx:779-802`): 4 независимых GitHub Actions. Два следствия,
названных прямо: `check.yml` не собирает приложения, поэтому зелёный PR может сломать сборку
образа; миграции и код деплоятся **параллельно без порядка** — писать миграции надо
совместимыми с предыдущей версией кода. **Тегирования версий и кнопки отката нет** — откат
это передеплой старого коммита.

## 11. Внутренний ассистент и AI

`docs/content/docs/reference/agent.mdx`: встроенный чат в ERP (кнопка Question / ⌘L) в текущей
версии **только read-only и только по документации** — он не читает ваши данные и ничего не
меняет; на вопрос «сколько у меня открытых заказов» ответит, что не умеет, и откроет страницу.
Тариф Business, помечен Beta, лимит 30 сообщений за 5 минут.

То есть «AI внутри Carbon» пока маркетингово слабее, чем наш текущий замысел с Email
Analyzer/Quotation Assistant. Зато **MCP-сервер с 1554 операциями** (раздел 4.2) — это готовая
точка, к которой наш собственный AI-слой подключается без написания интеграции.

## 12. Где документация расходится с кодом (проверять при принятии решений)

1. `requirePermissions` — документация говорит `packages/auth/src/services/auth.server.ts:195`,
   фактически `:211`. Документация сама предупреждает о дрейфе строк.
2. `docker-caddy.mdx:71` утверждает «ERP **fails to boot** with an empty Resend key». В коде
   это уже не так: `packages/lib/src/resend.server.ts:14-45` — ключ читается лениво, при его
   отсутствии отправка письма просто пропускается с debug-логом. Для self-host в РФ это хорошая
   новость (Resend недоступен).
3. Email-интеграция описана как доступная «на каждом издании и плане»
   (`integrations/index.mdx:9-12`), но её код лежит в `packages/ee/src/email/config.tsx`, а
   `LICENSE:5` требует коммерческую лицензию на всё под `packages/ee`. Противоречие надо
   прояснить у вендора письменно, если планируется Community + свой SMTP.
4. Sage Intacct и Radan присутствуют в коде, но выключены (`active: false` / закомментирован) —
   в каталоге интеграций их не будет.

## 13. Оценка объёма адаптации под Россию

Разделяю на то, что делается **снаружи** (без форка, без лицензии) и **внутри** (форк ⇒
коммерческая лицензия или публикация под AGPL).

**Снаружи, через Carbon API / MCP / webhooks — приоритетный путь**
- Коннектор к 1С (выгрузка реализаций/поступлений/контрагентов/номенклатуры): свой сервис,
  чтение через Data API (из представлений!), запись через Carbon API. Ориентир — недели, не дни:
  1554 операции надо разобрать, а маппинг номенклатуры и единиц — отдельная задача.
- ЭДО (Диадок/СБИС): свой мост, триггер — webhook на `salesInvoice`. Мешает отсутствие подписи
  вебхуков — нужен свой прокси с проверкой токена.
- Telegram-уведомления: workflow-шаг «Call an outside URL» → свой бот. Самое дешёвое из всего
  списка.
- Маркировка/ГИС МТ: строится на `traceability` + печати этикеток, но обмен с ГИС МТ — отдельный
  сервис.

**Внутри (форк)**
- Российские печатные формы (УПД, ТОРГ-12, счёт-фактура, М-11): новые React-PDF компоненты в
  `packages/documents/src/pdf/`. Конструктор шаблонов в системе есть (блоки Header/Parties/
  LineItems/Summary/Terms + `extensionRegistry.tsx`), но табличные формы российского образца в
  блоки не укладываются — это код.
- НДС по-российски (книги покупок/продаж, авансы, ставки 20/10/0): в модели учёта Carbon этого
  слоя нет, это не «настроить», это проектировать.
- РСБУ-план счетов и отчётность: практичнее оставить бухгалтерию в 1С, а Carbon держать как
  контур производства/склада/продаж с выгрузкой. Тогда `accountingEnabled` можно вообще
  **выключить** — документация прямо описывает такой режим: физика движется, проводки не
  пишутся (`docs/content/docs/reference/accounting.mdx:8-14`).
- Перевод доменных справочников (материалы, единицы, статусы, сидируемый план счетов) — данные,
  не код, но объём есть.

**Что переводить НЕ надо** — интерфейс уже русский на ~99,5% (6486 строк ERP, 509 MES).

**Главный лицензионный вопрос, который надо решить до начала работ:** если что-то из «внутри»
неизбежно — нужна коммерческая лицензия Carbon (подписка или перпетуальная). Если удаётся
удержать всю российскую специфику «снаружи» — работает AGPLv3-Community, но тогда нет
конфигуратора-редактора правил, интеграций, SSO и storage rules.

## 14. Что стоит проверить отдельно (открытые вопросы)

1. Собирается и работает ли Carbon при `CARBON_EDITION=community` без `packages/ee` — или пакет
   всё равно импортируется приложением (проверка: реальная сборка с исключённым пакетом).
2. Цена коммерческой лицензии: подписка на пользователя в год vs перпетуальная — в репозитории
   цен нет, только `mailto:chase@carbon.ms`.
3. Позиция вендора по Email-интеграции в Community (п.12.3).
4. Производительность Supabase-стека на одном VPS при реальном объёме завода: документация даёт
   только «≥4 ГБ RAM», без профиля нагрузки.
5. Как ведёт себя `bypassRls: true` при наших доработках — это самый вероятный источник утечки
   данных между компаниями.
