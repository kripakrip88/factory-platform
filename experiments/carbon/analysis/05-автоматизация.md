# Carbon: автоматизация процессов и интеграции

Анализ репозитория `crbnos/carbon` (коммит `7daffaa`). Все ссылки — `путь:строка` от корня репо.
Источники: `.claude/rules/*.md` (внутренние правила разработки Carbon) + проверка по реальному коду.

---

## 0. Короткий ответ на вопрос «как автоматизировать X»

В Carbon **пять** разных механизмов автоматизации, и выбор между ними — это и есть
первое решение при любой задаче:

| Слой | Кто настраивает | Где живёт | Задержка | Для чего |
|---|---|---|---|---|
| **1. Workflows** (визуальный конструктор процессов, *workflow builder*) | пользователь мышкой | `apps/erp/app/routes/x+/workflow+/$id.tsx`, `packages/workflows/` | ~3–5 с | «когда случилось А — сделай Б»: уведомить, создать заказ/задание, дёрнуть внешний URL |
| **2. Event system** (система событий) | разработчик (SQL-миграция + код) | `packages/database/supabase/migrations/`, `packages/jobs/src/inngest/functions/events/` | ~3–5 с | всё асинхронное: индекс поиска, аудит, эмбеддинги, бух-синхронизация, вебхуки |
| **3. Webhooks** (исходящие вебхуки) | пользователь в Настройках | таблица `webhook`, `packages/jobs/src/inngest/functions/events/webhook.ts` | ~3–5 с | «шлите JSON на мой URL при любом изменении таблицы» |
| **4. HTTP API / MCP** (внешний вызов) | внешняя система или AI-агент | `apps/erp/app/routes/api+/v1+/`, `apps/erp/app/routes/api+/mcp+/` | синхронно | ~1200 функций ERP как REST- и MCP-инструментов |
| **5. Edge functions** (привилегированные функции Deno) | разработчик | `packages/database/supabase/functions/` | синхронно | тяжёлые транзакционные операции: проведение документов, MRP, импорт CSV |

Плюс **CSV-импорт** (разовая/пакетная заливка справочников) и **интеграции** (Xero, QBO,
Rillet, Jira, Linear, Slack, Onshape, Paperless Parts, Radan).

## 1. Движок процессов (Workflows engine)

### 1.1 Что это с точки зрения пользователя

Раздел **Automate → Workflows**. Холст (canvas), карточки-шаги, соединяются «ручками»
(handles), кнопка **Publish**. Документация для пользователя: `docs/content/docs/reference/workflows.mdx`.

Маршруты:
- список: `apps/erp/app/routes/x+/workflows+/_index.tsx`
- конструктор: `apps/erp/app/routes/x+/workflow+/$id.tsx` (+ `$id.canvas.tsx`, `$id.save.tsx`,
  `$id.publish.tsx`, `$id.unpublish.tsx`, `$id.test-run.tsx`, `$id.version.new.tsx`)
- история запусков: `apps/erp/app/routes/x+/workflows+/runs.tsx`, `runs.$runId.tsx`
- UI-компоненты: `apps/erp/app/modules/workflows/ui/Builder/`, `.../ui/Runs/`

**Гейт по тарифу:** `WORKFLOWS: [Plan.Business, Plan.Partner]` — `packages/ee/src/plan.ts:18`.
**Важно для самохостинга:** `packages/ee/src/plan.server.ts:76` — `if (CarbonEdition !== Edition.Cloud) return true;`.
То есть на Community/Enterprise-редакции (self-hosted) **все платные фичи открыты**:
Workflows, API-ключи, вебхуки, интеграции, аудит-лог, AI-агент, 2FA.

### 1.2 Схема БД

Миграция `packages/database/supabase/migrations/20260810100100_workflows-foundation.sql`:

| Таблица | Строка | Назначение |
|---|---|---|
| `workflow` | :32 | сам процесс: `name`, `ownerId`, `active`, `activeVersionId`, `nextRunAt`, `canvasState` |
| `workflowVersion` | :55 | версия холста: `nodes JSONB`, `edges JSONB`, `versionNumber`, `formatVersion` |
| `workflowTriggerEvent` | :85 | производный индекс подписок: одна строка на `eventId` + `origin` |
| `workflowRun` | :109 | один запуск: `status`, `sourceEventId`, `rootRunId`/`causedByRunId`/`depth`/`path`, `isTest` |
| `workflowStepRun` | :149 | один шаг запуска: `nodeId`, `itemKey`, `input`/`output`/`detail` JSONB, `branchTaken` |

Права: та же миграция заводит ключи `workflows_view/create/update/delete` в `userPermission`.

и `workflowStepRun_idempotency_key (runId, companyId, nodeId, itemKey)` — на них держится
идемпотентность (повтор доставки ничего не продублирует).

### 1.3 Какие бывают события (триггеры)

Каталог событий **генерируется** из четырёх рукописных файлов и коммитится:

```
packages/workflows/src/catalog/entities.ts    ← справочник сущностей: watch / write / display
packages/workflows/src/catalog/moments.ts     ← бизнес-моменты
packages/workflows/src/catalog/actions.ts     ← действия без универсальной формы
packages/workflows/src/catalog/operations.ts  ← read-only вычисления
        │  pnpm run generate:workflow-catalog  (scripts/generate-workflow-catalog.ts)
        ▼
packages/workflows/src/catalog/events.generated.ts   (106 событий)
packages/workflows/src/catalog/actions.generated.ts  (16 действий + 15 операций)
packages/workflows/src/catalog/labels.generated.ts   (переводимые подписи)
```

Руками `*.generated.ts` править нельзя — `pnpm run check:workflow-catalog` (CI-джоб `catalog`)
сравнивает данные, а не текст, и падает.

**Три вида триггеров** (`packages/workflows/src/run-trigger.ts` — union `record | moment | schedule`):

**(а) Изменения записей (record events).** 10 отслеживаемых сущностей × 77 наблюдаемых колонок
→ 97 событий. Формула: `<entity>.created`, `<entity>.deleted`, `<entity>.<column>.changed`.
**Генерического `updated` нет намеренно** — пользователь выбирает конкретное поле.

Сущности и их `watch`-колонки (`packages/workflows/src/catalog/entities.ts`):

| Сущность | Таблица | Строка | Наблюдаемые поля (watch) |
|---|---|---|---|
| purchaseOrder | `purchaseOrder` | :29 | status, supplierId, assignee, orderDate, purchaseOrderType, supplierReference, supplierLocationId, tags |
| salesOrder | `salesOrder` | :65 | status, customerId, assignee, salesPersonId, orderDate, locationId, customerReference, completedDate |
| job (произв. задание) | `job` | :101 | status, assignee, dueDate, startDate, quantity, priority, deadlineType, scrapQuantity |
| item (номенклатура) | `item` | :135 | — |
| receipt (приход) | `receipt` | :167 | — |
| shipment (отгрузка) | `shipment` | :194 | — |
| quote (КП) | `quote` | :224 | — |
| supplier | `supplier` | :265 | supplierStatus (имя колонки именно такое) |

Ещё 7 сущностей — **только для чтения** (без своих триггеров, но на них можно ссылаться
через внешние ключи): `user` :370, `group` :377, `jobOperation` :383, `nonConformanceType` :389,
`salesInvoice` :395, `purchaseInvoice` :401, `location` :407.

`.changed`-событие отдаёт три значения: `record`, `before`, `after` (все — один и тот же id,
но `before`/`after` несут собственный снимок строки: `packages/jobs/src/workflows/engine/loader.ts`,
`triggerOutputs`). `created`/`deleted` отдают только `record`.

**(б) Бизнес-моменты (business moments) — 9 штук.** То, что изменением строки не выразить.
Объявлены в `packages/workflows/src/catalog/moments.ts:6-62`:

| Момент | Выходы | Где поднимается (`raiseMoment`) |
|---|---|---|
| `production.jobReleased` | job, releasedBy | `apps/erp/app/modules/production/production.service.ts:2708` |
| `production.jobHeld` | job, heldBy | `apps/erp/app/modules/production/production.service.ts:2722` |
| `production.jobOperationCompleted` | job, jobOperation, completedBy | `apps/mes/app/services/operations.service.ts:273` и `production.service.ts:9848` |
| `sales.quoteSent` | quote, sentBy | `apps/erp/app/modules/sales/sales.service.ts:2069` |
| `sales.quoteAccepted` | quote, salesOrder | `apps/erp/app/modules/sales/sales.service.ts:240` |
| `inventory.receiptPosted` | receipt, postedBy | `apps/erp/app/routes/x+/receipt+/$receiptId.post.tsx:314` |
| `inventory.shipmentPosted` | shipment, postedBy | `apps/erp/app/routes/x+/shipment+/$shipmentId.post.tsx:358` |
| `invoicing.salesInvoicePosted` | salesInvoice, postedBy | `apps/erp/app/routes/x+/sales-invoice+/$invoiceId.post.tsx:635` |
| `invoicing.purchaseInvoicePosted` | purchaseInvoice, postedBy | `apps/erp/app/routes/x+/purchase-invoice+/$invoiceId.post.tsx:115` |

Момент отдаёт **только идентификатор** записи, не её поля — чтобы прочитать поля, в процесс
добавляют шаг **Find** (lookup).

**Чего НЕТ (явно перечислено как незакрытое в `.claude/rules/workflow-event-catalog.md`):**
момент «задание завершено», «заказ поставщику выпущен», «заказ клиента подтверждён»,
«КП проиграно», «несоответствие открыто/закрыто», «инспекция провалена» — у каждого два и
более независимых пути записи, одна точка вызова их не покроет.

**(в) Расписание (schedule).** Daily / Weekly / Monthly + час, минута, таймзона
(`packages/workflows/src/definition/schedule.ts`). Время хранится как «настенное» + зона,
поэтому 09:00 остаётся 09:00 при переходе на летнее время. Месячное «31 число» **пропускает**
месяцы без 31-го, а не сдвигается на последний день. Каждому процессу добавляется стабильный
сдвиг 0–299 секунд (`SPREAD_SECONDS = 300`, :10), чтобы сотни расписаний на 9:00 не ударили
одновременно. Пропущенные из-за простоя запуски **не догоняются**; опоздание > 1 часа
записывается как `Skipped`. Диспетчер: `packages/jobs/src/inngest/functions/workflows/scheduler.ts`
+ `packages/jobs/src/workflows/scheduler.ts` (цепочка «разбудить себя», токен в Redis).

**(г) Custom fields (пользовательские поля).** Кастомное поле компании тоже становится
триггером: id вида `<entity>.customFields.<fieldId>.changed`
(`packages/workflows/src/catalog/custom-fields.ts`). Id **выводится из данных, не ищется в
каталоге**, поэтому матчер остаётся «слепым к компании». Запись кастомных полей идёт через
RPC `workflow_merge_custom_fields` (миграция `20260819105102_workflow-merge-custom-fields.sql`),
чтобы запись одного поля не стёрла соседние. Исключены: `item` (его кастомные поля живут на
подтипах `part`/`material`/…) и справочные сущности.

**«Кем вызвано» (origin filter).** У триггера три значения: `Person` / `Automation` / `Both`
(`packages/workflows/src/definition/schema.ts:26`). Решение принимается **только** по наличию
метки `workflowRunId` в JWT автора записи. `Person` — это на самом деле «не workflow»: сюда
попадают человек, импорт, интеграция, API-ключ и фоновая задача; в UI подписано «Everything else».

### 1.4 Узлы (шаги) — их ровно 6

`packages/workflows/src/definition/schema.ts:41-110`, исполнители —
`packages/workflows/src/runtime/executors.ts:11-19`:

| Узел | Тип | Исполнитель | Что делает |
|---|---|---|---|
| Trigger | `trigger` | — (нет исполнителя; строка в истории пишется напрямую) | старт, ровно один на процесс |
| Condition | `condition` | `runtime/condition.ts` | ветвление: пути `if` / `elseIf` / `else`, набор клауз + комбинатор and/or |
| Compute | `compute` | `runtime/compute.ts` | вычисление (одна из 15 операций) |
| Lookup («Find») | `lookup` | `runtime/lookup.ts` | поиск записи/списка: `returns: "one" \| "list"`, набор `match` |
| Filter | `filter` | `runtime/filter.ts` | отфильтровать список по клаузам |
| Action | `action` | `runtime/action.ts` | сделать дело; два выхода — Success и Failure |

**Операторы сравнения** (`packages/workflows/src/definition/types.ts:97-105`), жёстко привязаны к типу:
- boolean: `eq`, `neq`
- string: `eq`, `neq`, `contains`, `startsWith`, `endsWith`
- number / date: `eq`, `neq`, `gt`, `gte`, `lt`, `lte`
- entity: `eq`, `neq`
- list: `contains`

Семантика — только в `packages/workflows/src/runtime/compare.ts`: `contains/startsWith/endsWith`
регистр **игнорируют**, `eq/neq` — **нет**. Null никогда не упорядочивается и не бросает ошибку.

**Шаблоны и ссылки.** В текстовом поле набирается `{` — выпадает меню переменных: шаги выше,
их выходы, до двух уровней свойств. Предлагаются **только** шаги, гарантированно выполнившиеся
раньше; ссылка «с другой ветки» отклоняется при публикации.

**Повтор шага (batch)** — нет галочки «повторять». Если в поле, ожидающее одиночное значение,
заведён список, шаг выполняется по разу на элемент, **до 100** (`MAX_LIST_ITEMS = 100`,
`packages/workflows/src/definition/schema.ts:14`). Два списка в один шаг — ошибка публикации
`INCOMPLETE_CONFIG`, а не догадка. Логика — `packages/workflows/src/definition/batch.ts`
(`batchCandidates` + `batchPlan`) и `packages/workflows/src/runtime/batch.ts` (`planBatch`, `itemKeyFor`).
Агрегатная строка шага успешна, если успешен **хотя бы один** элемент, но упавший элемент
помечает **запуск** как Failed.

### 1.5 Какие действия можно навесить — 16 действий

`packages/workflows/src/catalog/actions.generated.ts` (+ рукописные в `catalog/actions.ts`):

**Создание (4)** — идут через те же `upsert*`-сервисы, что и экраны ERP,
поэтому нумерация, значения по умолчанию и обязательные поля совпадают:

| Действие | Строка в `actions.ts` | Обязательные входы | MCP-функция (`call`) |
|---|---|---|---|
| `job.create` (создать произв. задание) | :45 | itemId, quantity | `production_insertJob`-семейство |
| `nonConformance.create` (открыть несоответствие) | :73 | — | `quality_*` |
| `purchaseOrder.create` (заказ поставщику) | :101 | supplierId | `purchasing_insertPurchaseOrder` |
| `salesOrder.create` (заказ клиента) | :122 | customerId | `sales_*` |

**Обновление (10)** — генерируются автоматически из `write`-allowlist каждой сущности:
`customer.update`, `item.update`, `job.update`, `nonConformance.update`, `purchaseOrder.update`,
`quote.update`, `receipt.update`, `salesOrder.update`, `shipment.update`, `supplier.update`.

> `write` и `watch` **несимметричны намеренно**: `watch` инертен (только решает, породить ли
> событие), а `write` — это эффект, который процесс совершает от имени владельца. Поэтому
> `write` — жёсткий белый список: всего **34 колонки на 10 сущностей** — по сути назначенный
> (assignee), даты, приоритет, внешние ссылки. **Статусы из процесса не пишутся. Действия
> «удалить» нет ни в каком виде.**

**Встроенные (2):**

1. **`notify`** — «Уведомить кого-то» (`actions.generated.ts:131`, исполнитель
   `packages/jobs/src/workflows/actions/notify.ts`). Входы: `user` или `role` (требуется хотя бы
   одно — `requireOneOf: [["user","role"]]`), `subject` (обязателен, шаблон), `message`
   (шаблон, с `linkify` — запись рендерится ссылкой `[имя](url)`), `channels`,
   `aboutId`/`aboutType`.
   Каналы (`packages/notifications/src/index.ts:119-123`): **`inApp`, `email`, `slack`** —
   и всё. `inApp` **нельзя выключить** (жёстко добавляется в `notify.ts`), `email` требует
   фичу `EMAIL_NOTIFICATIONS` (Business/Partner), `slack` — активной интеграции Slack.
   **Telegram-канала в коде нет.**

2. **`webhook`** — «Вызвать внешний URL» (`catalog/actions.ts:196`, исполнитель
   `packages/jobs/src/workflows/actions/webhook.ts`). Входы: `url` (обяз.), `method`
   (обяз., `GET|POST|PUT|PATCH|DELETE`, по умолчанию GET), `headers` (пары имя/значение,
   каждое — литерал, ссылка или шаблон), `body` (шаблон, показывается только для POST/PUT/PATCH).
   Выход — `status`.
   Ограничения, о которых надо знать заранее:
   - **только `https`**, иначе «Only https addresses are allowed.»;
   - **защита от SSRF** (`packages/jobs/src/workflows/actions/url-guard.ts`): DNS-резолв и отказ,
     если *хоть один* адрес приватный (`10/8`, `172.16–31`, `192.168/16`, `127/8`, `169.254/16`
     включая метадату облака, IPv6 ULA/link-local). Та же проверка ставится вторым слоем как
     `connect.lookup` у undici-агента — защита от DNS rebinding;
   - **редиректы запрещены** (`redirect: "manual"`, 3xx = отказ), таймаут **10 с**;
   - запрещены 8 заголовков: Host, Content-Length, Connection, Transfer-Encoding, Upgrade, TE,
     Keep-Alive, Proxy-Authorization;
   - **подписи запроса нет** — если получателю нужна аутентификация, добавляют свой заголовок;
   - значения заголовков в истории запусков **маскируются** (`[REDACTED]`), имена видны;
   - в итог шага кладётся до 2048 байт тела ответа.

### 1.7 Конвейер: от записи в БД до выполнения

```
изменение строки                              бизнес-момент                 расписание
dispatch_event_batch() → pgmq                 raiseMoment()                 scheduler.ts
  → event-queue (Inngest)                     → carbon/workflow-moment.raised
  → carbon/event-workflow
        │                                            │                           │
  events/workflow.ts                          workflows/moment.ts          dispatchDue()
  computeEventIds(table, op, old, new)        момент = сам id события
        └────────────────┬───────────────────────────┴───────────────────────────┘
                         ▼
        matchAndQueue()   packages/jobs/src/workflows/matcher.ts
          1. читает подписчиков (workflowTriggerEvent × workflow — одно индексное чтение)
          2. фильтр происхождения (Person / Automation / Both)
          3. защита от петель: цикл, затем глубина
          4. INSERT workflowRun, ON CONFLICT DO NOTHING
          5. по одному carbon/workflow-run.queued на реально вставленную строку
                         ▼
        workflows/run.ts → engine/execute.ts
```

**Порядок шагов внутри запуска** (`packages/jobs/src/workflows/engine/execute.ts`), каждый —
durable-step Inngest с детерминированным id:
`"load"` → `"custom-fields"` → `"permissions"` → `node:<nodeId>` (или `node:<nodeId>:<itemKey>`
для повторов) → `"finish"`.

**Подписки не ведут руками.** `packages/workflows/src/sync.ts`:
- `deriveWorkflowTriggerRows(nodes)` — узлы-триггеры → строки `workflowTriggerEvent`;
- `deriveWorkflowSubscriptions(eventIds)` — id событий → по одной подписке
  `eventSystemSubscription` на таблицу, с точным набором операций;
- `syncWorkflowTriggers(db, companyId, workflowId, lockCompany)` — вызывается на publish /
  правке триггера / unpublish; всё в одной транзакции, под `pg_advisory_xact_lock(hashtext(companyId))`.
- Реконсиляция **хирургическая**: трогаются только строки `handlerType = 'WORKFLOW'`, чужие
  WEBHOOK/SEARCH/AUDIT-подписки не сбрасываются.
- Если у компании нет процессов на таблицу — подписки нет, и триггер вообще ничего не кладёт
  в очередь. Пустая система ничего не стоит.

### 1.8 Безопасность: процесс действует от имени владельца

Правило, которое в Carbon называют неотменяемым (`.claude/rules/workflow-engine.md`):
**процесс не может сделать того, чего его владелец не мог бы сделать руками.**

- Клиент владельца выпускается **на каждый шаг** внутри шага:
  `getUserScopedClient(ownerId, { workflowRunId })` (`packages/jobs/src/workflows/engine/owner.ts`).
  Токен живёт 5 минут, а запуск с ретраями — дольше.
- `workflowRunId` **обязателен**: `dispatch_event_batch()` читает эту claim из JWT и метит
  ею запись в очередь. Непомеченная запись выглядит как человеческая → фильтр происхождения
  и обе защиты от петель слепнут.
- Разрешение проверяется **явно**, а не только через RLS: модуль события на старте запуска
  и пара `{module, action}` перед каждым узлом. RLS вернул бы ноль строк («нет данных»),
  а пользователю нужно сообщение вида «The owner of this workflow no longer has access to Purchasing.»
- **Привилегированный доступ есть только к двум таблицам журнала запусков.** Любое бизнес-чтение
  через привилегированного клиента — это баг безопасности, не оптимизация.
- В `update`-исполнителе (`packages/jobs/src/workflows/actions/update.ts`) порядок проверок —
  контракт: сущность известна → вход — реально запись → **целевая запись существует в этой
  компании** → значения enum валидны → **каждый внешний ключ тоже существует в этой компании**
  → только потом `.update(...)` с `.eq("id",…).eq("companyId",…)`. Пятый шаг — гарантия
  мультитенантности: Postgres принял бы FK на строку другой компании.
  Особый случай: у `user` нет `companyId`, членство проверяется через `userToCompany`.

**Защита от петель** (`packages/jobs/src/workflows/matcher.ts`):
- **Цикл** — id процесса уже есть в `path` → блокируется, «Cycle: this workflow already ran in this chain».
- **Глубина** — `depth >= MAX_CHAIN_DEPTH` (**10**, `packages/workflows/src/definition/schema.ts:16`)
  → «Chain depth limit reached (10 hops)».
- Заблокированный запуск **записывается** как `Blocked`, а не молча выбрасывается — иначе
  пользователь никогда не поймёт, почему цепочка встала.

Ещё один предел: `MAX_NODE_EXECUTIONS = 500` (`packages/jobs/src/workflows/engine/walk.ts:7`).

**Идемпотентность.** На уровне запуска — `claimRun` = `UPDATE ... WHERE status='Queued' RETURNING id`.
На уровне шага — `claimStep` вставляет `Running` с `ON CONFLICT ... DO NOTHING`. Модель
**«максимум один раз, намеренно»**: в ERP продублированное проведение хуже пропущенного.
Потеря делается видимой — `failInterruptedSteps` в конце запуска переводит всё, что осталось
`Running`, в `Failed`.

### 1.9 История запусков и хранение

`.claude/rules/workflow-run-history.md`. Экраны: `/x/workflows/runs` и
`/x/workflows/runs/:runId` (выдвижная панель). Порядок шагов строится
`topologicalNodeOrder(definition)`; непройденные узлы показываются как «Not reached».

**Тестовый запуск из конструктора имеет реальные побочные эффекты** и пишет реальную историю
(`workflowRun.isTest = true`, `packages/jobs/src/workflows/engine/manual.ts`), но не попадает

**Ретенция — 4 прохода каждую ночь в 04:00**
(`packages/jobs/src/inngest/functions/scheduled/workflow-run-retention.ts`):

| Проход | Что | Константа |
|---|---|---|
| 1 `reap-stale-runs` | закрыть `Queued`/`Running` старше 24 ч как Failed | `STALE_RUN_HOURS = 24` |
| 2 `purge-run-headers` | удалить терминальные `workflowRun` (шаги каскадом) | `RUN_HEADER_DAYS = 90` |
| 3 `compact-step-payloads` | ужать `input`/`output`/`detail` | `FULL_DETAIL_DAYS = 7` |
| 4 `drop-step-detail` | удалить строки шагов, шапка остаётся | `COMPACT_DETAIL_DAYS = 30` |

**Маскирование.** `redactForLog` (`packages/jobs/src/workflows/engine/ledger.ts`) заменяет
значение на `[REDACTED]` для ключей по регэкспу
`/secret|token|password|passwd|credential|signature|authorization|apikey|api_key|client_secret|clientsecret|private_key|privatekey|bearer|cookie/i`,

`sessionId`.

**Кнопки «повторить запуск» нет.** Упавший запуск не перезапускается из UI: чините причину и
ждите следующего срабатывания, либо жмите «Test run» в конструкторе.

## 2. Как написать своё

### 2.1 Новый триггер-момент (нужен разработчик)

1. Объявить в `packages/workflows/src/catalog/moments.ts` (label, permission, outputs).
2. Поднять его из **сервисной функции**, а не из маршрута:
   ```ts
   await raiseMoment("production.jobReleased", {
     outputs: { job: { id }, releasedBy: { id: updatedBy } },
     companyId, actorId: updatedBy
   });
   ```
   Почему из сервиса: каждый экспорт `apps/erp/app/modules/*/*.service.ts` доступен и через
   `POST /api/mcp`; вызов из маршрута молча пройдёт мимо всех MCP-вызовов.
3. Поднимать **после** коммита записи и только если он состоялся; для проводок — ниже
   `catch` с откатом, не внутри `try`.
4. `raiseMoment` **никогда не бросает исключение в вызывающий код** — логирует и возвращается.
5. `pnpm run generate:workflow-catalog` + `pnpm run check:workflow-catalog`.

CI-проверка: **у каждого объявленного момента должна быть точка вызова**. Мёртвый триггер
хуже отсутствующего — пользователь построит правило, которое никогда не сработает.

### 2.2 Новое действие

Два пути:
- **Обновление поля** — просто добавить колонку в `write` нужной сущности в
  `catalog/entities.ts`; генератор сам создаст/расширит `<entity>.update`.
  Запрещены: `id`, `companyId`, `createdBy`, `createdAt`, `updatedBy`, `updatedAt` (`UNWRITABLE_COLUMNS`).
- **Своё действие** — запись в `catalog/actions.ts` с полем `call` = имя реального
  MCP-инструмента из `apps/erp/app/routes/api+/mcp+/lib/tool-metadata.json`
  (после `pnpm run generate:mcp`), либо членство в `BUILT_IN_ACTIONS` (`notify`, `webhook`).
  Иначе `validateCatalogInputs` скажет `Action "<id>" has no implementation route.`

**Шов диспетчера** (`packages/jobs/src/workflows/actions/dispatcher.ts`): `packages/jobs` не
может импортировать `~/modules/*`, поэтому там лежит один слот
`setWorkflowDispatch(fn)`, который `apps/erp/app/routes/api+/inngest.ts` заполняет при первом
запросе, подставляя `callOperation` — ту же каноническую точку входа, которой пользуются MCP и
встроенный агент. Незаполненный слот — не падение: `runAction` вернёт
«This step is not available in this environment.»

**Новый тип узла** — одна строка в `EXECUTORS` (`packages/workflows/src/runtime/executors.ts:13`).
Разрешение и работа берутся из **одной и той же** записи реестра, чтобы проверка прав не
разошлась с исполнением.

### 2.3 Новый тип обработчика событий (нижний слой)

Процедура целиком: `.claude/rules/workflow-event-system.md`. Кратко — 6 правок:
1. расширить `HandlerTypeSchema` в `packages/database/src/event.ts`;
2. расширить CHECK-ограничение `eventSystemSubscription.handlerType` новой миграцией;
3. объявить имя события в `packages/lib/src/events.ts` (именно там, `packages/jobs/src/events.ts` только реэкспорт);
4. создать функцию-обработчик `packages/jobs/src/inngest/functions/events/<type>.ts`, `id: "event-handler-<name>"`;
5. добавить ветку в диспетчер очереди `packages/jobs/src/inngest/functions/events/queue.ts`
   (обязательно `chunk(..., CHUNK_SIZE)` — Inngest режет события на 256 КБ);
6. **зарегистрировать в двух местах**: бочка `events/index.ts` И массив `functions` в
   `packages/jobs/src/inngest/index.ts` — иначе функция просто не обслуживается.

## 3. Слой ниже: система событий (event system)

`.claude/rules/event-system.md`. Это Postgres-триггеры + PGMQ + **Inngest** (не Trigger.dev —
старый дизайн выпилен).

```
запись в БД → AFTER STATEMENT триггер → dispatch_event_batch() → pgmq.send_batch('event_system')
                                       → util.wake_event_queue()  [pg_net POST, раз на транзакцию]
                                               ↓
             edge fn event-wake → Inngest "carbon/event-queue.process"
                                               ↓
             event-queue (concurrency: 1), читает pgmq по 100, до 10 проходов
                                               ↓
             группирует по handlerType → step.sendEvent("carbon/event-<handler>")
                                               ↓
             pgmq.delete() обработанных msg_id

pg_cron 'event-queue-sweeper' (* * * * *) — страховка на случай потерянного «звонка»
```

**Шесть типов обработчиков** (`eventSystemSubscription.handlerType`):

| Тип | Событие Inngest | Файл | Назначение | Форма |
|---|---|---|---|---|
| `WEBHOOK` | `carbon/event-webhook` | `events/webhook.ts` | пользовательские вебхуки | построчно |
| `WORKFLOW` | `carbon/event-workflow` | `events/workflow.ts` | матчер процессов | построчно |
| `SYNC` | `carbon/event-sync` | `events/sync.ts` | синхронизация с бухгалтерией | пачкой |
| `SEARCH` | `carbon/event-search` | `events/search.ts` | индекс поиска | пачкой |
| `AUDIT` | `carbon/event-audit` | `events/audit.ts` | журнал аудита | пачкой |
| `EMBEDDING` | `carbon/event-embedding` | `events/embedding.ts` | векторные эмбеддинги | пачкой |

Подключение триггеров к таблице — SQL-хелпер с **тремя** аргументами:
`attach_event_trigger('таблица', ARRAY[]::TEXT[] /*BEFORE ROW sync*/, ARRAY[]::TEXT[] /*AFTER ROW*/)`.
Синхронные «перехватчики» (interceptors) выполняются inline — для целостности данных;
подписки — асинхронные, для всего остального.

**Задержка:** типично ~3–5 с, в худшем случае ~1 минута (если «звонок» потерялся и сработал
pg_cron). **Не годится** для real-time и целостности данных — там нужны sync-перехватчики.

**Грабли, названные прямым текстом:** незаполненная таблица `config` (`apiUrl`, `anonKey`)
= события **вообще не обрабатываются** (и push, и sweeper молча ничего не делают). Для
self-hosted это первая вещь, которую надо проверить.

### 3.1 Пользовательские вебхуки (Settings → Webhooks)

Таблица `webhook` (миграция `20250203121216_webhooks.sql:40`): `name`, `table`, `url`,
`active`, `onInsert`/`onUpdate`/`onDelete`, `successCount`/`errorCount`/`lastSuccess`/`lastError`.
С миграции `20260807234512_webhooks-via-event-system.sql` они работают поверх системы событий;
подписка `webhook-<id>` поддерживается AFTER-ROW перехватчиком `sync_webhook_subscription`,
то есть таблица `webhook` — единственный источник правды (UI/API/MCP пишут в неё без доп. кода).

**Тело запроса — публичный контракт:** `{type, record, old?, companyId, table, eventId}`
(`docs/content/docs/building/webhooks.mdx`, тест `webhook.test.ts`). Доставка **at-least-once**
(Inngest `retries: 3`); ключ дедупликации — `eventId` (это `msgId` из pgmq). Пара
`type + record.id` для дедупликации **не годится** — два разных обновления строки дадут одно и то же.

Важное отличие от workflow-action `webhook`: у обработчика событий **нет ни SSRF-защиты, ни
проверки https, ни подписи** (`axios.post` на настроенный URL). Три разные вещи в репо
называются «webhook», и объединять их запрещено (`.claude/rules/workflow-actions.md`):
1) workflow-действие (защищённое), 2) обработчик `WEBHOOK` (незащищённый, но это существующий
клиентский контракт), 3) **входящие** маршруты интеграций
(`apps/erp/app/routes/api+/webhook.{jira,linear,paperless-parts,stripe,xero}*.ts`).

## 4. Синхронизация с бухгалтерией (accounting sync)

`.claude/rules/accounting-sync-handlers.md` (42 КБ — самый крупный документ правил; это
объективный показатель сложности узла).

### 4.1 Что поддерживается

**Три живых провайдера:** Xero (`ProviderID.XERO`), QuickBooks Online (`QBO`), Rillet.
QuickBooks **Desktop** был и удалён 2026-08-01; Sage — папка есть (`packages/ee/src/sage/`),
но синхронизатор никогда не писался. **1С, Диадок, СБИС, любые российские системы —
отсутствуют полностью.**

Архитектура — класс на сущность, не таблица обработчиков:
- `packages/ee/src/accounting/core/sync.ts` — `SyncFactory.getSyncer(context)`, реестр
  `registries[providerId][entityType]`;
- `packages/ee/src/accounting/core/types.ts` — база `BaseEntitySyncer<TLocal, TRemote, TOmit>`
  (~800 строк): поиск маппинга, гейт `shouldSync`, быстрый выход по неизменившемуся времени,
  `mapToRemote`/`mapToLocal`, запись под `withTriggersDisabled`, `linkEntities`;
- `packages/ee/src/accounting/providers/{xero,quickbooks-online,rillet}/entities/*.ts` — конкретные синхронизаторы.

**Типы сущностей:** `customer | vendor | item | employee | purchaseOrder | bill | salesOrder |
invoice | payment | inventoryAdjustment | journalEntry` (`employee` не реализован).

**Направления:** `two-way | push-to-accounting | pull-from-accounting`. Стандартная позиция —
**Carbon владеет всем**: мастер-данные и документы принудительно `push-to-accounting`/
`owner: "carbon"`, провайдер — зеркало вниз по потоку. Единственное исключение — `payment`
(владелец — бухгалтерия).

### 4.2 Таблица связи идентификаторов

`externalIntegrationMapping` — единственный источник правды по внешним id (старые JSONB-колонки
`externalId` удалены). Миграции `20260128140000_external-integration-mapping.sql`,
`20260130005853`, `20260204001831`.

Колонки: `id`, `entityType`, `entityId`, `integration` (`'xero'`, `'linear'`, `'csv'`, …),
`externalId`, `allowDuplicateExternalId`, `metadata JSONB`, `lastSyncedAt`, `remoteUpdatedAt`,
аудит, `companyId`.
Ограничения: `UNIQUE (entityType, entityId, integration, companyId)` и частичный
`UNIQUE (integration, externalId, entityType, companyId) WHERE allowDuplicateExternalId = false`.

**Грабли RLS:** у таблицы есть политики только на SELECT и INSERT
(`20260204001831_external-integration-mapping-rls.sql`) — **UPDATE/DELETE нет**. Любое удаление
идёт через `getCarbonServiceRole()`.

### 4.3 Как это крутится

Точки входа (`packages/jobs/src/inngest/functions/integrations/`):

| Функция | Запуск | Роль |
|---|---|---|
| `sync-external-accounting` | входящие вебхуки провайдеров | реакция на изменение у провайдера |
| `accounting-pull-sweep` | cron `*/30 * * * *` | **гарантия входящей корректности** (вебхуки — это про задержку, не про корректность) |
| `accounting-outbound-sweep` | cron `15,45 * * * *` | **гарантия исходящей корректности** |
| `accounting-consolidation` | cron `0 2 * * *` | одна сводная проводка на дату |
| `accounting-reconciliation` | cron `0 3 * * 1` | сверка присутствия + запись `accountingSyncTieOut` |
| `event-handler-sync` | `carbon/event-sync` | изменения в БД → пуш провайдеру |

Между «поставить в очередь» и «выполнить» стоит durable-журнал **`accountingSyncOperation`**:
поглощение повторов, кулдаун 60 с (`SYNC_OPERATION_COOLDOWN_MS`,
`packages/ee/src/accounting/core/operations.ts:21`), лимит `MAX_SYNC_OPERATION_ATTEMPTS = 10`
(после — статус `Failed ATTEMPTS_EXHAUSTED`, дальше только ручной Retry), и «честное закрытие»:
push, завершившийся успехом **без** внешнего id, закрывается как `Failed POSTCONDITION` —
запись такого «зелёной галочкой» и была багом «фантомного успеха».

Доктрина, сформулированная в правилах: **события — это про задержку; sweep — про корректность.**
Любое потерянное событие превращается максимум в 30-минутное отставание, а не в вечную потерю.

Один «мозг» принятия решений: `computeReconcileDecision` (`integrations/reconcile.ts`) — чистая
функция, решающая **по текущему состоянию**, а не по дельте события; исполнитель
`reconcile-executor.ts`. Событие — это подсказка, а не решение.

**Вывод для завода в Хабаровске:** каркас синхронизации отличный и провайдеро-агностичный,
но **ни одного российского провайдера нет**. Реалистичный путь: либо выгрузка в 1С через
`webhook`-действие / HTTP API, либо написание своего провайдера в
`packages/ee/src/accounting/providers/<name>/` (регистрация в `SyncFactory`, набор
`REQUIRED_SYNC_SUBSCRIPTIONS[providerId]` в `core/subscriptions.ts`). Это работа уровня
нескольких человеко-месяцев: базовый класс `BaseEntitySyncer` берёт на себя маппинг, журнал
и sweep, но каждая сущность — свой маппер.

## 5. Встроенный AI-агент и MCP

### 5.1 MCP-сервер ERP — самое сильное место для автоматизации

`apps/erp/app/routes/api+/mcp+/`. Эндпоинт **`POST /api/mcp`**, JSON-RPC поверх
`WebStandardStreamableHTTPServerTransport`, **без сессий**.

Зарегистрировано **ровно три мета-инструмента** (чтобы не взорвать контекст модели) —
`apps/erp/app/routes/api+/mcp+/lib/server.ts`:

| Инструмент | Что делает |
|---|---|
| `search_tools` | BM25-поиск по каталогу (движок `zbsearch`, индекс строится лениво). Фильтры: `query`, `module`, `classification` (`READ`/`WRITE`/`DESTRUCTIVE`), `limit`/`offset` |
| `describe_tool` | полный контракт инструмента: описание, требуемое разрешение, схема входа И схема ответа |
| `call_tool` | выполнить любой инструмент ERP: `{ name, arguments }` |

За ними — **~1200 функций ERP** (точное число плавает; живой список —
`apps/erp/app/routes/api+/mcp+/lib/tool-metadata.json`, это **сгенерированный** файл 1,9 МБ,
он в `.gitignore`; в репозитории лежит его дайджест `tool-manifest.digest.json`).
Генератор: `scripts/generate-mcp.ts`, команда `pnpm generate:mcp` (запускается из `postinstall`).

**15 модулей:** `account`, `accounting`, `documents`, `inventory`, `invoicing`, `items`,
`people`, `production`, `purchasing`, `quality`, `resources`, `sales`, `settings`, `shared`, `users`.
Имена инструментов: `<модуль>_<глагол><Сущность>` — `sales_getCustomers`, `inventory_upsertStorageUnit`.

**Три способа аутентификации** (`_index.ts` → `resolveAuth`), в этом порядке:
1. OAuth Bearer (токен не с префиксом `crbn_`) — SHA-256, поиск в таблице `oauthToken`;
   это путь удалённого MCP-коннектора Claude;
2. API-ключ — `Bearer crbn_…` или заголовок `carbon-key`; проверяется скоуп на каждую операцию;
3. без авторизации → 401 с `WWW-Authenticate`, чтобы клиент нашёл OAuth-поток.

`companyId`/`userId` **всегда** берутся из контекста авторизации и подставляются на сервере —
никогда из аргументов инструмента.

**Публичные точки обнаружения (без авторизации):** `GET /.well-known/mcp.json`,
`GET /.well-known/oauth-protected-resource`, `GET /.well-known/oauth-authorization-server`,
`GET /agent-setup/prompt.md` (markdown-инструкция «подключи свой MCP-клиент»). Все URL
выводятся из `getAppUrl() || url.origin` — self-hosted-инстанс рекламирует **свой** адрес.

**Единая точка исполнения.** `call_tool` не ходит обратно через протокол MCP, а зовёт
`callOperation(name, ctx, args)` из `apps/erp/app/routes/api+/v1+/lib/call.server.ts` — одну и ту же
серверную точку входа для **MCP, встроенного агента и диспетчера workflow**. Дальше — реальная
процедура oRPC с валидацией входа, middleware-гейтами и разворачиванием конверта Supabase
`{data, error}`. Поведение зафиксировано тестом `dispatch-parity.test.ts` — изменение там
меняет поведение сразу у четырёх потребителей.

**Заблокированные инструменты** (`lib/mcp-blocked-tools.ts`): операции уровня арендатора
(`settings_insertCompany`, `settings_deleteSubsidiary` — пустое тело создало бы или снесло
компанию) и операции над таблицами с user-scoped RLS (`"createdBy"::uuid = auth.uid()` —
`note`, `maintenanceDispatchComment`, шесть таблиц `*Favorite`): API-ключ не даёт `auth.uid()`,
и UPDATE/DELETE по нулю строк PostgREST считает **успехом** — `deleteNote` отвечал `200`,
не удалив ничего.

### 5.2 Встроенный агент в интерфейсе

## 6. Импорт данных (CSV)

`.claude/rules/csv-import-system.md`. Мастер из двух шагов + тонкий маршрут + edge-функция Deno.

**Поток:**
1. `apps/erp/app/components/ImportCSVModal/UploadCSV.tsx` — парсинг на клиенте **PapaParse**,
   загрузка в приватный бакет Supabase по пути `${companyId}/imports/${nanoid()}.csv`;
2. `FieldMappings.tsx` — сопоставление колонок с полями + **сопоставление значений enum**
   (CSV `"B"` → `"Buy"`, нечёткое совпадение в `enumMatch.ts`) + создание отсутствующих
   справочных значений прямо в мастере (`useCreateLookup.ts`);
3. POST на `apps/erp/app/routes/x+/shared+/import.$tableId.tsx`;
4. маршрут валидирует и зовёт `importCsv` → `client.functions.invoke("import-csv", {body})`;
5. edge-функция `packages/database/supabase/functions/import-csv/index.ts` качает файл,
   применяет маппинги, классифицирует каждую строку и пишет **в транзакции** (Kysely, минуя RLS).

**Модели** — `apps/erp/app/modules/shared/imports.models.ts`: три карты по имени таблицы —
`fieldMappings` (описания полей), `importPermissions` (таблица → модуль разрешений),
`importSchemas` (zod на таблицу).

> **Инвариант, стоивший бага:** каждое поле из `fieldMappings[table]` обязано быть и в
> `importSchemas[table]`. zod срезает необъявленные ключи — поле, которое мастер предлагает,
> а схема не описывает, пользователь сопоставит, отправит, и оно молча потеряется. Именно
> поэтому все импортированные из CSV номенклатуры получали ревизию `"0"`. Тест —
> `imports.models.test.ts`.

**Что можно импортировать** (и под каким разрешением):
- `customer`, `customerContact` → `sales`;
- `supplier`, `supplierContact` → `purchasing`;
- `part`, `material`, `tool`, `fixture`, `consumable`, `service`, `bom`, `operations`,
  `partWithMethod`, шесть справочников материалов (`materialSubstance/Form/Finish/Grade/Type/Dimension`),
  `unitOfMeasure`, `storageType` → `parts`;
- `workCenter`, `process`, `scrapReason` → `production`;
- `storageUnit` → `inventory`; `department` → `people`; `itemPostingGroup`, `fixedAsset` → `accounting`.

Для завода металлоконструкций ключевое: **есть импорт BOM (`bom`), маршрутов (`operations`),
номенклатуры с методом (`partWithMethod`), рабочих центров (`workCenter`) и всей таксономии
материалов** — то есть первичное наполнение справочников реально закрывается без разработки.

**Разрешение импорта — это разрешение из INSERT-политики RLS таблицы, а не то, что открывает
её экран.** Edge-функция пишет через service-role и RLS обходит, поэтому `importPermissions` —
**единственная** авторизация на массовой заливке. Наглядное расхождение: `itemPostingGroup` —
страница под `parts`, политики под `accounting_*`.

**Идемпотентность.** Через ту же `externalIntegrationMapping` с `integration = "csv"`:
повторный импорт того же файла с теми же id **обновит**, а не задвоит.
Часть справочников (`unitOfMeasure`, `itemPostingGroup`, `storageType`, `scrapReason`,
`department`, шесть материальных) работают в режиме **create-only, skip-duplicate** — без
маппингов и без обновлений.

**Известные дыры (прямо задокументированы):**
- `fixture` — «сирота»: зарегистрирован везде, но тип `Fixture` выпилен из enum типов
  номенклатуры, страницы нет;
- `fixedAsset` — есть модели и разрешения, но **нет** в enum таблиц edge-функции → импорт
  падает с «Table not found»;
- **кастомные поля номенклатуры при импорте не заполняются** — пути вставки пишут `customFields: {}`;
- клиент (PapaParse) и сервер (Deno std csv) парсят **разными** парсерами — одинакового
  поведения ждать нельзя.

**Экспорт** в CSV — отдельный механизм таблиц: `.claude/rules/table-csv-export.md`.

## 8. Биллинг и редакции (влияет на то, что вообще доступно)

`.claude/rules/billing-system.md`. Stripe активен **только в редакции Cloud**.

- `enum Edition { Cloud, Enterprise, Community, Test }`, значение из переменной `CARBON_EDITION`.
- `enum Plan { Starter, Business, Partner, Unknown }`; партнёрские тарифы в БД —
  `PARTNER-300/400/500`, схлопываются `normalizePlanId`.
- Таблицы: `plan` (каталог), `companyPlan` (**`id` == `company.id`**, не отдельный id!),
  `companyUsage` (счётчики: users, tasks, aiTokens).
- Единственный писатель состояния подписки — `syncStripeDataToKV` (Redis-кэш + зеркало в `companyPlan`).

**Вывод для self-hosted развёртывания в России:** Stripe не нужен и не работает; все три
функции гейта (`getPlan`, `companyHasPlan`, `requirePlan`) делают короткое замыкание при
`CarbonEdition !== Edition.Cloud` (`packages/ee/src/plan.server.ts:53, 76, 101`). То есть
**Workflows, вебхуки, API-ключи, интеграции, аудит-лог, AI-агент, 2FA доступны без оплаты**
на собственном сервере. Лицензия репозитория и EE-папка (`packages/ee`) — отдельный юридический
вопрос, который здесь не разбирается.

### Оценка объёма адаптации под Россию (по этому срезу кода)

**Не требует разработки:**
- русский язык уже в списке локалей: `lingui.config.js:5` — `["en","es","de","it","ja","zh","fr","pl","pt","ru","hi","tr","ko"]`,
  каталоги в `packages/locale/locales/ru/`;
- уведомления в интерфейсе, вебхуки, API, MCP, импорт CSV, конструктор процессов — работают
  как есть на self-hosted без оплаты.

**Требует разработки (по убыванию объёма):**
1. **Бухгалтерия/ЭДО** — нет ни одного российского провайдера. Либо свой синхронизатор
   (каркас хороший, но каждая сущность — свой маппер), либо интеграция через webhook/API.
   Самый дорогой пункт.
2. **Telegram как канал уведомлений** — в `NotificationDestination` три значения
   (`packages/notifications/src/index.ts:119-123`). Через workflow-действие `webhook` задача
   решается без кода, но «красивого» канала с настройкой в профиле пользователя не будет,
   пока не добавить четвёртое значение enum + службу отправки по образцу
   `packages/ee/src/notifications/services/linear.ts`.
3. **Почтовый разбор входящих заявок** — отсутствует как класс; это отдельная служба снаружи,
   которая складывает результат в Carbon через MCP.
4. **Статусные переходы из процессов** — сознательное ограничение Carbon; если заводу нужен
   автоматический перевод документов по статусам, это либо новое действие в каталоге, либо
   внешний вызов.
