# Штатный email-модуль ERPNext: что умеет с входящими и вложениями

Проверено по коду установленного инстанса (frappe `email/doctype/email_account`,
`email/receive.py`). Прод не трогали — только чтение исходников.

## Что умеет ИЗ КОРОБКИ

**1. Приём входящих по IMAP.**
DocType **Email Account** с полями: `enable_incoming`, `use_imap`, `imap_folder`,
`incoming_port`, `default_incoming`, `attachment_limit`. Настраивается в UI:
один Email Account = один ящик, периодический поллинг входящих.

**2. Автосоздание/привязка документа из письма (`append_to`).**
Поле **`append_to`** на Email Account задаёт DocType, к которому привязывать
входящие. Логика в `receive.py`:
- `_create_reference_document(doctype)` — **создаёт новый документ** (например
  **Lead**) из письма: тема → поле имени, отправитель → поле email/sender
  (через `get_email_fields`). То есть «письмо → лид» частично есть штатно.
- `enable_automatic_linking` — связывает ответы/треды с уже существующим
  документом по теме/отправителю (не плодит дубли на переписку).

**3. Сохранение вложений (`save_attachments_in_doc`, receive.py:615).**
Вложения входящего сохраняются как **File**-записи и привязываются к
**Communication** письма. Communication, в свою очередь, привязан к reference-
документу (Lead). Лимит — `attachment_limit`. То есть вложения **захватываются и
не теряются**, доступны через таймлайн письма в карточке лида.

## Чего НЕ хватает для нашего маршрута

| Нужно нам | Штатно | Вывод |
|---|---|---|
| Создать лид только из РЕЛЕВАНТНЫХ писем | `append_to=Lead` создаёт лид из **каждого** входящего | Спам/реклама/поставщики → мусорные лиды. Нужен **фильтр-классификатор ДО создания** (n8n + Claude) |
| Извлечь структуру (контакт, позиции, кол-во, сроки) в поля лида | Тянет только тему→имя, отправителя→email | Парсинг сути — **наш AI-слой**, штатно нет |
| Вложения именно на карточке лида («единое окно») | Файлы висят на Communication (виден в таймлайне лида), не как attachments самого Lead | Для «единого окна» — либо смотреть таймлайн (ок), либо хук, копирующий File на сам Lead |
| Черновик КП из заявки | — | Отдельная фаза |

## Практический вывод для архитектуры маршрута

- **Захват письма + вложений** можно опереть на штатный механизм (Email Account
  + Communication + File) — он надёжен и не теряет вложения. Это снимает риск с
  «единого окна».
- **Но `append_to=Lead` в лоб включать нельзя** — он создаст лид на каждое
  письмо, включая спам. Нужен порядок: **входящее → классификация (заявка?) →
  только для заявок создаём лид + извлекаем параметры**. Эту развилку делает
  n8n + Claude, а не штатный модуль.
- Два рабочих варианта компоновки (решим по цифрам из REPORT.md):
  1. **n8n-first:** n8n читает IMAP → Claude классифицирует/извлекает → создаёт
     Lead через ERPNext API, вложения прикладывает сам. Полный контроль, штатный
     append_to не используется.
  2. **Гибрид:** штатный Email Account захватывает письмо+вложения в
     Communication (без `append_to`), а n8n/AI обрабатывает Communication,
     классифицирует и при необходимости поднимает Lead. Переиспользует штатный
     захват вложений.

Выбор зависит от Блока 3/5 отчёта (где живёт заявка и доля вложений).
