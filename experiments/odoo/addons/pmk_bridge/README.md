# pmk_bridge — мост справочника pmk_calc в номенклатуру Odoo

**Статус:** заливка отрепетирована на копии `odoo_rehearsal` (752 карточки,
второй прогон создал 0). В живую базу не заливали. Модуль не установлен ни
на одной базе и автоматически не ставится.

## Зачем

Цена поставщика в Odoo живёт в `product.supplierinfo` и требует товар.
Сортамент лежит в собственных таблицах `pmk_calc` и товаром не является —
цене некуда лечь. Значит на каждую строку справочника нужна карточка товара,
а карточку нужно чем-то опознавать при следующей загрузке прайса. Этим ключом
и служит артикул (`default_code`): имя для опознания не годится, оно
переводится и в каждом прайсе пишется по-своему.

## Схема артикула (утверждена владельцем)

Латинская, говорящая, без контрольного хвоста. Ноль не-ASCII символов.

| Справочник | Формат | Примеры |
|---|---|---|
| Прокат | `<ВИД>-<типоразмер>` | `ARM-d12`, `DVT-20B1`, `DVT-20SH1`, `SHV-6.5U`, `SHV-16aP`, `UGR-63x63x5`, `UGN-125x80x8`, `KRG-d12`, `KVD-10`, `SHG-S24`, `TRK-89x4`, `TPK-100x100x3`, `TPP-180x100x6`, `VGP-Du15x2.5` |
| Труба бесшовная | то же + `-BS` | `TRK-89x4-BS` |
| Лист | `LST-<ВИД>-<толщина>` | `LST-GL-3`, `LST-RF-4`, `LST-PV-406`, `LST-ZN-0.5` |
| Метизы | `MTZ-<ВИД>-<типоразмер>` | `MTZ-BLT-M8x20`, `MTZ-NUT-M8`, `MTZ-WSH-M8`, `MTZ-ANC-M10x100`, `MTZ-SCR-4.8x35` |
| ЛКП | `LKP-<XML-id>` | `LKP-GF021`, `LKP-PF115`, `LKP-ZINC-HOT` |
| Вариант | артикул + характеристики через дефис | `DVT-20B1-09G2S`, `LST-GL-3-St3sp-1500x6000` |

Транслитерация сохраняет регистр — на этом держится `Ду` → `Du` и `16аП` →
`16aP`. Многобуквенные: `Ш`→`SH`, `Ж`→`ZH`, `Ц`→`TS`, `Ч`→`CH`, `Щ`→`SCH`,
токен `ромб`→`RHM`.

Что в артикул НЕ входит:

* **габарит листа** — лист считаем штуками листа определённого размера,
  габарит (1500x3000 / 1500x6000 / 1000x4000) это характеристика варианта;
* **марка стали** — тоже характеристика, `create_variant='dynamic'`;
* **рифление «ромб»** — оно одно на все 8 строк рифлёного листа и ничего не
  различает. Появится чечевичное — попадёт в артикул, ромбовые не изменятся.

## Два разных парсера

Это не перестраховка, а факт из данных:

* прокат — разделитель **латинская `x`** (U+0078); кириллической `х` (U+0445)
  в 665 строках нет ни одной;
* метизы — разделитель **`×`** (U+00D7, 15 строк), резьба через **кириллическую
  `М`** (U+041C, 23 строки); латинской `x` в 25 строках нет ни одной.

Каждый парсер проверяет, что ему отдали строку из его справочника, и падает
с `SkuError`, если разделитель чужой. Кириллическая `х` в `63х63х5` глазом не
отличается от латинской — пропустив её, получишь второй артикул на тот же
уголок и раздвоенные цены.

## Дубль листа id=57

В бэкапе `odoo_20260920_102418.dump` в `pmk_metal_sheet` 57 строк против 56 в
CSV: id=57 и id=58 — одинаковый оцинкованный 0,6 мм, ГОСТ 14918-2020,
4,71 кг/м². XML-id `pmk_calc.sheet_оцинк_0_6` принадлежит id=58, у id=57
XML-id нет — это ручной дубль. Прогон генератора показывает его как
единственное столкновение во всей базе (`LST-ZN-0.6`), и в 752 карточки он
не входит.

Ссылок на id=57 не было ни одной: на `pmk_metal_sheet` смотрят два внешних
ключа — `pmk_metal_spec_line.sheet_id` и `pmk_dobor_order_line.sheet_id`, оба
`ON DELETE SET NULL`, и ни в одном из них id=57 не встречается. Проверять это
обязательно ДО удаления: `SET NULL` не падает с ошибкой, а молча обнуляет
ссылку — вес уже посчитанной спецификации поехал бы без единого сообщения.
На копии дубль удалён (осталось 56 строк, id=58 на месте). В живой базе его
на 20.09.2026 уже нет — там 56 строк.

## Заливка номенклатуры

Карточки заводит скрипт, а не файл данных модуля: 752 карточки — это данные
завода, и переустановка модуля не должна их трогать. Модуль несёт только
среду — коды ОКЕИ, дерево из 25 категорий и две характеристики.

**Ключ сопоставления — внешний идентификатор строки справочника.** На строку
`pmk_calc.profile_двутавр_20б1` заводится карточка
`pmk_bridge.product_profile_двутавр_20б1`. Не имя (переводится и
переписывается) и не артикул (схему артикулов владелец может поменять, а связь
со справочником рваться не должна).

### Порядок запуска

```bash
# 0. копия живой базы (на ХОСТЕ pg_restore нет, работаем внутри контейнера db)
docker cp /opt/backups/odoo/odoo_<дата>.dump odoo-db:/tmp/reh.dump
docker exec odoo-db psql -U odoo -d postgres -c "CREATE DATABASE odoo_rehearsal OWNER odoo"
docker exec odoo-db pg_restore -U odoo -d odoo_rehearsal --no-owner --no-acl /tmp/reh.dump
docker exec odoo-db psql -U odoo -d odoo_rehearsal -c \
  "UPDATE ir_cron SET active=false; UPDATE ir_mail_server SET active=false;
   UPDATE fetchmail_server SET active=false;"

# 1. контрольные цифры ДО (сравнивать «после» иначе не с чем)
sh /tmp/run_reh.sh scripts/control_numbers.py
# 2. главный риск, всё внутри SAVEPOINT и откатывается
sh /tmp/run_reh.sh scripts/risk_attribute.py
# 3. среда: ОКЕИ, категории, характеристики, четыре существующих товара
sh /tmp/run_reh.sh scripts/prepare_environment.py
# 4. карточки
sh /tmp/run_reh.sh scripts/load_products.py
# 5. приёмка по семи пунктам
sh /tmp/run_reh.sh scripts/verify_load.py
```

Все пять скриптов начинаются предохранителем по имени базы: на базе `odoo`
они умирают до первой записи.

### Порядок действий внутри заливки — не переставлять

Разобрано по `product_template.py::_create_variant_ids` и подтверждено замером:

1. карточка создаётся **без характеристик** — Odoo делает ей один вариант;
2. на этот вариант пишется артикул;
3. характеристика вешается с **одним** значением — ветка `single_value_lines`
   дописывает метку существующему варианту, и он остаётся жив;
4. строка расширяется до всех значений.

Если создать карточку сразу с характеристикой, вариантов ещё нет, ветка
`single_value_lines` работать не с чем, а `dynamic` новых не создаёт —
получается карточка с нулём вариантов, без места под артикул и без склада.

Замер на трубе с остатком 3621,790 м и 15 движениями (`risk_attribute.py`):

| Как вешаем | Вариант | Остаток |
|---|---|---|
| 8 значений сразу, dynamic | архивирован | 3621,790 в базе, но не виден нигде |
| 1 значение, потом 8 (наше) | жив, метка Ст3сп | 3621,790 на месте |
| 8 значений сразу, always | архивирован + 8 пустых | 3621,790 не виден |

### Две вещи, о которых надо знать заранее

**Точность массы.** `product.template.weight` объявлен как
`Float(digits='Stock Weight')`, а на стенде это 2 знака. Массы метизов в них
не влезают и округляются молча: шайба 0,00210 кг → 0,00, то есть цена штуки
при пересчёте из руб/кг обнуляется. Скрипт поднимает точность до 5 знаков —
ровно столько у `weight_kg` в справочнике.

**Артикул и второй вариант.** `product.template.default_code` — поле
вычисляемое: оно берёт артикул у ЕДИНСТВЕННОГО варианта, а при двух и более
ставит False. Замер: у карточки TPK-100x100x3 после создания варианта 09Г2С
артикул шаблона обнулился сам, новый вариант пришёл без артикула. Пока марка
на карточке одна, сопоставление прайса работает; хук, проставляющий варианту
артикул по утверждённой схеме (`TPK-100x100x3-09G2S`), — следующая задача.

## Цены поставщика

Карточки заведены ради этого: `product.supplierinfo` требует товар, и теперь
ему есть куда лечь. Грузит цены `tools/load_prices.py` — отдельным файлом от
заливки карточек, потому что карточки заводят один раз, а прайсы приходят
каждый месяц.

### Почему цену нельзя просто записать

Замер на копии живой базы, карточка `TRK-89x4`, единица учёта — МЕТР:

| Что делаем с ценой 62 000 руб/т | Что получилось | Возражение Odoo |
|---|---|---|
| записали как есть | 62 000 руб за МЕТР (завышение в 143 раза) | нет |
| объявили `product_uom_id` = «тонна» | 62,00 руб за метр (занижение в 7 раз) | нет |
| **правильно: через массу метра** | **433,07 руб/м** | — |

Второй случай — не наследие: в Odoo 19 из `uom.uom::_compute_price` убрали
проверку категории, осталось `price * to_unit.factor / self.factor`. Тонна
(множитель 1e6 от грамма) и метр (1e3 от миллиметра) лежат в разных
измерениях, но деление всё равно выполняется и даёт правдоподобное число.
Правдоподобное хуже абсурдного: абсурдное заметят.

Поэтому в загрузчике цена — не число, а пара «сумма + единица» (`Money`), а
запись идёт ровно одной дверью `assert_price_unit()`. Попытка положить цену
тонны на метровый товар кончается отказом с объяснением, что сделал бы Odoo
без проверки. После записи `verify_written()` перечитывает `price_discounted`
— то самое число, которое увидит закупка, — и сверяет с записанным.

### Как считаем

```
цена без НДС = цена с НДС / (1 + ставка/100)      ставка — параметр ПРАЙСА
руб/метр     = цена_без_НДС / 1000 * кг_в_метре   (кг_в_метре = вес хлыста / длина)
руб/штуку    = цена_без_НДС / 1000 * кг_в_листе   (лист)
```

**Ставка НДС — параметр, а не константа.** Она меняется реже прайсов, но
меняется (18 → 20 → 22), и залитый по вчерашней ставке прайс ошибается молча
на всю разницу. Ставка лежит рядом с датой и поставщиком в описании прайса
(`PriceBook`) и печатается в отчёте. Проверено прогоном: те же строки при
22% дают 546,85 руб/м, при 20% — 555,97.

**Массу берём ИЗ ПРАЙСА, а не из справочника** — решение владельца, причина
денежная: счёт поставщик выставит по своей массе, на тонкостенных разница
доходит до 5%. Наша теоретическая масса остаётся для расчёта КП, а здесь
работает СТОРОЖЕМ: расхождение больше допуска (по умолчанию 10%) — строка
отбивается. Улов на живом прайсе Металлсервиса:

* «Балка 30К2, вес 1 шт. 1,128 кг» при 12-метровом хлысте — тонны вместо
  килограммов; без сторожа цена метра ушла бы в 1000 раз вниз;
* «Лист г/к 6 х 1500 х **3000**» с весом 430 кг — поставщик скопировал вес
  шестиметрового листа в строку трёхметрового; цена штуки удвоилась бы;
* уголок 40x40x4 длиной 9 м с весом 29,3 кг (3,26 кг/м против 2,42).

**Дату прайса задаёт человек.** В файле Металлсервиса две ячейки-даты
(16.06.2026 и 20.08.2018) и ни одной подписи, какая из них дата прайса.
Угадывать её — та же ошибка класса «чужая единица»: цены копятся рядом по
`date_start`, и неверная дата тихо перекроет чужой период. Без `--date`
загрузчик отказывается работать и печатает найденные в файле кандидаты.

### Уровни объёма — тоже пересчёт

Три цены в прайсе — это три записи `product.supplierinfo` с разным `min_qty`
и номером уровня в `sequence`. Границы уровней в прайсе заданы В ТОННАХ, а
Odoo сравнивает `min_qty` с количеством в единице продавца
(`product_product.py::_get_filtered_sellers`), то есть в МЕТРАХ. Оставить там
0,3 значит объявить оптовую цену с 0,3 метра. Считаем: `0,3 т × 1000 / кг_м`,
округляя ВВЕРХ — округлив вниз, дадим скидку на объёме, на котором поставщик
её не даёт.

Границы берём из шапки КАЖДОГО раздела, а не из кода: в файле они разные —
«до 0,3 тн» у труб, «до 0,5 тн» у листа, «до 10 шт» у арматурной сетки. Раздел
со штучными уровнями означает, что и цена в нём не за тонну: такие строки
отбиваются, а не пересчитываются наугад.

Проверка на `TRK-89x4` (8,5217 кг/м из прайса): 0,3 т → 35,205 м, 1 т →
117,348 м. Сам Odoo при закупке 10 / 40 / 200 м выбирает уровни 1 / 2 / 3.

### Куда ложится цена

* **прокат — на ШАБЛОН**: габарита у него нет, цена метра одна на карточку;
* **лист — на ВАРИАНТ**: единица «штука», и штука 1500x6000 стоит вдвое
  дороже штуки 1500x3000; на шаблоне это означало бы «лист любого размера по
  цене шестиметрового».

Вариантов загрузчик цен НЕ СОЗДАЁТ: второй вариант обнуляет артикул шаблона
(см. «Артикул и второй вариант» выше), и чинить это должен тот, кто заливает
карточки. Строки листа, которым не нашлось варианта, отбиваются с указанием
пары (марка, габарит) — на прайсе Металлсервиса таких 22.

### Ряд по датам, а не затирание

Ключ ряда — (поставщик, товар, номер уровня). `min_qty` ключом быть не может:
он пересчитывается из массы, и у следующего прайса будет другим. Новая цена
не переписывает старую: прошлой записи проставляется `date_end` за день до
новой, и в базе остаётся история. Перекрывать периоды нельзя — Odoo не считает
это ошибкой, он просто возьмёт ту, что дешевле, и старая цена будет всплывать
годами. Проверено: при дате 2026-07-01 Odoo берёт июньскую цену, при
2026-10-01 — сентябрьскую.

### Что ещё отбивается и почему

Разборщик названий (`experiments/price-matching`) сличает вид и размеры, но на
покрытие и сплав не смотрит. Без дополнительной проверки на карточки легли бы:
оцинкованная труба на чёрную, алюминиевый лист на стальной, чечевичное
рифление на гладкий лист. Поэтому слово-признак из строки прайса
(«оцинк», «алюмин», «нержав», «чечев», «рифл», «просечно», «б/ш») обязано
подтверждаться позицией справочника — иначе отказ. На этом прайсе так отбито
17 строк.

Одна и та же позиция встречается в прайсе дважды — разной длиной хлыста
(вес поставщика отличается на 2–3%) или разной маркой («Труба эл/св 114 х 4»
есть Ст3сп\пс за 78 290 и 09Г2С за 92 290 руб/т). Предпочитаем строку базовой
марки Ст3сп (её и купят), среди равных берём большую цену — занизить
себестоимость КП хуже, чем завысить. Обе строки печатаются: выбор наш, и
человек должен видеть, из чего выбирали.

### Запуск

```bash
# без базы: разбор, пересчёт и отчёт — ничего никуда не пишет
python3 experiments/odoo/addons/pmk_bridge/tools/load_prices.py \
    --file price_metallservice.xls --date 2026-06-16 --vat 22 --supplier 19

# на копии базы (цели ищутся среди карточек), с записью и показом защиты
sh /tmp/run_prices.sh tools/load_prices.py \
    "PMK_PRICE_FILE=/tmp/price_metallservice.xls PMK_PRICE_DATE=2026-06-16 \
     PMK_PRICE_VAT=22 PMK_PRICE_SUPPLIER=19 PMK_PRICE_APPLY=1 PMK_PRICE_SELFTEST=1"
```

Рядом должен лежать `match.py` из `experiments/price-matching`
(`PMK_PRICE_MATCH`, по умолчанию `/tmp/pmk_price_code`).
