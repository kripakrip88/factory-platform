## 1. Общий формат всех XML (строго, подтверждено на 84 файлах)

- Первая строка: `<?xml version="1.0" encoding="utf-8"?>` и CRLF. Метки порядка байтов (BOM) нет. Кириллица записана как есть в UTF-8, без `&#..;`.
- Один элемент на строку. Отступ — по одному TAB на уровень вложенности. Конец строки — CRLF, в том числе после закрывающего тега корня.
- Элемент без детей и без текста: `<Tag a="1"/>`, пробела перед `/>` нет. Элемент только с текстом пишется в одну строку: `<Tag>text</Tag>`. Смешанного содержимого нет.
- Порядок атрибутов фиксирован для каждого элемента (раздел 2), значения в двойных кавычках.
- Экранирования `& < > "` в образцах нет ни разу, поэтому правило **НЕИЗВЕСТНО**. Сериализатор экранирует стандартно; в именах деталей эти символы лучше не использовать.
- **Числа.** Целые пишутся как есть. Дробные — через `printf("%.9g")`: 9 значащих цифр, хвостовые нули отбрасываются, ведущий `0` перед точкой убирается (`.5`, `.05`, `-.5`). Экспоненты нет. Пример: `Utilization="67.933928"` — это 67.9339280 с отброшенным нулём. `"466.667"` — так значение было введено. Реализация: `xml_model.fmt_num`.
- **Значения по умолчанию опускаются:**
  - координата 0: `<Point/>`, `<Point X="1500"/>`, `<ExtMin/>`, `<BasePoint/>`, `<InsertBase/>`, `<ViewCenter/>`;
  - `NestGroups` без `Count`, если групп 0;
  - `AmountUsed` у группы, которая ни разу не использовалась;
  - `OutlineID` и `Flags` у блока, `Flags` у результата, `LayerName` у фигуры.
  - Текстовые элементы пишутся всегда, даже равные 1 (`XScale`, `YScale`, `ZoomCoeff`).
  - В `Technical` умолчания у каждого поля свои: `PwmRatio="0"` записан явно, а `GasPressure` бывает опущен.

## 2. Схемы файлов (в фигурных скобках — константы или наблюдаемые значения)

| Файл | Структура |

| `content.xml` | `PackData DocType{Model2D}` > `Header DefaultChannel{1} HandleSeed ID Version{419963393} [OrgAppName OrgAppVer]` > `<InsertBase/>`. | `Technical/content.xml` | `Technical Handle{2} [MaterialName Thickness]` > `Channels` > 16 × `Channel`. Первый: `ParamFlag{256}`. Затем `ChannelPort=1..15`, у заполненных `ParamFlag DefPwmFreqFunc DefPwmRatioFunc [OEM]` > `CamParams(~22 атрибута)` > `LeadLineParam, LayerCutParams, CornerParams, SuperCut, SlopeCutParams, Cut, SlowEndExt, SlowLeadExt, Pierce1..9`. Дальше `[MaterialName]`, `[MaterialPath]` (текст), `PwmFreqFunc/PwmRatioFunc [KnotCount] > NormalS, NormalE, Bound, Knot X Y`, `MaterialParams MaterialName NozzleSpec [Thickness]`. Это параметры резки станка. В zonty и m14 файл **одинаков байт в байт**. Для генерации копировать из шаблона. |
| `Viewports/content.xml` | Константа: `Viewports Handle{3} Active{1}` > `VPort Handle Name{1}` > `<ViewCenter/>`, `ZoomCoeff{1}`, `ViewHeight{100}`, `AspectRatio{1}`, `DisplayRect > Right{1024} Bottom{768}`. Меняется только `VPort Handle`. |
| `Layers/content.xml`, `TextStyles/content.xml` | `<Layers Handle="5"/>`, `<TextStyles Handle="6"/>` |
| `Blocks/content.xml` | `Blocks` (без атрибутов) > `Block Handle Name [OutlineID] [Flags{512}]` > `<BasePoint/>`, `Shapes Handle(=Block+1)` > `Shape Class{Line/LwPolyline/Circle} Handle`. Вложенных Insert нет. |

| `Geometry2D/content.xml` | `Geometry2D` > `MD5` |
| `Nest2D/content.xml` | `NestInfo` > `Parts Count`, `NestGroups [Count]`, `Plates Count`, `Results Count` |

Затем `Shape Class{LwPolyline} Handle [NestPlate]` (тот же Handle) и `<ExtShapes/>`. |
| `Nest2D/Parts/content.xml` | `Parts` > `NestPart Handle Name Amount AmountUsed GUID ShapeCls{Insert}` > `Insert Handle ChannelPort{1}` > `BlockName`, `XScale{1}`, `YScale{1}`; затем `Shape Class{Insert}` — точная копия `Insert`; затем `<ExtShapes/>`. |

| `Nest2D/Results/content.xml` | `NestResults` > `NestResult Index Name{Nest result} PartCount Utilization PlanCount SizeX SizeY ID` |

Элементов позиции или поворота **нет нигде**: геометрия блоков вставок уже лежит в координатах листа. |

## 4. Zip-контейнер

Все 5 файлов разобраны и собраны обратно байт в байт тремя способами (раздел 0).

| Поле | Значение во всех 183 записях |
|---|---|
| Метод сжатия | 0 = STORED (без сжатия) |
| Флаги | 0: нет data descriptor, нет бита UTF-8, нет шифрования |
| version made by | 0x003F (хост 0 = MS-DOS, спецификация 6.3) |
| version needed | 10 у файла, 20 у папки |
| Локальный заголовок | Без extra. Поля совпадают с центральным каталогом. |
| Центральный каталог, extra | 36 байт NTFS: `0A00 2000`, reserved 0, атрибут 1 размером 24, далее Mtime, Atime=0, Ctime=Mtime |
| internal/external attr | 0, в том числе у папок |
| DOS time/date | **Одно на весь архив:** местное время сохранения, секунды округлены **вверх** до чётных (2·⌈t/2⌉). Например, 14:34:05.199 → :06, 09:43:56.76 → :58. |
| NTFS Mtime | Настоящее UTC с точностью 1 мс. Растёт вдоль архива (порядок записи), разброс 1–12 мс. Сдвиг UTC→местное = +10 ч во всех 5 файлах. |
| Папки | Каждая папка — отдельный плоский блок: `Папка/` (0 байт, crc 0) и сразу её файлы. Вложенные папки самостоятельны, например `Nest2D/Results/1/` идёт раньше `Nest2D/Results/`. |
| Порядок | `info.xml`, `content.xml` всегда первые; `Geometry2D/` всегда последняя; `data.bin` раньше `content.xml`, потому что там MD5; `content.xml` раньше `thumbnail.emf`. Порядок папок похож на порядок хеш-таблицы, у m14 и m3 он совсем разный. Гипотезы MFC/Java/FNV/ELF-хешей с размерами таблиц до 2000 не подтвердились (`xml_zip_order.py`), поэтому порядок сохраняется как метаданные. |
| Хвост архива | Без зазоров; центральный каталог сразу за данными; EOCD без комментария; без zip64; имена ASCII |

**Минимальные правила для нового архива** — `xml_zip.write_new(canonical_order(storages), save_utc)`:
1. Всё STORED, флаги 0, made 0x3F, need 10/20, атрибуты 0, локальный extra пустой. В центральном каталоге NTFS-extra: Mtime = Ctime = UTC сохранения в FILETIME с точностью 1 мс, Atime = 0.
2. У всех записей одно DOS-время: местное время с секундами, округлёнными вверх до чётных. `info.xml SaveTime` — то же местное время без долей секунды и с `Z`.
3. Сначала `info.xml`, `content.xml`. Дальше папки блоками `Папка/` + файлы: `data.bin` раньше `content.xml`, `content.xml` раньше `thumbnail.emf`. Порядок папок как в m3/m8/m30, `Geometry2D` в конце.
4. Папку `Nest2D/Parts/Groups/` не создавать, если групп нет (тогда `<NestGroups/>`).

Проверено: все 5 образцов, перепакованные так (`xml_zip_newtest.py`), проходят `xml_validate.py` без единого FAIL.

## 5. thumbnail.emf (по одному на раскладку)

- Это **рисунок раскладки**: лист и все контуры всех вставок в порядке реза, одним зелёным пером RGB(0,128,0). Лист рисуется пером PS_DASHDOTDOT (style 4; поправка ревизии 11.10), контуры — PS_SOLID. Рез и гравировка выглядят одинаково.
- Заголовок EMF 1.0 размером 108 байт (`szlMicrometers` есть; описания, палитры и pixel format нет), `nHandles=5`.
- Опорный квадрат 320×320 px экрана того ПК, где сохраняли:
  - `rclFrame = (0, 0, round(32000·мм/px))` по каждой оси. Пример: 2560×1440 / 600×330 мм → 7500×7333; 1920×1080 / 598×336 мм → 9967×9956;
  - `rclBounds` = габарит нарисованных точек, то есть прямоугольник листа.
- Отображение листа в пиксели: `s = 318/max(W,H)`, `px = 160+(x−W/2)·s`, `py = 160−(y−H/2)·s`, округление к чётному.
- Записи: 21 одинаковая во всех 15 файлах записи-преамбулы. Среди них шрифт Tahoma −11 (LogFontExDv, 368 байт); в хвосте `lfFaceName` после `Tahoma\0` лежит **неинициализированная память** (40–48 байт) — воспроизвести её нельзя. Затем лист `POLYBEZIER16`, смена пера, контуры:
  - `LwPolyline` и `Circle` — один `POLYBEZIER16`. Прямой отрезок рисуется кубической кривой с опорными точками на 1/3 и 2/3. Дуга делится на ⌈угол/22.5°⌉ кусков; окружность — 16 кусков, начиная с угла старта.
  - `Line` — пара `MOVETOEX` + `LINETO`.
  - В конце `SELECT BLACK_PEN`, `NULL_BRUSH`, `SYSTEM_FONT` и `EOF`.
- **Генератор `xml_emf.generate`** повторяет оригинал:
  - все 15 миниатюр той же длины и с той же последовательностью записей;
  - 109 524 из 109 564 точек совпадают точно, остальные расходятся на ±1 px;
  - m14, m30 ×2, m3, m8 совпадают **байт в байт**, если взять из оригинала мусорные байты шрифта;
  - у 10 миниатюр zonty отличаются 4 байта: опорные точки на краях листа 1250×2500, где округляется ровно 0.5.
  - Пример: `work/xml_emf_demo.emf`.
- Нужен ли файл, чтобы CypCut открыл программу, — **неизвестно**. Скорее всего, это только картинка в списке раскладок. Безопаснее всегда записывать сгенерированную миниатюру.

## 6. Неизвестное (с риском для генератора)

| Поле или вопрос | Что известно | Риск, решение |
|---|---|---|
| Экранирование `&<>"'` в XML | ни одного случая | средний: имена деталей очищать от этих символов |
| Элементы сдвига или поворота у Insert | не встречались | низкий, если, как CypCut, класть геометрию вставки уже в координатах листа |
| Приближение окружностей и дуг в Utilization | отн. ошибка ≤1.1e-5 | низкий: число, видимо, только для показа; писать точную площадь через `%.9g` |
| Порядок записей zip | похож на хеш, не воспроизводится | низкий: читатели zip идут по центральному каталогу, у m14 и m3 порядки разные |
| `Group AmountUsed = 1+Σ` | 8/8 | низкий: свои группы совмещённого реза не создавать — их геометрия CypCut-специфична |
| `Flags=512` у блока, `Flags=64` у результата, `Selected="true"` | 512 = блок детали (.11); 64 и Selected только в m14 | низкий: 512 писать, 64 и Selected опускать |
| `ChannelPort` у вставок результата | есть в 13 раскладках из 15, нет в обеих m30 | низкий: писать `1` |
