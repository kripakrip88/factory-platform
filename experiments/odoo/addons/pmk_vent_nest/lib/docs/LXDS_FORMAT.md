# LXDS_FORMAT — сводная спецификация записи программ раскроя CypCut 6.3.907 (.lxds)

> **Пометка пакета vent_nesting (12.10.2026).** Это документ периода расшифровки: `work/`, `samples/` и скрипты, на
> которые он ссылается, — рабочий стенд вне пакета. Код из него в пакете — `vent_nesting/cypcut/`. **Проверено на
> станке 12.10.2026 (CypCut 6.3.907.11):** собранные программы открываются, листы разной длины в одном файле
> читаются — риск §15 №1 снят, пакет пишет все длины бухты в один файл.

Документ для того, кто пишет генератор. Каждое правило помечено:

- **[П]** — проверено кодом на всех 5 образцах (zonty, m14, m30, m3_grpsh, m8_plates);
- **[Ш]** — копировать из шаблона, с обоснованием;
- **[Н]** — НЕИЗВЕСТНО, пишем наблюдаемое значение, риск в разделе 15.

Главное доказательство согласованности всех правил между файлами — эталонный стенд `work/spec_rebuild.py`.
Он разбирает настоящий файл в модель высокого уровня и собирает его заново ТОЛЬКО по правилам этого документа.
Все длины, адреса, MD5, DataAddr/GeoAddr, OutlineID, Flags, количества, PartCount, PlanCount, размеры,
HandleSeed, info.xml, content.xml и zip при этом вычисляются, а не копируются. Итог: **5 из 5 архивов совпали
байт в байт**, в том числе zonty (943 041 Б, 0 разных байт). Подробности в разделе 16.

Целевая версия: **CypCut 6.3.907.11** (на ней сохранены zonty, m14 и m30 на заводском ПК). Версия 6.3.907.8
(m3, m8) отличается в мелочах, они отмечены.

## 1. Что генератор получает на вход (модель высокого уровня)

| Сущность | Поля |
|---|---|
| Деталь *i* | имя (уникальное, без `& < > " '`); контуры в координатах детали: внешний — замкнутая `LwPolyline` (вершины x, y, bulge); внутренние — `Circle` (cx, cy, r) и замкнутые `LwPolyline`. Все на технологическом слое 1 |
| Лист *j* | W = 1250, L = Li (мм) |
| Раскладка *k* | лист *j*; PlateAmount (сколько одинаковых листов); список размещений: (деталь *i*, θ ∈ {0, 90, 180, 270}, dx, dy). Порядок размещений = порядок резки деталей |

Всё остальное (хэндлы, GUID, количества, адреса, MD5, миниатюры) вычисляется по правилам ниже.

**Система координат [П]:** начало в левом нижнем углу листа, X вдоль ширины 1250, Y вдоль длины, Y вверх.
Доказано по миниатюрам в 15 из 15 раскладок.

## 2. Состав архива и zip [П]

Архив — zip без сжатия. Набор записей при K раскладках и без групп:

```
info.xml, content.xml                                    (в корне, всегда первыми)
TextStyles/content.xml   Technical/content.xml   Layers/content.xml   Viewports/content.xml
Nest2D/content.xml   Nest2D/Parts/content.xml   Nest2D/Plates/content.xml   Nest2D/Results/content.xml
Nest2D/Results/<k>/content.xml + Nest2D/Results/<k>/thumbnail.emf     (k = 1..K)
Blocks/content.xml
Shapes2D/data.bin + Shapes2D/content.xml
Geometry2D/data.bin + Geometry2D/content.xml             (папка Geometry2D всегда последняя)
```

Папку `Nest2D/Parts/Groups/` **не создавать**: без групп совмещённого реза её нет (m14).

**Правила zip.** Все пять образцов собраны заново байт в байт при таких правилах:

| Поле | Значение |
|---|---|
| метод | 0 (STORED); флаги 0; без data descriptor, без UTF-8-бита, без шифрования |
| version made by / needed | 0x003F / 10 для файла, 20 для папки |
| локальный заголовок | без extra; поля совпадают с центральным каталогом |
| центральный extra | 36 байт NTFS: `0A00 2000`, `00000000`, `0100 1800`, Mtime, Atime = 0, Ctime = Mtime (FILETIME UTC, усечённый до 1 мс) |
| internal / external attr | 0 (и у папок) |
| DOS time/date | одно на весь архив: **местное** время сохранения, секунды округлены ВВЕРХ до чётных: 2·⌈t/2⌉ |
| Mtime по записям | не убывает вдоль архива; у CypCut шаг 0–4 мс |
| папки | запись `Папка/` (0 байт, crc 0), сразу за ней файлы этой папки. Вложенная папка — отдельный плоский блок |
| внутри папки | `data.bin` раньше `content.xml`, `content.xml` раньше `thumbnail.emf` |
| хвост | без зазоров, центральный каталог сразу за данными, EOCD без комментария, без zip64, имена ASCII |

Порядок папок у CypCut похож на порядок в хеш-таблице, и воспроизвести его не удалось. Читатели zip идут по
центральному каталогу, а у m14 и m3 порядки совсем разные, и оба файла открываются. Поэтому писать порядок
из m3/m8/m30 [Ш]: `''`, TextStyles, Technical, Layers, Nest2D, Nest2D/Results/1..K, Viewports, Shapes2D,
Nest2D/Parts, Blocks, Nest2D/Plates, Nest2D/Results, Geometry2D. Это готовые функции
`xml_zip.canonical_order()` + `xml_zip.write_new()`.
*Поправка ревизии 11.10:* при K ≥ 2 этот порядок не совпадает ни с одним образцом — в m30 Results/2/ стоит
после Viewports/. На чтение не влияет (каталог zip), но «взят из m30» — неточно.

## 3. Общий формат XML [П] (84 из 84 файлов собраны байт в байт)

- Первая строка `<?xml version="1.0" encoding="utf-8"?>` + CRLF. BOM нет. UTF-8, кириллица пишется как есть.
- Один элемент на строку, отступ — TAB на каждый уровень, конец строки CRLF, в том числе после корня.
- Пустой элемент пишется как `<T a="1"/>`, без пробела перед `/>`. Элемент с текстом — одной строкой: `<T>текст</T>`.
- **Порядок атрибутов фиксирован.** Он указан в схемах ниже.
- **Числа:** целые пишутся как есть. Дробные — `'%.9g'` без ведущего нуля (`.5`, `-.5`), экспоненты нет.
  Реализация — `xml_model.fmt_num`. Всего в образцах 27 378 чисел, но дробных среди них только 131, и девять
  значащих цифр у 26 из них. Правило подтверждается, однако держится в основном на Utilization.
- Значения по умолчанию опускаются: `<Point/>` для (0,0), `<Point X="1250"/>`, `<ExtMin/>`, `<BasePoint/>`,
  `<InsertBase/>`, `<ViewCenter/>`. Текстовые элементы пишутся всегда (`<XScale>1</XScale>`).
- Экранирование `& < > " '` в образцах не встретилось ни разу **[Н]**. Генератор должен очищать от этих
  символов имена деталей.

## 4. Хэндлы [П]

**Одно общее пространство.** Хэндлы делят разделы (2, 3, 4, 5, 6, 12), Block и Block/Shapes, контуры
(Shapes2D), NestPart и его Insert, NestPlate и его полилиния, NestResult и его фигуры, а также VPort. Повторов
нет. Хэндлы объектов больше 1000. Дыры допустимы: у CypCut они остаются от удалённых объектов, в m30 есть
дыра на 380 хэндлов.

**Связи, которые должны выполняться:**

| Правило | Где проверено |
|---|---|
| `Shapes Handle` блока = Block + 1 | все блоки, 5/5 |
| контуры блока раскладки: H+2 … H+1+n подряд | 723/723 |
| контуры блока детали: H+2 … подряд (6.3.907.11) | zonty, m14, m30 |
| Insert детали = NestPart − 1 (6.3.907.11) | 33/33. В 6.3.907.8 = NestPart + 9 |
| полилиния листа = NestPlate + 2, хэндл NestPlate + 1 не используется | 5/5 |
| копия листа в раскладке = R + 3, вставки R + 4, R + 5, … подряд; R + 1 и R + 2 не используются | 15/15 |
| `HandleSeed` = наибольший хэндл, VPort не в счёт | 5/5 |
| VPort = HandleSeed + 1 | в файлах, сохранённых один раз. В пересохранённых (m30, m8) VPort меньше |
| блоки в Blocks/content.xml идут по возрастанию хэндла | 5/5 |

**Алгоритм распределения для генератора.** Он повторяет схему 6.3.907.11 и проверен в
`spec_rebuild.fresh_identity`: 5 файлов собраны заново, `xml_validate` выдал 0 FAIL.

```
h = 1001
для каждой детали i:     Block=h, Shapes=h+1, контуры h+2..h+1+n;          h += 2+n
для каждой детали i:     Insert=h, NestPart=h+1, h+2..h+5 не использовать;  h += 6
для каждого листа j:     NestPlate=h, (h+1 пусто), полилиния=h+2;            h += 3
для каждой раскладки k, для каждого размещения m (в порядке раскладок и размещений):
                         Block=h, Shapes=h+1, контуры h+2..h+1+n;           h += 2+n
для каждой раскладки k:  NestResult=R=h, (R+1, R+2 пусто), копия листа=R+3, вставки R+4..R+3+m;  h = R+4+m
HandleSeed = h-1;  VPort = h
```

## 5. GUID, имена и время

| Что | Значение |
|---|---|
| GUID | везде случайный v4 в ВЕРХНЕМ регистре, в фигурных скобках: `{8-4-4-4-12}` [П: 1607 вхождений, 835 разных, все v4 и в верхнем регистре] |
| Header ID | новый GUID; больше нигде в архиве не встречается |
| имя блока детали | `{GUID}` [П: так названы 8 из 29 блоков деталей с Flags=512 в zonty; остальные — `Деталь1<число>`] |
| имя блока размещения | `{GUID}`, свой на каждое размещение [П: 732 вставки, повторов нет] |
| ID раскладки | новый GUID; тот же в `Results/content.xml` и `Results/k/content.xml` |
| `Portions ActiveModelID` | ID **последней** раскладки [П 5/5] |
| время сохранения | местное время завода (UTC+10). Из него получаются: `SaveTime` = местное, секунды отброшены, суффикс `Z` (так делает CypCut, хотя время не UTC); DOS-время zip (местное, ⌈до чётных секунд⌉); NTFS Mtime = UTC [П 5/5] |

## 6. Корневые файлы

**info.xml**

```
<?xml version="1.0" encoding="utf-8"?>
<PackData>
	<DocVersion Major="1"/>
	<Application AppName="CypCut" AppVer="6.3.907.11"/>
	<SavedBy User="…" UserLangID="1049" Computer="…" SysLangID="1049" SaveTime="2026-10-11T11:02:03Z"/>
</PackData>
```

User и Computer — имена пользователя и ПК **[Н]**: как CypCut их использует, неизвестно. В образцах это
`pmkpa`/`DESKTOP-DTOSM4M` и `XE`/`XE6642`. Генератор пишет свои честные значения.

**content.xml**

```
<PackData DocType="Model2D">
	<Header DefaultChannel="1" HandleSeed="{seed}" ID="{GUID}" Version="419963393">
		<InsertBase/>
	</Header>
	<Technical Handle="2"/>
	<Viewports Handle="3"/>
	<Layers Handle="5"/>
	<TextStyles Handle="6"/>
	<Blocks Handle="4"/>
	<Portions Handle="12" ActiveModelID="{ID последней раскладки}"/>
</PackData>
```

- `Version=419963393` (0x19082201) — константа [П 5/5].
- `OrgAppName`/`OrgAppVer` есть только в пересохранённых документах. **Не писать.**

**Technical/content.xml [Ш]** — байт в байт копия из **zonty.lxds** (3689 Б, md5
`36d662a29938d3cc8b2d48f2ef0deddc`). Это параметры резки станка. В zonty (0,65 мм) и m14 (14 мм) файл
одинаков байт в байт, то есть он не зависит от задания: оператор задаёт режимы на станке. Внутри есть
строки вида `CutGap="0,2"` с запятой — их не трогать.

**Layers/content.xml**: `<Layers Handle="5"/>`. **TextStyles/content.xml**: `<TextStyles Handle="6"/>` [П 5/5, побайтно одинаковы].

**Viewports/content.xml** — константа [П], меняется только `VPort Handle`:

```
<Viewports Handle="3" Active="1">
	<VPort Handle="{HandleSeed+1}" Name="1">
		<ViewCenter/>
		<ZoomCoeff>1</ZoomCoeff>
		<ViewHeight>100</ViewHeight>
		<AspectRatio>1</AspectRatio>
		<DisplayRect>
			<Right>1024</Right>
			<Bottom>768</Bottom>
		</DisplayRect>
	</VPort>
</Viewports>
```

## 7. Blocks/content.xml [П]

```
<Blocks>
	<Block Handle="H" Name="{GUID}" OutlineID="{хэндл внешнего контура}" Flags="512">   ← блок детали
		<BasePoint/>
		<Shapes Handle="H+1">
			<Shape Class="Circle" Handle="H+2"/>        ← внутренние контуры (любой порядок)
			<Shape Class="LwPolyline" Handle="…"/>
			<Shape Class="LwPolyline" Handle="{OutlineID}"/>   ← внешний контур ПОСЛЕДНИМ
		</Shapes>
	</Block>
	<Block Handle="H2" Name="{GUID}" OutlineID="…">       ← блок размещения: без Flags
	…
</Blocks>
```

- Сначала идут блоки деталей, затем блоки размещений, все по возрастанию хэндла.
- `Flags="512"` есть ровно у блоков, на которые ссылается NestPart, и только в 6.3.907.11. Выведенное значение
  совпало с записанным во всех блоках, включая 705 блоков m14.
- `OutlineID` — хэндл замкнутого контура слоя 1 с наибольшей площадью. Он же последний контур блока.
  Совпадение 758 из 761 блоков деталей и размещений. **Исключение [Н]:** m30 «Деталь1» и две её копии. У них
  замкнутый внешний LwPolyline на слое 1, но OutlineID не записан. В этих блоках 12 Line гравировки
  (flag64 = 1) упираются концами во внешний контур. Причина неизвестна. Объяснение темы xml («внешний контур
  из Line») не подтвердилось. Генератор пишет OutlineID всегда.
- Порядок резки внутри блока: внешний контур последний [П 761/761 блоков деталей и размещений NestPart]. Гравировка идёт перед резом. Порядок
  отверстий CypCut строит своим оптимизатором, алгоритм неизвестен **[Н]**. Генератор задаёт порядок сам.

## 8. Геометрия размещения [П]

У вставки в раскладке **нет** ни позиции, ни угла (732 из 732): блок размещения уже лежит в координатах листа.

```
R(0)(x,y)=(x,y);  R(90)(x,y)=(-y,x);  R(180)(x,y)=(-x,-y);  R(270)(x,y)=(y,-x)    (θ против часовой, Y вверх)
p' = R(θ)·p + (dx, dy)        — для вершин LwPolyline, центров Circle, концов Line
```

- Полилиния: порядок вершин, начальная вершина и направление обхода **сохраняются** (159/159). Bulge копируется
  без изменений, зеркала нет. Ориентация не нормализуется: у внешних контуров встречаются и CCW, и CW
  (58 и 31 из 89).
- Окружность: r без изменений; `a0' = (a0 + θ) mod 2π` (216/216); у детали a0 = π/4.
- Отрезок: p1 → p1', p2 → p2' (24/24).
- Состав и атрибуты контуров совпадают с деталью: слой, outer, LayerName. Порядок внутренних контуров
  задаёт генератор, внешний — последним.
- Зеркальные варианты деталей (A/B/C/D у вентзонтов) задаются отдельными деталями. Зеркальное размещение не
  встречалось ни разу (0 из 723).
- Биты координат CypCut с нашими не совпадут: у CypCut свой порядок арифметики. В zonty побитно совпали 47 из
  373 контуров, но все 373 — в пределах 1e-9 мм. Это нормально (раздел 16, AT-1).

## 9. Двоичный контейнер BCMP (Geometry2D/data.bin и Shapes2D/data.bin) [П]

```
0x0000  "BCMP"
0x0004  u32  полный размер файла
0x0008  u32  1
0x000C  нули до 0x1000
0x1000  объект, объект, …   (подряд; каждый дополнен нулями до кратности 8; после последнего ничего нет)
```

**Объект:** `d1d1d1d1 | u32 0 | u32 L (от d1 до конца d0d0d0d0, без выравнивания) | u32 0 | Str "TGks"+класс | … | d0d0d0d0`, затем 0–7 нулевых байт до кратности 8.

**Подзапись:** `c1c1c1c1 | u32 версия | u32 длина (от c1 до конца c0c0c0c0) | u32 0 | Str имя | данные | c0c0c0c0`.

**Строка (Str):** `53 00 | u16 n | n байт ASCII | нули`, так что всё поле занимает округлённое вверх до 8
число байт: `ceil8(4+n)`. Все строки, которые пишет генератор, стоят по адресам, кратным 8 (проверено на
23 868 строках). Там правила «от начала поля» и «по абсолютному адресу» совпадают — подробности о
расхождении в разделе 15.

**Порядок объектов** (одинаков в обоих bin и в Shapes2D/content.xml) [П 5/5]:

1. контуры всех блоков по порядку Blocks/content.xml, внутри блока в порядке `<Shape>`;
2. полилинии листов в порядке Nest2D/Plates;
3. копии листов из раскладок 1..K.

**Адреса:** `addr[0] = 0x1000`, `addr[i+1] = addr[i] + ceil8(L[i])`. GeoAddr i-го элемента — адрес i-го объекта
Geometry2D, DataAddr — адрес i-го объекта Shapes2D.

## 10. Geometry2D [П 3978/3978 объектов собраны с нуля байт в байт]

Хэндлов в этом файле нет: связь с контуром задаёт только GeoAddr. Версия подзаписи всегда 1.
Смещения ниже — от начала объекта.

| Класс | Размер (L / с выравниванием) | Поля |
|---|---|---|
| Line | 104 / 104 | 0x10 Str "TGksLine"; 0x20 c1, ver 1, len 0x44; 0x30 Str "Line"; 0x38 u32 `0x00020010`, 0x3C f64 x1, 0x44 y1; 0x4C u32 `0x00020010`, 0x50 x2, 0x58 y2; 0x60 c0; 0x64 d0 |
| Circle | 120 / 120 | 0x10 Str "TGksCircle"; 0x20 c1, ver 1, len 0x54; 0x30 Str "Circle"; 0x40 u32 `0x00020010`; 0x44 cx, 0x4C cy, 0x54 r; 0x5C u32 **0**; 0x60 f64 a0 (рад); 0x68 8 байт **0**; 0x70 c0; 0x74 d0 |
| LwPolyline | 100+32n / 104+32n | 0x10 Str "TGksLwPolyline"; 0x28 c1, ver 1, len 0x38+32n; 0x38 Str "LwPolyline"; 0x48 f64 start_param = **0**; 0x50 u32 flag; 0x54 u32 n; 0x58+32k: {u32 k+1, f64 x, f64 y, f64 bulge, u32 **0**}; затем u32 **0**, c0, d0 |

- flag полилинии: **1** — замкнутая. Генератор пишет 1 у всех контуров. Бит со значением 2 — **[Н]**, бит со значением 4 — только у открытых цепочек совмещённого реза.
- Замыкающая вершина не повторяется (1110/1110). Bulge = tg(угол/4), > 0 — дуга против часовой (как в DXF). Нулевой bulge писать как +0.0.
- start_param = 0: рез начинается в вершине 0. Ненулевые значения встречаются только в слитых контурах групп.
- Окружность в блоке детали: a0 = π/4 (`18 2d 44 54 fb 21 e9 3f`). В блоке размещения: (π/4 + θ) mod 2π.
- Полилиния листа: flag 1, 4 вершины (0,0), (W,0), (W,L), (0,L), все bulge 0.

**Geometry2D/content.xml:** `<?xml …?>` CRLF `<Geometry2D>` CRLF TAB `<MD5>{MD5(data.bin), 32 hex, ВЕРХНИЙ регистр}</MD5>` CRLF `</Geometry2D>` CRLF.

## 11. Shapes2D [П 3978/3978 записей собраны с нуля байт в байт]

Запись атрибутов контура (без LeadParam): LwPolyline 252 байта (256 с выравниванием), Circle и Line 244 (248).
Смещения указаны для LwPolyline. У Circle и Line строка класса на 8 байт короче, поэтому все смещения после
неё меньше на 8.

```
0x00 d1d1d1d1 | 0 | L | 0
0x10 Str "TGksLwPolyline"                                  (Circle/Line: "TGksCircle"/"TGksLine", 16 байт)
0x28 c1 | ver 1 | len 40 | 0 | Str "Object" | u32 HANDLE | c0
0x50 c1 | ver 6 | len 88 | 0 | Str "Shape"  | 13×u32: [LAYER,0,0,0,0, COEDGE,0,0, FLAG64,0,0,0,0] | c0
0xA8 u32 0     (число LeadParam)
0xAC u32 0     (длина второго списка, всегда 0)
0xB0 c1 | ver 2 | len 72 | 0 | Str "Curve"  | 9×u32: [OUTER,0,1,0,0,0,0,0,6] | c0
0xF8 d0d0d0d0  + 4 нулевых байта выравнивания
```

| Поле | Контур детали и размещения | Полилиния листа и её копии |
|---|---|---|
| HANDLE | хэндл контура (= XML Handle) | хэндл полилинии |
| LAYER | **1** (рез; 2 — гравировка) | **0** |
| COEDGE | 0. Это = (LwPolyline ∧ незамкнутая ∧ слой 1), 3978/3978 | 0 |
| FLAG64 | **0** [Н] | 0 |
| OUTER | **1** у внешнего контура (OutlineID), 0 у отверстий | 0 |
| LeadParam | не писать (как во всём zonty) | — |

**Shapes2D/content.xml**, в порядке раздела 9, последним идёт MD5:

```
<Shapes2D>
	<Circle Handle="…" LayerName="0" DataAddr="…" GeoAddr="…"/>
	<LwPolyline Handle="…" LayerName="0" DataAddr="…" GeoAddr="…"/>
	…
	<LwPolyline Handle="{полилиния листа}" DataAddr="…" GeoAddr="…"/>      ← у листов LayerName НЕТ
	<MD5>{MD5(Shapes2D/data.bin) ВЕРХНИЙ регистр}</MD5>
</Shapes2D>
```

`LayerName` — имя слоя CAD, к технологическому слою отношения не имеет. Генератор пишет `"0"` у всех
контуров деталей и размещений. В zonty `"0"` стоит у всех 1285 контуров деталей и их копий. Без LayerName
там только листы и 7 контуров, которые CypCut сам построил в блоках групп совмещённого реза.

## 13. Utilization [П для прямых отрезков; приближённо для дуг]

```
площадь(деталь) = S(наибольший замкнутый контур) − Σ S(все прочие замкнутые контуры: отверстия, пазы и замкнутая гравировка)
U = 100 · Σ_{размещения на листе} площадь(деталь) / (W · L)          → fmt_num('%.9g')
```

- Площадь берётся из блока детали. PlateAmount в формулу не входит. Замкнутые контуры — Circle и
  LwPolyline с flag&1; Line и открытые полилинии не учитываются. Дуги считаются точно: площадь многоугольника
  плюс круговые сегменты со знаком bulge.
- Где только отрезки (m30 ×2, m3, m8), совпадение строки точное, 4/4.
- Где есть окружности и дуги, CypCut их как-то многоугольно приближает. Относительное расхождение до
  1.08e-6 у zonty (0/10 совпадений строки) и 1.08e-5 у m14. Правило подобрать не удалось: проверены вписанные
  N-угольники с допуском по хорде, шагу и длине дуги и одинаковые N **[Н]**. Генератор пишет точную площадь.
  Число, по всей видимости, служит только для показа.

**Таблица идентичности для AT-0** — это ровно то, чего нет в модели высокого уровня и что нельзя вывести:

- хэндлы всех объектов, VPort, Header ID, OrgApp;
- GUID деталей, листа и групп, ID раскладок, имена блоков;
- LayerName каждого контура, FLAG64, байты LeadParam;
- флаги `Flags=64`, `Selected`, наличие `ChannelPort`;
- исключение OutlineID (m30);
- группы и их блоки (непрозрачные), устаревшие блоки;
- биты геометрии размещений и порядок контуров;
- строки Utilization для деталей с дугами;
- порядок записей zip и Mtime каждой записи;
- `device`, `mm` и хвост шрифта EMF;
- Technical, User, Computer, AppVer.

**Что при свежей генерации (AT-2) в принципе НЕ может совпасть с zonty:**

| Байты | Причина |
|---|---|
| все `Handle`, `HandleSeed`, VPort, OutlineID, хэндл в подзаписи Object, следовательно MD5 Shapes2D | история правок CypCut оставляет дыры (в zonty 1801..2426) |
| все GUID, имена блоков, ActiveModelID | случайные v4 |
| SaveTime, DOS-время, Mtime, CRC и порядок записей zip | время и хеш-порядок |
| младшие биты координат, r и a0 в блоках размещений, а с ними MD5 Geometry2D | своя арифметика CypCut, ≤ 1e-9 мм |
| Utilization при дугах и окружностях | неизвестное приближение, ≤ 1.1e-5 |
| порядок отверстий в блоках размещений | оптимизатор CypCut (в AT-0/1 подаётся на вход) |
| блоки групп совмещённого реза, LeadParam | генератор их не делает |
| хвост имени шрифта в EMF | неинициализированная память |

**Что совпадает и при свежей генерации** (проверено на AT-2 zonty): Technical, Layers, TextStyles,
Nest2D/content.xml, info.xml при том же времени, все 10 thumbnail.emf при той же геометрии с точностью 1e-9 и
тех же device и mm.

**Первая проверка на станке** (её не заменить офлайн-доказательством): открыть в CypCut 6.3.907.11
- `spec_demo.lxds` (минимальный);
- `spec_L2_zonty.lxds` (полный, со свежими хэндлами);
- затем файл генератора.

Смотреть: открывается ли файл, видны ли раскладки и миниатюры, совпадает ли Utilization в списке, строятся ли
подводы, правильна ли сторона компенсации у внешнего контура и отверстий. Только после этого — файл с двумя
размерами листа (неизвестное №1).
