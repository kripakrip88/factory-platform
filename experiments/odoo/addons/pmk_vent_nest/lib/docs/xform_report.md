# xform: как размещённая в раскладке деталь связана с определением детали (CypCut 6.3.907, .lxds)

Проверка: `python3 -I work/xform_check.py samples [--json work/xform_check.json]`. Скрипт читает 5 образцов
как zip в памяти, использует только стандартную библиотеку и работает около 2,5 с. Все числа ниже выдаёт он
(полный вывод сохранён в `work/xform_check_out.txt`).

## 0. Главное для генератора

* **Insert в раскладке не хранит ни позиции, ни угла.** У всех 732 вставок внутри только `BlockName`,
  `XScale=1` и `YScale=1`. Геометрия «запечена» в координаты листа в **отдельном блоке раскладки** (имя — GUID):
  у каждой вставки свой блок, ни одна вставка не делит блок с другой и не ссылается на блок детали
  (5 из 5 файлов).
* Блок раскладки получается из блока детали **жёстким преобразованием** `x' = R(θ)·x + d` **без зеркала**.
  Наблюдались только углы θ ∈ {0°, 90°, 180°, 270°} (поворот против часовой стрелки при оси Y вверх).
  Максимальная невязка по всем точкам составляет 9,4·10⁻¹³ мм, то есть это ошибка округления double.
* Порядок и номера вершин, стартовая вершина и направление обхода **сохраняются**, ориентация **не
  нормализуется**. Bulge копируется побитно, включая `-0.0`. У окружности угол старта меняется по правилу
  `a0' = (a0 + θ) mod 2π`, у отрезка сохраняется направление p1 → p2.
* Внешний контур (OutlineID) всегда **последний** в блоке, внутренние контуры (и гравировка) идут перед ним.
  CypCut переупорядочивает отверстия своим алгоритмом оптимизации пути. Алгоритм не установлен, и для
  генерации это не нужно.
* Файл без групп совместного реза — обычный случай: в m14 704 вставки NestPart, групп 0, `<NestGroups/>`
  пустой, папки `Parts/Groups` нет.
* Лист: в каждой раскладке своя копия прямоугольника `LwPolyline (0,0)-(W,0)-(W,L)-(0,L)` с атрибутом
  `NestPlate=<handle листа>`. Начало координат в левом нижнем углу, Y направлен вверх (подтверждено
  эскизом EMF на 15 из 15 раскладок).

## 1. Байт-в-байт: Geometry2D/data.bin и Shapes2D/data.bin

Модель: заголовок `BCMP`, затем u32 размер (пересчитывается), u32 версия, нули до 0x1000. Дальше идут объекты
`d1d1d1d1 u32 a, u32 len (пересчитывается), u32 c, имя класса`. За ними следуют подзаписи
`c1c1c1c1 u32 тип, u32 len (пересчитывается), u32 z, имя, payload, c0c0c0c0` и сырые байты между ними,
в конце `d0d0d0d0` и нули до кратности 8. Строки имеют вид `'S' 00 u16 длина + байты` и дополняются нулями
до абсолютного адреса, кратного 8. Геометрия разбирается в типизированные поля и затем **собирается
обратно из этих полей**.

| образец | Geometry2D, байт | идентичен | разных байт | Shapes2D, байт | идентичен | разных байт | объектов | типизир. записей, расхождений |
|---|---|---|---|---|---|---|---|---|
| m14 | 173 760 | да | 0 | 489 456 | да | 0 | 1412 | 1412 / 0 |
| m30 | 204 048 | да | 0 | 301 552 | да | 0 | 1178 | 1178 / 0 |
| m3_grpsh | 19 368 | да | 0 | 21 120 | да | 0 | 65 | 65 / 0 |
| m8_plates | 8 832 | да | 0 | 9 504 | да | 0 | 20 | 20 / 0 |
| zonty | 233 784 | да | 0 | 331 168 | да | 0 | 1303 | 1303 / 0 |

После пересчёта длин адреса всех объектов совпали с исходными (`moved=0`), то есть совпали и GeoAddr/DataAddr.
Подзапись «Object» в Shapes2D хранит Handle из XML (3978 из 3978). **XML этот скрипт байт-в-байт не
собирает** (это другая тема).

| поле | значения |

| LwPolyline: номер вершины | всегда k+1 (1110 из 1110) |
| LwPolyline: 4 байта после вершины / после последней | всегда нули (5314 / 1110) |

## 2. Цепочка ссылок и сопоставление

`Results/N/content.xml` Insert `NestPart=h` → `Parts/content.xml` NestPart h → `Insert/BlockName` (блок детали)
→ `Blocks` → контуры. Вставка раскладки ссылается на свой блок (GUID) с новыми контурами. Сопоставление
устроено так: для внешнего контура перебираются все сдвиги старта, оба направления и зеркало, затем
по методу Кабша подбирается поворот; все контуры детали сопоставляются с контурами раскладки по сигнатуре
и ближайшей точке привязки. Решение принимается, только если **все** контуры совпали в пределах 1·10⁻⁶ мм:
центры и радиусы окружностей, полный набор вершин полилиний, концы отрезков.

| | m14 | m30 | zonty | всего |
|---|---|---|---|---|
| вставок NestPart | 704 | 2 | 17 | 723 |
| угол θ | 0 (*) | 0×2 | 90×11, 180×3, 270×2, 0×1 | только 0/90/180/270 |
| зеркало | нет | нет | нет | **0 из 723** |
| невязка, мм (макс.) | 9·10⁻¹³ | | | **9,4·10⁻¹³** |

(*) Шайба m14 — это две концентрические окружности, поэтому поворот по геометрии не наблюдаем, взят только
сдвиг. Угол старта при этом остался π/4 (704 из 704), что по правилу `a0' = a0 + θ` означает θ = 0.

**Неоднозначность и как она снята.** У всех 19 деталей с полилиниями геометрия симметрична, поэтому
находится 2–4 точных решения: (θ, без зеркала), (θ, с зеркалом), а иногда ещё и θ+180°. В каждом из 19
случаев **ровно одно** решение переводит каждую сохранённую точку в её же номер: вершина k → вершина k,
p1 → p1 у отрезка, точка старта окружности → точка старта. Это решение во всех 19 случаях **без зеркала**.

## 4. Порядок резки

* Внутри блока NestPart **внешний контур последний** (721 из 721). Гравировка (слой 2) идёт **перед**
  резом (2 из 2 блоков m30 с гравировкой).
* Порядок отверстий — это не порядок в детали (19 из 19), не сортировка по X или Y (17 из 17) и не жадный
  «ближайший старт»: так устроены лишь 281 из 356 шагов. Коэффициент Кендалла |τ| вдоль одной оси равен
  0,53–0,95, то есть путь «метёт» вдоль одной оси с локальными перестановками. Для одной детали порядок
  одинаков при всех повторных размещениях, в том числе при 90° и 270° (4 из 4). Значит, его считают
  один раз на деталь. **Точный алгоритм неизвестен** (внутренняя сортировка CypCut).
* Порядок вставок в раскладке (то есть порядок деталей): X по возрастанию в 8 из 11 раскладок с
  несколькими вставками, Y по возрастанию 1, X по убыванию 1, прочее 1.

## 5. Группы совместного реза (NestGroup)

* Описание группы лежит в `Nest2D/Parts/Groups/content.xml`: `NestGroup Handle Name="CoedgePart" Amount
  [AmountUsed] GUID`, внутри `<Object Handle=NestPart>` с повторами (повтор = число копий детали). Блока
  группы в Parts **нет**: геометрия группы существует только как **один блок раскладки** на вставку
  (`NestGroup=h`), у этого блока нет ни OutlineID, ни Flags.
* Внутри блока группы отверстия и гравировка всех деталей — точные жёсткие копии (88 деталей с внутренними
  контурами найдены, 0 зеркальных). Внешние контуры перестроены: 4 целые; 71 заменён 1–3 открытыми
  цепочками, лежащими на контуре (общие кромки выброшены); у 15 своих цепочек нет: их кромки входят в
  «слитые» замкнутые контуры (14 таких контуров в группах m30/zonty, все их вершины лежат на контурах найденных
  деталей группы). В m3 и m8 (6.3.907.8, прямоугольники без отверстий)
  детали в группе не опознаются: там один замкнутый внешний контур плюс открытые цепочки.
* Экономия длины реза на группу: 1,0–16,7 м (например, zonty r4: 16,25 → 13,73 м). У открытых цепочек
  флаг 4 или 6, в Shape слово 5 = 1. У слитых контуров бывает ненулевой double перед флагом.
* Вывод: **группы не генерировать**. Без них раскладка состоит из независимых блоков-копий, то есть из
  обычных вставок NestPart, как в m14. В m30, m3 и m8 остались блоки, на которые никто не ссылается
  (4, 6 и 3 штуки соответственно) — следы прежних групп. В m14 и zonty таких нет.

**Несколько размеров листа (вывод из схемы, в образцах не встречалось).** Раскладка выбирает лист по ссылке
`NestPlate=P` и хранит свои SizeX/SizeY/ExtMax. Поэтому лист другого размера — это второй элемент
`<NestPlate Handle=P2 … ShapeCls="LwPolyline">` в `Plates/content.xml` со своей `LwPolyline Handle=P2+2
NestPlate=P2` и точками (0,0),(1250,0),(1250,L2),(0,L2) плюс записи этого хэндла в Shapes2D и Geometry2D.
Ещё нужно `<Plates Count="2"/>` в `Nest2D/content.xml`, а в каждой раскладке на нём —
`NestPlate=P2`, SizeX=1250, SizeY=L2, ExtMax=(1250,L2); `Amount`/`AmountUsed` у каждого листа равны сумме
PlateAmount его раскладок. **Не проверено**: файл с двумя листами нужно открыть в CypCut. Запасной вариант —
отдельный .lxds на каждый размер листа.

## 7. Система координат

Начало координат (0,0) в левом нижнем углу листа, X вдоль первого размера (1250 — ширина), Y вдоль второго
(2500 — длина), **Y направлен вверх**. Доказательство по эскизу `thumbnail.emf` каждой раскладки: первая
POLYBEZIER16 — прямоугольник листа, его первая точка (0,0) рисуется в левом нижнем пикселе. Все прочие
нарисованные точки совпадают с геометрией листа в гипотезе «Y вверх» на 96,6–100 %, в гипотезе «Y вниз» — на
0–86 %, и так в 15 из 15 раскладок. X всегда горизонтален, в том числе у m8 с листом 1500×575.

## 8. Рецепт размещения детали (то, что подтверждено)

1. Блок детали: `Flags="512"`, `OutlineID` = последний контур, в Curve слово 0 = 1 только у внешнего
   контура, `a0` окружностей = π/4, флаг замкнутых полилиний 1 (или как в детали).
2. Для каждого размещения (θ ∈ {0, 90, 180, 270}, d): новый блок `Name={GUID}`, Handle H, Shapes H+1,
   контуры H+2… в том же составе. Каждая точка преобразуется как `R(θ)p + d`; bulge, флаг, 8 байт перед
   флагом и номера вершин копируются; `a0 += θ (mod 2π)`; у отрезков p1 → p1. Запись Shapes2D копируется,
   «Object» получает новый хэндл. Внешний контур последний, `OutlineID` указывает на него.
3. Вставка: `<Shape Class="Insert" Handle ChannelPort="1" NestPart=…><BlockName>{GUID}</BlockName><XScale>1</XScale><YScale>1</YScale></Shape>`.
4. Лист раскладки: копия записи NestPlate с хэндлом R+3, вставки с R+4.

## 9. Неизвестное и риски для записи новых файлов

| неизвестно | наблюдение | риск |
|---|---|---|
| файл с несколькими NestPlate разных размеров | не встречался | **высокий**: проверить в CypCut; запасной вариант — один .lxds на размер |
| углы кроме 0/90/180/270 и зеркало при размещении | не встречались | низкий, если ограничиться кратными 90°; зеркальные детали задавать отдельной деталью (как A/B/C/D у вентзонтов) |

| Shape слово 8 (1 в детали m30 → 0 в раскладке), Curve слово 0 = «внешний» | выведено из данных | низкий |
| double перед флагом LwPolyline (2..13) | только в слитых контурах групп | нет (групп не делаем) |
| LeadParam (подводы) | в m14 добавлены в раскладке, в zonty их нет | низкий: можно не писать |
| thumbnail.emf, XML байт-в-байт | вне этой темы | см. соответствующие отчёты |
