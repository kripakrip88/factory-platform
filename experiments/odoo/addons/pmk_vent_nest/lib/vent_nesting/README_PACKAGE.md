# Раскрой вентзонтов + программы лазера CypCut — пакет для ERP

Версия пакета **1.0.0** (12.10.2026). Что делает:

1. Берёт заказ вентзонтов — DXF генератора зонтов (тот, что уже стоит в ERP) и количество зонтов по размерам.
2. Раскладывает детали на листы шириной 1250 мм в двух вариантах:
   - **склад** — только листы 2500;
   - **бухта** — длина листа кратна 50 мм, до 3000 (лист раскатывает поставщик, цена за погонный метр та же).
3. Показывает инженеру, сколько килограммов металла стоит каждый вариант, сколько экономит бухта, и картинку раскроя.
4. По запросу перебирает свес торцов 150…125 мм. Меньше 150 — только по решению инженера.
5. **После выбора инженера** собирает готовые программы CypCut (`.lxds`): по одной на материал заказа. Оператор
   открывает программу на станке, ставит свои параметры резки и подводы, режет.

Проверено на станке 12.10.2026:
- программы открываются в CypCut 6.3.907.11;
- листы разной длины в одном файле читаются;
- порядок резки исправлен по замечанию Антона — проверить новый файл на станке ещё предстоит.

Встраивает соседний ERP-чат. Перенос в репозиторий — по правилам `CLAUDE.md`: сначала план и подтверждение
Антона, ветка `develop`.

## Решения Антона (не менять без него)

| Правило | Значение |
|---|---|
| Лист | ширина 1250; станок принимает до 3000 |
| Склад | только 2500 |
| Бухта | длина кратна 50 мм, до 3000; цена за погонный метр та же, раскатывает поставщик |
| Зазор между деталями и отступ от края | **задаются перед раскладкой**. По умолчанию 2 и 2 мм — так инженер режет 0,65 и 14 мм. Зазор 0,5…50, отступ 0…100. Нулевой зазор не нужен: общий рез CypCut сводит детали сам |
| Поворот | 0/90/180/270; **зеркалить нельзя** (окрашенный лист) |
| Свес торцов | 150 по умолчанию; можно ужимать до 125 (СНиП), **решает инженер при проверке** |
| Сначала решение, потом файл | `plan()` только показывает; `build_lxds()` собирает **выбранный** вариант |
| Система наблюдает, а не блокирует | рекомендация «бухта выгоднее» — подсказка, а не запрет |

## Быстрый старт

Зависимости: Python 3.9–3.12, **numpy** и **Pillow** — обе обязательны (Pillow рисует детали в растр для самого
раскроя; без него `import vent_nesting.api` сразу даст ImportError с понятным текстом). **openpyxl** — для чтения
`*_сборка.xlsx`. Всё это есть в Odoo: в контейнере `odoo-app` Python 3.12, numpy, Pillow 10.2, openpyxl 3.1 и
шрифты DejaVu с кириллицей.

```bash
# все команды — из корня пакета (папки с README.md), иначе Python не найдёт vent_nesting
python3 tests/check_golden.py --quick                            # эталоны без раскроя большого заказа, ~40 с
python3 tests/check_golden.py                                    # все эталоны, ~2 мин (Mac M-серии)
python3 tests/check_faults.py                                    # инварианты и внедрённые неисправности, ~1 мин
python3 tests/check_faults.py --full                             # + пик памяти ВЗ-00002 и полная сетка генератора
python3 -m vent_nesting.cli plan tests/data/ВЗ-00002.zip --out /tmp/вз2           # варианты: картинка, JSON, DXF листов
python3 -m vent_nesting.cli sves tests/data/ВЗ-00002.zip --out /tmp/вз2           # перебор свеса
python3 -m vent_nesting.cli lxds tests/data/ВЗ-00002.zip --source coil --out /tmp/вз2   # программы CypCut
# в ВЗ-00003.zip нет ведомости — количество явно: --qty 750x4000=1 --qty 1000x1200=1
```

## Программный интерфейс (`vent_nesting.api`)

Принимает байты, возвращает словари и байты. На диск ничего не пишет, кроме временных папок, которые сам удаляет
(если процесс убит по таймауту — см. «Как встроить», п. 2). **Любая ошибка входа или параметров — `api.VentNestingError`**
(подкласс ValueError) с русским текстом, его можно показать пользователю как есть.

```python
from vent_nesting import api

order = api.order_from_zip(zip_bytes)          # «Скачать всё»: vsh_ШxД_tТОЛЩ_ЦВЕТ.dxf в корне + *_сборка.xlsx
order = api.order_from_zip(zip_bytes, qty={...})               # без ведомости — количество обязательно
# или напрямую: DXF генератора + количество НА КАЖДЫЙ DXF (ключ — имя DXF; «ШxД» — только если размер в заказе один)
order = api.order_from_dxf([("vsh_500x1000_t0.65_RAL8017.dxf", dxf_bytes), ...],
                           {"vsh_500x1000_t0.65_RAL8017.dxf": 11, "vsh_750x750_t0.65_RAL8017.dxf": 1})
order.hoods()                                  # что понято: [{dxf, size, color, thickness, qty, parts_per_hood}] — сверить с заказом

p = api.plan(order, gap=2, edge=2)             # варианты; ~25 с на заказ в 50 деталей
for m in p["materials"]:                       # по материалу; m["key"] — ключ вида «ral8017|0.65»
    m["stock"]["kg"], m["coil"]["kg"], m["coil"]["lengths"], m["saving"]["kg"], m["recommend"]   # 'coil' | 'stock'
p["png"]                                       # картинка раскроя (байты PNG)

rows = api.sves_table(order)                   # по запросу: свес 150…125 × склад/бухта (≈ plan × 6)

files = api.build_lxds(order, "coil", gap=2, edge=2, sves=None, material=None, name="ВЗ-00002")
for f in files:                                # по материалу
    f["filename"], f["bytes"], f["ok"], f["checks"], f["layouts"], f["key"]
```

**Что проверяется на входе** (иначе VentNestingError):
- архив читается, в нём ≤ 500 файлов; DXF ≤ 5 МБ (генератор даёт 9–20 КБ), ведомость ≤ 5 МБ — размер меряется при
  распаковке, а не по заголовку архива (его можно подделать); повреждённая или зашифрованная запись — ошибка; DXF
  берутся из корня архива, пропущенные (в подпапках, с чужим именем) перечисляются в ошибке;
- сборочная ведомость: колонки ищутся **по заголовкам**, читаются оба макета калькулятора — до v1.61 («Зонт» =
  «вш 500х1000») и с v1.61 («Шахта, мм» = «4000 × 750», длина × ширина; «Зонт, мм» — габарит); объединённые ячейки,
  итог «ИТОГО», строки после него; цвет «RAL 8017 Шоколад» = «RAL8017», пустой — оцинковка; не больше 5000 строк;
- имя строго `vsh_ШxД_tТОЛЩ_ЦВЕТ.dxf` (толщина обязательна, `.DXF` тоже годится);
- один и тот же зонт (размер + цвет + толщина) не передан дважды;
- количество — на каждый DXF, целое 1…1000; неизвестный ключ, неоднозначный размер (один размер в двух цветах,
  а ключ «ШxД»), пропущенный DXF — ошибка. Из ведомости — по ключу «размер + цвет + толщина», колонки
  «Зонт / Цвет / Металл, мм / Зонтов, шт»;
- **каждый DXF сверяется с генератором зонтов** (`hood_sves.py` при свесе 150 = генератор ERP): число деталей,
  габариты, площади, отверстия по диаметрам, пазы. Обрезанный, испорченный, переименованный («500x1000» с
  содержимым 1000x3000), с лишним вырезом — не пройдёт. Сверяется и колонка ведомости «Деталей на зонт»;
- зазор 0,5…50, отступ 0…100, свес 125…150 (числа, не строки; `None` — значение по умолчанию); вариант
  `stock`/`coil`; материал — ключ из `plan()` («ral8017|0.65», точное совпадение, с толщиной) или название цвета
  (все толщины этого цвета);
- деталь, которая не помещается на лист при заданном отступе, — понятная ошибка с её размером;
- создание заказа безопасно из нескольких потоков (разбор DXF не трогает общий вывод процесса).

**Вариант, который невозможен, не роняет план.** Например, тело 2500 мм (500x2200) не лезет на склад 2500 с
отступом 2 мм: `stock` = `{"error": "…"}`, бухта считается, `recommend` = `coil`, на картинке «ТОЛЬКО БУХТА».
В `sves_table` невозможный свес или вариант — строка с `error`, остальная таблица сохраняется.

| Функция | Что возвращает |
|---|---|
| `plan(order, gap, edge, sves=None, png=True, sheet_dxf=False)` | `{gap_mm, edge_mm, sves, hoods, materials, png, dxf}`. В `materials[i]`: `key`, `color`, `thickness`, `items`, `stock` и `coil` (`sheets`, `lengths_mm`, `lengths` — текстом «2550 × 6 + 2400», `length_m`, `m2`, `kg`, `util_pct`, `gap_min_mm`, `sheet_parts`, `placements`, `check_errors`), `saving` (`m`, `m2`, `kg`, `pct`), `recommend` |
| `sves_table(order, gap, edge, sves_list)` | строки `{sves, key, color, thickness, source, sheets, lengths, kg, util_pct}` |
| `build_lxds(order, source, gap, edge, sves, material, name)` | список `{filename, key, bytes, ok, checks, layouts}`. Считает только выбранный вариант. В `layouts` — `{no, length_mm, sheets, sheet_nos}`: соответствие «раскладка CypCut № ← листы раскроя» (номера расходятся: одинаковые листы слиты в одну раскладку «× N»). Имя файла очищено от `/ \ : * ? " < > \|` и `..` |

**Файл с `ok=False` оператору не отдавать.** Это ошибка сборки: записать в журнал и сообщить разработчику.
`ok=True` = программа цела, соответствует раскрою **и заказу**. Каждая программа после сборки проверяется сама,
15 проверок в `checks` (если их нет — `ok=False`):
- целостность формата CypCut (100–260 правил); независимая пересборка двоичных данных; «разбор → сборка даёт тот
  же файл»;
- независимый расшифровщик читает программу и сверяет:
  - детали всего — с раскроем; **по каждому зонту — с заказом** (зонтов × деталей на зонт у генератора);
  - **площадь каждого контура каждой детали** — с раскроем (ловит ошибку сборщика: дугу не той стороны);
  - **контуры каждой детали — с исходным DXF** независимо от сцепки контуров: каждая дуга проходит через середину
    дуги DXF, отверстия — те же центры и диаметры (ловит ошибку самой сцепки, потерянное отверстие);
  - **детали по каждому зонту — с заказом** с учётом свеса (свес меньше 150 может убрать панель: 500x4650 при 145 —
    4 детали на зонт вместо 5);
  - **внешний контур каждой детали режется последним**;
  - листы и их размеры, длину реза, загрузку, зазор и отступ от края.

**Детерминизм.** Один и тот же заказ с теми же параметрами всегда даёт те же листы. Меняются только время
сохранения и случайные идентификаторы внутри `.lxds`, а они построены от содержания заказа и тоже повторяются.

## Как встроить в Odoo (предложение для плана)

1. **Где взять вход.** Генератор зонтов уже есть в ERP: калькулятор вентзонтов `pmk_calc`, v1.59.0. Для
   каждого размера заказа он строит DXF, количество есть в расчёте. Передавать `order_from_dxf(...)` эти DXF
   и количество. Или `order_from_zip`, если удобнее брать «Скачать всё».
2. **Кнопка «Раскрой» → фоновое задание**: queue или cron с флагом. Держать экран открытым в ожидании нельзя.
   Время (Mac M-серии; сервер медленнее — замерить в контейнере):
   | Заказ | plan | build_lxds (один вариант) | sves_table (6 свесов) |
   |---|---|---|---|
   | ВЗ-00003, 10 деталей | 4 с | 2–4 с | ~25 с |
   | ВЗ-00002, 48 деталей | 25 с | 5–20 с | ~2,5 мин |
   | 90–150 деталей (30 зонтов) | 55–80 с | ~55 с | ~6–8 мин |
   - Таймаут ставить с запасом ×3 от замера на сервере.
   - Запускать **в отдельном процессе** (subprocess / воркер): у раскроя модульные глобальные настройки и кэши,
     внутри процесса вызовы сериализуются блокировкой (параллельности нет).
   - Дочернему процессу давать свою временную папку (`TMPDIR`): если его убьют по таймауту, удалить её целиком —
     иначе останутся папки `vent_nesting_*` с копиями DXF.
   - Память и скорость — см. раздел «Задачи для ERP-чата», п. 1: у контейнера Odoo предел 2,5 ГБ.
3. **Показать инженеру** таблицу «склад / бухта» по материалам: листы, длины, кг, экономия, картинка `png`.
   - Поля **зазор** и **отступ от края** (по умолчанию 2 и 2).
   - Кнопка «Перебрать свес» → `sves_table`.
4. **Инженер выбирает** склад или бухту и, если нужно, свес. Кнопка «Собрать программы» → `build_lxds`.
   - Файлы прикладываются к заказу вложениями.
   - Рядом — таблица `layouts` (раскладка CypCut № ← листы раскроя).
   - Если выбрана бухта — длины листов для заказа поставщику: `coil.lengths`.
5. **Хранить вместе с файлом**: версию пакета (`vent_nesting.__version__`), `gap`, `edge`, `sves`, `source`. Тот
   же вход даст ту же раскладку.
6. **Свес меньше 150** собирается копией генератора `hood_sves.py`: это `vent_hood.py` из калькулятора с параметром
   свеса; на свесе 150 она совпадает с ним 51/51. Если в ERP-генератор добавят параметр свеса (отдельная правка,
   прогнать его 51 тест), `Order.items(sves)` можно перевести на него.

## Задачи для ERP-чата (решить при встраивании)

1. **Память и скорость.** Замеры на заказе ВЗ-00002 (48 деталей), Mac, Python 3.9:
   | Потолок кэша спектров `nest._GCAP` | Пик памяти на раскрой | Время раскроя |
   |---|---|---|
   | без потолка (как было) | 0,6–1,1 ГБ (1,1 — раскрой + сборка до освобождения законченных листов) | 21 с |
   | 256 МБ | 0,65 ГБ (раскрой + сборка) | 21 с |
   | **64 МБ — стоит в пакете** | **~0,33 ГБ** | **25 с** |
   - Память уходит на кэш спектров Фурье масок деталей (по форме × повороту × длине листа) и на временные массивы
     поиска места. Кэш — LRU с потолком `nest._GCAP` (байты), его можно менять.
   - На сервере: у контейнера `odoo-app` **жёсткий предел 2,5 ГБ**, сам Odoo занимает ~0,9 ГБ (замер 12.10).
     Свободной памяти у машины ~8 ГБ, ядер 6.
   - Варианты (выбрать по замеру на сервере):
     - поднять предел памяти `odoo-app`. Антон: «если скорость можно увеличить за счёт параметров сервера — не
       проблема»;
     - или запускать раскрой в отдельном контейнере / процессе-воркере со своим пределом;
     - потолок кэша поднять до 256 МБ — минус 15% времени, если памяти хватает;
     - одновременно — не больше 1–2 раскроев: очередь заданий.
   - Скорость можно поднять и параллельностью: `best_pack` перебирает 4 порядка × 3 длины заготовки независимо,
     это можно раскидать по процессам (результат тот же — берётся лучший по тем же правилам).
2. **Pillow на сервере 10.2, у меня 11.3.** Раскрой рисует детали в растр через Pillow. Эталоны должны совпасть —
   проверить тестом в контейнере. Если разойдутся — прислать вывод.
3. **Параметр свеса в ERP-генераторе** (если инженеру нужен свес меньше 150 в ERP): сейчас его даёт копия
   `hood_sves.py`. Либо оставить копию, либо добавить параметр в генератор калькулятора и прогнать его 51 тест.
4. **Поля в форме**: зазор, отступ от края (по умолчанию 2 и 2), выбор склад/бухта, свес (по запросу) — и
   сохранять их вместе с программами.

## Что внутри

| Файл | Что делает |
|---|---|
| `vent_nesting/api.py` | интерфейс для ERP: проверки входа, сверка DXF с генератором, количество, VentNestingError |
| `nest.py` | раскладка и отчёт: растр 2 мм + FFT, повороты 0/90/180/270, перебор порядков и заготовок; доводка точной геометрией до зазора ровно; варианты склад/бухта; картинка; DXF листов |
| `parts.py`, `dxfread.py` | разбор DXF генератора: детали, отверстия, пазы |
| `contours.py` | рёбра DXF → полилинии с дугами (bulge) и окружности, как их хранит CypCut |
| `model.py` | раскрой → модель программы. Детали = зонт + все контуры. Одинаковые листы → раскладка «× N». Имена «вш 500х1000A» — как при импорте DXF в CypCut |
| `lxds_write.py` | модель → `.lxds`. Порядок резки: отверстия маршрутом (ближайший сосед + 2-opt + перестановки) от конца предыдущей детали к точке врезки внешнего контура, внешний контур последним. Самопроверки |
| `cypcut/` | расшифрованный формат CypCut. Эталонный сборщик пересобирает 5 заводских программ **байт в байт**. Параметры резки — шаблон из заводской программы (`technical_template.xml`) |
| `lxds_reader.py` | независимый расшифровщик программ: им проверяется каждая собранная программа |
| `hood_sves.py` | копия генератора зонтов с параметром свеса |
| `cli.py` | командная строка: `plan`, `sves`, `lxds` — поверх api, с теми же проверками |
| `geom.py` | точные расстояния между контурами (для проверок) |
| `docs/` | описание формата `.lxds` (`LXDS_FORMAT.md`) и отчёты расшифровки. Это **история расшифровки**: упомянутые там `work/`, `samples/` и скрипты — рабочий стенд вне пакета, команды из них здесь не запускаются |
| `tests/` | автотесты по эталонам, заказы ВЗ-00002 и ВЗ-00003 |

## Ограничения (честно)

- Раскрой проверен на деталях **вентзонтов** из генератора. Другие DXF он, скорее всего, разложит (разбор общий),
  но на них не проверялся.
- Повороты только 0/90/180/270. Свободный поворот, сетки для одинаковых деталей и подготовка под общий рез есть
  во **второй версии раскроя**. Она пока не в пакете: результат зависит от загрузки компьютера, и она не
  подключена к сборке `.lxds`. Придёт следующей версией пакета.
- **Общий рез в файл не пишется.** Инженер применяет его в CypCut сам. Запись групп общего реза — в новой версии
  сборки `.lxds`.
- Подводов и параметров резки в программе нет: их ставят операторы на станке, так решил Антон.
- Порядок отверстий внутри детали — свой, у CypCut он другой. Оператор может пересортировать.

## После переноса в Odoo

1. Запустить в окружении Odoo (контейнер) `python3 tests/check_golden.py` — должно быть 12 из 12 — и
   `python3 tests/check_faults.py --full` — 31 из 31.
   - Раскрой детерминирован, поэтому эталоны должны совпасть точно.
   - Если не совпали только на сервере, вероятная причина — другая версия Pillow (растр деталей). Прислать вывод
     теста, не менять эталоны.
2. Вход недоверенный: zip и DXF приходят от пользователя.
   - Пакет читает zip в памяти, берёт только файлы из корня с именем генератора и пишет их во временную папку под
     своим именем. Ничего из архива не исполняет.
   - Исходные файлы никогда не перезаписываются.
