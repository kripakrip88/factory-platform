# Odoo 19 Community — модель данных (data model) и способы расширения

Разбор локального клона `scratchpad/odoo` (версия подтверждена:
`odoo/release.py:15` → `version_info = (19, 0, 0, FINAL, 0, '')`, HEAD `73cccecd`),
официальной документации `scratchpad/odoo-docs/content/` и российской локализации
RuOdoo `scratchpad/ruodoo` (48 модулей).

Все пути — от корня соответствующего клона. Для сопоставимости выводы сверены с
разбором Carbon ERP в `experiments/carbon/analysis/`.

---

## 0. Краткий вывод (TL;DR)

1. **Пересчёт «тонна ↔ погонный метр ↔ штука» для одной номенклатуры Odoo умеет
   штатно, без доработки кода.** В Odoo 19 единицы измерения (units of measure)
   перестроены в **дерево коэффициентов**: `uom.uom` c полями `relative_uom_id`
   (родитель) и `relative_factor` (`addons/uom/models/uom_uom.py:36-44`).
   Достаточно завести для профиля единицу «пог. м 20Б1» с родителем «кг» и
   коэффициентом = погонная масса — и весь стек (закупка, склад, спецификация,
   производство, счёт) считает пересчёты сам. У Carbon такого механизма нет как
   класса (`experiments/carbon/analysis/10-единицы-измерения.md:231-240`) —
   это **самое крупное преимущество Odoo по данной теме**.
2. **Но точность по умолчанию для завода не годится.** `decimal.precision`
   «Product Unit» = **2 знака** (`addons/uom/data/uom_data.xml:5-8`), а
   `_compute_quantity` по умолчанию округляет **вверх** (`rounding_method='UP'`,
   `addons/uom/models/uom_uom.py:152`). 5 пог. м балки = 0,1065 т превратятся в
   **0,11 т** — приписка 3,5 кг на строку. Лечится записью «Product Unit» = 4 и
   «Stock Weight» = 3 в справочнике точности; DDL менять не надо (колонки —
   `numeric` без фиксированной шкалы, `odoo/orm/fields_numeric.py:126-133`).
3. **Отдельная грабля Odoo 19: округление стало ГЛОБАЛЬНЫМ для всех единиц.**
   `uom.uom.rounding` теперь не хранимое поле, а compute от той же «Product Unit»
   (`addons/uom/models/uom_uom.py:62-67`). Правила «штуки только целые, метры до
   0,001» больше нет — в 17-й версии оно было. Это надо закладывать в процессы.
4. **Своё поле и свой экран без Studio делаются модулем-расширением** —
   ~10 файлов, чистый Python + XML, ставится `-i имя_модуля`. Рабочий минимальный
   пример написан и синтаксически проверен, лежит в
   `scratchpad/pmk_metal/` (полный текст — раздел 4.3). Именно так устроена и сама
   российская локализация: `ruodoo/l10n_ru_upd_xml/models/uom_uom.py:5-7` добавляет
   в `uom.uom` поле «Код ОКЕИ» семью строками кода.
5. **Импорт 665 позиций проката — работа на часы, не на дни.** Штатный импорт
   понимает CSV/XLS/XLSX/ODS (`addons/base_import/models/base_import.py:47-49`),
   колонка `id` (External ID) делает повторный импорт **обновлением**, а не
   дублированием (`applications/essentials/export_import_data.rst:435-441`).
   Батч по умолчанию 2000 строк (`addons/base_import/static/src/import_model.js:111-113`)
   — весь справочник входит в один проход. Есть режим «Тест» с откатом
   (`base_import.py:1461,1495`).
6. **Права и мультикомпанийность — зрелые и декларативные**: CRUD-матрица в CSV
   (`ir.model.access`), построчные правила `ir.rule` с доменами, группы с
   наследованием `implied_ids`, компании с деревом филиалов
   (`res.company.parent_id/parent_path`, `odoo/addons/base/models/res_company.py:51-56`).
   Склады и локации — полноценное дерево с семью типами локаций
   (`addons/stock/models/stock_location.py:32-47`).

## 1. Архитектура: ORM, модели, наследование, устройство модуля

### 1.1. Где что лежит физически

| Слой | Путь | Что это |
|---|---|---|
| Ядро ORM | `odoo/orm/` | `models.py` (BaseModel, ~5000 строк), `fields_numeric.py`, `fields_relational.py`, `table_objects.py`, `domains.py` |
| Технические модели | `odoo/addons/base/models/` | `ir_model.py`, `ir_rule.py`, `res_groups.py`, `res_company.py`, `res_users.py`, `decimal_precision.py` |
| Прикладные модули | `addons/` | **638 каталогов** — `mrp`, `stock`, `sale`, `purchase`, `account`, `crm`, `project`, `hr`, `maintenance`, `repair`, `uom`, `product`, `base_import`… |
| Утилиты | `odoo/tools/` | `float_utils.py`, `sql.py`, `config.py` |

СУБД — PostgreSQL. В отличие от Carbon, где тяжёлая логика вынесена в SQL-функции
и Deno-функции (`experiments/carbon/analysis/00-обзор.md`, раздел 2.2), **у Odoo
вся бизнес-логика в Python-слое ORM**, а в БД лежат только таблицы, индексы и
CHECK-ограничения. Практическое следствие: писать доработки может Python-разработчик
без компетенций в PL/pgSQL, а «писать напрямую в таблицы» одинаково запрещено в
обеих системах.

### 1.2. Три вида моделей

```python
models.Model          # обычная, с таблицей в БД
models.TransientModel # «мастера» (wizards), записи чистятся автоматически
models.AbstractModel  # миксин без таблицы (mail.thread, mail.activity.mixin)
```

Пример TransientModel из реального кода — `addons/mrp/wizard/change_production_qty_views.xml`
+ соответствующий Python в `addons/mrp/wizard/`.

### 1.3. Три механизма наследования — все три живые, все три в стандартных модулях

**(а) `_inherit` — расширение существующей модели (самый частый случай).**
Новых таблиц нет, поля добавляются в ту же таблицу:

```python
# addons/mrp/models/product.py:22-32
class ProductTemplate(models.Model):
    _inherit = "product.template"

    bom_line_ids = fields.One2many('mrp.bom.line', 'product_tmpl_id', 'BoM Components')
    bom_ids = fields.One2many('mrp.bom', 'product_tmpl_id', 'Bill of Materials')
    bom_count = fields.Integer('# Bill of Material', compute='_compute_bom_count', compute_sudo=False)
    mrp_product_qty = fields.Float('Manufactured', digits='Product Unit', compute='_compute_mrp_product_qty')
```

Тут же виден второй приём — **переопределение метода через `super()`**:
`addons/mrp/models/product.py:73-78` перекрывает `write()` у `product.template`,
чтобы архивация товара архивировала и его спецификации.

**(б) `_inherits` — делегированное наследование (composition).** Дочерняя модель
хранит ссылку на родительскую и «прозрачно» отдаёт её поля:

```python
# addons/product/models/product_product.py:16-20
class ProductProduct(models.Model):
    _name = 'product.product'
    _description = "Product Variant"
    _inherits = {'product.template': 'product_tmpl_id'}
    _inherit = ['mail.thread', 'mail.activity.mixin']   # ещё и миксины
```

То есть `product.product` (вариант) физически отдельная таблица, но поля шаблона
(`name`, `uom_id`, `list_price`) читаются и пишутся напрямую. Приём редкий —
во всех 638 модулях `addons/` он встречается **10 раз** (проверено grep'ом,
не считая тестовых модулей): `addons/mail/models/mail_mail.py:31`,
`addons/mail/models/mail_alias_mixin.py:16`, `addons/hr/models/hr_employee.py:45`,
`addons/account/models/account_bank_statement_line.py:13`,
`addons/account/wizard/setup_wizards.py:96`,
`addons/website/models/website_page.py:26`,
`addons/website/models/website_controller_page.py:9`,
`addons/product/models/product_document.py:11`,
`addons/sale_pdf_quote_builder/models/quotation_document.py:15` и разобранный выше
`product.product`.

**(в) Прототипное наследование** — `_inherit = 'старая.модель'` **вместе с новым
`_name`**: создаётся новая модель-копия. В прикладных модулях почти не используется.

**Миксины** — `mail.thread` (чат/история), `mail.activity.mixin` (задачи),
`portal.mixin`, `rating.mixin`. Их подключение — одна строка `_inherit`, как выше.
Документация: `developer/reference/backend/mixins.rst`.

### 1.4. Устройство модуля — на реальном примере `addons/mrp`

```
addons/mrp/
  __init__.py          # from . import models / wizard / report / controller + хуки
  __manifest__.py      # метаданные и список файлов данных
  models/              # 24 файла: mrp_bom.py, mrp_production.py, mrp_workorder.py,
                       #   mrp_workcenter.py, mrp_routing.py, mrp_unbuild.py,
                       #   product.py, stock_move.py, stock_rule.py, …
  views/               # XML: формы, списки, канбаны, меню
  security/            # mrp_security.xml (группы + ir.rule) + ir.model.access.csv
  data/                # mrp_data.xml, mail_templates.xml, digest_data.xml
  report/              # QWeb-шаблоны PDF + модели отчётов
  wizard/              # TransientModel + их формы
  static/src/          # JS/SCSS/XML фронтенда (OWL)
  i18n/                # .po переводы (есть ru.po)
  tests/               # unit-тесты
```

`__manifest__.py` (`addons/mrp/__manifest__.py`) — ключи, которые реально нужны:

| Ключ | Значение в mrp | Смысл |
|---|---|---|
| `name`, `version`, `category`, `summary` | `'Manufacturing'`, `'2.0'`, `'Supply Chain/Manufacturing'` | метаданные |
| `depends` | `['product', 'stock', 'resource']` | зависимости; ставятся автоматически |
| `data` | 40 XML/CSV | **порядок важен**: security → wizard → views → report |
| `demo` | `['data/mrp_demo.xml']` | демо-данные (не ставятся с `--without-demo`) |
| `application` | `True` | модуль показывается как «приложение» |
| `pre_init_hook` / `post_init_hook` / `uninstall_hook` | `_pre_init_mrp` / `_create_warehouse_data` / `uninstall_hook` | python-хуки жизненного цикла, тела — в `addons/mrp/__init__.py:10-38` |
| `assets` | `{'web.assets_backend': ['mrp/static/src/**/*']}` | сборка фронтенда |
| `license` | `'LGPL-3'` | **все addons Community — LGPL-3** |

Про лицензию отдельно, потому что у Carbon это была юридическая развилка
(`experiments/carbon/analysis/00-обзор.md`, раздел 1: коммерческая лицензия на
`packages/ee`, где лежат MRP и планировщик). **У Odoo Community вся папка
`addons/` — LGPL-3.** Проверено сплошной проверкой всех 638 манифестов: ни один
не остался без ключа `license`, и ни в одном не встречается лицензия, отличная от
`LGPL-3` (`grep -h "'license'" addons/*/__manifest__.py | grep -v LGPL-3` → пусто).
LGPL позволяет держать свои доработки закрытыми — в отличие от AGPL.
Enterprise-модули — отдельная платная подписка, и их исходников тут нет.

### 1.5. Хуки жизненного цикла — реальный пример

```python
# addons/mrp/__init__.py:10-19
def _pre_init_mrp(env):
    """ Allow installing MRP in databases with large stock.move table (>1M records) """
    env.cr.execute("""ALTER TABLE "stock_move" ADD COLUMN "unit_factor" double precision NOT NULL DEFAULT 1;""")
    env.cr.execute("""ALTER TABLE "stock_move" ADD COLUMN "manual_consumption" boolean NOT NULL DEFAULT FALSE;""")
```

Это точка, куда мы будем вешать инициализацию справочника единиц под прокат
(создание единиц «пог. м <профиль>» пачкой при установке нашего модуля).

### 1.6. Данные и внешние идентификаторы (External ID)

Любая запись в XML модуля создаётся через `<record id="..." model="...">` и
получает **внешний идентификатор** вида `модуль.id`, хранимый в `ir.model.data`.
Пример — вся `addons/uom/data/uom_data.xml`; ссылка на запись — `ref="uom.product_uom_kgm"`
(`addons/uom/data/uom_data.xml:98`), из Python — `self.env.ref('uom.product_uom_kgm')`.

Атрибут `noupdate="1"` на `<odoo>` или `<data>` (см. `addons/uom/data/uom_data.xml:2`)
означает «при обновлении модуля не перезаписывать, пользователь мог править».
Это тот же механизм, который потом используется при импорте CSV (раздел 6).

## 2. Единицы измерения — критичный раздел для завода

### 2.1. Что изменилось в Odoo 19 (важно, старые статьи врут)

**Модели `uom.category` больше нет.** В 17-й версии единицы группировались в
категории, и пересчёт был возможен только внутри категории. В 19-й версии —
дерево:

```python
# addons/uom/models/uom_uom.py:17-44
class UomUom(models.Model):
    _name = 'uom.uom'
    _description = 'Product Unit of Measure'
    _parent_name = 'relative_uom_id'
    _parent_store = True
    _order = 'sequence, relative_uom_id, id'

    name            = fields.Char('Unit Name', required=True, translate=True)
    relative_factor = fields.Float('Contains', default=1.0, digits=0, required=True)
    rounding        = fields.Float('Rounding Precision', compute="_compute_rounding")
    active          = fields.Boolean('Active', default=True)
    relative_uom_id = fields.Many2one('uom.uom', 'Reference Unit', ondelete='cascade')
    related_uom_ids = fields.One2many('uom.uom', 'relative_uom_id', 'Related UoMs')
    factor          = fields.Float('Absolute Quantity', digits=0, compute='_compute_factor',
                                   recursive=True, store=True)
    parent_path     = fields.Char(index=True)
```

Что здесь важно построчно:

- `relative_factor` объявлен с `digits=0` — это **NUMERIC без ограничения
  точности** в PostgreSQL (см. комментарий в коде на строке 37 и механику в
  `odoo/orm/fields_numeric.py:126-133`). Коэффициент 21,3456 кг/м не потеряет
  разрядов.
- `factor` — **абсолютный** коэффициент к корню дерева, считается рекурсивно:
  `addons/uom/models/uom_uom.py:69-75` → `factor = relative_factor * relative_uom_id.factor`.
- `_parent_store = True` + `parent_path` — материализованный путь, по нему
  проверяется «единицы из одного дерева» (`_has_common_reference`,
  `addons/uom/models/uom_uom.py:218-230`).
- Ограничение: `CHECK (relative_factor != 0)` (`:46-49`) и Python-констрейнт
  «у не-корневой единицы должен быть родитель» (`:97-101`).
- Базовые единицы из `addons/uom/data/uom_data.xml` **защищены от удаления**
  (`_unlink_except_master_data`, `:105-112`; список исключений — `:24-32`).

### 2.2. Что поставляется в коробке

`addons/uom/data/uom_data.xml` — **30 единиц** (из них 16 поставляются архивными,
`active="False"`), семь независимых деревьев:

| Дерево (корень) | Записи | Строки |
|---|---|---|
| Штуки (`Units`) | Units → Pack of 6 (×6), Dozens (×12, архивная) | `:12-26` |
| Время (`Hours`) | Hours → Days (×8), Minutes (×0.0166667) | `:29-42` |
| Длина (`mm`) | mm → cm (×10) → m (×100) → km (×1000); архивные in/ft/yd/mi | `:45-65`, `:122-145` |
| Площадь (`m²`) | m²; архивный ft² | `:68-71`, `:148-153` |
| Объём (`ml`) | ml → L (×1000) → m³ (×1000, архивный); архивные fl oz/qt/gal/in³/ft³ | `:74-88`, `:156-185` |
| **Масса (`g`)** | **g → kg (×1000) → Ton (×1000)**; архивные oz/lb | `:91-104`, `:107-119` |
| Энергия (`KWH`) | KWH | `:188-191` |

Метрика — первичная, имперские единицы поставляются **архивными**
(`active=False`). Это уже лучше, чем в Carbon, где новая компания всегда получала
`useMetric = false` из-за регрессии (`experiments/carbon/analysis/10-единицы-измерения.md`,
раздел 2). Тонна в Odoo есть из коробки, ни мм, ни м², ни м³ добавлять не надо
(в Carbon их не было вообще — `10-единицы-измерения.md:227`).

**Чего нет:** «пог. м», «лист», «прут», «комплект», «т/м», кодов ОКЕИ (см. 2.6).

### 2.3. Как считается пересчёт

```python
# addons/uom/models/uom_uom.py:147-176
def _compute_quantity(self, qty, to_unit, round=True, rounding_method='UP', raise_if_failure=True):
    ...
    amount = qty * self.factor
    if to_unit:
        amount = amount / to_unit.factor
    if to_unit and round:
        amount = tools.float_round(amount, precision_rounding=to_unit.rounding,
                                   rounding_method=rounding_method)
    return amount
```

Чистое `qty * factor_from / factor_to`. **Проверки «общий корень» внутри
`_compute_quantity` нет** — она вынесена в `_has_common_reference` и вызывается
точечно (всего 9 мест: `addons/sale_timesheet/…`, `addons/account_edi_ubl_cii/models/account_edi_common.py:976,1410`,
`addons/stock/wizard/product_label_layout.py:60`, `addons/stock/wizard/stock_lot_label_layout.py:33`).

Цена пересчитывается зеркально — `_compute_price` (`:196-203`):
`price * factor_to / factor_from`.

**На документах выбор единицы ограничен списком, а не деревом.** Везде один и тот
же приём — вычисляемое поле `allowed_uom_ids` и домен по нему:

| Документ | Поле и логика | Файл:строка |
|---|---|---|
| Строка продажи | `uom_id \| uom_ids` | `addons/sale/models/sale_order_line.py:136-138,539-542` |
| Строка закупки | `uom_id \| uom_ids \| seller_ids.product_uom_id` | `addons/purchase/models/purchase_order_line.py:42-43,411-417` |
| Складское перемещение | `uom_id \| uom_ids \| seller_ids.product_uom_id` | `addons/stock/models/stock_move.py:202-205` |
| Заказ на производство | `uom_id \| uom_ids \| bom_ids.product_uom_id` | `addons/mrp/models/mrp_production.py:116-118,430-433` |
| Строка счёта | `uom_id \| uom_ids` | `addons/account/models/account_move_line.py:375-379,882-885` |

Источник этого списка — сам товар:

```python
# addons/product/models/product_template.py:118-123
uom_id  = fields.Many2one('uom.uom', 'Unit', default=_get_default_uom_id, required=True,
                          help="Default unit of measure used for all stock operations.")
uom_ids = fields.Many2many('uom.uom', string='Packagings',
                           help="Additional packagings for this product which can be used for sales",
                           domain="[('id', '!=', uom_id)]")
```

Обратите внимание: в Odoo 19 **упаковки (packagings) слились с единицами** —
отдельной модели `product.packaging` больше нет, «упаковка» = единица из `uom_ids`.
Штрихкод на упаковку вынесен в отдельную связку `product.uom`
(`addons/product/models/product_uom.py:8-18`: `uom_id` + `product_id` + `barcode`).

### 2.4. ✅ Тонны ↔ погонные метры ↔ штуки для одной номенклатуры — РАБОТАЕТ

Это главный вопрос раздела. Проверено по коду — механизм есть, кода писать не надо,
нужна только правильная настройка справочника.

**Схема.** Погонная масса профиля — это и есть коэффициент между длиной и массой.
Значит единица «пог. м конкретного профиля» вешается **в дерево массы**, а не длины:

```
g  (корень, factor = 1)
└── kg              relative_factor=1000        → factor = 1 000
    ├── Ton         relative_factor=1000        → factor = 1 000 000
    └── «пог.м 20Б1»  relative_factor = 21.3    → factor = 21 300
        └── «хлыст 12 м 20Б1»  relative_factor = 12 → factor = 255 600
```

(21,3 кг/м — иллюстративное значение, в реальности берётся из справочника проката.)

**Проверка арифметики по формуле `qty * factor_from / factor_to`:**

| Из | В | Расчёт | Результат |
|---|---|---|---|
| 1 т | пог. м | 1 × 1 000 000 / 21 300 | 46,9484 м |
| 5 пог. м | т | 5 × 21 300 / 1 000 000 | 0,1065 т |
| 1 хлыст 12 м | пог. м | 255 600 / 21 300 | 12 м (ровно) |
| 1 хлыст 12 м | т | 255 600 / 1 000 000 | 0,2556 т |
| 3,2 т | хлыстов | 3,2 × 1 000 000 / 255 600 | 12,52 шт |

Все три единицы в одном дереве → `_has_common_reference` даёт `True`, пересчёт
корректен везде: приход в тоннах от поставщика, склад в тоннах, списание в
спецификации в погонных метрах, отгрузка хлыстами.

**Настройка на товаре:** `uom_id` = «т» (единица склада и себестоимости),
`uom_ids` = [«пог. м 20Б1», «хлыст 12 м 20Б1»]. Домен `uom_ids` —
`[('id','!=',uom_id)]` (`product_template.py:122`), никаких ограничений по дереву,
но класть туда единицы из чужого дерева нельзя: арифметика молча даст ерунду.

**Цена в разных единицах работает автоматически:** прайс поставщика в руб/т,
продажа в руб/пог. м — `_compute_price` (`uom_uom.py:196-203`) и
`product.supplierinfo.price_discounted` (`addons/product/models/product_supplierinfo.py:70-74`)
пересчитают.

**Ограничения, которые надо знать заранее:**

1. **Единицы глобальные.** В `uom.uom` **нет** поля `company_id` (проверено:
   в `addons/uom/models/uom_uom.py` его нет, в `addons/product/models/uom_uom.py`
   тоже). На 665 позиций проката получится +665…1300 записей в общем справочнике
   единиц. Для БД это ничто, но выпадающий список «Единица» в настройках станет
   длинным. Смягчается тем, что на документах показывается не весь справочник, а
   `allowed_uom_ids` (см. таблицу выше).
2. **Изменение коэффициента задним числом не пересчитывает существующие данные** —
   `_onchange_critical_fields` (`uom_uom.py:79-93`) прямо предупреждает об этом.
   Значит погонную массу надо один раз выверить перед запуском.
3. Смена `uom_id` у товара, по которому уже есть движения, запускает
   `_update_uom` с переписыванием истории: `addons/product/models/product_product.py:1197`,
   плюс переопределения в `addons/stock/models/product.py:774-798`,
   `addons/sale/models/product_product.py:101-114`,
   `addons/purchase/models/product.py:117-132`, `addons/mrp/models/product.py:452-489`.
   Работает, но это не рутинная операция.
4. Механизм включается галкой: группа `uom.group_uom` («Manage Multiple Units of
   Measure», `addons/uom/security/uom_security.xml:4-6`), в настройках Склада —
   «Units of Measure & Packagings»
   (`applications/inventory_and_mrp/inventory/product_management/configure/uom.rst:23-27`).
   Проверка в коде — `addons/product/models/product_template.py:1571-1575`.

**Сопоставление с Carbon.** В Carbon пересчёта нет вообще: коэффициентов у
`unitOfMeasure` не существует, есть только `conversionFactor NUMERIC(10,2)` на
строках закупки, и связка «тонна ↔ погонный метр ↔ штука» системой не
поддерживается — оценка доработки 3–5 дней и своя таблица коэффициентов
(`experiments/carbon/analysis/10-единицы-измерения.md:231-248,474`). **В Odoo это
0 дней разработки и ~1 день наполнения справочника** (плюс скрипт из раздела 4,
который создаёт единицы пачкой из погонной массы).

### 2.5. ⚠️ Грабля Odoo 19: округление стало общим для всех единиц

```python
# addons/uom/models/uom_uom.py:62-67
def _compute_rounding(self):
    """ All Units of Measure share the same rounding precision defined in 'Product Unit'. """
    decimal_precision = self.env['decimal.precision'].precision_get('Product Unit')
    self.rounding = 10 ** -decimal_precision
```

`rounding` — **compute без store и без inverse**, задать его для отдельной единицы
нельзя. Раньше у каждой единицы была своя точность округления, и «штуки» можно
было заставить быть целыми. Теперь:

- нельзя запретить дробные штуки — при «Product Unit» = 4 система спокойно примет
  «2,5 листа»;
- методы `uom.round()`, `uom.compare()`, `uom.is_zero()` (`uom_uom.py:116-137`)
  все берут ту же «Product Unit»;
- единственный частичный заменитель — `_check_qty` (`uom_uom.py:178-194`),
  который округляет количество до кратного единице упаковки, но он вызывается
  точечно, а не как общее правило.

Для завода это скорее неудобство, чем блокер (металл дробный по природе), но
«штучные» позиции — метизы, узлы — придётся контролировать процессом.

## 3. Точность чисел: хватит ли для толщин металла и масс

### 3.1. Механизм

Точность задаётся **не в определении поля, а в справочнике** `decimal.precision`
(`odoo/addons/base/models/decimal_precision.py:9-27`):

```python
class DecimalPrecision(models.Model):
    _name = 'decimal.precision'
    name   = fields.Char('Usage', required=True)
    digits = fields.Integer('Digits', required=True, default=2)

    @api.model
    @tools.ormcache('application', cache='stable')
    def precision_get(self, application):
        ...
        return res[0] if res else 2       # по умолчанию 2 знака
```

Поле ссылается на запись справочника строкой:

```python
# odoo/orm/fields_numeric.py:135-141
def get_digits(self, env):
    if isinstance(self._digits, str):
        precision = env['decimal.precision'].precision_get(self._digits)
        return 16, precision
    return self._digits
```

### 3.2. Как это ложится в PostgreSQL — ключевой момент

```python
# odoo/orm/fields_numeric.py:126-133
@property
def _column_type(self):
    # Explicit support for "falsy" digits (0, False) to indicate a NUMERIC
    # field with no fixed precision. The values are saved in the database
    # with all significant digits.
    return ('numeric', 'numeric') if self._digits is not None else \
           ('float8', 'double precision')
```

Тип колонки — **`numeric` без указания (precision, scale)**. Масштаб применяется
не БД, а ORM при записи:

```python
# odoo/orm/fields_numeric.py:157-166
def convert_to_column(self, value, record, values=None, validate=True):
    value_float = value = float(value or 0.0)
    if digits := self.get_digits(record.env):
        _precision, scale = digits
        value_float = float_round(value, precision_digits=scale)
        value = float_repr(value_float, precision_digits=scale)
    ...
```

**Три практических следствия:**

1. Поднять точность «Product Unit» с 2 до 4 — это одна строка в справочнике,
   **без `ALTER TABLE` и без простоя**.
2. Ранее записанные значения **не пересчитываются** — система честно об этом
   предупреждает (`decimal_precision.py:45-59`), но только при **понижении**.
   Поэтому точность надо поднять **до** загрузки данных.
3. `precision_get` закэширован (`@tools.ormcache(..., cache='stable')`), кэш
   сбрасывается на `create/write/unlink` (`decimal_precision.py:29-43`) — после
   правки перезапуск не нужен.

Это, кстати, ровно та же архитектура, что у Carbon (голый `NUMERIC`, границы
обеспечивает вызывающий код — `experiments/carbon/analysis/03-модель-данных.md`,
раздел 9.1). Разница в умолчаниях: у Carbon внутренняя шкала **5 знаков**, у Odoo
**2**.

### 3.3. Что поставляется по умолчанию

| Запись `decimal.precision` | Знаков | Где объявлена | Что округляет |
|---|---|---|---|
| **Product Unit** | **2** | `addons/uom/data/uom_data.xml:5-8` | все количества + **округление всех единиц измерения** |
| Product Price | 2 | `addons/product/data/product_data.xml:19-22` | цены за единицу |
| Discount | 2 | `:23-26` | скидки |
| **Stock Weight** | **2** | `:27-30` | `product.weight`, вес упаковки, вес отгрузки |
| Volume | 2 | `:31-34` | объём |
| Payment Terms | — | `addons/account/data/account_data.xml:5` | платежи |
| Percentage Analytic | — | `addons/analytic/data/analytic_data.xml:4` | аналитика |

`digits='Product Unit'` встречается в 78 объявлениях полей в `addons/`
(в 160 местах с учётом вызовов `precision_get`). Это количества в
`stock.quant.quantity`, `stock.move.product_uom_qty`, `mrp.bom.product_qty`,
`mrp.bom.line.product_qty`, `mrp.production.product_qty` и т. д.

**Исключение, сделанное намеренно:** «настоящее» количество перемещения хранится
с неограниченной точностью —

```python
# addons/stock/models/stock_move.py:54-60
product_qty = fields.Float('Real Quantity', compute='_compute_product_qty',
                           inverse='_set_product_qty', digits=0, store=True, ...)
product_uom_qty = fields.Float('Demand', default=1.0, digits='Product Unit', ...)
```

`digits=0` → NUMERIC без ограничения. То есть внутренняя правда склада не теряет
разрядов; режет только ввод/вывод в выбранной единице.

### 3.4. Хватит ли — конкретный ответ

**Массы.** «Product Unit» = 2 при работе **в тоннах** даёт шаг **10 кг**. Это
непригодно. Хуже того, `_compute_quantity` по умолчанию округляет **вверх**
(`rounding_method='UP'`, `uom_uom.py:152`; `'UP'` = «всегда от нуля»,
`odoo/tools/float_utils.py:145-146`). Пример из 2.4: 5 пог. м = 0,1065 т, при двух
знаках станет **0,11 т** — приписка 3,5 кг на каждой строке, и всегда в одну
сторону. На спецификации из 200 позиций это систематическая ошибка в десятки
килограммов.

> **Обязательная настройка перед запуском: «Product Unit» = 4.**
> Шаг 0,0001 т = 100 г — достаточно и для тонн, и для погонных метров (0,1 мм),
> и для штук. Одновременно это единственный способ повлиять на округление
> пересчёта единиц (см. 2.5).

**Массы в кг (поле `product.weight`).** «Stock Weight» = 2 → шаг 10 г. Для
изделий это приемлемо, для мелких метизов — на грани. Рекомендация: **3 знака**.

**Толщины металла.** В ядре **поля «толщина» нет** — ни в `product.template`, ни в
`product.product` (проверено grep'ом по `addons/product/models/`). Это собственное
поле, и точность вы задаёте сами: в примере из раздела 4 —
`fields.Float('Толщина, мм', digits=(12, 3))`, то есть кортеж вместо ссылки на
справочник. Шаг 0,001 мм — с запасом (реальные толщины 0,4…60 мм, прокат ходит с
шагом 0,05 мм). Кортеж `(12, 3)` **не зависит** от глобальных настроек — это
правильный выбор для физических размеров.

**Цены.** «Product Price» = 2. Цена за тонну (десятки тысяч рублей) — с запасом.
Цена за кг или за штуку метиза (0,37 ₽) — тоже проходит. Если появится цена
за грамм — поднять до 4. Отдельно: у `list_price`/`standard_price` в 19-й версии
используется `min_display_digits='Product Price'`
(`addons/product/models/product_template.py:100-106`, `product_product.py:28-33`) —
это **минимум** знаков при показе, потолка нет, значение хранится полностью.

**Деньги (`fields.Monetary`)** берут число знаков из валюты
(`odoo/orm/fields_numeric.py:184-196`), а не из `decimal.precision` — для рубля
это 2 знака, и трогать не надо.

### 3.5. Инструменты сравнения — использовать обязательно

Прямое `==` между float в Odoo запрещено так же, как в Carbon. API:

| Функция | Файл | Назначение |
|---|---|---|
| `float_round(v, precision_digits=…, rounding_method=…)` | `odoo/tools/float_utils.py:72-155` | методы: `HALF-UP` (по умолчанию), `HALF-DOWN`, `HALF-EVEN`, `UP`, `DOWN` |
| `float_compare(a, b, …)` | `:201-…` | -1 / 0 / 1 |
| `float_is_zero(v, …)` | `:157-…` | сравнение с нулём |
| `float_repr`, `float_split` | `:313`, `:358` | строковое представление |
| `uom.round(v)`, `uom.compare(a,b)`, `uom.is_zero(v)` | `addons/uom/models/uom_uom.py:116-137` | те же, но с точностью «Product Unit» |
| `fields.Float.round/is_zero/compare` | `odoo/orm/fields_numeric.py:178-180` | статические алиасы |

Защита от IEEE-754 (эпсилон, масштабированный по порядку величины) встроена в
`float_round` — `float_utils.py:120-131`, там же комментарий про `2.675 == 2.6749999999999998`.
Это тот же класс решения, что `round()` через сдвиг экспоненты у Carbon
(`03-модель-данных.md`, раздел 9.3).

## 4. Своё поле и свой экран без Studio (то есть бесплатно)

### 4.1. Способ A — через интерфейс, режим разработчика (без единой строки кода)

**Когда годится:** одно-два поля «на посмотреть», быстрая проверка гипотезы.
**Когда нет:** всё, что должно пережить перенос на другой сервер, попасть в git,
иметь тесты или логику. Правки через UI живут только в БД.

```python
class ProductTemplate(models.Model):
    _inherit = 'product.template'

    pmk_steel_grade_id = fields.Many2one(
        'pmk.steel.grade', string='Марка стали', index='btree_not_null')
    pmk_thickness = fields.Float('Толщина, мм', digits=(12, 3))

        help='Масса одного погонного метра профиля — коэффициент пересчёта т <-> пог.м.')
    pmk_length_uom_id = fields.Many2one(
        'uom.uom', string='Единица «пог. м» профиля', copy=False,
        domain="[('relative_uom_id', '!=', False)]")

    def action_pmk_sync_length_uom(self):
        """Создать или обновить единицу «пог.м <профиль>» под погонную массу."""
        kg = self.env.ref('uom.product_uom_kgm')
        for tmpl in self:
            if not tmpl.pmk_linear_weight:
                raise UserError(_('Не заполнена погонная масса для %s', tmpl.display_name))
            vals = {
                'name': 'пог.м %s' % tmpl.name,
                'relative_uom_id': kg.id,
                'relative_factor': tmpl.pmk_linear_weight,
            }
            if tmpl.pmk_length_uom_id:
                tmpl.pmk_length_uom_id.write(vals)
            else:
                uom = self.env['uom.uom'].create(vals)
                tmpl.pmk_length_uom_id = uom
                tmpl.uom_ids = [fields.Command.link(uom.id)]
        return True
```

**Уровень 3 — построчные правила (`ir.rule`, `odoo/addons/base/models/ir_rule.py:15-36`).**
Домен, применяемый к каждому запросу:

```xml

    <field name="name">All Leads</field>
    <field name="domain_force">[(1,'=',1)]</field>
    <field name="groups" eval="[(4, ref('sales_team.group_sale_salesman_all_leads'))]"/>

```

**Логика комбинирования (важно, ошибаются часто):** правила **без групп**
(глобальные) соединяются через **И**; правила **с группами** — через **ИЛИ** между
собой; итог = `глобальные AND (объединение групповых)`. Подтверждено
`odoo/addons/base/models/ir_rule.py:84-104` («local rules are OR-ed together …
global rules get AND-ed») и реализацией `_compute_domain` (`:141-…`). Поэтому
«менеджер видит всё» делается **добавлением** правила `[(1,'=',1)]` его группе,
а не снятием ограничения.

В доменах доступны `user`, `company_id`, `company_ids` (`ir_rule.py:29-36`), причём
`company_ids` — это **включённые переключателем компании**, отфильтрованные и
доверенные.

Права per-field: у поля можно указать `groups="base.group_user"`
(пример — `standard_price` в `addons/product/models/product_template.py:100-106`).

**Уровень 4 — меню и представления.** `groups="…"` на `<menuitem>`
(`addons/mrp/views/mrp_views_menus.xml:5,27`) и на любом элементе формы.
Это **не** защита данных, а только видимость.

### 5.2. Мультикомпанийность

- `res.company` — дерево: `parent_id`, `child_ids`, `parent_path`, вычисляемые
  `parent_ids`/`root_id` (`odoo/addons/base/models/res_company.py:51-56,130-134`).

  (`res_company.py:199-204`).
- `res.users`: `company_id` (текущая) + `company_ids` (разрешённые)
  (`odoo/addons/base/models/res_users.py:245-247`). В коде: `self.env.company`
  и `self.env.companies`.
- Разделение данных — типовое правило `ir.rule` на каждой модели:


`+ [False]` = «общие для всех компаний» (спецификации, рабочие центры,

- **Защита от «перекрёстных» ссылок**: атрибут поля `check_company=True` плюс
  `_check_company_auto = True` на модели заставляют ORM проверять согласованность

Для ПМК с одним юрлицом это избыточно, **но** механизм ровно тот, которым можно
разделить производство и торговый дом без второй инсталляции. В Carbon
мультиарендность вшита в первичный ключ (`PK ("id","companyId")`,
`experiments/carbon/analysis/03-модель-данных.md`, раздел 1) — жёстче, но и

|---|---|
| `categ_id` | искать категорию по отображаемому имени |
| `categ_id/id` | искать по External ID — надёжно |
| `categ_id/.id` | по Database ID |
| `uom_ids/id` | many2many: несколько External ID **через запятую без пробелов** (`export_import_data.rst:368-373`) |
| `order_line/product_id/id` | one2many: одна строка файла = одна строка документа (`:378-384`) |

**Батчи и объём.** По умолчанию 2000 строк за вызов
(`addons/base_import/static/src/import_model.js:111-113`), дальше клиент сам
продолжает с `nextrow` (`:428-433`, серверная часть `base_import.py:1530-1536`).
665 строк = **один батч**.

**Безопасность прогона.** Режим «Тест» = `dryrun=True`: всё выполняется и
откатывается через savepoint (`base_import.py:1461,1495-1502`), кэши сбрасываются.
Ошибки возвращаются списком с указанием строки. Плюс `tracking_disable: true` по
умолчанию (`import_model.js:126-127`) — импорт не засоряет чаты записей.

### 6.3. Оговорки

1. **`id` менять нельзя.** Документация помечает это как `.. danger::`
   (`export_import_data.rst:549-551`): при смене External ID система создаст
   дубль, а не обновит. Значит ключ должен строиться из чего-то стабильного
   (артикул), а не из имени.
2. **Пустое значение в файле затирает поле.** Не заполненная колонка = «поставить
   значение по умолчанию», пустая ячейка = «записать пусто»
   (`export_import_data.rst:448-452`). Для обновлений берите **только те колонки,
   которые обновляете**.
3. **Кодировка и разделитель.** Ожидается запятая и кавычки как ограничитель
   (`:270-276`); файлы из русского Excel обычно `cp1251` + `;` — перегонять в
   UTF-8. Табуляция как разделитель **не** поддерживается (`:276`).
4. **Альтернатива UI** — внешний API (XML-RPC / JSON-RPC,
   `developer/reference/external_api/`), метод `load()` вызывается напрямую.
   Для повторяющейся синхронизации из n8n это правильнее, чем ручной импорт.

### 7.3. Сопоставление по этой теме: Odoo 19 CE vs Carbon vs ERPNext

| Критерий | Odoo 19 Community | Carbon | ERPNext (текущая) |
|---|---|---|---|
| Пересчёт т ↔ пог. м ↔ шт | **Есть, дерево коэффициентов** | **Нет как класса**, оценка 3–5 дней (`10-единицы-измерения.md:474`) | Есть UOM Conversion Factor на товаре |
| Точность количеств по умолчанию | 2 знака, настраивается без миграции | 5 знаков (`SCALE=5`) | 3 знака (float precision) |
| Округление на единицу | **Глобальное** (регресс 19-й версии) | нет понятия | на UOM (`must_be_whole_number`) |
| Тонна/мм/м²/м³ в поставке | Есть | **Нет ни одной** (`:227`) | Есть |
| Расширение модели | Модуль Python+XML, LGPL-3 | TS + SQL-миграции, **EE-лицензия на ключевые части** | Custom Field / Custom App |
| Расширение через UI без кода | Да (`x_`-поля, dev mode) | Нет | Да (Customize Form) |
| Импорт с обновлением по внешнему ключу | Да, штатно | CSV-импорт есть, edge-функция | Да (Data Import) |
| Мультикомпания | Дерево компаний + `ir.rule` | Прошита в PK, жёстче | Есть |
| Локализация РФ (ОКЕИ/УПД) | **Есть — RuOdoo, 48 модулей** | **Нет ничего**, PDF не печатает кириллицу | Своими силами |

**Главная мысль по этому документу:** по модели данных и способам расширения Odoo
для завода металлоконструкций **сильнее Carbon в двух решающих точках** —
пересчёт единиц измерения работает из коробки (у Carbon это доработка на 3–5 дней
плюс новая таблица), и расширяется всё под LGPL-3 без коммерческой лицензии
(у Carbon MRP и планировщик лежат в платном `packages/ee`). Единственное, что
надо сделать **до** первой загрузки данных, — поднять точность количеств:
умолчание в 2 знака при работе в тоннах даёт систематическую приписку веса.
