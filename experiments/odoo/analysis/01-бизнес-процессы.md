### 0.2. Три архитектурных изменения именно в версии 19 (важно, потому что ломает старые инструкции)

1. **`procurement.group` удалена.** Проверено: `grep "procurement.group"` по
   `addons/` и `odoo/` не даёт ни одного `_name = 'procurement.group'`, и в
   `stock/models/stock_rule.py` нет поля `group_id`. Вместо неё:
   - `stock.reference` — `stock/models/stock_reference.py:6`, поля `name`,
     `move_ids` (M2M на `stock.move`), вычисляемое `picking_ids`. Это
     «нитка», связывающая все документы одной потребности.
   - `mrp.production.group` — `mrp/models/mrp_production.py:25`, и поле
     `production_group_id` на `mrp.production:94`, `stock.move:35`,
     `stock.picking:140` — для группировки каскада МО (сборка из подсборок).

   Практически: связь «заказ клиента → отгрузка → производственный заказ»
   теперь идёт через `reference_ids` (M2M), а не через одну процурмент-группу.

2. **`uom.category` и `product.packaging` удалены.** `uom.uom`
   (`uom/models/uom_uom.py:18`) стала **деревом**: `_parent_name =
   'relative_uom_id'`, `_parent_store = True`, поля `relative_factor`
   («Contains»), `relative_uom_id` («Reference Unit»), вычисляемый
   `factor` (`:43`). Упаковки переехали в `product.template.uom_ids`
   (`product/models/product_template.py:122`, строка «Packagings»).
   Для металла это ключевое — см. раздел 6.4.

3. **Маршруты Buy/Manufacture скрыты с формы товара по умолчанию.** Прямая
   цитата документации
   `inventory_and_mrp/inventory/warehouses_storage/replenishment/mto.rst`:
   «As of Odoo 19.0, the *Buy* and *Manufacture* routes are hidden from the
   :guilabel:`Routes` field under the *Operations* tab by default. They are
   automatically applied on purchased and manufactured products depending on
   their respective configurations». Т.е. маршрут «Производить» применяется
   автоматически, если у товара есть спецификация.

## 1.2. Шаг 1 — лид (lead)

**Модель** `crm.lead`, `crm/models/crm_lead.py:85`. Одна модель обслуживает
и лид, и сделку — различает поле `type`
(`crm/models/crm_lead.py:123`): `[('lead','Lead'), ('opportunity','Opportunity')]`.
Это принципиальное отличие от ERPNext, где `Lead` и `Opportunity` — разные доктайпы.

Ключевые поля:

| Поле | Строка | Смысл |
|---|---|---|
| `type` | `crm_lead.py:123` | lead / opportunity |
| `stage_id` → `crm.stage` | `:130` | этап воронки |
| `expected_revenue` | `:141` | ожидаемая выручка |
| `probability` / `automated_probability` | `:222` / `:225` | вероятность; вторая считается предиктивным скорингом |
| `prorated_revenue` | `:142`, вычисление `:568-571` | `expected_revenue × probability / 100` |
| `date_deadline` | `:162` | ожидаемая дата закрытия |
| `partner_id` | `:171` | клиент (может быть пустым у лида) |
| `partner_name` / `contact_name` / `email_from` / `phone` | `:175-178` | «сырые» контактные данные до создания партнёра |
| `team_id` → `crm.team` | `:111` | отдел продаж |
| `won_status` | `:228` | won / lost / pending |
| `lost_reason_id` | `:234` | причина проигрыша |
| `lead_properties` | `:114` — `fields.Properties` | **произвольные поля на лету**, схема хранится в `team_id.lead_properties_definition` |

Этап: `crm.stage` (`crm/models/crm_stage.py`), поля `sequence:26`,
`is_won:27` (флаг «этап = выиграно»), `rotting_threshold_days:28`
(подсветка залежавшихся), `requirements:30` (подсказка «что нужно сделать
на этапе»), `team_ids:31` (этап может быть свой у каждого отдела), `fold:32`.

**Входящие каналы лида (автоматика):**
- **Email** — `crm.team` наследует `mail.alias.mixin`
  (`crm/models/crm_team.py:20`), `alias_id:25`. В
  `_alias_get_creation_values():147` алиас жёстко привязан к модели
  `crm.lead`, а `alias_defaults['type']` ставится `'lead'` или
  `'opportunity'` в зависимости от галок `use_leads`/`use_opportunities`
  (`:23-24`, `:155`). Парсинг входящего письма — `message_new()` в
  `crm/models/crm_lead.py:2125`.
- **Веб-форма** — модуль `website_crm` (есть в Community).
- **Обогащение** — `crm_iap_enrich`, `crm_iap_mine`, `partner_autocomplete`
  (платные IAP-кредиты, не подписка Enterprise).

**Где в интерфейсе:** CRM → Лиды (`crm/views/crm_menu_views.xml:51`,
меню `crm_menu_leads`, видно только с группой `crm.group_use_lead`).
Сама стадия «Лиды» выключаема: настройка CRM → Настройки → «Leads»
(`sales/crm/acquire_leads/convert.rst`). Без неё письма падают сразу
в сделки.

## 1.4. Шаг 3 — КП (quotation)

КП и заказ клиента — **одна модель** `sale.order`
(`sale/models/sale_order.py:34`). Разница только в статусе.

```python

    ('draft',  "Quotation"),       # КП, черновик
    ('sent',   "Quotation Sent"),  # КП отправлено клиенту
```

Плюс отдельный булев `locked` (`:78`) — «заказ заблокирован, править нельзя»
(в Odoo ≤16 это был статус `done`). Проверка в `action_cancel():1326-1329`:
заблокированный заказ отменить нельзя.

**Создание КП из сделки — три пути, все в `sale_crm`:**

| Действие | Код | Что делает |

| Кнопка «Новое КП» на сделке | `sale_crm/models/crm_lead.py:29 action_sale_quotations_new()` | если у сделки нет `partner_id` — сначала открывает мастер `crm.quotation.partner`; иначе сразу форму КП |

| Прямое создание | `sale_crm/models/crm_lead.py:34 action_new_quotation()` | подставляет контекст `_prepare_opportunity_quotation_context():76` |

Контекст переноса данных сделка→КП (`sale_crm/models/crm_lead.py:76-96`) —
что именно наследуется: `opportunity_id`, `partner_id`, `campaign_id`,

**Шаблоны КП** — `sale.order.template`
(`sale_management/models/sale_order_template.py`), поле на заказе

**Конструктор PDF КП** — модуль `sale_pdf_quote_builder` (есть в Community):

## 1.5. Шаг 4 — подтверждение заказа

`sale.order.action_confirm()` — `sale/models/sale_order.py:1168`.

Последовательность:
1. `_confirmation_error_message():1204` — проверки: статус должен быть
   `draft`/`sent`; во всех строках должен быть товар.
2. `_validate_analytic_distribution()` — валидация аналитики.
3. `_prepare_confirmation_values():1221` → `{'state': 'sale', 'date_order': now}`.
4. `_action_confirm()` — **точка расширения**, её переопределяют:
   - `sale_stock/models/sale_order.py:213` → `order_line._action_launch_stock_rule()`

     услуг с `service_to_purchase`;
   - `sale_project/models/sale_order.py:138` → создаёт проект/задачу.
5. `_should_be_locked():1200` — если включена настройка

6. `sale_crm/models/sale_order.py:14 action_confirm()` (override) → для каждой

## 1.6. Шаг 5 — отгрузка (delivery)

**Запуск логистики.** `sale.order.line._action_launch_stock_rule()` —
`sale_stock/models/sale_order_line.py:385`. Алгоритм:
- пропускает строки, где `state != 'sale'`, заказ `locked`, или товар
  не `type='consu'` (`:397`);
- считает уже запущенное количество `_get_qty_procurement()` (`:317`);
- если для заказа ещё нет `stock.reference` — создаёт (`:404-406`);
- формирует `values` через `_prepare_procurement_values()` (`:284`) —
  туда попадают `origin` (имя заказа), `reference_ids`, **`sale_line_id`**
  (обратная ссылка на строку заказа), `date_planned`, `date_deadline`,
  `route_ids`, `warehouse_id`, `partner_id`, `location_final_id`,
  `product_description_variants`;
- вызывает `self.env['stock.rule'].run(procurements)` (`:414`).

**Диспетчер правил.** `stock.rule.run()` — `stock/models/stock_rule.py:453`.
Для каждой потребности находит правило `_get_rule()`, группирует по
`rule.action` и вызывает `_run_<action>`:

| `action` | Метод | Модуль | Что рождается |
|---|---|---|---|
| `pull` / `pull_push` | `_run_pull()` `stock/models/stock_rule.py:290` | stock | `stock.move` → `stock.picking` |
| `push` | `_run_push()` `stock/models/stock_rule.py:222` | stock | следующее перемещение после прихода |
| `buy` | `_run_buy()` `purchase_stock/models/stock_rule.py:59` | purchase_stock | `purchase.order` + строки |
| `manufacture` | `_run_manufacture()` `mrp/models/stock_rule.py:81` | mrp | `mrp.production` |

`action` расширяется через `selection_add` — `purchase_stock/models/stock_rule.py:18`
добавляет `'buy'`, `mrp/models/stock_rule.py:15` добавляет `'manufacture'`.

**Способ снабжения** — `stock.rule.procure_method`
(`stock/models/stock_rule.py:78`):
- `make_to_stock` — брать со склада;
- `make_to_order` — **не смотреть остаток**, запустить следующее правило
  (это и есть MTO);
- `mts_else_mto` — брать со склада, при нехватке запустить цепочку.

**Отгрузка.** `stock.picking` (`stock/models/stock_picking.py:539`), статусы
(`:575`): `draft → waiting → confirmed → assigned → done / cancel`.
Ключевые методы: `action_confirm():1194`, `action_assign():1203`
(резервирование), `button_validate():1420`, `_action_done():1263`.
Недовоз → бэкордер (`backorder_id:560`, `backorder_ids:565`).

`stock.move` статусы (`stock/models/stock_move.py:107`):
`draft → waiting → confirmed → partially_available → assigned → done / cancel`.

Связь обратно на заказ: `sale.order.picking_ids`
(`sale_stock/models/sale_order.py:31`, O2M по `stock.picking.sale_id`),
`delivery_status` вычисляется из состояний отгрузок (`:90-107`).

**Склад: сколько шагов отгрузки** — `stock.warehouse.delivery_steps`
(`stock/models/stock_warehouse.py:62`): отгрузка в 1 / 2 (комплектация+отгрузка) /
3 (комплектация+упаковка+отгрузка) шага.

## 1.7. Шаг 6 — счёт клиенту

**Политика выставления счёта** — `product.template.invoice_policy`
(`sale/models/product_template.py:35`): `order` (по заказанному) /
`delivery` (по отгруженному). По умолчанию для товаров (`type='consu'`) —
`order` (`_compute_invoice_policy():163`).

**Статус счёта на заказе** — `sale.order.invoice_status` (`:246`), значения
из `INVOICE_STATUS` (`sale/models/sale_order.py:19`):
`upselling` / `invoiced` / `to invoice` / `no`.

Логика по строке — `sale/models/sale_order_line.py:1100-1115`:
- строка не в `sale` → `no`;
- есть `qty_to_invoice` → `to invoice`;
- политика `order`, но отгружено **больше** заказанного → `upselling`
  (сигнал «допродать»);
- `qty_invoiced >= product_uom_qty` → `invoiced`.

Величины: `qty_delivered` (`:230`), `qty_invoiced` (`:238`),
`qty_to_invoice` (`:247`), метод расчёта `qty_delivered_method`
(`:217`: stock_move / analytic / manual).

**Создание счёта** — `sale.order._create_invoices(grouped=False, final=False)`
(`sale/models/sale_order.py:1552`). Группировка по умолчанию —
по `(partner_id, partner_shipping_id, currency_id)` (`:1618`), т.е.
несколько заказов одного клиента можно слить в один счёт. Шапка счёта —
`_prepare_invoice()` (`:1413`), там же проставляется `invoice_origin`.

**Аванс (down payment)** — мастер `sale.advance.payment.inv`,

# Процесс 4. Как связаны CRM и продажи

Это место, где Odoo принципиально отличается от Carbon (у Carbon CRM нет
вообще — там всё начинается с подтверждённого заказа) и от ERPNext
(где Lead/Opportunity — отдельные доктайпы с ручной конвертацией).

## 4.1. Связь — один мост-модуль `sale_crm`

Модуль `sale_crm` (`addons/sale_crm/`, 3 файла моделей + 1 мастер) — вся
интеграция. Он `auto_install` при наличии `crm` и `sale`.

**Одно поле-связка:**
```python
# sale_crm/models/sale_order.py:9
opportunity_id = fields.Many2one(
    'crm.lead', string='Opportunity', check_company=True, index='btree_not_null',
    domain="[('type', '=', 'opportunity'), ...]")
```
Обратная сторона — `crm.lead.order_ids`
(`sale_crm/models/crm_lead.py:13`, O2M по `opportunity_id`).

## 4.2. Что считается автоматически на карточке сделки

`_compute_sale_data()` — `sale_crm/models/crm_lead.py:16-27`:

| Поле | Как считается |
|---|---|
| `quotation_count` | заказы со `state in ('draft','sent')` (`_get_lead_quotation_domain():76`) |
| `sale_order_count` | заказы со `state not in ('draft','sent','cancel')` (`_get_lead_sale_order_domain():79`) |
| `sale_amount_total` | сумма `amount_untaxed` подтверждённых заказов, **сконвертированная в валюту компании** по курсу на `date_order` |

То есть на сделке видно: «2 КП на рассмотрении, 1 заказ на 3,4 млн».

## 4.3. Обратное влияние заказа на сделку

`sale_crm/models/sale_order.py:14` — override `action_confirm()`:
```python
for order in self:
    order.opportunity_id._update_revenues_from_so(order)
```
`_update_revenues_from_so()` (`sale_crm/models/crm_lead.py:104`) поднимает
`expected_revenue` сделки до `order.amount_untaxed`, **если заказ больше
текущей оценки и валюта совпадает с валютой компании**, и пишет причину
в чаттер.

## 4.4. Что наследуется из сделки в КП

`_prepare_opportunity_quotation_context()` — `sale_crm/models/crm_lead.py:76-96`.
Переносятся: клиент, компания, отдел продаж, менеджер, теги,
**UTM-метки** (`campaign_id`, `medium_id`, `source_id`) и `origin = имя сделки`.
Это значит: сквозная атрибуция «откуда пришёл клиент → сколько он принёс»
работает из коробки, без доработок.

## 4.5. Слияние сделок не теряет заказы

`_merge_get_fields_specific()` (`sale_crm/models/crm_lead.py:98-102`) —
при слиянии дублей все `order_ids` всех сливаемых сделок цепляются к
результирующей.

## 4.6. Победа/поражение

- `action_set_won()` (`crm/models/crm_lead.py:1127`) — ищет этап с
  `is_won = True` (`:1133`), ставит `probability = 100`.
- `action_set_lost()` (`:1121`) + мастер `crm.lead.lost`
  (`crm/wizard/crm_lead_lost.py`) с `lost_reason_id`.
- Дата закрытия `date_closed` проставляется автоматически при попадании
  на выигрышный этап (`:803`).
- **Победа не создаёт заказ автоматически** — заказ создаётся отдельно,
  вручную или из сделки кнопкой. Odoo это не связывает жёстко.

## 4.7. Отчётность CRM (всё в Community)

Меню CRM → Отчётность (`crm/views/crm_menu_views.xml:60`):

Дополнительно в `sales/crm/performance/` и `sales/crm/track_leads/`

**Предиктивный скоринг лидов** — в Community: `crm.lead.scoring.frequency`

# Процесс 5. Работа под заказ: MTO, позаказное производство, «проект на заказ»

## 5.1. MTO (make-to-order) — механика

Маршрут «Replenish on Order (MTO)» — запись данных
`stock/data/stock_data.xml:42-49`:
```xml
<record id="route_warehouse0_mto" model='stock.route'>
    <field name="name">Replenish on Order (MTO)</field>
    <field name="active">False</field>       <!-- по умолчанию ВЫКЛЮЧЕН -->
    <field name="sequence">5</field>          <!-- ниже маршрутов пополнения -->
    <field name="product_categ_selectable" eval="True"/>
</record>
```
Комментарий в самом файле (`:41`): «set a lower sequence on the mto route
than on the resupply routes».

Включение: Склад → Настройки → Logistics → «Replenish on Order (MTO)»
(док `mto.rst`).

Суть: правило MTO имеет `procure_method = 'make_to_order'`
(`stock/models/stock_rule.py:78-80`) — «the available stock will be
ignored», система обязана запустить следующее правило. Дальше по цепочке
срабатывает либо `buy` → заказ поставщику, либо `manufacture` → МО.

**Практически важное предупреждение из доки** (`mto.rst`, `.. important::`):
если сгенерированное MTO запрос цен или МО **отменить**, Odoo **не создаст
замену автоматически**, и новый документ уже нельзя будет связать с
исходным заказом через смарт-кнопку. Надо менять документ, а не отменять.

**Альтернатива MTO** — `mts_else_mto` («Take From Stock, if unavailable,
Trigger Another Rule»): берём со склада, при нехватке запускаем цепочку.
Для завода это почти всегда правильнее чистого MTO: метизы и расходники
со склада, профиль под заказ.

## 5.2. Позаказное производство — что связывает документы

Три механизма связи «заказ клиента ↔ производство»:

1. **`mrp.production.sale_line_id`** (`sale_mrp/models/mrp_production.py:15`) —
   прямая ссылка на строку заказа. Проставляется маршрутом MTO.
2. **`stock.reference`** (`stock/models/stock_reference.py:6`) — общая
   «нитка». `sale.order.stock_reference_ids`
   (`sale_stock/models/sale_order.py:48`) →
   `mrp.production.reference_ids` (`mrp_production.py:240`) →
   `stock.picking.reference_ids` (`stock_picking.py:590`). Заменила
   `procurement.group`.
3. **`mrp.production.origin`** (`mrp_production.py:85`) — текстовое
   «SO0042», для поиска и печати.

Смарт-кнопка на МО «Sale Orders» — `action_view_sale_orders()`
(`sale_mrp/models/mrp_production.py:21`), собирает
`reference_ids.sale_ids | sale_line_id.order_id`.

**Ключевая возможность для единичного производства: МО без спецификации.**
`mrp.production.bom_id` (`mrp_production.py:160`) **не required**, а
`move_raw_ids` (`:203`) объявлены как `compute + store + readonly=False` —
компоненты можно вбить прямо в МО. И есть обратный ход:
`action_generate_bom()` (`mrp_production.py:1157`) — **создать
спецификацию из уже набранного МО**: переносит компоненты, побочную
продукцию и операции, называет её «New BoM from <МО>» и привязывает
к текущему МО. Для КМД-изделий, где каждая марка уникальна, это рабочий
паттерн: собрали МО по чертежу → если марка повторяется, превратили в
спецификацию.

**Комплект (kit)** — `mrp.bom.type = 'phantom'`
(`mrp/models/mrp_bom.py:27`). Такая спецификация **не** создаёт МО:
на отгрузке строка заказа разворачивается в компоненты
(`sale_mrp/models/sale_order_line.py:33 _prepare_qty_delivered()` считает
`_compute_kit_quantities`). Годится для метизных наборов и комплектов
поставки, не для сварных конструкций.

**Субподряд** (оцинковка, покраска, дробеструйка на стороне) —
`mrp_subcontracting`: `mrp.bom.type` расширяется значением `'subcontract'`
(`mrp_subcontracting/models/mrp_bom.py:11-13`) + поле `subcontractor_ids`
(`:14`). Ограничение в коде (`_check_subcontracting_no_operation():25`):
у субподрядной спецификации **нельзя** задать операции и побочную
продукцию. Схемы (доки `manufacturing/subcontracting/`): базовая,
с поставкой давальческого сырья (resupply), дропшиппинг.

## 5.3. «Проект на заказ» — три разных механизма, не путать

### (а) Проект из заказа клиента — `sale_project`

`product.template.service_tracking`
(`sale_project/models/product_template.py:22-32`) — что создавать при
подтверждении заказа:
- `no` — ничего;
- `task_global_project` — задачу в заранее выбранном проекте;
- `task_in_project` — **новый проект + задачу в нём**;
- `project_only` — только новый проект.

Реализация — `sale_project/models/sale_order_line.py`:
`_timesheet_create_project():196`, `_timesheet_create_task():307`,
`_timesheet_create_project_account_vals():247` (создание **аналитического
счёта** проекта). Поля на строке заказа: `project_id:11`, `task_id:14`.
Есть шаблоны проектов — `product.project_template_id` (`:358-360`).

### (б) Проект ↔ производство — `project_mrp` (auto_install)

Модуль новый и для завода важный. Всё содержимое:
- `mrp.bom.project_id` — `project_mrp/models/mrp_bom.py:8`;
- `mrp.production.project_id` — `project_mrp/models/mrp_production.py:9`,
  **вычисляется из `bom_id.project_id`** (`_compute_project_id():12`),
  но `readonly=False, store=True` — можно перебить руками;
- на проекте — смарт-кнопки: `bom_count`, `production_count`
  (`project_mrp/models/project_project.py:10-11`), действия
  `action_view_mrp_bom()`, просмотр МО.

То есть: проект «Ангар в Комсомольске» → к нему подвязаны спецификации
марок и производственные заказы.

### (в) Рентабельность проекта — `project` + `sale_project`

`_get_profitability_items()` — `project/models/project_project.py:1052`,
расширение `sale_project/models/project_project.py:768`, ярлыки
`_get_profitability_labels():521`. Панель «Profitability» на проекте
сводит доходы (счета по заказам) и затраты (табели, закупки, складские
проводки — через `project_stock_account`, `project_purchase_stock`,
`project_mrp_account`, `project_mrp_stock_landed_costs` — все есть
в Community).

Основа связи — **аналитика**: `analytic.mixin`
(`analytic/models/analytic_mixin.py:16`), поле `analytic_distribution`
типа `fields.Json` — распределение по нескольким аналитическим счетам
с процентами. Есть на строке заказа, строке закупки, движении склада,
строке счёта, рабочем задании.

### Какой механизм для чего

| Задача | Механизм |
|---|---|
| Объект/стройка как сущность с бюджетом и рентабельностью | (а)+(в): `service_tracking` + аналитика проекта |
| Привязать МО марок к объекту | (б) `project_mrp.project_id` |
| Позаказная себестоимость без проектов | `analytic_distribution` на строках заказа/закупки/МО |
| Связать отгрузку и производство с заказом | `stock.reference` + `sale_line_id` (5.2) |

# 6. Как ложится на завод металлоконструкций (ПМК Парк)

## 6.1. Позаказное производство — ложится, но есть чего нет

**Ложится:**
- МО **без спецификации** + `action_generate_bom()` (`mrp_production.py:1157`) —
  штатный паттерн для уникальных марок по КМД (см. 5.2);
- `mrp.bom.consumption = 'flexible'` (`mrp_bom.py:70`) — фактический расход
  металла законно отличается от расчётного;
- `byproduct_ids` (`mrp_bom.py:41`) — деловой остаток/обрезь как отдельная
  учётная позиция, попадает на склад с долей себестоимости;
- `stock.scrap` (`stock_scrap.py:11`) + `scrap_reason_tag_ids:56` — брак
  с причинами;
- `allow_operation_dependencies` + `blocked_by_operation_ids`
  (`mrp_routing.py:47`) — маршрут «резка → сборка → сварка → зачистка →
  покраска» с зависимостями, а не тупой цепочкой;
- `mrp.workcenter.alternative_workcenter_ids` (`mrp_workcenter.py:68`) —
  два сварочных поста как взаимозаменяемые;
- субподряд на оцинковку — `mrp_subcontracting` (5.2).

**Чего нет (Enterprise):**
- **Shop Floor** (`mrp_workorder`) — цехового терминала нет. Сварщик
  отмечает начало/конец операции в обычной форме `mrp.workorder`
  (`button_start` / `button_finish`). Своя простая веб-морда поверх
  этих двух методов — реалистичная доработка.
- **Quality** — контрольных точек (входной контроль металла, контроль
  сварных швов, УЗК) нет. Придётся делать своим модулем или
  вести в `maintenance`/`project` как задачи.
- **MPS** (`mrp_mps`) — главного плана производства нет. Есть
  `stock.warehouse.orderpoint` и отчёт Production Analysis.
- **PLM** (`mrp_plm`) — версионирования спецификаций/ECO нет. Ревизии КМД
  придётся вести своими средствами (например, `mrp.bom.code` + `active`).
- **Approvals** — согласования КП/закупок маршрутом нет; есть только
  двухступенчатое утверждение заказа поставщику по сумме
  (`po_double_validation`).

## 6.2. Спецификации по КМД

Что даёт Odoo:
- иерархия: `mrp.bom.line.child_bom_id` (`mrp_bom.py:711`) — марка →
  отправочные элементы → детали;
- привязка компонента к операции: `mrp.bom.line.operation_id`
  (`mrp_bom.py:707`) — лист выдаётся на резку, метизы на сборку;
- варианты: `bom_product_template_attribute_value_ids` (`mrp_bom.py:702`) —
  одна спецификация на типоразмерный ряд (например, балка одной серии
  разной длины), строки включаются по значению атрибута;
- разные спецификации на один товар под разные потоки —
  `mrp.bom.picking_type_id` (`mrp_bom.py:59`);
- документы на спецификации/товаре — `product.document`
  (`mrp/models/product_document.py`, `mrp/views/product_document_views.xml`):
  чертежи можно прикрепить к спецификации и они будут видны в МО.

Чего нет:
- **импорта из CAD/DXF/DWG** — модулей с такими признаками в `addons/`
  нет (`ls | grep -iE "nest|cut|cad|dxf|dwg"` — пусто). Carbon в этом месте
  имеет интеграцию с Radan. В Odoo это пишется своим модулем поверх
  `mrp.bom` / `mrp.production.move_raw_ids` через XML-RPC/JSON-RPC
  (модуль `rpc` есть в Community).
- **ревизий/ECO** — см. 6.1 (PLM Enterprise).

## 6.3. Раскрой (nesting) — прямого решения нет

В Community нет ни модуля раскроя, ни оптимизатора. Что можно построить
на штатных механизмах:

| Задача раскроя | Штатный механизм | Оценка |
|---|---|---|
| Деловой остаток от листа/профиля | `mrp.bom.byproduct_ids` (`mrp_bom.py:41`) + отдельная номенклатура остатка | работает, но остаток надо описать как товар |
| Учёт конкретного листа (плавка, сертификат) | `product.template.tracking = 'lot'` (`stock/models/product.py:846`) + `stock.lot` (`stock_lot.py:25`), `stock.lot.lot_properties:60` (произвольные поля — номер плавки, сертификат) | работает |
| Фактический расход ≠ расчётного | `mrp.bom.consumption = 'flexible'` | работает |
| Собственно карта раскроя, оптимизация | **нет** | внешний софт + импорт результата в `move_raw_ids` |

Реалистичный сценарий: раскрой считается внешней программой, результат
(перечень заготовок + остаток) заливается в МО через API как
`move_raw_ids` + `byproduct_ids`.

## 6.4. Длинномер и единицы измерения — здесь версия 19 меняет правила

**Что изменилось.** `uom.category` больше нет; `uom.uom` — дерево
(`uom/models/uom_uom.py:18-21`, `_parent_name = 'relative_uom_id'`).
Единица описывается как «сколько в ней содержится родительской»:
`relative_factor` («Contains»), `relative_uom_id` («Reference Unit»),
абсолютный коэффициент `factor` считается рекурсивно (`:69-75`).

**Что это даёт для металла.** Цепочка «тонна → килограмм → метр погонный
конкретного профиля» строится как дерево пересчётов. Но:
- пересчёт **линеен** — один коэффициент. Для «м → кг» это работает,
  только если коэффициент свой для каждого профиля. Значит: **каждый
  типоразмер профиля — отдельная номенклатура со своей единицей**
  (двутавр 20Б1 в м, с коэффициентом на кг). Универсального
  «м×погонная масса» в модели нет.
- `product.template.weight` (`product/models/product_template.py:111`) —
  масса единицы. Для «двутавр, шт=6 м» это масса шестиметровки.

**Упаковки.** `product.packaging` удалена; вместо неё
`product.template.uom_ids` (`product_template.py:122`) — «Packagings»
как дополнительные единицы продажи. Пачка листа / связка арматуры
описывается здесь.

**Партионный учёт длинномера.** `tracking='lot'` + `stock.lot` (6.3):
каждая партия профиля — своя партия с `lot_properties` (плавка,
сертификат, поставщик, длина хлыста).

**Чего нет:** учёта остатков хлыстов по фактической длине (кусок 2,7 м от
шестиметровки). Это либо отдельная номенклатура «остаток», либо
доработка. Штатной модели «мерный остаток» в Odoo нет.

## 6.5. Учёт по массе

Где масса реально участвует в штатной логике:

| Место | Код | Что делает |
|---|---|---|
| `product.template.weight` | `product/models/product_template.py:111` | масса единицы |
| Распределение допрасходов **по массе** | `stock_landed_costs/models/stock_landed_cost.py:216` — `split_method == 'by_weight'` | ж/д тариф и доставка металла ложатся на партии **пропорционально массе**, а не количеству. Для завода — ровно то, что нужно |
| Масса отгрузки | `stock.picking` / `stock.move` (поля weight через `delivery`) | печать ТТН, расчёт доставки |
| Цена за кг | `product.pricelist.item` | прайс в ₽/кг реализуем, если основная UoM — кг |

**Практический вывод.** Учёт «в тоннах» в Odoo строится так: основная
единица номенклатуры = кг (или т), а «штуки/метры» — производные
единицы в дереве `uom.uom`. Тогда и себестоимость, и прайс, и landed
costs считаются в массе автоматически.

## 6.6. Сводная оценка процессов под ПМК Парк

| Процесс | Готовность Community | Что дорабатывать |
|---|---|---|
| Лид → сделка → КП → заказ | **высокая** | шаблон КП под РФ-форму, свой PDF |
| Почта → лид автоматом | **высокая** (`crm.team` alias, `message_new`) | ничего |
| Заказ → отгрузка → счёт → оплата | **высокая** | РФ-формы (счёт, ТОРГ-12, УПД) — RuOdoo `l10n_ru_doc`, `l10n_ru_upd_xml` |
| Потребность → закупка → приёмка → счёт | **высокая** | «заявка от цеха» (нет модели) |
| Согласование КП/закупки маршрутом | **нет** (`approvals` Enterprise) | свой модуль или RuOdoo `base_tier_validation` (есть в ruodoo!) |
| Заказ → МО → рабочие задания → выпуск | **средне-высокая** | цеховой терминал (нет Shop Floor) |
| Себестоимость заказа | **высокая** (`mrp_account` + аналитика) | настройка плана аналитики |
| Позаказный проект/объект | **высокая** (`sale_project` + `project_mrp`) | ничего критичного |
| Контроль качества | **нет** | свой модуль |
| Раскрой | **нет** | внешний софт + импорт по API |
| Длинномер/мерный остаток | **частично** | доработка |
| Учёт по массе | **высокая** (дерево UoM + landed costs by_weight) | проектирование справочника номенклатуры |
| Планирование мощностей (MPS) | **нет** | orderpoint + отчёты как паллиатив |
| Версионирование КМД (ECO) | **нет** | свой механизм |

## 6.7. Что из RuOdoo закрывает пробелы

В `ruodoo/` (48 модулей) прямо относящееся к описанным процессам:
- `base_tier_validation` + `tier_communications`, `tier_communications_matrix` —
  **многоступенчатое согласование** (замена Enterprise `approvals`);
- `l10n_ru_doc`, `l10n_ru_upd_xml`, `l10n_ru_act_rev` — первичка РФ (УПД, акт сверки);
- `l10n_ru_contract*` (`_sale`, `_purchase`, `_account`, `_templates`) —
  договоры как сущность, привязка к заказам/счетам;
- `l10n_ru_advance_payments` — авансы;
- `l10n_ru_attorney` — доверенности (М-2);
- `account_bank_statement_1c_import` — импорт банковской выписки 1С
  (частично закрывает отсутствие `account_accountant`);
- `dms` / `mklab_dms_document` — документооборот (замена Enterprise `documents`);
- `docx_report`, `pdf_report_from_docx`, `report_weasyprint` — печатные формы
  из DOCX-шаблонов (важно: РФ-формы удобнее верстать в Word, чем в QWeb);
- `mklab_forecast_mrp`, `mklab_mrp_filters` — надстройки над MRP;
- `dadata_connector` — подтягивание реквизитов по ИНН.

Детальный разбор RuOdoo — в отдельном файле анализа.
