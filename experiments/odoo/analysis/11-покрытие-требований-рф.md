## 0. Краткий вывод

Ситуация принципиально другая, чем с Carbon. Carbon — «интернационализированный, но
не локализованный» продукт, где российских форм нет вообще и PDF физически не печатает
кириллицу. Odoo 19 Community **тоже не локализован под РФ силами Odoo S.A.** —
в официальном списке фискальных локализаций России нет (проверено:
`odoo-docs/content/applications/finance/fiscal_localizations.rst:126-131` — между
`Romania` и `Rwanda` пусто), и модуля `l10n_ru` в `addons/` **не существует**
(проверено: 231 модуль `l10n_*`, `l10n_ru*` — ноль).

Но **поверх Community есть готовый пласт RuOdoo**, и он закрывает почти всю первичку.
Это не «инфраструктура, на которой можно построить» — это работающие печатные формы,
УПД в XML по формату ФНС, акт сверки, доверенность, импорт банковской выписки из 1С.

Три вещи, которые блокируют запуск «как есть»:

| # | Блокер | Файл |
|---|---|---|
| 1 | **Плана счетов РСБУ нет ни в Odoo, ни в RuOdoo.** При создании компании подставится `generic_coa` — 46 англосаксонских счётов (`1010 Current Assets`, `3100 Retained Earnings`) и налог 15 % | `odoo/addons/account/data/template/account.account-generic_coa.csv` (46 строк), `account.tax-generic_coa.csv:2`, fallback — `account/models/chart_template.py:127` |
| 2 | **Печатные формы счёта-фактуры, ТОРГ-12 и акта выполненных работ в RuOdoo закомментированы.** QWeb-шаблоны загружаются, но записи `ir.actions.report` для них выключены → кнопки «Печать» нет | `ruodoo/l10n_ru_doc/report/l10n_ru_doc_report.xml:59-130` (блоки на строках 59, 83, 107 — в `<!-- -->`) |
| 3 | **Регламентированной отчётности нет ни в каком виде.** В Community `account` — только 3 записи `account.report` (все — generic tax report), ни баланса, ни ОСВ, ни главной книги (`account_reports` — Enterprise) | `odoo/addons/account/data/account_reports_data.xml` (3 × `model="account.report"`) |

Хорошая новость: блокер №2 — это раскомментировать четыре XML-блока. Блокер №1 —
заполнить справочник счётов (поле `code` — обычный `Char`), работа без кода.
Блокер №3 — не лечится внутри Odoo и не должен лечиться: регламентированный учёт
отдать 1С или бухгалтерскому аутсорсу (то же заключение, что и по Carbon, §11.4).

Что сразу лучше, чем в Carbon:

- ИНН/КПП/ОГРН/ОКПО — **есть поля**, плюс проверка контрольной суммы ИНН в ядре.
- Банковские реквизиты контрагента (р/с, БИК, к/с, банк) — **есть**, и они печатаются
  в «Счёте на оплату». В Carbon для них нет ни одной колонки.
- «В том числе НДС» — **работает штатно** (в Carbon это мёртвый код).
- Сумма прописью по-русски с правильными падежами — **две независимые реализации**.
- УПД в XML формата ФНС — **есть**, с именем файла по конвенции Диадока.
- Автосброс нумерации на новый год — **есть** (в Carbon нет).

## 1. Даты и время

### Формат даты

Формат берётся из `res.lang`, а не из кода. Строка русского языка —
`odoo/odoo/addons/base/data/res.lang.csv:64`:

```
"base.lang_ru","Russian / русский язык","ru_RU","ru","Left-to-Right","[3,0]",","," ","%d.%m.%Y","%H:%M:%S","1"
```

То есть **из коробки**: `date_format = %d.%m.%Y` (ДД.ММ.ГГГГ), время 24-часовое,
неделя начинается с понедельника (`week_start = 1`). Это всё, что нужно, — правок нет.

Сравнение с Carbon: там дефолт таблиц `dateStyle: "medium"` даёт `16 сент. 2026 г.`
и требует правки `packages/utils/src/date.ts:21-24`. В Odoo такой проблемы нет.

### Даты в печатных формах

RuOdoo даёт прописные даты через `pytils` —
`ruodoo/l10n_ru_doc/report_helper.py:31-40`:

```python
def ru_date(self, date):
    return dt.ru_strftime('"%d" %B %Y года', date=..., inflected=True)
def ru_date2(self, date):
    return dt.ru_strftime('%d %B %Y г.', date=..., inflected=True)
```

`inflected=True` — правильный падеж месяца («15» сентября 2026 года). Используется
в ТОРГ-12 (`report_bill.xml:746`) и остальных формах.

### Часовой пояс

`res.users.tz` + `res.partner.tz` в ядре. Хабаровск — `Asia/Vladivostok`, настройка,
кода не требует.

## 2. Валюта, числа, рубль, сумма прописью

### Рубль

`odoo/odoo/addons/base/data/res_currency_data.xml:337-345`:

```xml
<record id="RUB" model="res.currency">
    <field name="name">RUB</field>
    <field name="iso_numeric">643</field>
    <field name="full_name">Russian ruble</field>
    <field name="symbol">руб</field>
    <field name="rounding">0.01</field>
    <field name="active" eval="False"/>
    <field name="currency_unit_label">Ruble</field>
    <field name="currency_subunit_label">Kopek</field>
</record>
```

Два действия при внедрении:
1. `active = False` → включить рубль (галочка в справочнике валют).
2. `currency_unit_label` / `currency_subunit_label` — поля `translate=True`
   (`odoo/odoo/addons/base/models/res_currency.py:45-46`), вписать «рубль»/«копейка».

`position` по умолчанию `'after'` (`res_currency.py:42`) — «1 234,56 руб», правильный
порядок для РФ. `decimal_places` считается из `rounding`
(`res_currency.py:163-168`): 0.01 → 2 знака.

### Разделители разрядов

Тоже из `res.lang`: `grouping = [3,0]`, `decimal_point = ","`, `thousands_sep = " "`
(та же строка `res.lang.csv:64`). Получается `1 234 567,89` — как надо.
Разделитель — обычный пробел (U+0020), не неразрывный; в HTML-печати это может дать
перенос строки внутри числа. Мелочь, но при вёрстке форм видно.

### Цена за единицу с бо́льшей точностью (за кг, за тонну)

Отдельный механизм — `decimal.precision`, запись `Product Price`. Не связан с
`decimal_places` валюты. Для металла ставится 4–5 знаков.

### Сумма прописью — три реализации, две из них годные

**(а) Ядро Odoo — НЕ годится.** `res.currency.amount_to_text`,
`odoo/odoo/addons/base/models/res_currency.py:175-202`:

```python
def _num2words(number, lang):
    return num2words(number, lang=lang).title()
...
return self.env._('%(integral_amount)s %(currency_unit)s',
    integral_amount=_num2words(integer_value, lang=lang.iso_code),
    currency_unit=self.currency_unit_label)
```

Используется `to='cardinal'` + подстановка фиксированной метки → по-русски получится
«Сто Двадцать Три рубль» (нет согласования числа с существительным, плюс `.title()`
капитализирует каждое слово). **Для российских форм не использовать.**

**(б) RuOdoo `report_monetary_helpers` — годится.** Прокидывает в контекст рендеринга
любого отчёта три функции (`ruodoo/report_monetary_helpers/models/ir_actions_report.py:15-24`):
`number2words`, `currency2words`, `format_number`. Реализация —
`utils/num2words.py:24-40`, `num2words(..., to='currency', lang='ru', currency='RUB')`,
целая часть капитализируется, копейки дописываются двумя цифрами.
Зависимость: `num2words` (pip).

**(в) RuOdoo `l10n_ru_doc` — годится, и именно она используется в формах.**
`ruodoo/l10n_ru_doc/report_helper.py:44-49`:

```python
def rubles(self, sum):
    text_rubles = numeral.rubles(int(sum))
    copeck = round((sum - int(sum))*100)
    text_copeck = numeral.choose_plural(int(copeck), ("копейка", "копейки", "копеек"))
    return ("%s %02d %s")%(text_rubles, copeck, text_copeck)
```

`pytils.numeral` — правильные падежи и склонения. Зависимость: `pytils` (pip).
Плюс поле на заказе продаж: `sale.order.amount_total_words`
(`ruodoo/l10n_ru_doc/models/sale.py:11-15`) — хранимое computed, доступно в любом отчёте.

Итог: сумма прописью закрыта полностью. В Carbon её нет вообще.

## 3. Адреса

### Поля ядра

`res.partner`: `street`, `street2`, `city`, `state_id` (справочник
`res.country.state`), `zip`, `country_id`. Россия в справочнике стран есть.
Субъекты РФ — в `odoo/odoo/addons/base/data/res.country.state.csv` для части стран;
для RU надо проверить и при необходимости залить (файл — обычный CSV, заливается
импортом).

### Что добавляет RuOdoo

`ruodoo/l10n_ru_upd_xml/models/res_partner.py:11-13`:

```python
house = fields.Char(_('Дом'))
office = fields.Char(_('Квартира, офис'))
fias_id = fields.Char(_('Код ФИАС'))
```

То есть дом/офис отдельными полями и **код ФИАС** — этого в Carbon нет в принципе
(там нет даже места под район/населённый пункт).

### Порядок вывода адреса

RuOdoo переопределяет порядок в печати — `ruodoo/l10n_ru_doc/report_helper.py:57-70`,
метод `address(partner)` собирает: `zip, country, state, city, street, street2`.
Это российский порядок («680000, Российская Федерация, Хабаровский край,
Хабаровск, ул. ...»). В Carbon `formatAddress` даёт западный порядок и требует
переписывания (`packages/utils/src/address.ts:43-68`).

Оговорка: это порядок **только в печатных формах RuOdoo**. Стандартный
`res.partner.contact_address` (используется на экране и в письмах) остаётся
западным, он собирается из `country_id.address_format`. Меняется правкой
`address_format` у записи страны Россия — данные, не код.

### Автодополнение адреса и реквизитов

`ruodoo/dadata_connector` — интеграция с DaData. Механика:
`models/res_partner.py:41` → `dadata.find_by_id("party", vat, branch_type="MAIN")`,
то есть **по ИНН тянутся все реквизиты контрагента**. Что реально записывается
(`models/res_partner.py:98-120`): `vat`, `okpo`, `ogrn`, `kpp` (для ЮЛ), `name`
(краткое с ОПФ), адрес, ФИО руководителя (создаётся дочерний контакт).

Два поля из ответа DaData **никуда не пишутся**, потому что таких полей в системе нет:
`result["arceat"] = data["okved"]` (ОКВЭД) и `result["company_form"]`
(`models/res_partner.py:100-101`). Проверено грепом по всему `ruodoo/` и
`odoo/addons/` — полей `arceat`, `company_form`, `sp_register_number`,
`sp_register_date` не существует. Ошибки не будет: JS-виджет явно отбрасывает
неизвестные поля — `static/src/views/fields/search/search_field.js:41`,
`const field = record.fields[key]; if (!field) continue;`. **ОКВЭД просто теряется.**

Токен DaData — в настройках (`dadata_connector.dadata_token`), внешняя зависимость
`dadata==21.10.1`.

Сравнение: в Carbon автодополнение — Google Places, для РФ непригодно
(`AddressAutocomplete.tsx`). Здесь — DaData «из коробки». Существенный плюс.

## 4. Реквизиты контрагентов: ИНН, КПП, ОГРН, ОКПО, банк

### ИНН

**ИНН = штатное поле ядра `res.partner.vat`**
(`odoo/odoo/addons/base/models/res_partner.py:237`), переименованное в интерфейсе.
`ruodoo/l10n_ru_doc/views/res_partner_view.xml:19-21`:

```xml
<xpath expr="//field[@name='vat']" position="attributes">
    <attribute name="string">ИНН</attribute>
</xpath>
```

Плюс `res.partner.inn` как related-алиас на `vat`
(`ruodoo/l10n_ru_doc/models/res_partner.py:4`), скрытый в форме
(`res_partner_view.xml:11` — `invisible="True"`, с комментарием `<!-- reason: need-->`);
он нужен только для шаблонов и XML.

**Важная тонкость с наложением модулей.** Поле `inn` объявлено дважды:

- `ruodoo/l10n_ru_doc/models/res_partner.py:4` → `fields.Char('INN', related='vat')`
- `ruodoo/l10n_ru_upd_xml/models/res_partner.py:6` → `fields.Char(_('ИНН'), size=12)`

`l10n_ru_upd_xml` зависит от `l10n_ru_doc`, то есть грузится позже. По механике
слияния атрибутов поля (`odoo/odoo/orm/fields.py:414-431`, `_get_attrs`:
`attrs.update(field._args__)` в порядке переопределения, затем `attrs.update(self._args__)`)
атрибуты **накапливаются**, а не заменяются — типы совместимы (оба `Char`), поэтому
`related='vat'` сохраняется, а `size=12` добавляется. Итог: `inn` остаётся
related-полем на `vat`, единая точка истины — `vat`. Это надо один раз проверить на
живом инстансе (`res.partner.fields_get(['inn'])`), потому что весь XML УПД читает
именно `pid.inn`.

**Проверка контрольной суммы ИНН есть в ядре**:
`odoo/addons/base_vat/models/res_partner.py:607-640`, `check_vat_ru` — полный алгоритм
для 10 и 12 знаков (скопирован из библиотеки `vatnumber`). Включается галочкой
«Verify VAT Numbers» у компании. В Carbon валидации нет никакой
(`z.string().optional()`).

### КПП, ОКПО, ОГРН

`ruodoo/l10n_ru_doc/models/res_partner.py:5-8`:

```python
kpp  = fields.Char('KPP', size=9)
okpo = fields.Char('OKPO', size=14)
ogrn = fields.Char('ОГРН')
```

Выводятся в форме контрагента только для юрлиц
(`res_partner_view.xml:12-14`, `invisible="is_company==False"`).

У компании (`res.company`) те же реквизиты через related на партнёра —
`ruodoo/l10n_ru_doc/models/res_company.py:6-8` (`inn`, `kpp`, `okpo`, все с
`readonly=False`, то есть редактируемые).

Сравнение с Carbon: там КПП **негде хранить вообще**, ОГРН есть только у компании и
спрятан за страновым гейтом, из которого RU исключён (`packages/utils/src/country.ts:6-32`).

### Подписанты и печать

Это то, чего в Carbon нет и близко.

`ruodoo/l10n_ru_doc/models/res_partner.py:9-11`:
```python
type = fields.Selection(selection_add=[('director', 'Директор'), ('accountant', 'Бухгалтер')])
facsimile = fields.Binary("Подпись")
stamp = fields.Binary("Печать")
```

`ruodoo/l10n_ru_doc/models/res_company.py:9-20`: `chief_id`, `accountant_id`
(ссылки на `res.users`), `print_facsimile`, `print_stamp`, `stamp`, `print_anywhere`
(«ставить факсимиле только в письме или всегда»).

Печатные формы это используют — `report_bill.xml:626,658,744`: подпись руководителя,
подпись бухгалтера, печать организации вставляются картинкой через
`helper.img()` (`report_helper.py:9-23`). Инициалы — `helper.initials()`
(`report_helper.py:51-54`): «Иванов И.И.».

### Банковские реквизиты

Основа — ядро: `res.partner.bank` с `acc_number` (расчётный счёт),
`bank_id` → `res.bank` с `bic` (БИК), и related `bank_bic`
(`odoo/odoo/addons/base/models/res_bank.py:90,98`).

RuOdoo добавляет корсчёт — `ruodoo/l10n_ru_doc/models/res_bank.py`:

```python
class Bank(models.Model):
    _inherit = 'res.bank'
    corr_acc = fields.Char('Corresponding account', size=64)

class ResPartnerBank(models.Model):
    _inherit = 'res.partner.bank'
    bank_corr_acc = fields.Char('Corresponding account', size=64)

    @api.onchange('bank_id')
    def onchange_bank_id(self):
        s.bank_name = s.bank_id.name
        s.bank_bic  = s.bank_id.bic
        s.bank_corr_acc = s.bank_id.corr_acc
```

То есть полный комплект: **р/с + БИК + к/с + наименование банка**, с автоподстановкой
из справочника банков при выборе банка.

Печатается: в «Счёте на оплату» — `ruodoo/l10n_ru_doc/report/report_order.xml:127`
(банк + город), `:133` (БИК), `:143` (корсчёт), `:162` (расчётный счёт).
В ТОРГ-12 — через `helper.full_representation()`
(`report_helper.py:85-104`), который собирает строку «Название, ИНН …, КПП …, адрес,
тел., р/сч …, в банке …, БИК …, к/с …».

Сравнение с Carbon: там банковских реквизитов контрагента **нет ни одной колонки**
(единственный `bankAccount` — FK на свой GL-счёт), и вывод «Счёта на оплату»
невозможен. Здесь всё готово.

## 5. НДС 20 %

### Модель налога

Odoo — полноценная модель `account.tax`, а не число на строке. Ключевое:

- `amount = fields.Float(required=True, digits=(16, 4))`
  (`odoo/addons/account/models/account_tax.py:133`) — ставка в процентах (20, не 0.20).
- `amount_type` (`:84`) — `percent` / `fixed` / `group` / `division`.
  `division` — это «налог от суммы с налогом», то есть штатно поддерживается схема
  «20/120» для авансов.
- `type_tax_use` (`:81`) — `sale` / `purchase` / `none`.
- `tax_group_id` (`:156-161`) — группа налога; на этом строятся итоги с разбивкой
  по ставкам.
- `include_base_amount`, `is_base_affected` (`:148-153`) — каскад налогов.
- `tax_exigibility` (`:169-176`) — `on_invoice` / `on_payment`, то есть НДС «по отгрузке»
  или «по оплате», с транзитным счётом `cash_basis_transition_account_id`.
- Репартиция — `invoice_repartition_line_ids` / `refund_repartition_line_ids`:
  на какие счета ложатся база и налог, отдельно для счёта и для корректировки.
  Это то место, куда маппятся 19 и 68.02.

**Ставки 20 / 10 / 0 / «без НДС» — создаются записями `account.tax`, кода не требуют.**
Единственное: RuOdoo **не создаёт** их за вас — модуля с российскими налогами нет
(проверено: `chart_template` в `ruodoo/` встречается только в двух `.po`-файлах
переводов). Без плана счетов РФ подставится `generic_coa` с двумя налогами 15 %
(`odoo/addons/account/data/template/account.tax-generic_coa.csv:2,6`) — их надо либо
переименовать/перенастроить, либо создать свои.

Это главное отличие от Carbon, где та же функция — мёртвый код.

Два уровня. Дефолт компании —
`odoo/addons/account/models/company.py:272-278`:

Переопределение на конкретном налоге —

И парная величина на строке —

итог строки, посчитанный только по налогам с `invisiblePF == False`. Нужно, когда в

### Найденный дефект в ТОРГ-12

`ruodoo/l10n_ru_doc/report/report_bill.xml:358-359`:

```xml
<t t-set="page_tax"  t-value="sum([line.price_unit*line.quantity - line.price_subtotal for line in o.invoice_line_ids])"/>
<t t-set="total_tax" t-value="sum([line.price_unit*line.quantity - line.price_subtotal for line in o.invoice_line_ids])"/>
```

Разность «цена × количество − подытог» равна сумме НДС **только если** налог

даст ноль. При наличии скидки (`line.discount`) разность даст **сумму скидки**, а не
НДС. Колонка «Сумма НДС» в ТОРГ-12 (`:391`, `:402`) в этих случаях врёт.
Счёт-фактура этой ошибки не содержит — там `price_total_pf`. Лечится заменой формулы
на ту же, что в счёте-фактуре.

## 6. Нумерация документов

Два независимых механизма, и оба подходят под РФ.

### Счета и все бухгалтерские документы — `SequenceMixin`

`odoo/addons/account/models/sequence_mixin.py:31-45`:

```python
prefix = r'(?P<prefix1>.*?)'
prefix2 = r'(?P<prefix2>\D)'
seq = r'(?P<seq>\d*)'
year = r'(?P<year>((?<=\D)|(?<=^))((19|20|21)\d{2}|(\d{2}(?=\D))))'
_sequence_yearly_regex = fr'^{prefix}(?P<year>...)(?P<prefix2>\D+?){seq}{suffix}$'
_sequence_monthly_regex = ...
_sequence_year_range_regex = ...
_sequence_fixed_regex = fr'^{prefix}(?P<seq>\d{{0,9}}){suffix}$'
```

Номер не берётся из `ir.sequence` — он **выводится из номера предыдущего документа
того же журнала** (`_sequence_index = "journal_id"`,
`odoo/addons/account/models/account_move.py:80`). Формат распознаётся регулярками:
`_deduce_sequence_number_reset` (`sequence_mixin.py:194-206`).

Практический смысл для завода:

- Пишете у первого счёта в журнале `СЧФ-2026-00001` — дальше система сама продолжит
  `СЧФ-2026-00002` и **сама сбросит нумерацию на `СЧФ-2027-00001`** 1 января,
  потому что распознает `year`-схему.
- Кириллица в префиксе проходит: в регулярках префиксы описаны как `.*?` и `\D+?`,
  а кириллица — это `\D`. Отдельной поддержки не требуется.
- **Автосброс на новый год есть**. В Carbon его нет вообще
  (`get-next-sequence.ts:31-40` — только инкремент), и там надо писать cron.

### Прочие документы — `ir.sequence`

`odoo/odoo/addons/base/models/ir_sequence.py:138-152`: `prefix`, `suffix`,
`padding`, `number_next`, `number_increment`, `implementation`
(`standard` / `no_gap`), `use_date_range`.

Токены подстановки — `ir_sequence.py:220-223`:

```python
sequences = {'year': '%Y', 'month': '%m', 'day': '%d', 'y': '%y', 'doy': '%j',
             'woy': '%W', 'weekday': '%w', 'h24': '%H', 'h12': '%I',
             'min': '%M', 'sec': '%S', 'isoyear': '%G', 'isoy': '%g', 'isoweek': '%V'}
```

плюс варианты `range_*` и `current_*`. То есть префикс
`ЗП-%(range_year)s-` + `use_date_range=True` + `padding=5` даёт `ЗП-2026-00042`
с честным сбросом счётчика по годовым поддиапазонам.

Дефолт заказа продаж — `odoo/addons/sale/data/ir_sequence_data.xml:4-10`:
`prefix = S`, `padding = 5`. Меняется в интерфейсе, кода не требует.

`implementation = 'no_gap'` — важная опция: гарантирует нумерацию **без пропусков**
(за счёт блокировки строки). Для российской первички, где пропуск номера — вопрос
к бухгалтеру, это правильный режим.

### Что не так внутри форм — точечно

**ТОРГ-12, код ОКЕИ захардкожен.** `report_bill.xml:367`:

```xml
<TD CLASS="R25C5">796<!-- TO DO: БазоваяЕдиницаКодПоОКЕИ --></TD>
```

796 — «штука». Для завода, отпускающего в тоннах (168), метрах (006) и килограммах
(166), это неверно для каждой строки. Автор оставил `TO DO`. Данные для подстановки
уже есть — `uom.uom.okei` (см. §8), надо подставить поле вместо константы.

**ТОРГ-12, сумма НДС** — см. §5, формула `price_unit*qty - price_subtotal`.

**Счёт-фактура, ставка НДС берётся у первого налога и потом фильтруется.**
`report_invoice.xml:219`:

```xml
<t t-esc="line.tax_ids[0].filtered(lambda tax: tax.invisiblePF == False).amount
          if line.tax_ids.filtered(lambda tax: tax.invisiblePF == False) else ''"/>
```

Условие проверяет, что **хоть один** видимый налог есть, а значение берёт из
`tax_ids[0]` и фильтрует его. Если первый налог — технический (`invisiblePF=True`),
а второй — НДС 20 %, в графе «Налоговая ставка» будет пусто. Правится на
`line.tax_ids.filtered(...)[0].amount`.

**Доверенность — не унифицированная форма М-2.** `l10n_ru_attorney` — своя модель
`base.consent` (`models/base_consent.py:14-23`: `name`, `date_from`, `date_to`,
`partner_id`, `employee_id`, `purchaseorder_id`, `company_id`), строки ТМЦ берутся из
заказа на закупку (`report/consent_report.xml:249-261`), паспорт — из
`hr.employee.passport_id` (`:175`). Это рабочий документ, но **не бланк ОКУД 0315002
с корешком**. Если банк или поставщик требует именно М-2 — форму надо верстать.
README модуля устарел: там написано, что отчёт надо вручную добавлять в меню «Печать»,
но `binding_model_id` в XML уже задан (`consent_report.xml:17`), кнопка появится сама.

**Акт сверки** — построен на собственной реализации главной книги
(`l10n_ru_act_rev/report/general_ledger.py`, визард
`wizard/general_ledger_wizard.py`: период, `target_move` = «все проведённые» /
«включая черновики», фильтры по счетам/партнёрам/журналам, `centralize`,
`foreign_currency`). Печатается из карточки контакта → Действия. Это единственный
способ получить главную книгу в Community — в ядре её нет (см. §9).

## 8. УПД в XML и точка стыковки с ЭДО

### Что есть

`ruodoo/l10n_ru_upd_xml` — генератор XML-файла УПД. Не «заготовка», а рабочий
генератор на 343 строки шаблона.

**Шапка файла** — `reports/upd_report.xml:16-27`:

```xml
<Файл ИдФайл="..." ВерсФорм="5.03" ВерсПрог="Odoo19">
  <Документ КНД="1115131" Функция="СЧФДОП"
            ПоФактХЖ="Документ об отгрузке товаров (выполнении работ)..."
            НаимДокОпр="Счет-фактура и документ об отгрузке товаров..."
            ДатаИнфПр="..." ВремИнфПр="..." НаимЭконСубСост="...">
```

КНД 1115131, функция `СЧФДОП` (счёт-фактура + передаточный документ в одном) —
то есть полноценный УПД, а не только накладная.

**Расхождение версии формата.** Манифест заявляет 5.01
(`l10n_ru_upd_xml/__manifest__.py:6` — «Формирует УПД в формате XML, формат 5.01»),
шаблон отдаёт `ВерсФорм = '5.03'` (`upd_report.xml:17`). Это надо сверить с тем,
что принимает оператор ЭДО заказчика, — расхождение в описании модуля обычно значит,
что версию поднимали, а манифест не поправили.

**Кодировка** — `reports/report_report_xml_abstract.py:163-171`:

```python
content = etree.tostring(etree.fromstring(result),
    encoding=ir_report.xml_encoding or "WINDOWS-1251",
    xml_declaration=True, pretty_print=True)
```

WINDOWS-1251 по умолчанию (как требует ФНС), с возможностью переопределить на записи
отчёта. Отдача — через свой контроллер `controllers/main.py:19-47` (перехватывает
`converter == "xml"`), `Content-Type: text/xml`, то есть файл скачивается.

**Имя файла — по конвенции Диадока.** `models/account_move.py:22-23`:

```python
self.edi = 'ON_NSCHFDOPPR_2BM-' + str(pid.edi) + '_' + str(self.company_id.edi) \
           + '_' + hash_object.hexdigest()
```

`ON_NSCHFDOPPR` — стандартный префикс имени файла УПД; `pid.edi` и `company.edi` —
идентификаторы участников ЭДО (`res.partner.edi`,
`l10n_ru_upd_xml/models/res_partner.py:9`; `res.company.edi`,
`models/res_company.py:9`). Хвост — sha1 от номера документа. Файл с таким именем
Диадок/СБИС принимает на загрузку.

**Предполётная валидация — сильная сторона.** `models/account_move.py:32-207`,
метод `check_correct_upd` — 40+ проверок перед формированием: ИНН компании и
контрагента (с разбором 10 vs 12 знаков → ЮЛ vs ИП), КПП, ОКПО, город, улица,
руководитель с должностью и ФИО, грузоотправитель, грузополучатель, ответственный за
передачу с должностью, договор, реквизиты платёжки, по каждой строке — цена,
количество и **код ОКЕИ**. Всё выдаётся одним списком в `UserError`. Это заметно
лучше, чем «сформировали и оператор отбил».

### Точка стыковки с ЭДО — есть, но только файловая

**Чего нет, прямо:**

- Нет API ни Диадока, ни СБИС, ни Такскома. Проверено: грепом по всему `ruodoo/`
  слово «Diadoc» встречается **только в текстах сообщений об ошибках**
  (`models/account_move.py:46,88,114`, `reports/report_report_xml_abstract.py:40`).
  Ни одного HTTP-вызова к оператору нет.
- Нет квалифицированной электронной подписи. Грепом по `ruodoo/`:
  `cryptopro`, `КриптоПро`, `gost`, `pkcs7`, `xmldsig` — **ноль попаданий**.
- Нет разбора **входящих** УПД от поставщиков. Парсинг XML в модуле есть только в
  тестах и в самом рендерере (`tests/test_upd_xml.py`,
  `reports/report_report_xml_abstract.py`), импорта нет.
- Нет статусов документооборота, квитанций, роуминга между операторами.
- Нет отдельной функции `СЧФ` (только счёт-фактура, без передаточного документа) —
  в шаблоне единственное значение `Функция="СЧФДОП"`.

**Итого реальный сценарий на сегодня:** нажать «Печать УПД в xml-формате», получить
файл, вручную загрузить в веб-кабинет Диадока/СБИС, там подписать и отправить.
Для завода с десятками реализаций в месяц это терпимо; для сотен — нет.

**Куда встраивать автоматизацию.** В Community есть готовый каркас ЭДО, которым
RuOdoo не пользуется:

- `odoo/addons/account_edi` — модели `account.edi.format`, `account.edi.document`
  со статусами: `odoo/addons/account_edi/models/account_edi_document.py:26-33` —
  `state` из `to_send` / `sent` / `to_cancel` / `cancelled`, поле `error` (HTML),
  `blocking_level` (`info` / `warning` / `error`). Плюс `account_edi/models/account_move.py`
  и cron-отправка. Это ровно та машина состояний, которая нужна для документооборота
  с оператором.
- `odoo/addons/account_edi_ubl_cii/models/` — 15 классов-форматов
  (`account_edi_xml_ubl_20.py`, `ubl_21.py`, `ubl_bis3.py`, `xrechnung`, `nlcius`,
  `facturx`…). Это образец, **как правильно** делать страновой XML в Odoo: класс-наследник
  с `_export_invoice`, встроенные проверки, привязка к `account.move.send`. RuOdoo
  делает XML через QWeb-шаблон, что работает, но не даёт ни валидации по схеме, ни
  интеграции с механизмом отправки.

То есть коннектор к Диадоку — это модуль, который регистрирует свой
`account.edi.format`, переиспользует готовый XML-рендер RuOdoo и вешает на него
HTTP-клиент оператора. Подпись — единственная часть, которую нельзя сделать на
питоне «внутри Odoo»: нужен внешний сервис с КриптоПро.

Сравнение с Carbon: там ЭДО-точки стыковки нет вообще — ни XML, ни модели статусов;
всё пришлось бы строить с нуля во внешнем сервисе (`experiments/carbon/analysis/12-…md`, §11.1).

### ОКЕИ и ТНВЭД: поля есть, но с сюрпризами

Три отдельных поля, два из них — дубликаты одной сущности:

| Поле | Где | Назначение |
|---|---|---|
| `uom.uom.okei` | `ruodoo/l10n_ru_upd_xml/models/uom_uom.py:6` | «Код ОКЕИ» — используется в валидации УПД |
| `uom.uom.kod` | `ruodoo/l10n_ru_doc/models/uom.py:5` | «Код единицы измерения» — тот же ОКЕИ, другое поле |
| `product.product.kod_tnved` | `ruodoo/l10n_ru_doc/models/product.py:5` | «Код ТНВЭД» |

Оба поля единицы измерения выводятся в одну и ту же форму разными представлениями
(`l10n_ru_doc/views/uom.xml:10` → `kod`; `l10n_ru_upd_xml/views/views_uom_okei.xml:9`
→ `okei`). При установке обоих модулей в форме единицы измерения будет **два поля под
один код**. Надо выбрать одно и вычистить второе.

**Справочник ОКЕИ не предзаполнен.** Проверено: в `l10n_ru_upd_xml/demo/demo.xml:7`
единственное значение `796`, и то демо-данные. Коды ОКЕИ придётся вбить руками для
каждой используемой единицы (для завода это 5-10 записей: 166 кг, 168 т, 006 м,
055 м², 796 шт).

**И главное: валидация требует ОКЕИ, а XML его не пишет.** Валидатор ругается
«Не указан код ОКЕИ для единицы измерения» (`models/account_move.py:172-173`,
`reports/report_report_xml_abstract.py:129-130`), но в шаблоне УПД атрибута с кодом
ОКЕИ нет — проверено: `grep -c "ОКЕИ" upd_report.xml` → **0**. В XML уходит только
текстовое наименование единицы: `upd_report.xml:212`,
`'НаимЕдИзм': line.product_uom_id.name`. Формат ФНС в `СведТов` предусматривает
`ОКЕИ_Тов`; его надо дописать.

### Три дефекта в XML УПД, которые надо править до первой отправки

**(1) Номер документа берётся из источника, а не из счёта.**
`upd_report.xml:30-31`:

```xml
<СвСчФакт НомерДок="..." ...>
```
значение — `o and (o.invoice_origin or o.name) or ''`.

`invoice_origin` — это ссылка на исходный документ (номер заказа продаж, например
`S00042`). То есть в графу «Номер счёта-фактуры» уйдёт **номер заказа**, а не номер
счёта, если поле `invoice_origin` заполнено (а оно заполнено всегда, когда счёт создан
из заказа). Такая же подстановка в `РеквНомерДок` (`:146`, `:277`). Это надо поменять
на `o.name` — иначе номер в ЭДО не совпадёт с номером в учёте и в ТОРГ-12.

**(2) Страна происхождения захардкожена «Китай».** `upd_report.xml:225`:

```xml
<t t-if="line.product_id and line.product_id.tracking == 'serial'">
    <КрНаимСтрПр>Китай</КрНаимСтрПр>
```

Для любой позиции с серийным учётом в УПД уйдёт страна происхождения «Китай».
Для завода металлоконструкций в Хабаровске это прямая ошибка в юридически значимом
документе. Поля «страна происхождения» в системе нет — проверено: `country_of_origin`
в Odoo Community есть только в `addons/stock_delivery/models/product_template.py`
(в контексте доставки), и RuOdoo его не использует. Надо либо завести поле и
подставлять, либо убрать блок.

**(3) Ссылка на несуществующее поле в том же блоке.** `upd_report.xml:230-231`:

```xml
<t t-if="lot.lot_id and lot.lot_id.cz_code_id">
    <КИЗ><t t-esc="lot.lot_id.cz_code_id.code_without_characters"/></КИЗ>
```

`cz_code_id` — код «Честного ЗНАКа». Проверено грепом по `odoo/addons/` и по всему
`ruodoo/`: поля `cz_code_id` **не существует нигде**, кроме этой строки шаблона.
Значит для любого товара с `tracking == 'serial'` рендер УПД упадёт. Для завода это
сработает, как только начнут вести серийный учёт изделий. Блок надо убрать (маркировка
металлоконструкций не требуется) либо завести поле.

**Плюс мягкая зависимость:** `upd_report.xml:222` читает `line.product_id.hs_code`.
Поле объявлено в `odoo/addons/stock_delivery/models/product_template.py:9`, а
`l10n_ru_upd_xml` от `stock_delivery` не зависит (`depends`: `web`, `base`, `account`,
`account_payment`, `l10n_ru_doc`, `l10n_ru_base`, `uom`). `stock_delivery` помечен
`auto_install: True` и зависит от `sale_stock` + `delivery`
(`addons/stock_delivery/__manifest__.py:14,33`) — то есть доустановится сам, только
если поставить `delivery`. Если `delivery` не ставить — рендер УПД упадёт на
отсутствующем `hs_code`. Вывод: `delivery` обязателен к установке.

**Отдельно — хрупкая связка с отгрузками.**
`ruodoo/l10n_ru_doc/models/account_invoice.py:75-79`, `get_delivery_doc_name`:

```python
orders = self.env['sale.order'].sudo().search([('name','=',s.invoice_origin)]) if s.invoice_origin else []
```

Поиск заказа точным совпадением имени с `invoice_origin`. Если счёт собран из
нескольких заказов, `invoice_origin` содержит список через запятую → заказ не
найдётся → в УПД не попадут номера отгрузок, а валидация выдаст «Отсутствуют
связанные отгрузки» (`models/account_move.py:38-39`) и **заблокирует формирование**.
Для завода, где один счёт часто закрывает несколько заказов, это сработает быстро.

## 9. План счетов РСБУ и регламентированная отчётность

### Плана счетов РФ нет — ни в Odoo, ни в RuOdoo

Проверено:

- `l10n_ru` в `addons/` — **нет** (231 модуль `l10n_*`, ни одного `l10n_ru*`).
- Россия отсутствует в официальном списке фискальных локализаций:
  `odoo-docs/content/applications/finance/fiscal_localizations.rst:126-131`.
- В `ruodoo/` слово `chart_template` встречается **только** в двух файлах переводов
  (`translation_helper/translations/ru/account.po`, `sale.po`). Ни одного
  `account.account` в данных, ни одного счёта вида `62.01` / `68.02` / `90.01`.

Что подставится по факту — `generic_coa`
(fallback в `odoo/addons/account/models/chart_template.py:127`):
`odoo/addons/account/data/template/account.account-generic_coa.csv`, 46 счётов
англосаксонского вида:

```
"current_assets","Current Assets","1010","asset_current",...
"stock_valuation","Stock Valuation","1101","asset_current",...
"cost_of_production","Cost of Production","1104","asset_current",...
"wip","Work in Progress","1105","asset_current",...
```

и два налога 15 % (`account.tax-generic_coa.csv:2,6`).

### Что делать

Хорошая новость: `account.account.code` — обычное текстовое поле, `62.01` и `68.02`
в него ложатся. Плюс есть `account.group` (группировка счётов по префиксу кода) и
модель `account_code_mapping` (`addons/account/models/account_code_mapping.py`).
То есть план счетов РСБУ **заводится данными**: CSV-импорт 200-400 строк, без кода.

Что надо решить руками при этом:
1. **`account_type`** — закрытое перечисление Odoo (`asset_current`,
   `asset_receivable`, `liability_payable`, `income`, `expense_direct_cost`…).
   Каждый счёт РСБУ надо смаппить на один из типов; от этого зависит поведение
   сверки, отчётов и закрытия периода. Это содержательная работа бухгалтера, не
   механическая.
2. **Субсчёта и аналитика.** РСБУ-аналитика (по контрагентам, договорам, номенклатуре)
   в Odoo делается не субсчётами, а `analytic_distribution` + партнёром на строке.
   Это другая методология учёта — её надо принять, а не воспроизводить 1С.
3. **Налоговые счета.** Через `invoice_repartition_line_ids` налога
  (`account_tax.py`) — 19 на входящий НДС, 68.02 на исходящий.

### Регламентированной отчётности нет — и её не надо делать

В Community `account` есть движок отчётов (`account.report`, `account.report.column`,
`account/models/account_report.py`), но **данных всего три записи**
(`odoo/addons/account/data/account_reports_data.xml`):
`generic_tax_report`, `generic_tax_report_account_tax`, `generic_tax_report_tax_account`.

Проверено грепом по `addons/account/`: `balance_sheet`, `profit_and_loss`,
`general_ledger` — ни одной записи отчёта (единственное попадание
`account_type_selection.js` — это компонент выбора типа счёта). В представлениях
`addons/account/views/*.xml` из знакомых названий есть только `Partner Ledger`
(`account_move_views.xml:1910`).

То есть в Community **нет**: баланса, ОПУ, оборотно-сальдовой ведомости, главной
книги, отчётов по срокам задолженности. Всё это — `account_reports`, Enterprise.
Отсюда и понятно, почему RuOdoo сделал собственную главную книгу внутри модуля
акта сверки (`l10n_ru_act_rev/report/general_ledger.py`) — иначе акт сверки не
собрать.

Нет тем более: декларации по НДС, книг покупок и продаж, журнала счетов-фактур,
6-НДФЛ, РСВ, форм Минфина. Ни в Odoo Community, ни в RuOdoo.

**Вывод тот же, что по Carbon (§11.4):** регламентированный учёт и отчётность отдать
1С или бухгалтерскому аутсорсу. Odoo держит контур «продажи → производство → склад →
первичка», 1С — регламентированный учёт.

## 10. Обмен с 1С

### Что реально умеет `account_bank_statement_1c_import`

Модуль один, 202 строки логики. Разбор по коду
(`ruodoo/account_bank_statement_1c_import/wizard/invoice_import_wizard.py`):

**Формат.** Только `.txt` (`:25-27`, жёсткая проверка расширения), декодирование
`cp1251` (`:29`). Это формат **1CClientBankExchange** — выгрузка «банк → клиент»,
которую делает «1С:Бухгалтерия» или интернет-банк. Разбор — примитивный, по строкам
`ключ=значение` (`:70-77`), секции делятся по литералам `СекцияДокумент` (`:37`) и
`СекцияРасчСчет` (`:39`).

**Что вытягивает.** Из шапки выписки (`:80-87`): `РасчСчет`, `НачальныйОстаток`,
`КонечныйОстаток`, `ДатаНачала`. Из каждой транзакции (`:108-137`): `Дата`, `Сумма`,
`Номер`, `НазначениеПлатежа`, и полный набор реквизитов обеих сторон —
`ПлательщикИНН` / `ПлательщикКПП` / `Плательщик` / `ПлательщикСчет` /
`ПлательщикБИК` / `ПлательщикКорсчет` / `ПлательщикБанк1` и такие же `Получатель*`.

**Что делает сам.** Определяет направление платежа сравнением ИНН своей компании
с `ПлательщикИНН` / `ПолучательИНН` (`:112`, `:120`) и ставит знак суммы.
**Создаёт отсутствующего контрагента** по ИНН+КПП (`:160-167`), **создаёт банк**
по БИК+корсчёту (`:169-175`), **создаёт расчётный счёт контрагента** (`:177-183`).
Дедуплицирует строки по (дата, сумма, назначение, номер) (`:150-158`).

Это неплохо: одним импортом выписки в системе заводятся контрагенты с ИНН, КПП,
банком и счётом.

### Чего не хватает

1. **Только импорт, обратной выгрузки нет.** Платёжных поручений из Odoo в банк
   (секция `СекцияДокумент` на выход) модуль не формирует. То есть исходящие платежи
   придётся вбивать в банке руками или писать выгрузку.
2. **Один банковский счёт.** `:30-31`:
   ```python
   journal = self.env['account.journal'].search(
       [('type','=','bank'), ('use_in_bank_statement','=',True)], limit=1)
   ```
   Берётся **первый** журнал с галочкой, независимо от того, по какому счёту выписка.
   Если у завода два расчётных счёта — импорт свалит всё в один журнал.
3. **Поиск выписки по дате без привязки к журналу.** `:114-116`:
   ```python
   statement = self.env['account.bank.statement'].search([('date_from','=',transaction_date)], limit=1)
   ```
   Ищется выписка, у которой `date_from` равна **дате транзакции**. Для выписки за
   период (а такие и выгружают) `date_from` совпадёт только с первым днём — остальные
   транзакции упадут с «Statement not found». То есть модуль рассчитан на
   **однодневные** выписки. Это серьёзное ограничение, и оно не описано в манифесте.
4. **Контрагент ищется по `vat` + `kpp`** (`:160`). Если ИНН в базе введён с пробелами
   или префиксом «RU» (а `base_vat` умеет нормализовать по-своему), совпадения не
   будет и создастся дубль контрагента.
5. **Нет обмена номенклатурой, контрагентами, реализацией, поступлением.** Ни
   CommerceML, ни EnterpriseData, ни какого-либо другого формата 1С. Проверено:
   в `ruodoo/` нет ни одного модуля с упоминанием CommerceML.

### Реалистичная схема

Та же, что и для Carbon (§11.2), но с более широким контуром на стороне Odoo:

| Контур | Где | Обмен |
|---|---|---|
| Продажи, КП, производство, склад, первичка (счёт, УПД, ТОРГ-12, акт) | Odoo | — |
| Регламентированный учёт, НДС-декларация, книги, зарплата, отчётность | 1С | реализация/поступление/платежи |
| Банк | Клиент-банк | `.txt` 1CClientBankExchange → Odoo (есть), Odoo → банк (нет) |

Синхронизация Odoo ↔ 1С делается через XML-RPC/JSON-RPC Odoo (штатный внешний API,
`odoo-docs/content/developer/reference/external_api.rst`) — это проще, чем в Carbon,
где пришлось бы ходить в Supabase/PostgREST.

## 13. Чего нет принципиально — и что с этим делать

Три подсистемы существуют только в российском правовом поле; ни Odoo, ни RuOdoo их
не содержат.

### 13.1 Квалифицированная электронная подпись

ГОСТ Р 34.10-2012 / КриптоПро. В питоне «внутри Odoo» это не делается — нужен внешний
сервис (КриптоПро CSP + служба подписи) или подписание в веб-кабинете оператора.
Пока файл УПД подписывается в Диадоке руками, это не проблема; при автоматизации —
это отдельный сервис, как и в случае Carbon.

### 13.2 Регламентированная отчётность

См. §9. Строить в Odoo не надо. Community даже не имеет баланса и ОСВ, а строить
российскую отчётность на движке `account.report` без Enterprise-надстройки — это
проект сам по себе.

### 13.3 Зарплата по ТК РФ

`hr` в Community есть (штат, подразделения, `passport_id`, отпуска), расчёта зарплаты
нет. Для Хабаровска это ещё и районный коэффициент + дальневосточная надбавка.
Отдать 1С:ЗУП.

### 13.4 Лицензионная гигиена RuOdoo — проверить до внедрения

Проверка манифестов 48 модулей (`grep license` по всем `__manifest__.py`) даёт
неоднородную картину:

| Лицензия | Модули |
|---|---|
| `AGPL-3` | `l10n_ru_doc`, `base_tier_validation` |
| `LGPL-3` | `l10n_ru_base`, `report_monetary_helpers`, `docx_report*`, `report_weasyprint`, `translation_helper`, `dms`, `ruodoo_setup_all` и др. |
| MIT | `access_apps`, `access_restricted`, `access_settings_menu`, `ir_rule_protected`, `pos_debranding` |
| **`OPL-1`** (проприетарная Odoo) | **`web_debranding`** |
| **`OEEL-1`** (Odoo Enterprise Edition License) | **`premium_client`** |
| **не указана** (Odoo подставит LGPL-3, `odoo/modules/module.py:432-434`) | **`l10n_ru_upd_xml`, `l10n_ru_act_rev`, `l10n_ru_attorney`, `l10n_ru_advance_payments`, `l10n_ru_contract*` (5 модулей), `account_bank_statement_1c_import`, `dadata_connector`, `mklab_*` (6 модулей)** |

То есть у **ключевых** модулей локализации (УПД XML, акт сверки, доверенность,
авансовые счета, договоры, импорт выписки, DaData) лицензия в манифесте **не
объявлена**. Odoo при загрузке подставит LGPL-3 и напишет warning
(`module.py:434`), но юридически отсутствие явной лицензии — это риск, а не
разрешение. Плюс два модуля (`web_debranding`, `premium_client`) заявлены под
платными лицензиями Odoo.

Отдельно — механика в `ruodoo/l10n_ru_base/models/res_config_settings.py:33-45`:

```python
if missing_modules:
    message = "Обратитесь в тех.поддержку для получения лицензии для следующих модулей:\n" + ...
    raise UserError(message)
```

Плюс гейт по стране (`:28-32`): если `company.country_id.code != 'RU'`, включить
российские модули нельзя. Технически проверка мягкая — она смотрит лишь, есть ли
запись в `ir.module.module`, то есть лежит ли модуль в addons-path. Но сам текст
говорит о том, что **это дистрибутив с платной поддержкой**. До внедрения надо
получить от MK.Lab письменное подтверждение условий использования — иначе на заводе
окажется юридически значимый документооборот на модулях с неясным правовым статусом.

### 13.5 Единственная неудовлетворимая зависимость на Enterprise

Проверено скриптом по всем 48 манифестам против 638 модулей `addons/` + ядра:
**неудовлетворённая зависимость одна** —

```
mklab_mrp_filters -> ['mrp_workorder']
```

`mrp_workorder` — Enterprise. Значит `mklab_mrp_filters` на Community не поставится.
Все остальные 47 модулей RuOdoo, включая всю локализацию и `l10n_ru_advance_payments`
(зависит от `l10n_latam_check` — **есть** в Community), устанавливаются на чистый
Community. Это важный положительный результат: **пласт российской локализации не
тянет за собой Enterprise.**

## 16. Что надо проверить руками, прежде чем принимать решение

1. **Слияние двойного объявления `res.partner.inn`.** По коду `_get_attrs`
   (`odoo/odoo/orm/fields.py:414-431`) атрибуты накапливаются и `related='vat'`
   должен сохраниться, но от этого зависит весь XML УПД (он читает `pid.inn`).
   Проверка: `env['res.partner'].fields_get(['inn'])` на инстансе с обоими модулями.
2. **Версия формата УПД.** Манифест — 5.01, шаблон — 5.03. Что принимает оператор
   заказчика (Диадок? СБИС?) — узнать и сверить тестовой загрузкой одного файла.
3. **Тестовая отправка УПД в Диадок** после починки четырёх дефектов из §14.12 —
   до этого никакие выводы о готовности ЭДО делать нельзя.
4. **Лицензии RuOdoo.** Получить от MK.Lab письменные условия на
   `l10n_ru_upd_xml`, `l10n_ru_act_rev`, `l10n_ru_attorney`,
   `l10n_ru_advance_payments`, `l10n_ru_contract*`, `account_bank_statement_1c_import`,
   `dadata_connector`. Это блокирующий вопрос: на этих модулях будет юридически
   значимый документооборот.
5. **Реальная выписка из банка заказчика** — прогнать через
   `account_bank_statement_1c_import` и увидеть, многодневная она или однодневная
   (от этого зависит объём доработки §14.15).
6. **Внешние python-зависимости**: `pytils`, `num2words`, `lxml`, `weasyprint`,
   `pymorphy2`, `dadata==21.10.1`. `pymorphy2` давно не развивается и на свежих
   версиях Python ставится с оговорками — проверить сборку в docker-образе до
   внедрения `l10n_ru_contract`.
7. **Реальный отпуск в тоннах** — сделать ТОРГ-12 и УПД на позицию в тоннах и
   убедиться, что после починки ОКЕИ в обе формы уходит 168, а не 796.
8. **Счёт из двух заказов продаж** — проверить, формируется ли УПД (см. §8, дефект
   в `get_delivery_doc_name`).
