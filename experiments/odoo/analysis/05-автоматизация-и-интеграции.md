Разбор по исходникам Odoo 19 Community (638 модулей в `addons/`), официальной документации
(`odoo-docs/content/`) и российской локализации RuOdoo (48 модулей).

Все ссылки `путь:строка` — от корня клона `odoo/` (ядро — `odoo/odoo/…`, модули — `odoo/addons/…`),
документация — от `odoo-docs/content/`, локализация — от `ruodoo/`.

**Граница Community/Enterprise.** Проверено наличием каталога в `addons/`:
`base_automation`, `mail`, `crm`, `sale`, `mrp`, `stock`, `purchase`, `account`, `rpc`, `api_doc`,
`attachment_indexation`, `bus`, `sms`, `iap` — **ЕСТЬ**.

## 0. Короткий ответ: «как автоматизировать X»

В Odoo Community **шесть** слоёв автоматизации. Выбор слоя — первое решение любой задачи.

| Слой | Кто настраивает | Где живёт | Когда срабатывает | Для чего |
|---|---|---|---|---|
| **1. Правила автоматизации** (`base.automation`, *automation rules*) | админ мышкой (без кода) | `addons/base_automation/models/base_automation.py` | синхронно, внутри той же транзакции | «когда случилось А — сделай Б» на любой модели |
| **2. Серверные действия** (`ir.actions.server`, *server actions*) | админ мышкой; Python-код — только `base.group_system` | `odoo/addons/base/models/ir_actions.py:567` | по вызову из правила, кнопки, крона, меню «Действие» | обновить/создать запись, письмо, активность, исходящий вебхук, Python |
| **3. Планировщик** (`ir.cron`, *scheduled actions*) | админ мышкой | `odoo/addons/base/models/ir_cron.py` | по расписанию + событийный `_trigger()` | ночные пересчёты, опросы почты, очереди |
| **4. Вычисляемые поля и онченджи** (*computed fields / onchange*) | админ мышкой (ограниченно), обычно — модуль | `odoo/addons/base/models/ir_model.py:543-582` | при чтении/записи/в форме | производные значения, автозаполнение формы |
| **5. Входящие вебхуки** (*incoming webhooks*) | админ мышкой | `addons/base_automation/controllers/main.py:6` | по HTTP POST снаружи | «внешняя система дёрнула Odoo» |
| **6. Внешний API** (JSON-2 / XML-RPC / JSON-RPC) | внешняя система по API-ключу | `addons/rpc/controllers/json2.py`, `xmlrpc.py`, `jsonrpc.py` | синхронно | любой ORM-метод модели снаружи |

Плюс **почтовый шлюз** (`fetchmail.server` + `mail.alias` + `mail.thread.message_process`) —
это отдельный, самый важный для вас механизм; ему посвящены разделы 6–7.

**Главное ограничение, которое меняет архитектуру:** из «мышиного» Python-действия
**нельзя сделать HTTP-запрос**. `safe_eval` разрешает импорт только трёх модулей —
`odoo/tools/safe_eval.py:38`:

```python
_ALLOWED_MODULES = ['_strptime', 'math', 'time']
```

`import requests`, `urllib`, `json` (как модуль), `socket` — запрещены. Единственный
«мышиный» способ достучаться наружу — серверное действие типа **«Send Webhook Notification»**
(`state='webhook'`), и оно fire-and-forget с таймаутом 1 секунда (см. 4.3). Всё остальное —
свой модуль на Python.

## 1. Правила автоматизации (`base.automation`)

Модуль `addons/base_automation/` — **в Community**. Манифест `addons/base_automation/__manifest__.py`,
зависимости: `base`, `digest`, `resource`, `mail`, `sms`.

Модель `base.automation` — `addons/base_automation/models/base_automation.py:141`.
Она наследует `mail.thread` и `mail.activity.mixin` (у самого правила есть чаттер).

### 1.1 Где это в интерфейсе

- **Настройки → Технические → Автоматизация → Правила автоматизации**
  (`addons/base_automation/views/base_automation_views.xml:243` — окно `base_automation_act`,
  `:265` — пункт меню в `base.menu_automation`).
  Меню `base.menu_custom` («Технические») закрыто группой `base.group_no_one`
  (`odoo/addons/base/views/base_menus.xml:20`) — то есть **нужен режим разработчика**.
- **Из канбана — без режима разработчика.** `addons/base_automation/static/src/group_config_menu_patch.js`
  добавляет в меню колонки канбана пункт **Automations** (иконка «волшебная палочка», `:86-96`),
  видимый при `user.isAdmin` (`:66`). При открытии он подставляет готовый триггер по типу
  группировки: «Этап установлен в …», «Добавлен тег …», «Назначен пользователь» (`:17-46`).
  Это и есть штатный «мышиный» вход в автоматизацию в Community — аналог кнопки Studio,
  которой в Community нет.
- Доступ: `addons/base_automation/security/ir.model.access.csv` — единственная строка,
  группа `base.group_system` (Настройки). Обычный менеджер правила настраивать не может.

### 1.2 Триггеры — 19 штук

`addons/base_automation/models/base_automation.py:175-198`:

| Группа | Значения `trigger` | Как работает |
|---|---|---|
| Значение поля | `on_stage_set`, `on_user_set`, `on_tag_set`, `on_state_set`, `on_priority_set` | патч `create`/`write` |
| Архивация | `on_archive`, `on_unarchive` | патч `write` |
| CRUD | `on_create`, `on_create_or_write`, `on_write` (устарел), `on_unlink` | патч `create`/`write`/`unlink` |
| Форма | `on_change` («On UI change») | регистрируется как onchange-метод |
| Время | `on_time` (по полю-дате), `on_time_created`, `on_time_updated` | крон |
| Почта/чаттер | `on_message_received`, `on_message_sent` | патч `message_post` |
| HTTP | `on_webhook` | контроллер `/web/hook/<uuid>` |

Механика: `_register_hook()` (`:851`) при старте реестра патчит методы моделей —
`create`, `write`, `_compute_field_value`, `unlink`, `_onchange_methods`, `message_post`
(`:1050-1082`, список для снятия патчей — `:1086`). Правила времени сидят на кроне
`base_automation.ir_cron_data_base_automation_check`
(`addons/base_automation/data/base_automation_data.xml:5`, код `model._cron_process_time_based_actions()`,
по умолчанию каждые 4 часа, `active=False` пока нет правил времени; интервал автоподстраивается
под самую короткую задержку — `_update_cron()`, `:664-690`).

**Почтовые триггеры — ключевые для вашего сценария.** `:1013-1038`:

```python
mail_trigger = "on_message_received" if not message_sudo.author_id or message_sudo.author_id.partner_share else "on_message_sent"
```

То есть: письмо без опознанного автора **или** от внешнего контрагента (`partner_share=True`)
→ `on_message_received`. Сообщение от внутреннего сотрудника → `on_message_sent`.
Отсекаются служебные: `is_internal`, внутренний subtype, `message_type` из
`('notification', 'auto_comment', 'user_notification')` (`:1021-1023`), и рекурсия
(`__action_done` в контексте, `:1021`). Ограничение: `@api.constrains` `:167-171` —
почтовый триггер можно вешать только на модель с `is_mail_thread=True`.

### 1.3 Условия

- `filter_domain` («Apply on», `:251`) — домен, который должен выполниться **после** изменения.
- `filter_pre_domain` («Before Update Domain», `:246`) — домен **до** изменения; не проверяется
  при создании. Пара «pre/post» даёт классическое «поле перешло из X в Y».
- `trigger_field_ids` (`:272`) — правило сработает, только если изменилось одно из этих полей;
  пусто = все поля (`_check_trigger_fields`, `:832`).
- `trg_date_id` / `trg_date_range` / `trg_date_range_mode` / `trg_date_range_type` /
  `trg_date_calendar_id` (`:218-241`) — «через N минут/часов/дней/месяцев после (до) даты»,
  опционально по рабочему календарю `resource.calendar`.

### 1.4 Что правило делает

Правило — это контейнер для одного или нескольких `ir.actions.server`
(поле `action_server_ids`, `:143`, с `usage='base_automation'`).
Исполнение — `_process()` (`:783-802`): для каждой записи формируется контекст
`{'active_model', 'active_ids', 'active_id', 'domain_post'}` и запускается `action.run()`.

Ограничения-констрейнты (`:295-320`):
- `on_change` — **только** действия типа «Execute Python Code» (`state='code'`);
- `on_unlink` — нельзя действия `mail_post`, `followers`, `next_activity` (записи уже нет);
- модель действия обязана совпадать с моделью правила.

**Важно про транзакции:** правило выполняется синхронно, внутри той же транзакции, что и
исходный `create`/`write`. Ошибка в действии откатит пользовательскую операцию. Это ровно
противоположно Carbon, где Workflows асинхронны (~3-5 с через очередь Inngest) и падение
процесса не роняет исходную операцию. Плюс Odoo: отсутствие рассинхрона. Минус: тяжёлое
действие (вызов ИИ) блокирует пользователя — его надо выносить в крон или вебхук.

## 2. Серверные действия (`ir.actions.server`)

Модель — `odoo/addons/base/models/ir_actions.py:567`. Поле `state`
(`odoo/addons/base/models/ir_actions.py:612-618`) в базе даёт 6 типов:

| `state` | Название в UI | Что делает | Реализация |
|---|---|---|---|
| `object_write` | Update Record | пишет значение в поле (в т.ч. по пути `partner_id.name`) | `:1025-1038` |
| `object_create` | Create Record | `name_create` новой записи + связка через `link_field_id` | `:1097-1109` |
| `object_copy` | Duplicate Record | `copy()` | `:1083-1095` |

| `webhook` | Send Webhook Notification | POST JSON на внешний URL | `:1040-1081` |

Модуль `mail` добавляет ещё 4 (`addons/mail/models/ir_actions_server.py:24-38`):

подписчиков), `remove_followers`.
Модуль `sms` добавляет `sms` (`addons/sms/models/ir_actions_server.py:11-13`) — но отправка
SMS идёт через платный сервис Odoo IAP.

Итого «мышиных» типов действий в Community: **11**.

### 2.1 Python-действие: что доступно и чего нет

Контекст вычисления — `odoo/addons/base/models/ir_actions.py:1111-1148` + базовый `:140-153`:

```
env, model, record, records, log(), _logger,
uid, user, time, datetime, dateutil, timezone,
float_compare, b64encode, b64decode, Command, UserError
```

`addons/base_automation/models/ir_actions_server.py:53-62` добавляет для `state='code'`

Поле `code` объявлено с `groups='base.group_system'`
(`odoo/addons/base/models/ir_actions.py:643`) — Python-код видит и правит только админ Настроек.

## 3. Планировщик (`ir.cron`)

`odoo/odoo/addons/base/models/ir_cron.py:89`. Модель `ir.cron` наследует `ir.actions.server`
через `_inherits` (`:102-105`) — то есть крон = серверное действие + расписание.

Настраиваемые мышкой поля: `cron_name`, `user_id` (от кого выполнять), `active`,
`interval_number` + `interval_type` (minutes/hours/days/weeks/months, `:110-116`),
`nextcall` (`:118`), `priority` (`:120`). Поля `numbercall`/`doall` из старых версий
**убраны**; вместо них — `failure_count` и `first_failure_date` (`:121-122`) и авто-отключение
задания после ≥5 подряд сбоев и ≥7 дней (`MIN_FAILURE_COUNT_BEFORE_DEACTIVATION`,
`MIN_DELTA_BEFORE_DEACTIVATION`, `:34-36`).

Две вещи, которых нет в ERPNext-планировщике и которые полезны для интеграций:

1. **Событийный запуск** — `_trigger(at=datetime)` (`:735-792`) кладёт строку в
   `ir_cron_trigger` и шлёт `pg_notify('cron_trigger')` (`:794-801`), воркер просыпается
   сразу, не дожидаясь интервала. Так, например, работает очередь писем:
   `addons/mail/models/mail_mail.py:666` вызывает
   `self.env.ref('mail.ir_cron_mail_scheduler_action')._trigger(...)`.
2. **Кооперативная многозадачность** — `_commit_progress(done, remaining)` (`:846`):
   длинное задание само коммитит порциями и отдаёт время следующему. На этом построено
   чтение почты (`addons/mail/models/fetchmail.py:263-333`) — по 50 писем за проход,
   коммит после каждого письма.

Кнопка ручного запуска: `method_direct_trigger` (`:150`).

**Важно для развёртывания:** крон-воркеры работают только если в `odoo.conf` задано
`max_cron_threads > 0` (или запущен отдельный процесс). При `workers=0` (dev-режим) кроны
крутятся в том же потоке.

## 4. Вычисляемые поля и онченджи

### 4.1 Мышкой

**Настройки → Технические → Структура базы данных → Поля** (`ir.model.fields`).
Поля модели — `odoo/addons/base/models/ir_model.py`:

- `related` (`:543`) — «поле = поле связанной записи», через точку: `partner_id.country_id.name`.
  Настраивается мышкой, кода не требует вообще.
- `compute` (`:574`) — Python-код вычисления, `depends` (`:579`) — от чего зависит,
  `store` (`:582`) — хранить ли в БД.
- В форме это вкладка **Compute** — `odoo/addons/base/views/ir_model_views.xml:325-329`,
  закрыта группой `base.group_no_one` (режим разработчика).

Код в `compute` исполняется тем же `safe_eval` → те же ограничения, что в разделе 2.1.
Практический предел: арифметика, строки, обращения к `self`/`env`. Ни HTTP, ни библиотек.

Чего мышкой **нет**: онченджей (`@api.onchange`). Единственный «мышиный» способ
повесить логику на изменение поля в открытой форме — правило автоматизации с
`trigger='on_change'` + `on_change_field_ids` (`addons/base_automation/models/base_automation.py:264-271`),
и только с действием типа `code`.

### 4.2 Модулем

Полноценные `@api.depends` / `@api.onchange` / `@api.constrains` / `@api.model_create_multi` —
только в своём аддоне. Для завода это неизбежно: расчёт массы металлопроката, раскрой,
нормы времени — это модуль, а не мышь.

### 4.3 Исходящий вебхук — единственный «мышиный» выход наружу

`odoo/addons/base/models/ir_actions.py:1040-1081`. Настраивается двумя полями:
`webhook_url` (`:703`) и `webhook_field_ids` (`:704-708`).

Что реально уходит (`:1048-1058`):

```python
vals = {'_model': ..., '_id': record.id, '_action': f'{self.name}(#{self.id})'}
if self.webhook_field_ids:
    vals.update(record.read(self.webhook_field_ids.mapped('name'), load=None)[0])
```

Три подводных камня, которые надо заложить в архитектуру:

1. **Таймаут 1 секунда** и стратегия «send and forget» (`:1074`):
   `requests.post(url, ..., timeout=1)`. Это не средство синхронного вызова ИИ —
   это уведомление «сходи и забери сам».
2. **Отправка после коммита** — `@self.env.cr.postcommit.add` (`:1068`). Значит, когда
   ваш n8n получит POST, запись уже зафиксирована в БД и её можно читать по API.
   При откате транзакции вебхук не уйдёт (`postrollback`, `:1063-1065`).
3. **Нет ретраев, нет очереди, нет журнала доставки.** Ошибка и таймаут только пишутся
   в лог Odoo (`:1076-1081`). Если n8n лежал — событие потеряно. Это заметно слабее
   Carbon, где вебхуки идут через Inngest с дедупликацией и повторами.

## 6. Внешний API

### 6.1 JSON-2 — новый штатный API (Odoo 19)

Модуль `addons/rpc/` (`auto_install: True`, зависит только от `base` —
`addons/rpc/__manifest__.py`), контроллер `addons/rpc/controllers/json2.py:44-90`.

**Эндпоинт:** `POST /json/2/<model>/<method>`
**Аутентификация:** `auth='bearer'` — заголовок `Authorization: bearer <API-ключ>`
**Тело:** JSON-объект `{"ids": [...], "context": {...}, <именованные параметры метода>}`

Реализация (`addons/rpc/controllers/json2.py:56-90`):

```python
Model = request.env[__model__].with_context(context)
func = get_public_method(Model, __method__)
records = Model.browse(ids)
signature.bind(records, **kwargs)     # валидация сигнатуры → 422 при несовпадении
result = func(records, **kwargs)
```

Пример из документации (`odoo-docs/content/developer/reference/external_api.rst:50-70`):

```http
POST /json/2/res.partner/search_read HTTP/1.1
Host: erp.example.ru
X-Odoo-Database: erp
Authorization: bearer 6578616d706c65206a736f6e20617069206b6579
Content-Type: application/json; charset=utf-8

{"domain": [["name","ilike","%ПМК%"],["is_company","=",true]], "fields": ["name"]}
```

Что нужно знать:

- **Это не REST.** Нет `/api/v1/leads`, нет GET-семантики, нет ресурсов. Это RPC поверх HTTP:
  URL = `<модель>/<метод>`, всегда POST, всегда JSON. Аналога MCP-сервера Carbon
  (`apps/erp/app/routes/api+/mcp+/`, ~1200 функций как инструментов) в Odoo Community **нет**.
- **Приватные методы недоступны.** `odoo/service/model.py:40-66` (`get_public_method`):
  запрещены имена на `_`, `classmethod`/`staticmethod`, и методы с декоратором `@api.private`
  (`odoo/orm/decorators.py:327-341`). В ядре `@api.private` стоит на 32 методах, в аддонах — на 4.
- **Одна транзакция на один вызов.** `external_api.rst:441-451`: «it is not possible to chain
  multiple calls inside a single transaction». Цепочку операций надо оформлять одним методом
  (`action_confirm`, `search_read`) — иначе своим модулем.
- **Права полноценные.** `external_api.rst:386-390`: работают `ir.model.access`, `ir.rule`,
  групповые ограничения полей. Рекомендация документации — заводить **отдельного бот-пользователя**
  с пустым паролем и минимальными правами (`:392-400`). Для нас это прямо то, что нужно:
  пользователь `ai-assistant`, пользователь `n8n`, пользователь `telegram-bot` — раздельные
  ключи и раздельный аудит в `create_uid`/`write_uid`.

### 6.2 Самодокументирование `/doc`

Модуль `addons/api_doc/` (`auto_install: True`) поднимает страницу `/doc`

Практическая ценность высокая: интегратору не нужно лезть в исходники, чтобы узнать

### 6.3 API-ключи

Модель `res.users.apikeys` — `odoo/addons/base/models/res_users.py:1520`, поля `scope` (`:1527`),
`expiration_date` (`:1529`). Связь с пользователем — `api_key_ids` (`:225`).

- **Мышкой:** Настройки профиля → Account Security → New API Key.
- **Программно:** `res.users.apikeys.generate(key, scope, name, expiration_date)` (`:1637`)
  и `revoke(key)` (`:1688`) — вызываются через тот же JSON-2. По умолчанию доступно только
  админу Настроек; для остальных включается системным параметром
  `base.enable_programmatic_api_keys` (`:1632-1633`), лимит ключей —

- **Срок жизни.** Обычному пользователю потолок задаётся `res.groups.api_key_duration`

- Проверка ключа при запросе — `odoo/addons/base/models/ir_http.py:212-250`
  (`_auth_method_bearer`), scope `'rpc'`.

### 6.4 XML-RPC и JSON-RPC — работают, но объявлены устаревшими

- `POST /xmlrpc/2/<service>` — `addons/rpc/controllers/xmlrpc.py:148-163`
  (`common.authenticate`, `object.execute_kw`).
- `POST /xmlrpc/<service>` — `:130-146` (историческая версия, faultCode строкой).
- `POST /jsonrpc` — `addons/rpc/controllers/jsonrpc.py:8-14`.

**Все три печатают предупреждение в лог при каждом вызове** — текст в
`addons/rpc/controllers/__init__.py:5-10`:

> «The /xmlrpc, /xmlrpc/2 and /jsonrpc endpoints are deprecated in Odoo 19 and scheduled
> for removal in Odoo 22.»

Документация подтверждает жёстче — `odoo-docs/content/developer/reference/external_rpc_api.rst:5-14`:
удаление в **Odoo 22 (осень 2028)** и в Odoo Online 21.1 (зима 2027).

**Что это значит для нас практически.** Готовые коннекторы к Odoo (в том числе стандартный
узел Odoo в n8n) исторически ходят через `/jsonrpc` либо `/xmlrpc/2/object`. Они будут
работать на 19-й версии — но это дорога с известным концом. Проверить, какой эндпоинт
использует ваша версия n8n-узла, надо на месте; если `/jsonrpc` — планировать переход
на HTTP Request + `/json/2/...` заранее. Важная оговорка из того же текста (`__init__.py:9-10`,
`external_rpc_api.rst:13-14`): депрекация **не касается** обычных контроллеров
`@route(type='jsonrpc')` — то есть внутреннего API веб-клиента (`/web/dataset/call_kw`)
и собственных контроллеров в ваших модулях.

### 6.5 REST — чего нет

Готового ресурсного REST API (`GET /api/leads/42`, коды 200/201/404 по семантике ресурсов,
OpenAPI-схема) в Community **нет**. Есть только RPC-стиль `/json/2/<model>/<method>`.
Если нужен именно REST-фасад — это свой модуль с контроллерами
(`@http.route('/api/v1/...', type='http'|'jsonrpc', auth='bearer')`). Пример такого
самописного контроллера есть прямо в RuOdoo:
`ruodoo/tier_communications_matrix/controllers/matrix_webhook.py:16-24`.

## 7. Вебхуки

### 7.1 Входящие — есть, настраиваются мышкой

Контроллер — `addons/base_automation/controllers/main.py:6-18`:

```python
@route(['/web/hook/<string:rule_uuid>'], type='http', auth='public',
       methods=['GET', 'POST'], csrf=False, save_session=False)
```

Настройка: правило автоматизации с `trigger='on_webhook'`. Поля
(`addons/base_automation/models/base_automation.py:160-165`):

- `url` — вычисляется как `<base_url>/web/hook/<webhook_uuid>` (`:288-294`);
- `webhook_uuid` — UUID4, кнопка «Rotate Secret» → `action_rotate_webhook_uuid()` (`:561-563`);
- `record_getter` — Python-выражение, определяющее, на какой записи выполнить правило;
  по умолчанию `model.env[payload.get('_model')].browse(int(payload.get('_id')))` (`:162`);
- `log_webhook_calls` — писать вызовы в `ir.logging`; просмотр — `action_view_webhook_logs()`
  (`:565-573`, домен `path = "base_automation(<id>)"`).

Исполнение — `_execute_webhook(payload)` (`:619-662`). Payload берётся из
`get_webhook_request_payload()` (`:131-138`): сначала пробуется JSON-тело, при ошибке —
query-параметры. Внутри Python-действий эта переменная доступна как `payload`
(`addons/base_automation/models/ir_actions_server.py:56-60`).

**Три предупреждения:**

1. **Аутентификации нет вообще.** `auth='public'`, `csrf=False`. Единственная защита —
   секретность UUID в URL. Никакого HMAC-подписывания, whitelisting IP или проверки
   заголовков в коде нет. Для нашего контура: закрывать на nginx (allow только IP n8n),
   держать URL в секретах, ротировать при утечке.
2. **Правило всегда исполняется НА ЗАПИСИ.** `:642-652`: если `record_getter` вернул пустой
   набор — `raise ValidationError("No record to run the automation on was found")`, HTTP 500.
   Чтобы **создавать** записи по вебхуку, документация
   (`odoo-docs/content/applications/studio/automated_actions/webhooks.rst:76-79`) советует
   подменить `record_getter` на `model.browse(i)`/`model.search(i)` с заведомо существующей
   записью-якорем, а саму запись создавать уже в Python-действии из `payload`. Это костыль,
   но рабочий.
3. **Ответ всегда одинаков:** `{'status': 'ok'}` / `{'status': 'error'}` (`main.py:11,16,18`).
   Вернуть данные в ответе вебхука нельзя — только 200/404/500. Двусторонний обмен строится
   как «вебхук внутрь + JSON-2 обратно».

### 7.2 Исходящие — есть, см. 4.3

Серверное действие `state='webhook'`. Ограничения: 1 с таймаут, без ретраев, без очереди.

## 8. Почта: как Odoo принимает письма и куда встроить ИИ

Это ключевой раздел: вся текущая платформа заказчика строится вокруг ИИ-разбора входящих писем.

### 8.1 Исходящая почта

- `ir.mail_server` — `odoo/addons/base/models/ir_mail_server.py:126`. Поля: `smtp_host` (`:145`),
  `smtp_port` (`:146`), `smtp_encryption` (`:155`), `smtp_user`/`smtp_pass` (`:153-154`,
  под `base.group_system`), `smtp_authentication` (`:147`), `from_filter` (`:141`),
  `sequence` = приоритет (`:179`), `max_email_size` (`:178`), клиентские SSL-сертификаты
  (`:169-173`). Несколько серверов + выбор по `from_filter` — штатно.
- Очередь: письма складываются в `mail.mail`, разгребает крон **«Mail: Email Queue Manager»**
  (`addons/mail/data/ir_cron_data.xml:4-13`, `model.process_email_queue(batch_size=1000)`,
  раз в час) — но при обычной отправке очередь дёргается сразу через `_trigger()`
  (`addons/mail/models/mail_mail.py:666`), так что час — это только «подметалка».
- `send_after_commit()` (`addons/mail/models/mail_mail.py:674`) — отправить письмо только
  если транзакция прошла.
- Шаблоны — `mail.template` (`addons/mail/models/mail_template.py`), рендер QWeb + Jinja-подобные
  выражения, привязываются к действию `mail_post`.

### 8.2 Входящая почта: три способа доставки

**Способ 1 — Odoo сам ходит по IMAP/POP.** Модель `fetchmail.server`
(`addons/mail/models/fetchmail.py:88`). Поля: `server_type` = `imap`/`pop`/`local` (`:104`),
`server`, `port`, `is_ssl`, `user`, `password`, `attach` («забирать вложения», `:111`),
`original` («хранить исходник письма целиком», `:113`), `object_id` — модель по умолчанию
для новых записей (`:121`), `priority` (`:125`).

Крон — **«Mail: Fetchmail Service»** (`addons/mail/data/ir_cron_data.xml:40-49`,
`model._fetch_mails()`, **каждые 5 минут**, включается автоматически при создании
подтверждённого сервера — `_update_cron()`, `fetchmail.py:355-364`).

Механика IMAP (`:27-53`): ищутся письма `(UNSEEN)`, снимается флаг `\Seen` на время обработки,
после успешной обработки ставится обратно (`handled_message`, `:46-47`). POP —
письмо **удаляется** с сервера (`dele`, `:76-77`). Обработка каждого письма — в отдельном
курсоре с коммитом (`:290-307`), сбой одного письма не роняет пачку. Батч — 50 писем
за проход (`_fetch_mail(batch_limit=50)`, `:263`). После 5 дней подряд ошибок сервер
автоматически переводится в draft и админу шлётся уведомление (`:315-321`).

**Способ 2 — MTA отдаёт письмо скриптом.** `addons/mail/static/scripts/odoo-mailgate.py`.
Постфиксный pipe-alias: письмо читается из stdin и уходит в Odoo вызовом

```python
models.execute_kw(db, uid, password, 'mail.thread', 'message_process',
                  [False, xmlrpclib.Binary(msg)], {})
```

(`odoo-mailgate.py:86-87`). Способ мгновенный (нет 5-минутной задержки), но использует
устаревающий `/xmlrpc/2/object`.

**Способ 3 — кто угодно вызывает `message_process` по API.** Это самое интересное:
`mail.thread.message_process` — публичный `@api.model` метод
(`addons/mail/models/mail_thread.py:1437-1438`), **не** помечен `@api.private`, значит
проходит `get_public_method` и вызывается снаружи через JSON-2:

```
POST /json/2/mail.thread/message_process
{"model": null, "message": "<сырой RFC-822 текст письма>"}
```

Сигнатура принимает `str` и сама кодирует в utf-8 (`:1473-1474`), так что JSON-строки
достаточно. Параметры: `model` (фолбэк-модель, `null` → маршрутизация только по алиасам),
`custom_values` (словарь значений для создаваемой записи), `save_original`, `strip_attachments`,
`thread_id`.

Это и есть штатная точка входа для внешнего почтового обработчика.

### 8.3 Что происходит внутри `message_process`

`addons/mail/models/mail_thread.py:1438-1511`:

1. **Разбор** — `message_parse()` (`:1784-1893`). Возвращает `msg_dict` со стабильным
   набором ключей (`:1800-1814`): `message_id`, `subject`, `email_from`, `to`, `cc`,
   `recipients`, `to_filtered`/`cc_filtered` (адреса без алиасов Odoo, `:1861-1867`),
   `body` (склеенный HTML), `references`, `in_reply_to`, `date`, `parent_id`, `is_internal`,
   `is_bounce`, `attachments` как список `(имя, байты)`.
2. **Дедупликация по `Message-Id`** (`:1481-1493`) — включая advisory-lock в PostgreSQL
   на случай гонки двух параллельных обработчиков. Повторное письмо игнорируется.
3. **Защита от петель** — `_detect_loop_headers()` (`:1092`) по заголовкам и
   `_detect_loop_sender()` (`:1004-1080`) по частоте: больше `mail.gateway.loop.threshold`
   (по умолчанию **20**) писем от одного отправителя за `mail.gateway.loop.minutes`
   (по умолчанию **120** минут) → письма отбрасываются. Обход — занести адрес в
   `mail.gateway.allowed` (`addons/mail/models/mail_gateway_allowed.py:8`).
   **Это прямо касается нас:** если робот (n8n, тестовый прогон, автоответчик поставщика)
   шлёт на алиас чаще 20 писем за 2 часа — Odoo молча их проглотит. Адрес робота
   обязательно в whitelist.
4. **Маршрутизация** — `message_route()` (`:1122-1341`). Порядок эвристик описан в докстринге
   (`:1128-1137`):
   - письмо — ответ в существующую ветку (`References`/`In-Reply-To` совпали с
     `mail_message.message_id`, поиск по последним 32 ссылкам, `:1186-1191`)
     → модель и `res_id` берутся из исходного сообщения, `custom_values` игнорируются;
   - иначе ищется `mail.alias` по локальной части адреса получателя → модель, значения
     по умолчанию, ответственный из алиаса;
   - иначе — фолбэк на переданный `model`/`thread_id`;
   - иначе — исключение «No possible route».
5. **Применение маршрута** — `_message_route_process()` (`:1343-1434`): если ветка есть —
   `record.message_update(msg_dict)`; если нет — `Model.message_new(msg_dict, custom_values)`,
   затем в любом случае `message_post(...)`, которое создаёт `mail.message`, прикрепляет
   вложения как `ir.attachment` и рассылает уведомления подписчикам.

### 8.4 Алиасы (`mail.alias`) — «почтовый ящик = модель»

`alias_domain_id` (`:43`), `alias_model_id` — **какую модель создавать** (`:48`),

Домены — `mail.alias.domain` (`addons/mail/models/mail_alias_domain.py:16`):
`name`, `bounce_alias` (`:27`), `catchall_alias` (`:32`), `default_from` (`:37`).
Миграция из системных параметров `mail.catchall.domain`, `mail.bounce.alias`,
`mail.catchall.alias`, `mail.default.from` (`:261-268`).

**Готовый алиас для лидов есть из коробки:** `addons/crm/data/crm_team_data.xml:3-5` —
команда продаж по умолчанию получает `alias_name = "info"`. Значения алиаса собирает

То есть **«письмо на info@домен → лид в CRM» работает без единой строки кода** —

### 8.5 Как письмо превращается в лид

`addons/crm/models/crm_lead.py:2125-2146` — переопределённый `message_new`:

```python
defaults = {
    'name':  msg_dict.get('subject') or _("No Subject"),
    'email_from': msg_dict.get('from'),
    'partner_id': msg_dict.get('author_id', False),
}
defaults.update(custom_values)
new_lead = super().message_new(msg_dict, custom_values=defaults)
new_lead._assign_userless_lead_in_team(_('incoming email'))
```

Базовая реализация (`addons/mail/models/mail_thread.py:1515-1545`) кладёт тему в `_rec_name`
и адрес отправителя в «первичное email-поле» модели.

То есть из коробки лид получает: **тему письма как название, адрес отправителя,
контрагента (если узнан), команду и тип из `alias_defaults`, автоназначение менеджера**.
Тело письма и вложения при этом уходят в чаттер (`mail.message` + `ir.attachment`),
а **в поля лида — ничего**. Вот ровно этот зазор и закрывает ИИ.

### 8.6 Четыре архитектуры подключения ИИ к разбору писем

**Вариант A — «Odoo ловит, ИИ дообогащает» (без модуля, всё мышкой).**

1. `fetchmail.server` тянет ящик → алиас `info@` → создаётся `crm.lead` с темой и адресом.
2. Правило автоматизации на `crm.lead`, триггер `on_message_received`, действие
   **Send Webhook Notification** на URL n8n. В `webhook_field_ids` добавить `id`, `email_from`.
   В n8n прилетает `{"_model":"crm.lead","_id":42,"_action":"...","email_from":"..."}`.
3. n8n по JSON-2 забирает тело и вложения:
   `POST /json/2/mail.message/search_read` с доменом `[["model","=","crm.lead"],["res_id","=",42]]`,
   поля `body`, `attachment_ids`; вложения — `POST /json/2/ir.attachment/read` (`datas` в base64).
4. Claude разбирает → n8n пишет обратно: `POST /json/2/crm.lead/write` с
   `{"ids":[42],"vals":{...}}` и `POST /json/2/crm.lead/message_post` с резюме разбора в чаттер.

Плюсы: **ноль кода в Odoo**, вся логика в n8n/AI, вся история письма остаётся в чаттере.
Минусы: два круга (вебхук наружу + API обратно), исходящий вебхук без ретраев — при
недоступности n8n событие теряется (лечится подстраховкой: ночной крон-выборкой
«лиды без разметки ИИ»).

**Вариант B — «ИИ ловит первым, Odoo получает готовое» (без модуля).**
n8n сам читает IMAP, зовёт Claude, затем:
`POST /json/2/crm.lead/create` с уже заполненными полями и
`POST /json/2/crm.lead/message_post` с телом письма.
Либо — отдать Odoo сырое письмо `POST /json/2/mail.thread/message_process` (чтобы получить
бесплатно дедупликацию, треды и вложения), а потом дообогатить.
**Критично:** нельзя одновременно держать включённым `fetchmail.server` на тот же ящик
и читать его из n8n — или Odoo, или n8n. Иначе дублей не будет (Message-Id спасёт),
но флаги `\Seen` / удаление по POP разъедутся.

**Вариант C — «модуль в Odoo» (аналог того, что сделано в ERPNext).**
Свой аддон, переопределяющий `crm.lead.message_new(msg_dict, custom_values)` или
`mail.thread.message_route`. Внутри уже доступен полный `msg_dict` — тело, вложения байтами,
все заголовки. Вызов ИИ отсюда **нельзя делать синхронно** (это заблокирует почтовый крон и
транзакцию) — правильный паттерн: в `message_new` создать лид со статусом «в разборе»,
дёрнуть `self.env.ref('<module>.cron_ai_parse')._trigger()` и разобрать в кроне.
Плюсы: доступ к оригиналу письма без второго круга по API, полный контроль.
Минусы: код надо сопровождать при апгрейдах.

**Вариант D — «обратный канал без API-ключа».**
Если не хочется выдавать ИИ-сервису ключ к ORM: правило `on_webhook` на `crm.lead`,
`record_getter = model.browse(int(payload.get('lead_id')))`, действие `code`, которое
разбирает `payload` и пишет поля. ИИ шлёт один POST на `/web/hook/<uuid>` — и всё.
Минус: у этого URL нет аутентификации (см. 7.1), закрывать на nginx.

**Рекомендация.** Для старта — **A** (ноль кода, всё проверяемо мышкой, быстрая обратная
связь от заказчика). При выходе на поток и при необходимости читать PDF-чертежи из вложений —
переезд на **C**, потому что там msg_dict с вложениями уже в руках и не надо гонять base64
через HTTP. **B** оправдан, только если ИИ-конвейер должен работать и когда Odoo лежит.

### 8.7 Вложения и PDF

Вложения письма превращаются в `ir.attachment`, привязанные к `mail.message` и записи.
Модуль `addons/attachment_indexation/` (**в Community**) индексирует текст из
`docx`, `pptx`, `xlsx`, `opendoc`, `pdf` (`addons/attachment_indexation/models/ir_attachment.py:20`),
PDF — через `pdfminer.six` (`:215-253`, библиотека ставится отдельно, предупреждение при
её отсутствии — `:16-18`). Поле `index_content` можно читать по API — то есть **текстовый
слой PDF-заявки доступен без отдельного OCR**. Векторного слоя чертежей и распознавания
сканов здесь нет — это по-прежнему задача вашего Drawing Analyzer.

При `fetchmail.server.original = True` (`addons/mail/models/fetchmail.py:113`) к сообщению
прикладывается **полный исходник письма** (`.eml`) — удобно для ИИ, который хочет видеть
сырые заголовки, но удваивает объём базы (прямо сказано в help-тексте поля).

## 9. Подключение внешних сервисов

### 9.1 n8n

Два направления, оба без кода на стороне Odoo:

**Odoo → n8n:** правило автоматизации + действие `webhook` на URL n8n Webhook-ноды.
Помнить про 1 с таймаут (`odoo/addons/base/models/ir_actions.py:1074`) — нода n8n должна
отвечать сразу (`respond: immediately`), а работу делать после.

**n8n → Odoo:** два варианта.
- HTTP Request на `/json/2/<model>/<method>` с `Authorization: bearer <ключ>` — рекомендуемый,
  переживёт Odoo 22.
- Штатный узел Odoo в n8n — работает, но поверх устаревающих RPC-эндпоинтов
  (`addons/rpc/controllers/__init__.py:5-10`). Проверить фактический URL в настройках узла
  на месте; при `/jsonrpc` закладывать миграцию.

Отдельный пользователь `n8n` + свой API-ключ + минимальные права
(`odoo-docs/content/developer/reference/external_api.rst:392-400`).

### 9.2 AI Assistant (ваш NestJS-сервис)

- **Внутрь:** JSON-2 (`/json/2/...`) с bearer-ключом сервисного пользователя `ai-assistant`.
  Сигнатуры методов и кастомные поля смотреть на живой базе через `/doc`
  (`addons/api_doc/controllers/api_doc.py:39`).
- **Наружу:** либо исходящий вебхук (быстро, ненадёжно), либо — для критичных событий —
  свой модуль с очередью на `ir.cron` + `_trigger()` (`odoo/addons/base/models/ir_cron.py:735`),
  где вы сами контролируете ретраи. В Community готовой надёжной шины событий **нет** —
  это заметная разница с Carbon, где event system + Inngest дают ретраи и идемпотентность
  из коробки.
- **Запись результата разбора:** `crm.lead/write` + `crm.lead/message_post`. Последнее даёт
  след в чаттере — что именно ИИ решил и когда. Для аудита это лучше, чем тихая запись полей.
- Ограничение на цепочки: одна транзакция на один вызов
  (`external_api.rst:441-451`). «Создать лид + строки КП + подтвердить» — либо три вызова
  с риском частичного результата, либо один метод в своём модуле.

### 9.3 Telegram-бот

Готового модуля Telegram в Community **нет** (проверено: в `addons/` такого каталога нет;
в RuOdoo тоже — `grep -ril telegram` по 48 модулям даёт только упоминание в
`ruodoo/premium_client/`, не интеграцию). Доступны косвенные вещи: `mail_push`/`mail_push_device`
(браузерные web-push, `addons/mail/models/mail_push.py`), `sms` (через платный Odoo IAP),
`bus` (websocket для веб-клиента).

Практическая схема без единой строки в Odoo:
`правило автоматизации → действие webhook → n8n → Telegram Bot API`,
а кнопки согласования в Telegram шлют callback → n8n → `/web/hook/<uuid>` или
`/json/2/sale.order/action_confirm`. То есть бот остаётся вашим сервисом, Odoo про него
не знает — ровно как сейчас с ERPNext.

### 9.4 Что уже написано в RuOdoo (готовые кирпичи)

| Модуль | Что даёт | Файл |

| `base_tier_validation` | многоступенчатое согласование документов (замена Enterprise `approvals`); от OCA/ForgeFlow, AGPL-3 | `ruodoo/base_tier_validation/__manifest__.py` |

## 10. Сравнение с Carbon и с текущим ERPNext

| Возможность | ERPNext (сейчас) | Odoo 19 CE | Carbon |
|---|---|---|---|
| Автоматизация мышкой | Server Script / Notification | ✅ `base.automation`, 19 триггеров, 11 типов действий | ✅ Workflows (визуальный конструктор, холст) |
| Визуальный конструктор процессов | ❌ | ❌ (список правил, не холст) | ✅ |
| Асинхронность автоматизации | ⚠️ частично | ❌ синхронно в транзакции | ✅ очередь, ~3-5 с |
| Ретраи/идемпотентность | ❌ | ❌ | ✅ |
| Python-скрипты из UI | ✅ Server Script | ✅ `ir.actions.server` (`state='code'`), но **без HTTP** | ✅ Edge functions (разработчик) |
| HTTP-вызов наружу из UI-скрипта | ✅ (в ERPNext `requests` доступен) | ❌ `safe_eval` не пустит | ✅ |
| Внешний API | ✅ REST `/api/resource/<Doctype>` | ⚠️ RPC `/json/2/<model>/<method>`, не REST | ✅ REST + MCP (~1200 функций) |
| Самодокументирование API | ⚠️ | ✅ `/doc` по живой базе | ✅ |
| Входящие вебхуки мышкой | ⚠️ | ✅ `/web/hook/<uuid>` | ✅ |
| Исходящие вебхуки мышкой | ✅ Webhook doctype (с ретраями) | ⚠️ есть, но 1 с и без ретраев | ✅ |
| Почтовый шлюз с маршрутизацией | ✅ Email Account + Communication | ✅ `fetchmail` + `mail.alias` + `mail.thread` | — (см. разбор Carbon) |
| Письмо → лид из коробки | ⚠️ настраивается | ✅ `info@` → `crm.lead` штатно | — |
| Дедупликация писем по Message-Id | ⚠️ | ✅ + advisory-lock | — |
| Защита от почтовых петель | ⚠️ | ✅ 20 писем / 120 мин + whitelist | — |
| MCP / встроенный AI-агент | ❌ | ❌ | ✅ |

Короткий вывод для заказчика: **по почте Odoo сильнее и ERPNext, и Carbon** — это самый
зрелый кусок платформы, и именно он у вас в центре. **По автоматизации Odoo слабее Carbon**
(нет холста, нет асинхронной шины с ретраями), но покрывает 80% типовых «если — то» мышкой.
**По API Odoo 19 в переходном состоянии:** новый JSON-2 удобен и документирован, старые
XML-RPC/JSON-RPC (на которых сидят почти все готовые коннекторы) объявлены к удалению
в 2028 году.

  `iot` — нет.

## 12. Практические рецепты под завод металлоконструкций

1. **«Письмо на info@пмк.рф → лид»** — без кода: `fetchmail.server` (IMAP, 5 мин) +
   `mail.alias.domain` + готовый алиас `info` на команде продаж
   (`addons/crm/data/crm_team_data.xml:3`).
2. **«ИИ разобрал письмо → заполнил параметры заявки»** — вариант A из 8.6:
   правило `on_message_received` на `crm.lead` → webhook в n8n → Claude →
   `/json/2/crm.lead/write` + `message_post`.
3. **«Менеджеру в Telegram при новом лиде»** — правило `on_create` на `crm.lead` →
   действие `webhook` → n8n → Telegram Bot API.
4. **«Директор согласовал КП кнопкой в Telegram»** — callback в n8n →
   `POST /json/2/sale.order/action_confirm` с `{"ids":[<id>]}` (один метод = одна транзакция,
   как советует `external_api.rst:452-460`).
5. **«КП не согласовано 2 дня — напомнить»** — правило `on_time_updated`,
   `trg_date_range=2 days`, действие `next_activity` или `mail_post`. Мышкой.
6. **«Ночью пересчитать загрузку цеха»** — `ir.cron` с Python-действием;
   если нужен вызов ИИ — крон дёргает вебхук, а не считает сам.
7. **Обязательно на старте:** завести адрес робота-отправителя в
   `mail.gateway.allowed` (`addons/mail/models/mail_gateway_allowed.py:8`), иначе на
   нагрузочном тесте письма начнут исчезать после 20-го за 2 часа.
8. **Обязательно на старте:** отдельные пользователи-боты (`ai-assistant`, `n8n`,
   `telegram-bot`) с раздельными API-ключами и минимальными правами; ключ админского
   уровня может быть бессрочным (`odoo/addons/base/models/res_users.py:1581-1583`),
   пользовательский — максимум 90 дней (`odoo/addons/base/security/base_groups.xml:45`).
